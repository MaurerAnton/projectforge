File #1: build.gradle.kts

Path: ./build.gradle.kts

Type: Gradle build script (Kotlin DSL)

Lines: 35

Purpose: Root build configuration — sets project-wide version, repositories, and dependency exclusions

Source: GitHub

What it does

This is the root build script for the entire ProjectForge multi-module Gradle project. It defines cross-cutting configuration that applies to all subprojects (modules like projectforge-business, projectforge-webapp, etc.).

Three things happen here:

  1. The Kotlin compiler is declared (line 4) — the JVM variant, version controlled via the Gradle version catalog
  2. All subprojects get the same group/version and repository list (lines 7–21)
  3. Specific problematic dependencies are excluded globally to prevent classpath conflicts (lines 23–35)

Line-by-line

Lines 1–5: Kotlin plugin

1 import org.jetbrains.kotlin.gradle.tasks.KotlinCompile
2 
3 plugins {
4     kotlin("jvm") version libs.versions.org.jetbrains.kotlin.get() apply false
5 }

Line 1: Imports the KotlinCompile task type — needed if any subproject customizes Kotlin compiler options (used in buildSrc/build.gradle.kts).

Line 4: Declares the Kotlin JVM plugin at the root level with apply false. This means the plugin is available to all subprojects but not applied automatically — each subproject must apply it explicitly. Version comes from the version catalog (gradle/libs.versions.toml), not hardcoded here.

Line 8: Maven group ID — all submodules produce artifacts under org.projectforge:module-name.

Line 9: Project version — 8.2-SNAPSHOT. The comment says "Update version string here (nowhere else)" — this is the single source of truth for the version number across all 15+ modules.

Lines 12–19: Four repository sources:

  • Maven Central — standard Java dependencies (Spring Boot, Hibernate, etc.)
  • Gradle Plugin Portal — Gradle plugins (Spring Boot plugin, Kotlin plugin)
  • Sonatype OSS — snapshot and staging releases (typically for development dependencies)
  • Maven2 — older repository mirror

Lines 23–35: Global dependency exclusions

23 allprojects {
24     configurations.all {
25         exclude(group = "org.slf4j", module = "slf4j-jul")
26         exclude(group = "org.slf4j", module = "slf4j-log4j12")
27         exclude(group = "com.sun.mail", module = "jakarta.mail")
28         exclude(group = "jakarta.mail", module = "jakarta.mail-api")
29         exclude(group = "org.apache.logging.log4j", module = "log4j-core")
30         exclude(group = "commons-logging", module = "commons-logging")
31         resolutionStrategy {
32             preferProjectModules()
33         }
34     }
35 }

Lines 25–30: Six dependency exclusion rules applied to every configuration in every subproject. Why?

ExclusionWhy
slf4j-julJava Util Logging bridge — conflicts with Logback (ProjectForge uses Logback via Spring Boot)
slf4j-log4j12Log4j 1.x bridge — obsolete, replaced by Log4j 2 / Logback
jakarta.mail (com.sun)Old Sun mail implementation — conflicts with Jakarta Mail
jakarta.mail-apiAPI stubs that conflict with real implementation
log4j-coreLog4j 2 core — ProjectForge uses Logback via Spring Boot, Log4j 2 is pulled in transitively by some libraries
commons-loggingApache Commons Logging — legacy wrapper, Spring Boot replaces it with jcl-over-slf4j

Lines 31–33: preferProjectModules() — tells Gradle to prioritize local project modules over external dependencies with the same group/name. This prevents accidentally resolving a published artifact of ProjectForge when a local module is intended.

Why global exclusions? Without them, every build.gradle.kts in every submodule would need to repeat these exclusions. Centralising here ensures consistency and prevents difficult-to-debug classpath conflicts (e.g. two SLF4J bindings at runtime = silent log failures).

How this file connects to the rest of the project

This file is the entry point for all Gradle operations:

./gradlew build        ← reads build.gradle.kts → applies to all subprojects
./gradlew bootRun      ← same entry point, boots Spring Boot
./gradlew test         ← runs tests across all modules

Every subproject (projectforge-business/, projectforge-webapp/, etc.) has its own build.gradle.kts that inherits from this root configuration via the allprojects { } and subprojects { } blocks.

The version catalog at gradle/libs.versions.toml is referenced at line 4 via libs.versions.org.jetbrains.kotlin.get() — this is the central place where all dependency versions are managed (not this file).

Key takeaways for new contributors

  • Version number: Only change it on line 9. The comment is there for a reason — changing it elsewhere will lead to inconsistent builds.
  • Adding a dependency: Don't touch this file. Add it to the subproject's build.gradle.kts or to gradle/libs.versions.toml.
  • If your logs are silent: Check you're not using a conflicting SLF4J binding. The exclusions on lines 25–30 prevent this, but custom dependencies might bring their own.
  • Gradle plugin updates: Line 4 controls which Kotlin version is available. The actual version is in gradle/libs.versions.toml.
