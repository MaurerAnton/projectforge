Nicht Spring Security. Die Authentifizierung verwendet ein benutzerdefiniertes tokenbasiertes Sitzungssystem (DataTransferPublicSession), NICHT die Filterkette von Spring Security. Externe Benutzer erhalten ein Zugriffstoken (typischerweise eine UUID in einem URL-Parameter), das einem ProjectForge-Datentransferbereich zugeordnet ist. Es wird kein ProjectForge-Benutzerkonto benötigt – dies dient zum Teilen von Dateien mit Kunden, Lieferanten oder der Öffentlichkeit.

Jeder Endpunkt beginnt mit denselben 3 Prüfungen: (1) Validierung der Kategorie = "datatransfer", (2) Validierung der listId = DEFAULT_NODE, (3) Authentifizierung über dataTransferPublicSession.checkLogin(). Die check()-Funktion wirft eine IllegalStateException, wenn die Bedingung fehlschlägt – unbehandelt wird daraus ein 500-Fehler. Diese sollten wohl eher 400-Antworten zurückgeben.

Tokenbasierte öffentliche Authentifizierung – kein Benutzerkonto erforderlich

val data = dataTransferPublicSession.checkLogin(request, id)
    ?: return RestUtils.badRequest("Keine gültige Anmeldung.")
val area: DataTransferAreaDO = data.first        // Der DataTransfer-Bereich
val sessionData = data.second                      // Sitzungsinfo (userInfo, token)

DataTransferPublicSession.checkLogin() ist die benutzerdefinierte Authentifizierungsschicht. Sie extrahiert ein Zugriffstoken aus der HTTP-Anfrage (wahrscheinlich aus Abfrageparametern: ?accessToken=abc123) und validiert es gegen die Datenbank. Bei Erfolg gibt sie ein Pair<DataTransferAreaDO, TransferAreaData> zurück – den aufgerufenen Bereich und Sitzungsmetadaten. Bei Misserfolg wird null zurückgegeben und der Endpunkt antwortet mit 400 „Keine gültige Anmeldung."

Kein JWT- oder OAuth-System – dies ist eine einfache Token-Suche. Das Token wird generiert, wenn ein Administrator einen Datentransferbereich mit aktiviertem externem Zugriff erstellt. Das Token ist in der teilbaren URL eingebettet: https://projectforge.acme.com/rsPublic/datatransfer/download/datatransfer/42?accessToken=uuid.

multiDownload – der Datei-ID-Präfix-Trick (Zeilen 157-198)

@RequestParam("fileIds") fileIds: String,     // CSV: "abc1,def2,ghi3"
val fileIdList = fileIds.split(",")
val attachments = attachmentsService.getAttachments(...)
    ?.filter { attachment ->
        fileIdList.any { attachment.fileId?.startsWith(it) == true }
        // Übereinstimmung nach PRÄFIX, nicht exakter ID! "abc" passt auf "abc123def456"
    }

Der Javadoc in Zeile 154 erklärt den Trick: "Um die URL-Länge zu begrenzen, können Datei-IDs auch gekürzt werden (z.B. erste 4 Zeichen)." JCR-Datei-IDs sind lange UUIDs wie "a1b2c3d4-e5f6-7890-abcd-ef1234567890". Das Einfügen mehrerer vollständiger UUIDs in eine URL-Abfragezeichenfolge bläht die URL über die Browser-Grenzen hinaus auf (~2000 Zeichen). Die Lösung: Benutzer können nur die ersten 4 Zeichen jeder Datei-ID senden.

Wie der Abgleich funktioniert: fileIdList.any { attachment.fileId?.startsWith(it) == true } – für jeden Anhang wird geprüft, ob seine vollständige Datei-ID mit einem der angegebenen Präfixe beginnt. Sendet der Benutzer "a1b2,d4e5", findet der Server "a1b2c3d4-..." und "d4e5f6a7-...". Dies ist ein Kompromiss: kürzere URLs gegen das Risiko von Präfixkollisionen. Bei UUIDs haben die ersten 4 Hex-Zeichen 16^4 = 65536 Möglichkeiten – das Kollisionsrisiko ist bei typischer Nutzung (10-20 Dateien pro Bereich) äußerst gering.

ResponseAction-Muster – servergesteuerte UI-Updates

// Nach dem Upload: Das React-Frontend anweisen, die Anhangsliste zu aktualisieren
return ResponseEntity.ok()
    .body(
        ResponseAction(targetType = TargetType.UPDATE, merge = true)
            .addVariable("data", AttachmentsServicesRest.ResponseData(list))
    )

// Nach dem Löschen/Ändern: React anweisen, das Modal zu schließen
return ResponseEntity.ok()
    .body(
        ResponseAction(targetType = TargetType.CLOSE_MODAL, merge = true)
            .addVariable("data", AttachmentsServicesRest.ResponseData(list))
    )

Anstatt nur die aktualisierten Daten zurückzugeben, geben die Endpunkte eine ResponseAction zurück – einen Befehl an das React-Frontend, was als Nächstes zu tun ist. Dies ist das servergesteuerte UI-Muster (SDUI), das ProjectForge für sein dynamisches Layoutsystem verwendet:

  • UPDATE – das Frontend soll die aktuelle Ansicht mit den neuen Daten aktualisieren (merge=true bedeutet, in den vorhandenen Zustand einfügen, nicht ersetzen)
  • CLOSE_MODAL – das Frontend soll den aktuellen Modaldialog schließen und die übergeordnete Ansicht aktualisieren

Das addVariable("data", ...) hängt die neue Anhangsliste als benannte Variable an. Die dynamische Layout-Engine des Frontends liest die ResponseAction und entscheidet, welche Komponenten neu gerendert werden sollen. Der Server kennt keine React-Komponenten – er sendet abstrakte Aktionen; das Frontend interpretiert sie.

Audit-Trail – jeder Vorgang mit externen Benutzerinformationen protokolliert

attachmentsService.addAttachment(
    jcrPath, fileInfo, inputStream,
    baseDao = dataTransferAreaDao,
    obj = area,
    accessChecker = attachmentsAccessChecker,
    userString = getExternalUserString(request, sessionData.userInfo)  // Audit!
)

Jede JCR-Operation übergibt einen userString – eine Zeichenfolge, die den externen Benutzer identifiziert. getExternalUserString() (aus dem Begleitobjekt von DataTransferAreaDao) extrahiert die IP-Adresse des Clients und optionale Identitätsinformationen aus der HTTP-Anfrage: "192.168.1.42 (John von der Acme Corp)". Diese Zeichenfolge wird zusammen mit der Dateiänderung im JCR-Audit-Log gespeichert. Auch wenn der Benutzer kein ProjectForge-Konto hat, sind seine Aktionen nachvollziehbar – entscheidend für die DSGVO-Konformität und Sicherheitsforensik.

registerFileAsOwner() (Zeile 323): Nach dem Upload zeichnet die Sitzung auf, welche Dateien der externe Benutzer hochgeladen hat. Dies ermöglicht dateibasierte Besitzprüfungen – ein Benutzer kann nur Dateien löschen/ändern, die er selbst hochgeladen hat, nicht solche, die von anderen externen Benutzern im selben freigegebenen Bereich hochgeladen wurden.

convert() – Erstellen des gefilterten DTO (Zeilen 442-464)

Der convert()-Helfer erstellt ein DataTransferPublicArea-DTO für das Frontend. Zwei wichtige Transformationen:

  1. Zugriffsfilterung: attachmentsAccessChecker.filterAttachments() – entfernt Dateien, die der aktuelle externe Benutzer nicht sehen soll. Dies ist eine mehrschichtige Verteidigung: Selbst wenn die JCR-Abfrage alle Dateien zurückgibt, entfernt der Zugriffsprüfer nicht autorisierte, bevor sie den Client erreichen.
  2. Ablaufinformationen: DataTransferUtils.expiryTimeLeft() – Datentransferbereiche können ablaufen. Jeder Anhang erhält einen Ablauf-Countdown, der seinem DTO hinzugefügt wird. Das Frontend kann „Läuft in 3 Tagen ab" oder eine rote Warnung für abgelaufene Dateien anzeigen.
