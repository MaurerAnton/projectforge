No es Spring Security. La autenticación utiliza un sistema de sesión personalizado basado en tokens (DataTransferPublicSession), NO la cadena de filtros de Spring Security. Los usuarios externos obtienen un token de acceso (típicamente un UUID en un parámetro de URL) que se asigna a un área de transferencia de datos de ProjectForge. No se necesita una cuenta de usuario de ProjectForge — esto es para compartir archivos con clientes, proveedores o el público.

Cada endpoint comienza con las mismas 3 verificaciones: (1) validar categoría = "datatransfer", (2) validar listId = DEFAULT_NODE, (3) autenticar mediante dataTransferPublicSession.checkLogin(). La función check() lanza IllegalStateException si la condición falla — no capturada, se convierte en un error 500. Podría argumentarse que estas deberían devolver respuestas 400.

Autenticación pública basada en token — no se necesita cuenta de usuario

val data = dataTransferPublicSession.checkLogin(request, id)
    ?: return RestUtils.badRequest("No hay un inicio de sesión válido.")
val area: DataTransferAreaDO = data.first        // El área de DataTransfer
val sessionData = data.second                      // Información de sesión (userInfo, token)

DataTransferPublicSession.checkLogin() es la capa de autenticación personalizada. Extrae un token de acceso de la solicitud HTTP (probablemente de parámetros de consulta: ?accessToken=abc123) y lo valida contra la base de datos. En caso de éxito, devuelve un Pair<DataTransferAreaDO, TransferAreaData> — el área a la que se accede y los metadatos de la sesión. En caso de fallo, devuelve null y el endpoint responde con 400 "No hay un inicio de sesión válido."

No es un sistema JWT u OAuth — es una simple búsqueda de token. El token se genera cuando un administrador crea un área de transferencia de datos con acceso externo habilitado. El token se incrusta en la URL compartible: https://projectforge.acme.com/rsPublic/datatransfer/download/datatransfer/42?accessToken=uuid.

multiDownload — el truco del prefijo de ID de archivo (líneas 157-198)

@RequestParam("fileIds") fileIds: String,     // CSV: "abc1,def2,ghi3"
val fileIdList = fileIds.split(",")
val attachments = attachmentsService.getAttachments(...)
    ?.filter { attachment ->
        fileIdList.any { attachment.fileId?.startsWith(it) == true }
        // Coincidir por PREFIJO, ¡no por ID exacto! "abc" coincide con "abc123def456"
    }

El Javadoc en la línea 154 explica el truco: "Para preservar la longitud de la URL, los fileIds también pueden acortarse (por ejemplo, primeros 4 caracteres)." Los IDs de archivo JCR son UUIDs largos como "a1b2c3d4-e5f6-7890-abcd-ef1234567890". Poner múltiples UUIDs completos en una cadena de consulta de URL infla la URL más allá de los límites del navegador (~2000 caracteres). La solución: los usuarios pueden enviar solo los primeros 4 caracteres de cada ID de archivo.

Cómo funciona la coincidencia: fileIdList.any { attachment.fileId?.startsWith(it) == true } — para cada adjunto, verifica si su fileId completo comienza con ALGUNO de los prefijos proporcionados. Si el usuario envía "a1b2,d4e5", el servidor coincide con "a1b2c3d4-..." y "d4e5f6a7-...". Esto es un compromiso: URLs más cortas vs. riesgo de colisiones de prefijos. Con UUIDs, los primeros 4 caracteres hexadecimales tienen 16^4 = 65536 posibilidades — el riesgo de colisión es extremadamente bajo para uso típico (10-20 archivos por área).

Patrón ResponseAction — actualizaciones de UI impulsadas por el servidor

// Después de subir, indicar al frontend React que actualice la lista de adjuntos
return ResponseEntity.ok()
    .body(
        ResponseAction(targetType = TargetType.UPDATE, merge = true)
            .addVariable("data", AttachmentsServicesRest.ResponseData(list))
    )

// Después de eliminar/modificar, indicar a React que cierre el modal
return ResponseEntity.ok()
    .body(
        ResponseAction(targetType = TargetType.CLOSE_MODAL, merge = true)
            .addVariable("data", AttachmentsServicesRest.ResponseData(list))
    )

En lugar de devolver solo los datos actualizados, los endpoints devuelven un ResponseAction — un comando para el frontend React sobre qué hacer a continuación. Este es el patrón de UI impulsado por el servidor (SDUI) que ProjectForge utiliza para su sistema de diseño dinámico:

  • UPDATE — el frontend debe actualizar la vista actual con los nuevos datos (merge=true significa fusionar con el estado existente, no reemplazar)
  • CLOSE_MODAL — el frontend debe cerrar el diálogo modal actual y actualizar la vista padre

El addVariable("data", ...) adjunta la nueva lista de adjuntos como una variable nombrada. El motor de diseño dinámico del frontend lee el ResponseAction y decide qué componentes volver a renderizar. El servidor no conoce los componentes de React — envía acciones abstractas; el frontend las interpreta.

Registro de auditoría — cada operación registrada con información del usuario externo

attachmentsService.addAttachment(
    jcrPath, fileInfo, inputStream,
    baseDao = dataTransferAreaDao,
    obj = area,
    accessChecker = attachmentsAccessChecker,
    userString = getExternalUserString(request, sessionData.userInfo)  // ¡Auditoría!
)

Cada operación JCR pasa un userString — una cadena que identifica al usuario externo. getExternalUserString() (del objeto complementario de DataTransferAreaDao) extrae la dirección IP del cliente y la información de identidad opcional de la solicitud HTTP: "192.168.1.42 (John de Acme Corp)". Esta cadena se almacena en el registro de auditoría de JCR junto con la modificación del archivo. Aunque el usuario no tiene una cuenta de ProjectForge, sus acciones son rastreables — crítico para el cumplimiento de GDPR y la investigación forense de seguridad.

registerFileAsOwner() (línea 323): Después de la subida, la sesión registra qué archivos subió el usuario externo. Esto permite verificaciones de propiedad por archivo — un usuario solo puede eliminar/modificar archivos que él mismo subió, no archivos subidos por otros usuarios externos en la misma área compartida.

convert() — construyendo el DTO filtrado (líneas 442-464)

El helper convert() construye un DTO DataTransferPublicArea para el frontend. Dos transformaciones clave:

  1. Filtrado de acceso: attachmentsAccessChecker.filterAttachments() — elimina archivos que el usuario externo actual no debería ver. Esto es defensa en profundidad: incluso si la consulta JCR devuelve todos los archivos, el verificador de acceso elimina los no autorizados antes de que lleguen al cliente.
  2. Información de caducidad: DataTransferUtils.expiryTimeLeft() — las áreas de transferencia de datos pueden tener caducidad. Cada adjunto recibe una cuenta regresiva de caducidad añadida a su DTO. El frontend puede mostrar "Caduca en 3 días" o una advertencia en rojo para archivos caducados.
