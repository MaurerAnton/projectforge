Pas Spring Security. L'authentification utilise un système de session personnalisé basé sur des jetons (DataTransferPublicSession), PAS la chaîne de filtres de Spring Security. Les utilisateurs externes reçoivent un jeton d'accès (généralement un UUID dans un paramètre d'URL) qui correspond à une zone de transfert de données ProjectForge. Aucun compte utilisateur ProjectForge requis — ceci est destiné au partage de fichiers avec des clients, fournisseurs ou le public.

Chaque endpoint commence par les 3 mêmes vérifications : (1) valider que category = "datatransfer", (2) valider que listId = DEFAULT_NODE, (3) authentifier via dataTransferPublicSession.checkLogin(). La fonction check() lève une IllegalStateException si la condition échoue — non interceptée, elle devient une erreur 500. On pourrait soutenir que ces vérifications devraient retourner des réponses 400 à la place.

Authentification publique basée sur jeton — aucun compte utilisateur requis

val data = dataTransferPublicSession.checkLogin(request, id)
    ?: return RestUtils.badRequest("Aucune connexion valide.")
val area: DataTransferAreaDO = data.first        // La zone DataTransfer
val sessionData = data.second                      // Infos de session (userInfo, token)

DataTransferPublicSession.checkLogin() est la couche d'authentification personnalisée. Elle extrait un jeton d'accès de la requête HTTP (probablement depuis les paramètres de requête : ?accessToken=abc123) et le valide auprès de la base de données. En cas de succès, elle retourne un Pair<DataTransferAreaDO, TransferAreaData> — la zone accédée et les métadonnées de session. En cas d'échec, retourne null et l'endpoint répond avec 400 "Aucune connexion valide."

Ce n'est pas un système JWT ou OAuth — il s'agit d'une simple recherche de jeton. Le jeton est généré lorsqu'un administrateur crée une zone de transfert de données avec accès externe activé. Le jeton est intégré dans l'URL partageable : https://projectforge.acme.com/rsPublic/datatransfer/download/datatransfer/42?accessToken=uuid.

multiDownload — l'astuce du préfixe d'ID de fichier (lignes 157-198)

@RequestParam("fileIds") fileIds: String,     // CSV : "abc1,def2,ghi3"
val fileIdList = fileIds.split(",")
val attachments = attachmentsService.getAttachments(...)
    ?.filter { attachment ->
        fileIdList.any { attachment.fileId?.startsWith(it) == true }
        // Correspondance par PRÉFIXE, pas par ID exact ! "abc" correspond à "abc123def456"
    }

La Javadoc à la ligne 154 explique l'astuce : "Pour préserver la longueur de l'URL, les fileIds peuvent également être raccourcis (par exemple, les 4 premiers caractères)." Les ID de fichiers JCR sont de longs UUID comme "a1b2c3d4-e5f6-7890-abcd-ef1234567890". Mettre plusieurs UUID complets dans une chaîne de requête d'URL gonfle l'URL au-delà des limites du navigateur (~2000 caractères). La solution : les utilisateurs peuvent envoyer seulement les 4 premiers caractères de chaque ID de fichier.

Comment fonctionne la correspondance : fileIdList.any { attachment.fileId?.startsWith(it) == true } — pour chaque pièce jointe, vérifier si son fileId complet commence par N'IMPORTE LEQUEL des préfixes fournis. Si l'utilisateur envoie "a1b2,d4e5", le serveur fait correspondre "a1b2c3d4-..." et "d4e5f6a7-...". C'est un compromis : URLs plus courtes contre risque de collisions de préfixes. Avec les UUID, les 4 premiers caractères hexadécimaux offrent 16^4 = 65536 possibilités — le risque de collision est extrêmement faible pour une utilisation typique (10-20 fichiers par zone).

Modèle ResponseAction — mises à jour de l'interface pilotées par le serveur

// Après l'upload, dire au frontend React de mettre à jour la liste des pièces jointes
return ResponseEntity.ok()
    .body(
        ResponseAction(targetType = TargetType.UPDATE, merge = true)
            .addVariable("data", AttachmentsServicesRest.ResponseData(list))
    )

// Après suppression/modification, dire à React de fermer la modale
return ResponseEntity.ok()
    .body(
        ResponseAction(targetType = TargetType.CLOSE_MODAL, merge = true)
            .addVariable("data", AttachmentsServicesRest.ResponseData(list))
    )

Au lieu de retourner uniquement les données mises à jour, les endpoints retournent un ResponseAction — une commande pour le frontend React sur la marche à suivre. C'est le modèle d'interface pilotée par le serveur (SDUI) que ProjectForge utilise pour son système de mise en page dynamique :

  • UPDATE — le frontend doit mettre à jour la vue actuelle avec les nouvelles données (merge=true signifie fusionner avec l'état existant, pas remplacer)
  • CLOSE_MODAL — le frontend doit fermer la boîte de dialogue modale actuelle et mettre à jour la vue parente

Le addVariable("data", ...) attache la nouvelle liste de pièces jointes comme variable nommée. Le moteur de mise en page dynamique du frontend lit le ResponseAction et décide quels composants réafficher. Le serveur ne connaît pas les composants React — il envoie des actions abstraites ; le frontend les interprète.

Piste d'audit — chaque opération journalisée avec les informations de l'utilisateur externe

attachmentsService.addAttachment(
    jcrPath, fileInfo, inputStream,
    baseDao = dataTransferAreaDao,
    obj = area,
    accessChecker = attachmentsAccessChecker,
    userString = getExternalUserString(request, sessionData.userInfo)  // Audit !
)

Chaque opération JCR passe un userString — une chaîne identifiant l'utilisateur externe. getExternalUserString() (de l'objet compagnon de DataTransferAreaDao) extrait l'adresse IP du client et les informations d'identité facultatives de la requête HTTP : "192.168.1.42 (John d'Acme Corp)". Cette chaîne est stockée dans le journal d'audit JCR avec la modification du fichier. Même si l'utilisateur n'a pas de compte ProjectForge, ses actions sont traçables — essentiel pour la conformité RGPD et la criminalistique de sécurité.

registerFileAsOwner() (ligne 323) : Après l'upload, la session enregistre les fichiers que l'utilisateur externe a uploadés. Cela permet des vérifications de propriété par fichier — un utilisateur ne peut supprimer/modifier que les fichiers qu'il a lui-même uploadés, pas ceux uploadés par d'autres utilisateurs externes dans la même zone partagée.

convert() — construction du DTO filtré (lignes 442-464)

Le helper convert() construit un DTO DataTransferPublicArea pour le frontend. Deux transformations clés :

  1. Filtrage d'accès : attachmentsAccessChecker.filterAttachments() — supprime les fichiers que l'utilisateur externe actuel ne devrait pas voir. C'est une défense en profondeur : même si la requête JCR retourne tous les fichiers, le vérificateur d'accès supprime ceux non autorisés avant qu'ils n'atteignent le client.
  2. Infos d'expiration : DataTransferUtils.expiryTimeLeft() — les zones de transfert de données peuvent avoir une expiration. Chaque pièce jointe reçoit un compte à rebours d'expiration ajouté à son DTO. Le frontend peut afficher "Expire dans 3 jours" ou un avertissement rouge pour les fichiers expirés.
