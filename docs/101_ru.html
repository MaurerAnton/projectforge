Не Spring Security. Аутентификация использует собственную систему сессий на основе токенов (DataTransferPublicSession), а НЕ цепочку фильтров Spring Security. Внешние пользователи получают токен доступа (обычно UUID в параметре URL), который сопоставляется с областью передачи данных ProjectForge. Учётная запись пользователя ProjectForge не требуется — это для обмена файлами с клиентами, поставщиками или публикой.

Каждая конечная точка начинается с одних и тех же 3 проверок: (1) проверить category = "datatransfer", (2) проверить listId = DEFAULT_NODE, (3) аутентификация через dataTransferPublicSession.checkLogin(). Функция check() выбрасывает IllegalStateException при неудаче условия — неперехваченное исключение становится ошибкой 500. По-хорошему, они должны возвращать ответы 400.

Публичная аутентификация на основе токена — учётная запись не требуется

val data = dataTransferPublicSession.checkLogin(request, id)
    ?: return RestUtils.badRequest("Нет действительного входа.")
val area: DataTransferAreaDO = data.first        // Область DataTransfer
val sessionData = data.second                      // Информация о сессии (userInfo, token)

DataTransferPublicSession.checkLogin() — это собственный слой аутентификации. Он извлекает токен доступа из HTTP-запроса (вероятно, из параметров запроса: ?accessToken=abc123) и проверяет его в базе данных. В случае успеха возвращает Pair<DataTransferAreaDO, TransferAreaData> — область доступа и метаданные сессии. В случае неудачи возвращает null, и конечная точка отвечает 400 "Нет действительного входа."

Не JWT и не OAuth — это простой поиск токена. Токен генерируется, когда администратор создаёт область передачи данных с включённым внешним доступом. Токен встраивается в URL для отправки: https://projectforge.acme.com/rsPublic/datatransfer/download/datatransfer/42?accessToken=uuid.

multiDownload — трюк с префиксом ID файла (строки 157-198)

@RequestParam("fileIds") fileIds: String,     // CSV: "abc1,def2,ghi3"
val fileIdList = fileIds.split(",")
val attachments = attachmentsService.getAttachments(...)
    ?.filter { attachment ->
        fileIdList.any { attachment.fileId?.startsWith(it) == true }
        // Сопоставление по ПРЕФИКСУ, а не точному ID! "abc" соответствует "abc123def456"
    }

Javadoc в строке 154 объясняет трюк: "Для сохранения длины URL fileIds могут быть сокращены (например, первые 4 символа)." ID файлов JCR — это длинные UUID, например "a1b2c3d4-e5f6-7890-abcd-ef1234567890". Размещение нескольких полных UUID в строке запроса URL раздувает URL за пределы ограничений браузера (~2000 символов). Решение: пользователи могут отправлять только первые 4 символа каждого ID файла.

Как работает сопоставление: fileIdList.any { attachment.fileId?.startsWith(it) == true } — для каждого вложения проверяется, начинается ли его полный fileId с любого из предоставленных префиксов. Если пользователь отправляет "a1b2,d4e5", сервер сопоставляет "a1b2c3d4-..." и "d4e5f6a7-...". Это компромисс: более короткие URL против риска коллизий префиксов. Для UUID первые 4 шестнадцатеричных символа дают 16^4 = 65536 возможностей — риск коллизий чрезвычайно низок для типичного использования (10-20 файлов на область).

Паттерн ResponseAction — обновления UI со стороны сервера

// После загрузки сообщить React-фронтенду об обновлении списка вложений
return ResponseEntity.ok()
    .body(
        ResponseAction(targetType = TargetType.UPDATE, merge = true)
            .addVariable("data", AttachmentsServicesRest.ResponseData(list))
    )

// После удаления/изменения сообщить React о закрытии модального окна
return ResponseEntity.ok()
    .body(
        ResponseAction(targetType = TargetType.CLOSE_MODAL, merge = true)
            .addVariable("data", AttachmentsServicesRest.ResponseData(list))
    )

Вместо возврата только обновлённых данных конечные точки возвращают ResponseAction — команду для React-фронтенда о том, что делать дальше. Это паттерн "серверного управления UI" (SDUI), который ProjectForge использует для своей динамической системы макетов:

  • UPDATE — фронтенд должен обновить текущее представление новыми данными (merge=true означает слияние с существующим состоянием, а не замену)
  • CLOSE_MODAL — фронтенд должен закрыть текущее модальное окно и обновить родительское представление

addVariable("data", ...) прикрепляет новый список вложений как именованную переменную. Динамический движок макетов фронтенда читает ResponseAction и решает, какие компоненты перерендерить. Сервер не знает о React-компонентах — он отправляет абстрактные действия; фронтенд их интерпретирует.

Журнал аудита — каждая операция логируется с информацией о внешнем пользователе

attachmentsService.addAttachment(
    jcrPath, fileInfo, inputStream,
    baseDao = dataTransferAreaDao,
    obj = area,
    accessChecker = attachmentsAccessChecker,
    userString = getExternalUserString(request, sessionData.userInfo)  // Аудит!
)

Каждая операция JCR передаёт userString — строку, идентифицирующую внешнего пользователя. getExternalUserString() (из сопутствующего объекта DataTransferAreaDao) извлекает IP-адрес клиента и дополнительную информацию об идентификации из HTTP-запроса: "192.168.1.42 (John из Acme Corp)". Эта строка сохраняется в журнале аудита JCR вместе с изменением файла. Даже если у пользователя нет учётной записи ProjectForge, его действия отслеживаются — критически важно для соответствия GDPR и судебной экспертизы безопасности.

registerFileAsOwner() (строка 323): После загрузки сессия записывает, какие файлы загрузил внешний пользователь. Это позволяет проверять владение файлами — пользователь может удалять/изменять только те файлы, которые загрузил сам, а не файлы, загруженные другими внешними пользователями в той же общей области.

convert() — построение отфильтрованного DTO (строки 442-464)

Вспомогательная функция convert() строит DTO DataTransferPublicArea для фронтенда. Два ключевых преобразования:

  1. Фильтрация доступа: attachmentsAccessChecker.filterAttachments() — удаляет файлы, которые текущий внешний пользователь не должен видеть. Это защита в глубину: даже если запрос JCR возвращает все файлы, проверка доступа отсеивает неавторизованные, прежде чем они достигнут клиента.
  2. Информация об истечении: DataTransferUtils.expiryTimeLeft() — области передачи данных могут иметь срок действия. Каждое вложение получает обратный отсчёт срока действия, добавленный в его DTO. Фронтенд может отображать "Истекает через 3 дня" или красное предупреждение для просроченных файлов.
