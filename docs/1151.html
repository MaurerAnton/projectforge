1151: UserXmlPreferencesMigrationDao.kt

Migration DAO, projectforge-business/src/main/kotlin/org/projectforge/business/user/UserXmlPreferencesMigrationDao.kt
Migrates serialized user XML preferences across version upgrades using a version-numbered migration scheme with admin-only access.

Architecture

This @Service class implements a migration engine for UserXmlPreferencesDO — serialized user settings (filters, personal preferences) stored as XML in the database. It follows a strategy pattern: each deployment may introduce new migration steps triggered by the oldest version field found among all preference records.

Dependency Graph

UserXmlPreferencesMigrationDao relies on AccessChecker (admin gate), UserGroupCache (user lookups), UserXmlPreferencesDao (persistence), UserXmlPreferencesCache (cache refresh), and PfPersistenceService (JPQL execution). The access gate ensures only administrators can trigger migrations.

Migration Flow

  1. migrateAllUserPrefs() — Entry point. Checks admin membership, queries all UserXmlPreferencesDO ordered by user and key, finds the oldest version number.
  2. migrateUserPrefs(userPrefs) — Per-entry migration. If the version is current, skips. Otherwise calls migrate(userPrefs) and then attempts deserialization (userXmlPreferencesDao.deserialize) as a compatibility check.
  3. migrate(version) — Optional override point for bulk operations (e.g. deleting entries by unused keys). Currently contains a commented-out example for version < 4.
  4. deleteOldKeys(key) — Deletes all preference entries with a given key via JPQL delete.

Version Handling

The companion object's migrate(userPrefs) performs in-place version upgrades. Currently only one rule: versions before 4 are bumped to 4. UserXmlPreferencesDO.getCurrentVersion() defines the target version number. New migration rules are added as conditional branches inside this method.

Design Rationale

User preferences are serialized objects (XStream or Java serialization), making schema migrations impossible through SQL. The version field on each preference record enables lazy, per-entry migration at read time while this DAO provides a bulk migration option for administrators. The deserialization check after migration serves as a smoke test — if re-serialization fails after version upgrade, the entry is flagged but not deleted, preserving data for manual repair.
