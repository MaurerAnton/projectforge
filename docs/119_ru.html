Чистый модульный тест для логики получателей уведомлений наблюдателя — проверяет, кто получает уведомление для каждого типа события. В отличие от DataTransferNotificationMailTest (который тестирует полный почтовый конвейер), этот тест изолирует алгоритм выбора получателей. Не расширяет AbstractTestBase — выполняется без контекста Spring, что делает его быстрым.

Метод теста: registerRecipientsTest()

Использует вспомогательный метод testAudit(uploadUserId, byUserId, eventType, observerIds, expected), который:

  1. Создаёт mock-объекты PFUserDO для загрузчика, пользователя, выполняющего действие, и наблюдателей
  2. Симулирует событие аудита путём прямого вызова логики уведомлений
  3. Проверяет, что только ожидаемый набор идентификаторов наблюдателей получает уведомление

Проверяемые правила уведомлений

  • ЗАГРУЗКА другим пользователем: все наблюдатели, кроме загрузчика, должны быть уведомлены (загрузчик уже знает, что он загрузил)
  • ЗАГРУЗКА собой: никто не должен быть уведомлен (observerIds = [1,2,3], uploadUserId = 1, byUserId = 1 → ожидается = [2,3])
  • УДАЛЕНИЕ самим наблюдателем: удаляющий наблюдатель не должен получать уведомление о своём собственном действии
  • СКАЧИВАНИЕ внешним пользователем: все наблюдатели должны быть уведомлены (внешний пользователь не является наблюдателем)
  • ПЕРЕИМЕНОВАНИЕ: наблюдатели уведомляются, загрузчик исключается, если он же выполняет переименование

Инвариант: вы никогда не получаете уведомления о своих собственных действиях — только активность других людей вызывает уведомления.

Примечание по дизайну

Это модульный тест (без базы данных, без JCR, без Spring), который тестирует только логику получателей уведомлений. Вспомогательный метод testAudit напрямую вызывает метод уведомления с подготовленными входными данными. Фактический DataTransferNotificationJob + рендеринг почты тестируется в DataTransferNotificationMailTest. Такое разделение делает тест логики уведомлений быстрым (миллисекунды против секунд для интеграционных тестов).
