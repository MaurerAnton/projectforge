Quelle: GitHub

64 Zeilen · 50 Code · 4 Kommentare · 10 Leerzeilen

Was es tut

Dies ist das Herzstück des ProjectForge-Buildsystems. Jedes Modul (projectforge-business, projectforge-webapp, usw.) wendet dieses Plugin mit einer Zeile an und erhält:

  • Java 17-Kompilierung mit --release 17 (baut auf JDK 21, läuft auf JDK 17)
  • Kotlin stdlib + kotlin-logging als Modulabhängigkeiten
  • JUnit 5-Testframework (useJUnitPlatform())
  • Jackson-Version festlegen — erzwingt, dass alle Module dieselbe Jackson-Version verwenden
  • GitHub-basierter Repository-Zugriff (für die Gephi-Abhängigkeit)

Zeilen 1–3: Basis-Plugin

1 plugins {
2     id("java-library")
3 }

java-library erweitert java um die Trennung von api und implementation. Wenn Modul A dieses Plugin anwendet und api() zur Deklaration einer Abhängigkeit verwendet, wird diese Abhängigkeit an die Konsumenten von Modul A weitergegeben. Dies ist wichtig für das Plugin-System: Plugins hängen über api-Abhängigkeiten von ProjectForge-Modulen ab.

⚠️ Wichtige Einschränkung: Die Kurzform libs.versions.xxx, die in regulären build.gradle.kts-Dateien funktioniert, funktioniert NICHT innerhalb von Konventions-Plugins in buildSrc/. Stattdessen müssen Sie findVersion() und findLibrary() verwenden, wie in Zeile 13 und in dieser gesamten Datei gezeigt.

Zeile 13: Ruft die Versionskatalog-Erweiterung nach Typ ab — der einzige Weg, in buildSrc darauf zuzugreifen.

Zeile 17: Setzt group = "org.projectforge" — identisch mit Zeile 8 der root build.gradle.kts. Hier dupliziert, weil buildSrc ein separates Projekt ist.

Zeile 18: Liest die Version aus dem Katalog (libs.versions.toml) — keine fest codierte Versionsnummer.

Zeilen 20–29: Java 17-Konfiguration

20 extensions.configure<JavaPluginExtension> {
21     sourceCompatibility = JavaVersion.VERSION_17
22     targetCompatibility = JavaVersion.VERSION_17
23 }
24 
25 tasks.withType<JavaCompile> {
26     options.encoding = "UTF-8"
27     options.isIncremental = true
28     options.release.set(17)
29 }

Zeilen 21–22: sourceCompatibility und targetCompatibility — teilen Gradle mit, welche Java-Version der Quellcode verwendet (17) und welche Bytecode-Version erzeugt werden soll (17). Diese steuern Sprachfunktionen und die Kompilierungsausgabe.

Zeile 28: options.release.set(17) — das Compiler-Flag --release 17. Dies ist stärker als sourceCompatibility allein — es schränkt den Compiler auf nur Java 17-API-Symbole ein. Ohne dies könnte das Bauen auf JDK 21 Bytecode erzeugen, der auf Java 18+ APIs verweist, die auf JDK 17 nicht existieren, was zur Laufzeit einen UnsupportedClassVersionError verursacht.

Warum Java 17? Es ist die aktuelle LTS-Version, die von Spring Boot 3.x unterstützt wird (erforderliches Minimum). ProjectForge verwendet Kotlin, das zu JVM-Bytecode kompiliert wird, daher ist die JDK-Version für beide Sprachen wichtig.

Zeilen 30–35: Kotlin-Kompilierung (auskommentiert)

30 /*
31 tasks.withType<KotlinCompile> {
32     compilerOptions {
33         jvmTarget.set(JvmTarget.JVM_17)
34     }
35 }*/

Kotlin JVM Target 17 — derzeit auskommentiert. Kotlin kompiliert standardmäßig zu 1.8 (Java 8) Bytecode, der mit Java 17 kompatibel ist. Die Datei verwendet options.release = 17 in Zeile 28 für Java-Dateien. Das Kotlin-Äquivalent würde auskommentiert, wenn das Projekt explizit Java 17 Kotlin-Bytecode benötigt.

Zeilen 37–39: JUnit 5

37 tasks.withType<Test> {
38     useJUnitPlatform()
39 }

Aktiviert JUnit 5 (Jupiter) für alle Testaufgaben in allen Modulen. Ohne dies verwendet Gradle standardmäßig JUnit 4. ProjectForge migrierte von einer Mischung aus TestNG + JUnit4 zu reinem JUnit5 in Commits wie 20e07f9d1.

Zeilen 45–56: Jackson-Version erzwingen

45 configurations.all {
46     resolutionStrategy {
47         preferProjectModules()
48         // Erzwingt, dass alle Jackson-Modulversionen mit der expliziten Jackson-Version des Projekts übereinstimmen.
49         // Transitive Abhängigkeiten (z.B. ez-vcard, groovy-yaml, flyway) können neuere Jackson-Versionen einbringen.
50         val jacksonVersion = libs.findVersion("com.fasterxml.jackson").get().requiredVersion
51         force("com.fasterxml.jackson:jackson-bom:$jacksonVersion")
52         force("com.fasterxml.jackson.core:jackson-core:$jacksonVersion")
53         force("com.fasterxml.jackson.core:jackson-databind:$jacksonVersion")
54         force("com.fasterxml.jackson.core:jackson-annotations:$jacksonVersion")
55     }
56 }

Dies ist der wichtigste Abschnitt für die Build-Stabilität. Jackson ist eine transitive Abhängigkeit vieler Bibliotheken (ez-vcard, groovy-yaml, flyway). Jede Bibliothek kann eine andere Jackson-Version mitbringen, was zu Laufzeitfehlern wie NoSuchMethodError oder ClassNotFoundException führt.

Wie force() funktioniert: Die Abhängigkeitsauflösung von Gradle sammelt alle angeforderten Versionen von Jackson im gesamten Abhängigkeitsbaum. Die force()-Direktive überschreibt jede Version — unabhängig davon, was eine Bibliothek anfordert, wird Jackson auf die Version aus libs.versions.toml festgelegt.

Warum vier Artefakte: Jackson ist in Module aufgeteilt (jackson-core, jackson-databind, jackson-annotations), die versionssynchron sein müssen. Der jackson-bom (Bill of Materials) bietet koordinierte Versionen, aber force() auf einzelne Artefakte ist expliziter.

Ohne diesen Abschnitt: Verschiedene Unterprojekte könnten gegen unterschiedliche Jackson-Versionen kompilieren — das fat JAR würde mehrere Jackson-JARs enthalten, und der Classloader würde dasjenige auswählen, das er zuerst findet. Dies äußert sich in mysteriösen Serialisierungsfehlern in der Produktion.

Wichtige Erkenntnisse

  • 64 Zeilen, jedes Modul: Diese Datei ist die DNA des ProjectForge-Builds — angewendet auf alle 15+ Module.
  • Zeile 28 ist entscheidend: --release 17 ist der Grund, warum ProjectForge auf JDK 21 baut, aber auf JDK 17 läuft.
  • Jackson erzwingen (Zeilen 50–54): Verhindert die häufigste Ursache für Laufzeitfehler im Klassenpfad (Versionskonflikte).
  • Kommentar in Zeile 15: Erklärt, warum findVersion()/findLibrary() anstelle der üblichen Kurzform libs.versions.xxx verwendet wird.
  • Änderungsrate: Wird aktualisiert, wenn sich Abhängigkeiten ändern — vielleicht einmal alle paar Releases.
