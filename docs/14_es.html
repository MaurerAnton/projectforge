Qué hace

Este es el corazón del sistema de compilación de ProjectForge. Cada módulo (projectforge-business, projectforge-webapp, etc.) aplica este plugin con una sola línea y obtiene:

  • Compilación con Java 17 usando --release 17 (compila en JDK 21, ejecuta en JDK 17)
  • Kotlin stdlib + kotlin-logging como dependencias de módulo
  • Framework de pruebas JUnit 5 (useJUnitPlatform())
  • Fijación de versión de Jackson: obliga a todos los módulos a usar la misma versión de Jackson
  • Acceso a repositorios basados en GitHub (para la dependencia gephi)

2     id("java-library")

java-library extiende java con la separación api vs implementation. Cuando el módulo A aplica este plugin y usa api() para declarar una dependencia, esa dependencia se filtra a los consumidores del módulo A. Esto es importante para el sistema de plugins: los plugins dependen de los módulos de ProjectForge a través de dependencias api.

Líneas 20–29: Configuración de Java 17

20 extensions.configure<JavaPluginExtension> {
21     sourceCompatibility = JavaVersion.VERSION_17
22     targetCompatibility = JavaVersion.VERSION_17
23 }
24 
25 tasks.withType<JavaCompile> {
26     options.encoding = "UTF-8"
27     options.isIncremental = true
28     options.release.set(17)
29 }

Líneas 21–22: sourceCompatibility y targetCompatibility — indican a Gradle qué versión de Java usa el código fuente (17) y qué versión de bytecode producir (17). Controlan las características del lenguaje y la salida de compilación.

Línea 28: options.release.set(17) — el indicador del compilador --release 17. Esto es más fuerte que sourceCompatibility solo: restringe el compilador únicamente a los símbolos de la API de Java 17. Sin esto, compilar en JDK 21 podría producir bytecode que haga referencia a API de Java 18+ que no existen en JDK 17, causando UnsupportedClassVersionError en tiempo de ejecución.

¿Por qué Java 17? Es la versión LTS actual compatible con Spring Boot 3.x (mínimo requerido). ProjectForge usa Kotlin, que compila a bytecode JVM, por lo que la versión del JDK es importante para ambos lenguajes.

Objetivo JVM 17 de Kotlin — actualmente comentado. Kotlin compila a bytecode 1.8 (Java 8) por defecto, que es compatible con Java 17. El archivo usa options.release = 17 en la línea 28 para archivos Java. El equivalente de Kotlin se descomentaría cuando el proyecto necesite explícitamente bytecode de Kotlin para Java 17.

Líneas 37–39: JUnit 5

37 tasks.withType<Test> {
38     useJUnitPlatform()
39 }

Habilita JUnit 5 (Jupiter) para todas las tareas de prueba en todos los módulos. Sin esto, Gradle usa JUnit 4 por defecto. ProjectForge migró de TestNG + JUnit4 mixto a JUnit5 puro en commits como 20e07f9d1.

Líneas 45–56: Forzado de versión de Jackson

45 configurations.all {
46     resolutionStrategy {
47         preferProjectModules()
48         // Forzar que todas las versiones de los módulos de Jackson coincidan con la versión explícita de Jackson del proyecto.
49         // Las dependencias transitivas (ej. ez-vcard, groovy-yaml, flyway) pueden traer versiones más nuevas de Jackson.
50         val jacksonVersion = libs.findVersion("com.fasterxml.jackson").get().requiredVersion
51         force("com.fasterxml.jackson:jackson-bom:$jacksonVersion")
52         force("com.fasterxml.jackson.core:jackson-core:$jacksonVersion")
53         force("com.fasterxml.jackson.core:jackson-databind:$jacksonVersion")
54         force("com.fasterxml.jackson.core:jackson-annotations:$jacksonVersion")
55     }
56 }

Esta es la sección más importante para la estabilidad de la compilación. Jackson es una dependencia transitiva de muchas bibliotecas (ez-vcard, groovy-yaml, flyway). Cada biblioteca puede traer una versión diferente de Jackson, lo que provoca NoSuchMethodError o ClassNotFoundException en tiempo de ejecución.

Cómo funciona force(): La resolución de dependencias de Gradle recopila todas las versiones solicitadas de Jackson en todo el árbol de dependencias. La directiva force() anula cualquier versión — independientemente de lo que solicite cualquier biblioteca, Jackson se fijará a la versión de libs.versions.toml.

Por qué cuatro artefactos: Jackson está dividido en módulos (jackson-core, jackson-databind, jackson-annotations) que deben estar sincronizados en versión. El jackson-bom (Bill of Materials) proporciona versiones coordinadas, pero force() en artefactos individuales es más explícito.

Sin esta sección: Diferentes subproyectos podrían compilar contra diferentes versiones de Jackson — el JAR gordo contendría múltiples JARs de Jackson, y el cargador de clases elegiría el que encuentre primero. Esto se manifiesta como misteriosos errores de serialización en producción.

Conclusiones clave

  • 64 líneas, cada módulo: Este archivo es el ADN de la compilación de ProjectForge — aplicado a los más de 15 módulos.
  • La línea 28 importa: --release 17 es la razón por la que ProjectForge compila en JDK 21 pero se ejecuta en JDK 17.
  • Forzado de Jackson (líneas 50–54): Previene la fuente #1 de errores de classpath en tiempo de ejecución (desajuste de versiones).
  • Comentario en la línea 15: Explica por qué se usa findVersion()/findLibrary() en lugar de la abreviatura habitual libs.versions.xxx.
  • Frecuencia de cambios: Se actualiza cuando cambian las dependencias — quizás una vez cada pocos lanzamientos.
