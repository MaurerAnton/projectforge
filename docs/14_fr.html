Ce qu'il fait

C'est le cœur du système de build de ProjectForge. Chaque module (projectforge-business, projectforge-webapp, etc.) applique ce plugin avec une seule ligne, et obtient :

  • Compilation Java 17 avec --release 17 (construit sur JDK 21, s'exécute sur JDK 17)
  • Kotlin stdlib + kotlin-logging comme dépendances de module
  • Framework de test JUnit 5 (useJUnitPlatform())
  • Verrouillage de version Jackson — force tous les modules à utiliser la même version de Jackson
  • Accès au dépôt basé sur GitHub (pour la dépendance gephi)

java-library étend java avec la séparation api vs implementation. Lorsque le module A applique ce plugin et utilise api() pour déclarer une dépendance, cette dépendance est transmise aux consommateurs du module A. Ceci est important pour le système de plugins : les plugins dépendent des modules ProjectForge via des dépendances api.

Lignes 20–29 : Configuration Java 17

20 extensions.configure<JavaPluginExtension> {
21     sourceCompatibility = JavaVersion.VERSION_17
22     targetCompatibility = JavaVersion.VERSION_17
23 }
24 
25 tasks.withType<JavaCompile> {
26     options.encoding = "UTF-8"
27     options.isIncremental = true
28     options.release.set(17)
29 }

Lignes 21–22 : sourceCompatibility et targetCompatibility — indiquent à Gradle quelle version de Java le code source utilise (17) et quelle version de bytecode produire (17). Ceux-ci contrôlent les fonctionnalités du langage et la sortie de compilation.

Ligne 28 : options.release.set(17) — le drapeau du compilateur --release 17. C'est plus fort que sourceCompatibility seul — il restreint le compilateur aux seuls symboles de l'API Java 17. Sans cela, la construction sur JDK 21 pourrait produire du bytecode référençant des API Java 18+ qui n'existent pas sur JDK 17, provoquant une UnsupportedClassVersionError à l'exécution.

Pourquoi Java 17 ? C'est la version LTS actuelle supportée par Spring Boot 3.x (minimum requis). ProjectForge utilise Kotlin qui compile en bytecode JVM, donc la version du JDK est importante pour les deux langages.

Cible JVM Kotlin 17 — actuellement commentée. Kotlin compile en bytecode 1.8 (Java 8) par défaut, ce qui est compatible avec Java 17. Le fichier utilise options.release = 17 à la ligne 28 pour les fichiers Java. L'équivalent Kotlin serait décommenté lorsque le projet aura explicitement besoin du bytecode Kotlin Java 17.

Lignes 37–39 : JUnit 5

37 tasks.withType<Test> {
38     useJUnitPlatform()
39 }

Active JUnit 5 (Jupiter) pour toutes les tâches de test dans tous les modules. Sans cela, Gradle utilise par défaut JUnit 4. ProjectForge a migré du mélange TestNG + JUnit4 vers JUnit5 pur dans des commits comme 20e07f9d1.

Lignes 45–56 : Forçage de version Jackson

45 configurations.all {
46     resolutionStrategy {
47         preferProjectModules()
48         // Forcer toutes les versions des modules Jackson à correspondre à la version Jackson explicite du projet.
49         // Les dépendances transitives (ex. ez-vcard, groovy-yaml, flyway) peuvent apporter des versions plus récentes de Jackson.
50         val jacksonVersion = libs.findVersion("com.fasterxml.jackson").get().requiredVersion
51         force("com.fasterxml.jackson:jackson-bom:$jacksonVersion")
52         force("com.fasterxml.jackson.core:jackson-core:$jacksonVersion")
53         force("com.fasterxml.jackson.core:jackson-databind:$jacksonVersion")
54         force("com.fasterxml.jackson.core:jackson-annotations:$jacksonVersion")
55     }
56 }

C'est la section la plus importante pour la stabilité du build. Jackson est une dépendance transitive de nombreuses bibliothèques (ez-vcard, groovy-yaml, flyway). Chaque bibliothèque peut apporter une version différente de Jackson, conduisant à des NoSuchMethodError ou ClassNotFoundException à l'exécution.

Comment fonctionne force() : La résolution des dépendances de Gradle collecte toutes les versions demandées de Jackson dans tout l'arbre de dépendances. La directive force() remplace toute version — indépendamment de ce que demande une bibliothèque, Jackson sera verrouillé sur la version de libs.versions.toml.

Pourquoi quatre artefacts : Jackson est divisé en modules (jackson-core, jackson-databind, jackson-annotations) qui doivent être synchronisés en version. Le jackson-bom (Bill of Materials) fournit des versions coordonnées, mais force() sur des artefacts individuels est plus explicite.

Sans cette section : Différents sous-projets pourraient compiler avec différentes versions de Jackson — le JAR complet contiendrait plusieurs JAR Jackson, et le chargeur de classe prendrait le premier trouvé. Cela se manifeste par des erreurs de sérialisation mystérieuses en production.

Points clés à retenir

  • 64 lignes, chaque module : Ce fichier est l'ADN du build de ProjectForge — appliqué à tous les 15+ modules.
  • La ligne 28 est importante : --release 17 est la raison pour laquelle ProjectForge se construit sur JDK 21 mais s'exécute sur JDK 17.
  • Forçage Jackson (lignes 50–54) : Empêche la source n°1 de bugs de classpath à l'exécution (incompatibilité de version).
  • Commentaire à la ligne 15 : Explique pourquoi findVersion()/findLibrary() est utilisé à la place du raccourci habituel libs.versions.xxx.
  • Fréquence de modification : Mis à jour lorsque les dépendances changent — peut-être une fois toutes les quelques versions.
