Что делает

Это сердце системы сборки ProjectForge. Каждый модуль (projectforge-business, projectforge-webapp и т.д.) применяет этот плагин одной строкой и получает:

  • Компиляцию Java 17 с --release 17 (сборка на JDK 21, выполнение на JDK 17)
  • Kotlin stdlib + kotlin-logging в качестве зависимостей модуля
  • Тестовый фреймворк JUnit 5 (useJUnitPlatform())
  • Фиксацию версии Jackson — принуждает все модули использовать одну и ту же версию Jackson
  • Доступ к репозиториям на основе GitHub (для зависимости gephi)

Строки 1–3: Базовый плагин

1 plugins {
2     id("java-library")
3 }

java-library расширяет java разделением api и implementation. Когда модуль A применяет этот плагин и использует api() для объявления зависимости, эта зависимость становится доступной потребителям модуля A. Это важно для системы плагинов: плагины зависят от модулей ProjectForge через зависимости api.

⚠️ Ключевое ограничение: Сокращение libs.versions.xxx, которое работает в обычных файлах build.gradle.kts, НЕ работает внутри соглашение-плагинов buildSrc/. Вместо этого необходимо использовать findVersion() и findLibrary(), как показано в строке 13 и далее в этом файле.

Строка 18: Читает версию из каталога (libs.versions.toml) — без жестко заданного номера версии.

Строки 20–29: Конфигурация Java 17

20 extensions.configure<JavaPluginExtension> {
21     sourceCompatibility = JavaVersion.VERSION_17
22     targetCompatibility = JavaVersion.VERSION_17
23 }
24 
25 tasks.withType<JavaCompile> {
26     options.encoding = "UTF-8"
27     options.isIncremental = true
28     options.release.set(17)
29 }

Строки 21–22: sourceCompatibility и targetCompatibility — сообщают Gradle, какую версию Java использует исходный код (17) и какую версию байт-кода создавать (17). Они управляют возможностями языка и выводом компиляции.

Строка 28: options.release.set(17) — флаг компилятора --release 17. Это сильнее, чем просто sourceCompatibility — он ограничивает компилятор только API-символами Java 17. Без этого сборка на JDK 21 может создать байт-код, ссылающийся на API Java 18+, которых нет на JDK 17, что вызовет UnsupportedClassVersionError во время выполнения.

Почему Java 17? Это текущая версия LTS, поддерживаемая Spring Boot 3.x (требуемый минимум). ProjectForge использует Kotlin, который компилируется в байт-код JVM, поэтому версия JDK важна для обоих языков.

Строки 30–35: Компиляция Kotlin (закомментировано)

30 /*
31 tasks.withType<KotlinCompile> {
32     compilerOptions {
33         jvmTarget.set(JvmTarget.JVM_17)
34     }
35 }*/

Цель JVM Kotlin 17 — в настоящее время закомментировано. Kotlin по умолчанию компилируется в байт-код 1.8 (Java 8), который совместим с Java 17. Файл использует options.release = 17 в строке 28 для файлов Java. Эквивалент для Kotlin будет раскомментирован, когда проекту явно потребуется байт-код Kotlin для Java 17.

Строки 37–39: JUnit 5

37 tasks.withType<Test> {
38     useJUnitPlatform()
39 }

Включает JUnit 5 (Jupiter) для всех тестовых задач во всех модулях. Без этого Gradle по умолчанию использует JUnit 4. ProjectForge перешёл со смешанного TestNG + JUnit4 на чистый JUnit5 в коммитах, таких как 20e07f9d1.

Строки 45–56: Принудительная фиксация версии Jackson

45 configurations.all {
46     resolutionStrategy {
47         preferProjectModules()
48         // Принудительно устанавливает версии всех модулей Jackson в соответствии с явной версией Jackson проекта.
49         // Транзитивные зависимости (например, ez-vcard, groovy-yaml, flyway) могут подтягивать более новые версии Jackson.
50         val jacksonVersion = libs.findVersion("com.fasterxml.jackson").get().requiredVersion
51         force("com.fasterxml.jackson:jackson-bom:$jacksonVersion")
52         force("com.fasterxml.jackson.core:jackson-core:$jacksonVersion")
53         force("com.fasterxml.jackson.core:jackson-databind:$jacksonVersion")
54         force("com.fasterxml.jackson.core:jackson-annotations:$jacksonVersion")
55     }
56 }

Это самый важный раздел для стабильности сборки. Jackson является транзитивной зависимостью многих библиотек (ez-vcard, groovy-yaml, flyway). Каждая библиотека может подтянуть другую версию Jackson, что приводит к ошибкам времени выполнения NoSuchMethodError или ClassNotFoundException.

Как работает force(): Разрешение зависимостей Gradle собирает все запрошенные версии Jackson по всему дереву зависимостей. Директива force() переопределяет любую версию — независимо от того, что запрашивает какая-либо библиотека, Jackson будет зафиксирован на версии из libs.versions.toml.

Почему четыре артефакта: Jackson разделён на модули (jackson-core, jackson-databind, jackson-annotations), которые должны быть синхронизированы по версиям. jackson-bom (Bill of Materials) предоставляет согласованные версии, но force() для отдельных артефактов более явный.

Без этого раздела: Разные подпроекты могут компилироваться с разными версиями Jackson — толстый JAR будет содержать несколько JAR-файлов Jackson, и загрузчик классов выберет тот, который найдёт первым. Это проявляется как загадочные ошибки сериализации в продакшене.

Ключевые выводы

  • 64 строки, каждый модуль: Этот файл — ДНК сборки ProjectForge, применяется ко всем 15+ модулям.
  • Строка 28 важна: --release 17 — причина, по которой ProjectForge собирается на JDK 21, но выполняется на JDK 17.
  • Принудительная фиксация Jackson (строки 50–54): Предотвращает основной источник ошибок classpath во время выполнения (несоответствие версий).
  • Комментарий в строке 15: Объясняет, почему используется findVersion()/findLibrary() вместо обычного сокращения libs.versions.xxx.
  • Частота изменений: Обновляется при изменении зависимостей — возможно, раз в несколько релизов.
