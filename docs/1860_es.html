Propósito: CardDAV es una extensión de libreta de direcciones para WebDAV (RFC 6352). Este servicio actúa como puente entre los endpoints HTTP del módulo projectforge-carddav y los datos de direcciones de la capa de negocio. Traduce los objetos de dominio de direcciones de ProjectForge al modelo Contact de CardDAV, aplicando la política de acceso de solo favoritos.

Arquitectura

El servicio sigue un patrón de fachada de solo lectura. Las operaciones de Crear y Actualizar están comentadas y devuelven objetos Contact() vacíos — la implementación de CardDAV es de solo lectura. El método deleteContact() no elimina realmente la dirección; solo elimina la dirección de los favoritos del usuario (establece isFavoriteCard = false en PersonalAddressDO). Esto se debe a que:
  • Eliminar la dirección real afectaría a otros usuarios que también la han marcado como favorita
  • Los clientes CardDAV esperan "eliminar" contactos de su libreta de direcciones personal, no del directorio corporativo compartido
  • Las operaciones de escritura son complejas: análisis de vCard, resolución de conflictos y semántica de sincronización requerirían un trabajo adicional significativo

Grafo de dependencias

El AddressDAVCache (contexto #844) envuelve la costosa generación de vCard (que implica codificación en base64 de fotos de contacto, mapeo de campos y serialización de formato) en un caché basado en TTL. Sin este caché, cada sincronización del cliente CardDAV regeneraría las vCards de todos los contactos — una operación intensiva en CPU para libretas de direcciones con cientos de entradas y fotos.

Contexto del protocolo CardDAV

Los clientes CardDAV (por ejemplo, Contactos de Apple en iOS/macOS, Thunderbird con CardBook, DAVx⁵ en Android) envían solicitudes HTTP a los endpoints /{username}/addressBooks/. El servicio es invocado por la capa de servlet/manejador CardDAV cuando:

1. PROPFIND / address-query REPORT: El cliente lista todos los contactos → getContactList()
2. GET /addressBooks/{uid}.vcf: El cliente obtiene un solo contacto → getContact() (actualmente comentado)
3. DELETE /addressBooks/{uid}.vcf: El cliente elimina de la libreta de direcciones → deleteContact()
4. PUT: Crear/actualizar → no soportado

La política de solo favoritos significa que un usuario debe marcar explícitamente los contactos como favoritos en la interfaz web de ProjectForge para que aparezcan en su libreta de direcciones sincronizada. Esto actúa como una puerta intencional — el directorio completo de la empresa suele ser demasiado grande para las libretas de direcciones personales (más de 1000 entradas inundarían la aplicación de contactos de un teléfono).

Commit clave: dc92ae34c

Este commit introdujo el AddressDAVCache después de descubrir que la generación de vCard era "muy lenta" — una corrección crítica de rendimiento. Generar vCards implica manipulación de cadenas, codificación de imágenes en base64 y formato de fechas para cada contacto. Sin caché, cada solicitud de sincronización CardDAV (que puede ocurrir cada pocos minutos desde dispositivos móviles) regeneraría todas las vCards desde cero.

Commit clave: d0aed59ed — Renombre de módulo

El módulo se llamaba originalmente projectforge-caldav (Calendario + Contacto juntos) pero se renombró a projectforge-carddav cuando las implementaciones de CalDAV (sincronización de calendario) y CardDAV (sincronización de contactos) se separaron en módulos distintos. Esto refleja la evolución de un módulo DAV monolítico a implementaciones separadas y específicas del protocolo.

Commit clave: 27692785d — Eliminación de Milton

La implementación inicial usaba la biblioteca Milton Java WebDAV, pero se eliminó debido a los costos de licencia. La implementación del protocolo DAV se reescribió utilizando un enfoque personalizado y ligero. Este es un punto de dolor común en las implementaciones de WebDAV/CardDAV de código abierto — las bibliotecas Java disponibles (Milton, Bedework) tienen licencias restrictivas o soporte insuficiente para CardDAV.
Advertencia — Eliminación de Milton: La biblioteca Milton ofrecía anotaciones convenientes (@AddressBooks, @AddressBook) para el mapeo de endpoints CardDAV. Después de su eliminación, los endpoints CardDAV tuvieron que implementarse manualmente utilizando manejo de servlets sin procesar o anotaciones personalizadas. Esto aumentó la complejidad de implementación para el cumplimiento del protocolo CardDAV (particularmente las solicitudes addressbook-query REPORT y las respuestas PROPFIND con propiedades addressbook-description).
Justificación de la política de solo favoritos: CardDAV se utiliza principalmente para sincronizar contactos con dispositivos móviles y clientes de correo de escritorio. Exponer el directorio completo de la empresa (potencialmente miles de contactos) a cada dispositivo sería poco práctico. Los usuarios marcan selectivamente como favoritos los contactos que necesitan, creando un subconjunto personalizado. El método deleteContact() respeta la naturaleza multiusuario de la libreta de direcciones al eliminar solo el marcador de favorito del usuario, no el registro de dirección subyacente.
