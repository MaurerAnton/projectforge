Was es tut

Schließt Build-Artefakte, Dokumentation und Werkzeuge aus dem Docker-Build-Kontext aus. Ohne diese Datei würde das gesamte Projektverzeichnis (~2GB+ an Gradle-Caches, Build-Ausgaben, node_modules) vor dem Bauen an den Docker-Daemon gesendet werden – was docker build verlangsamt und den Layer-Cache aufbläht. Mit .dockerignore werden nur die Dateien übertragen, die tatsächlich vom Dockerfile benötigt werden (JAR-Datei, entrypoint.sh, environment.sh).

Dateiinhalt

1  dist                              ← dist-Verzeichnisse auf oberster Ebene
2  doc                               ← Dokumentationsdateien
3  misc                              ← diverse Skripte/Werkzeuge
4  tools                             ← Build-Werkzeuge
5  target                            ← Maven-Ziel auf oberster Ebene
6  */target                          ← target/ in jedem Unterverzeichnis

9  */build                           ← build/ in jedem Unterverzeichnis

Was ausgeschlossen wird und warum

MusterWas es ausschließtWarumTypische Größe
target Maven-Build-Ausgaben Kein Maven hier (Gradle-Projekt) – aber Sicherheitsnetz 0 (nicht zutreffend)
build Gradle-Build-Ausgaben (classes/, libs/, tmp/) Wird bei jedem Build neu generiert; das JAR wird bereits über COPY ${JAR_FILE} angegeben 500MB+
dist Verteilungsfertige Bündel Nicht für Docker benötigt – das JAR ist das Verteilungsformat Variiert
doc AsciiDoc-Dokumentation Kein Laufzeitzweck innerhalb des Containers ~100KB
misc, tools Hilfsskripte und Werkzeuge Nur zur Build-Zeit, nicht zur Laufzeit Klein
projectforge-webapp/node_modules Alle npm-Abhängigkeiten Die Webapp wird während des Gradle-Builds in das JAR eingebunden – rohes node_modules/ wird nicht benötigt 300MB+
projectforge-webapp/package-lock.json npm-Sperrdatei Build-Zeit-Metadaten, zur Laufzeit irrelevant ~500KB

Fehler: doppelter dist-Eintrag

Die Zeilen 1 und 11 enthalten beide dist. Dies ist harmlos (Docker ignoriert Duplikate), deutet aber darauf hin, dass die Datei inkrementell zusammengestellt wurde – jemand hat später die tiefen Ausschlussmuster */dist und */*/dist hinzugefügt, ohne den ursprünglichen Eintrag auf oberster Ebene zu entfernen.

Warum Muster für Ebene-2-Tiefe?

Docker .dockerignore verwendet die gleiche Mustersyntax wie .gitignore. Der Drei-Ebenen-Ansatz ist notwendig, da Build-Artefakte in mehreren Tiefen existieren:

MusterEntsprichtEntspricht NICHT
build./build/./projectforge-webapp/build/
*/build./projectforge-webapp/build/./tools/foo/build/
*/*/build./projectforge-webapp/sub/build/—

Ohne das Muster */*/build könnten tief verschachtelte Build-Verzeichnisse in Multi-Modul-Gradle-Projekten immer noch in den Kontext gelangen. Mit über 20 Gradle-Modulen in ProjectForge verhindern diese tiefen Muster das Problem, dass „ein Modul durchrutscht“.

Wichtige Erkenntnisse

  • 15 Zeilen, die 800MB+ Netzwerkübertragung während docker build sparen.
  • Mehrschichtige Verteidigung: Schließt Builds auf 3 Verzeichnisebenen aus – kein einzelnes übersehenes tiefes Verzeichnis kann den Kontext aufblähen.
  • Doppeltes Muster: dist erscheint zweimal – harmlos, deutet aber auf inkrementelle Dateizusammenstellung hin.
  • 300MB node_modules: Die größte einzelne Einsparung – der npm-Baum der Webapp ist riesig und zur Docker-Build-Zeit völlig unnötig.
