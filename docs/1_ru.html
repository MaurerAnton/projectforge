#1: .dockerignore

.dockerignore

Путь: ./.dockerignore · Тип: Список исключений сборки Docker · Строк: 15 · Источник: GitHub

15 строк · 9 кода · 6 комментариев · 0 пустых

Назначение

Исключает артефакты сборки, документацию и инструменты из контекста сборки Docker. Без этого файла весь каталог проекта (~2 ГБ+ кеша Gradle, результатов сборки, node_modules) отправлялся бы демону Docker перед началом сборки — замедляя docker build и раздувая кеш слоёв. С .dockerignore передаются только файлы, необходимые Dockerfile (JAR-файл, entrypoint.sh, environment.sh).

Содержимое файла

1  dist                              ← корневые каталоги dist
2  doc                               ← файлы документации
3  misc                              ← различные скрипты/инструменты
4  tools                             ← инструменты сборки
5  target                            ← корневая папка Maven target
6  */target                          ← target/ в любой поддиректории
7  */*/target                        ← target/ на 2 уровня вглубь
8  build                             ← корневой вывод сборки Gradle
9  */build                           ← build/ в любой поддиректории
10 */*/build                         ← build/ на 2 уровня вглубь
11 dist                              ← ДУБЛИКАТ: уже исключено в строке 1
12 */dist
13 */*/dist
14 projectforge-webapp/node_modules  ← 300 МБ+ npm-зависимостей
15 projectforge-webapp/package-lock.json

Что исключается и почему

ШаблонЧто исключаетПочемуТипичный размер
target Результаты сборки Maven Maven здесь не используется (проект Gradle) — но подстраховка 0 (не применимо)
build Результаты сборки Gradle (classes/, libs/, tmp/) Пересоздаются при каждой сборке; JAR уже указан через COPY ${JAR_FILE} 500 МБ+
dist Готовые к распространению сборки Не нужны для Docker — JAR и есть дистрибутив Различается
doc Документация AsciiDoc Не имеет назначения во время выполнения внутри контейнера ~100 КБ
misc, tools Вспомогательные скрипты и инструменты Только для сборки, не для выполнения Мало
projectforge-webapp/node_modules Все npm-зависимости Веб-приложение упаковывается в JAR во время сборки Gradle — сырые node_modules/ не нужны 300 МБ+
projectforge-webapp/package-lock.json npm lock-файл Метаданные времени сборки, неактуальны во время выполнения ~500 КБ

Ошибка: дублирующаяся запись dist

Строки 1 и 11 содержат dist. Это безвредно (Docker игнорирует дубликаты), но указывает на то, что файл собирался постепенно — кто-то добавил шаблоны глубокого исключения */dist и */*/dist позже, не удалив исходную запись верхнего уровня.

Зачем нужны шаблоны глубины 2 уровня?

Docker .dockerignore использует тот же синтаксис шаблонов, что и .gitignore. Трёхуровневый подход необходим, потому что артефакты сборки находятся на разной глубине:

ШаблонСовпадаетНЕ совпадает
build./build/./projectforge-webapp/build/
*/build./projectforge-webapp/build/./tools/foo/build/
*/*/build./projectforge-webapp/sub/build/—

Без шаблона */*/build глубоко вложенные каталоги сборки в многомодульных проектах Gradle всё равно могли бы просочиться в контекст. С 20+ модулями Gradle в ProjectForge эти глубокие шаблоны предотвращают проблему «один модуль проскальзывает».

Ключевые выводы

  • 15 строк экономят 800 МБ+ сетевого трафика во время docker build.
  • Эшелонированная защита: исключает сборки на 3 уровнях каталогов — ни одна пропущенная глубокая директория не сможет раздуть контекст.
  • Дублирующийся шаблон: dist встречается дважды — безвредно, но указывает на постепенную сборку файла.
  • 300 МБ node_modules: Самая большая экономия — npm-дерево веб-приложения огромно и совершенно не нужно во время сборки Docker.
