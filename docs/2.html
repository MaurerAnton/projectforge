File #2: buildSrc/build.gradle.kts

Path: ./buildSrc/build.gradle.kts

Type: Gradle build script (Kotlin DSL)

Lines: 9

Purpose: Enables convention plugins — reusable build logic shared across all ProjectForge modules

Source: GitHub

What it does

This 9-line file turns the buildSrc/ directory into a Gradle convention plugins source. Convention plugins are reusable build scripts that each ProjectForge module can apply with a single line in its build.gradle.kts.

Without this file, every module would need to repeat the same Kotlin, Java, and WAR plugin configuration across 15+ build.gradle.kts files. With it, each module just writes plugins { id("pf-module-conventions") } and gets everything pre-configured.

Line-by-line

Lines 1–4: Kotlin DSL plugin

1 plugins {
2     // Support convention plugins written in Kotlin.
3     `kotlin-dsl`
4 }

Line 3: Applies the kotlin-dsl plugin. This does three things:

  1. Configures Kotlin compilation inside buildSrc/ — Kotlin source files in src/main/kotlin/ can define Gradle plugins and tasks
  2. Adds Gradle API and Kotlin stdlib as implicit dependencies — no need to declare them in a build.gradle.kts inside buildSrc/
  3. Enables precompiled script plugins — Kotlin files in src/main/kotlin/ ending with .gradle.kts become automatically available as plugins in the main build

The comment on line 2 explains this concisely: convention plugins are build scripts in src/main that become available to the main build without additional registration.

Lines 6–9: Plugin portal repository

6 repositories {
7     // Use the plugin portal to apply community plugins in convention plugins.
8     gradlePluginPortal()
9 }

Line 8: Adds the Gradle Plugin Portal as a repository only for buildSrc/. This allows the convention plugins in src/main/kotlin/ to apply community Gradle plugins (e.g. Spring Boot, dependency management, etc.).

Note: this repositories { } block applies to buildSrc/ itself, not to the main project. The main project's repositories are set in the root build.gradle.kts at lines 11–20.

How it works with the rest of buildSrc/

With kotlin-dsl applied, the following structure becomes a convention plugin factory:

buildSrc/ ├── build.gradle.kts ← this file — enables kotlin-dsl ├── settings.gradle.kts ← names the buildSrc project └── src/main/kotlin/ ├── buildlogic.pf-module-conventions.gradle.kts ← convention plugin #1 └── org.projectforge/ └── BuildPropertiesGenerator.kt ← custom Gradle task

Without line 3 (kotlin-dsl), the file buildlogic.pf-module-conventions.gradle.kts would not be auto-registered as a plugin — each module would need to apply(from = ...) it explicitly. The kotlin-dsl plugin makes the filename double as the plugin ID: buildlogic.pf-module-conventions.

Why this file matters

Impact on the build: Without this file, any change to Kotlin compiler settings, dependency management, or plugin versions would need to be copied across 15+ build.gradle.kts files — a maintenance nightmare. Convention plugins centralise this.

Impact on buildSrc/ itself: The kotlin-dsl plugin also limits what can be used inside buildSrc/. You can't just drop any dependency into buildSrc/ — it must be compatible with the version of the Gradle API and Kotlin that kotlin-dsl ships.

Change frequency: This file almost never changes — it was written once when the project adopted Gradle multi-project builds and has remained stable.

Key takeaways

  • 9 lines, one job: Enable convention plugins. Don't add unrelated config here.
  • Plugin IDs come from filenames: Adding foo.gradle.kts to src/main/kotlin/ creates a plugin with ID foo — no registration needed.
  • Repository scope: The gradlePluginPortal() on line 8 applies only to buildSrc/, not the main project.
