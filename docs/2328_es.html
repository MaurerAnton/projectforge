Cliente REST para la API de telefonía Sipgate: lista usuarios, dispositivos, números, direcciones, registros de llamadas; inicia llamadas y envía SMS mediante WebClient.

Arquitectura

SipgateService es un @Service en la capa REST que envuelve la API REST de Sipgate. Depende de SipgateClient (que proporciona un WebClient autenticado con OAuth2). La propiedad webClient se inicializa de forma diferida en @PostConstruct.

Manejo de paginación

El método genérico getList() del objeto complementario maneja la paginación por desplazamiento/límite de Sipgate. Itera hasta maxNumberOfPages (por defecto 100), realizando solicitudes GET con los parámetros de consulta offset y limit hasta que currentOffset > totalCount. Las respuestas se deserializan desde JSON usando JsonUtils.fromJson en clases de datos de lista tipadas (ej. UserListData, DeviceListData) que extienden ListData<T>.

Inicio de llamada

initCall(deviceId, caller, callee, callerId) envía un JSON NewCallRequest mediante POST a /sessions/calls esperando HTTP 200. El deviceId es opcional (necesario solo cuando caller es un número telefónico, no un dispositivo). El parámetro callerId establece el número telefónico mostrado para el destinatario.

Envío de SMS

sendSms(smsId, recipient, message) envía un SendWebSmsRequest mediante POST a /sessions/sms esperando HTTP 204 (Sin contenido). El smsId identifica el número/extensión telefónica de envío.

Privacidad

Tanto NewCallRequest.toString() como SendWebSmsRequest.toString() ocultan el número telefónico del destinatario usando StringHelper.hideStringEnding(), mostrando solo los últimos 5 caracteres enmascarados, para privacidad en registros.

Justificación del diseño

El servicio reside en el módulo REST (no en el módulo de negocio) porque es puramente un cliente de API externo — sin lógica de negocio, sin persistencia. El método genérico getList con clases de datos de lista tipadas evita la duplicación de código en cinco endpoints con paginación idéntica. El manejo de errores es silencioso (captura excepciones, registra, retorna listas vacías / falso) porque las fallas de la API de Sipgate no son críticas para la operación central de ProjectForge. La separación de SipgateClient (autenticación/HTTP) de SipgateService (conocimiento de endpoints) sigue el principio de responsabilidad única.
