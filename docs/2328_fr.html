Client REST pour l'API téléphonique Sipgate : liste les utilisateurs, appareils, numéros, adresses, journaux d'appels ; initie des appels et envoie des SMS via WebClient.

Architecture

SipgateService est un @Service de la couche REST qui encapsule l'API REST Sipgate. Il dépend de SipgateClient (qui fournit un WebClient authentifié OAuth2). La propriété webClient est initialisée paresseusement dans @PostConstruct.

Couverture de l'API

MéthodePoint d'accès API SipgateRetourne
getLogs()GET /log/webhooksListe de SipgateIoLogsResponse (journaux d'appels)
getUsers()GET /usersListe de SipgateUser

sendSms(...)POST /sessions/smsBooléen succès (envoie un SMS)

Gestion de la pagination

La méthode générique getList() de l'objet compagnon gère la pagination par décalage/limite de Sipgate. Elle boucle jusqu'à maxNumberOfPages (100 par défaut), en effectuant des requêtes GET avec les paramètres de requête offset et limit jusqu'à ce que currentOffset > totalCount. Les réponses sont désérialisées depuis le JSON à l'aide de JsonUtils.fromJson en classes de données typées (par ex. UserListData, DeviceListData) qui étendent ListData<T>.

Initiation d'appel

initCall(deviceId, caller, callee, callerId) POSTe un JSON NewCallRequest vers /sessions/calls en attendant un code HTTP 200. Le deviceId est optionnel (nécessaire uniquement lorsque caller est un numéro de téléphone, pas un appareil). Le paramètre callerId définit le numéro de téléphone affiché pour le destinataire.

Envoi de SMS

sendSms(smsId, recipient, message) POSTe un SendWebSmsRequest vers /sessions/sms en attendant un code HTTP 204 (Pas de contenu). Le smsId identifie le numéro de téléphone/extension émetteur.

Confidentialité

Les méthodes NewCallRequest.toString() et SendWebSmsRequest.toString() masquent le numéro de téléphone du destinataire en utilisant StringHelper.hideStringEnding(), n'affichant que les 5 derniers caractères masqués, pour la confidentialité des journaux.

Justification de la conception

Le service réside dans le module REST (et non dans le module métier) car il s'agit purement d'un client API externe — aucune logique métier, aucune persistance. La méthode générique getList avec des classes de données typées évite la duplication de code sur cinq points d'accès ayant une pagination identique. La gestion des erreurs est silencieuse (capture les exceptions, journalise, retourne des listes vides / false) car les échecs de l'API Sipgate ne sont pas critiques pour le fonctionnement principal de ProjectForge. La séparation de SipgateClient (authentification/HTTP) de SipgateService (connaissance des points d'accès) suit le principe de responsabilité unique.
