REST-клиент для телефонии Sipgate API: список пользователей, устройств, номеров, адресов, журналов вызовов; инициирует звонки и отправляет SMS через WebClient.

Архитектура

SipgateService — это @Service в REST-слое, который оборачивает Sipgate REST API. Он зависит от SipgateClient (предоставляет WebClient с аутентификацией OAuth2). Свойство webClient лениво инициализируется в @PostConstruct.

Обработка пагинации

Обобщённый метод getList() в сопутствующем объекте обрабатывает пагинацию Sipgate со смещением/лимитом. Он выполняет цикл до maxNumberOfPages (по умолчанию 100), отправляя GET-запросы с параметрами запроса offset и limit, пока currentOffset > totalCount. Ответы десериализуются из JSON с помощью JsonUtils.fromJson в типизированные классы данных списков (например, UserListData, DeviceListData), которые расширяют ListData<T>.

Инициализация звонка

initCall(deviceId, caller, callee, callerId) отправляет POST-запрос с JSON NewCallRequest на /sessions/calls, ожидая HTTP 200. Параметр deviceId необязателен (требуется только когда caller является телефонным номером, а не устройством). Параметр callerId задаёт отображаемый номер для вызываемого абонента.

Отправка SMS

sendSms(smsId, recipient, message) отправляет POST-запрос с SendWebSmsRequest на /sessions/sms, ожидая HTTP 204 (Нет содержимого). Параметр smsId идентифицирует номер/добавочный номер отправителя.

Конфиденциальность

Оба метода NewCallRequest.toString() и SendWebSmsRequest.toString() скрывают номер вызываемого/получателя с помощью StringHelper.hideStringEnding(), показывая только последние 5 символов в замаскированном виде для конфиденциальности логов.

Обоснование дизайна

Сервис находится в REST-модуле (не в бизнес-модуле), потому что это чисто внешний API-клиент — без бизнес-логики, без сохранения состояния. Обобщённый метод getList с типизированными классами данных списков позволяет избежать дублирования кода для пяти конечных точек с одинаковой пагинацией. Обработка ошибок выполняется незаметно (перехватывает исключения, логирует, возвращает пустые списки / false), так как сбои Sipgate API не критичны для основной работы ProjectForge. Разделение SipgateClient (аутентификация/HTTP) и SipgateService (знание конечных точек) следует принципу единственной ответственности.
