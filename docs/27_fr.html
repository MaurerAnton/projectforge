Protocole d'arrêt en deux phases

Le script identifie le processus Java de ProjectForge via pgrep -f "java.*projectforge-application" (correspondance de motif sur la ligne de commande JVM), puis exécute :

  1. Phase 1 — Progressive (60 secondes) : kill $pid envoie SIGTERM (signal 15). La JVM intercepte ce signal et déclenche les rappels de cycle de vie @PreDestroy de Spring — Hibernate vide les caches, les pools de connexions se ferment, les tâches Quartz s'arrêtent, Tomcat s'éteint. Le script boucle 20 fois × 3 secondes, en vérifiant si le processus a disparu.
  2. Phase 2 — Forcée : Si toujours actif après 60 s, kill -9 $pid envoie SIGKILL (signal 9) — non interceptable, terminaison immédiate. Aucun nettoyage : connexions à la base de données orphelines, index Lucene potentiellement corrompus, tampons de journaux perdus. Le script attend 2 secondes et vérifie à nouveau.

Cette approche en deux phases évite le problème de production le plus courant : les fuites de connexions à la base de données provenant de processus Java tués. La fenêtre de 60 secondes est généreuse — la plupart des applications Spring Boot s'arrêtent en 5 à 15 secondes.

Analyse du script — lignes clés

checkStopped() {
  pid=$(pgrep -f $PROCESS_IDENTIFIER)      # Revérifie si le processus existe
  if [[ -z $pid ]]; then                     # Si aucun PID trouvé
    echo "${APP_NAME} $1"                    # Affiche le message de succès
    exit 0                                   # Quitte immédiatement
  fi
  if [[ -n $2 ]]; then                       # Si un second argument est fourni (mode avertissement)
    echo "${APP_NAME} $2"                    # Affiche l'avertissement mais continue
  fi
}

Fonction à double mode : checkStopped sert à deux fins selon le nombre d'arguments — avec 1 argument, c'est une « vérification de succès » (quitte si arrêté), avec 2 arguments, c'est un « rapport d'état » (affiche et continue).

Bogue de portée de variable : $pid est défini à l'intérieur de la fonction (ligne 7) mais utilisé à l'extérieur à la ligne 20 — cela fonctionne car pid n'est pas déclaré local, donc il fuit dans la portée de l'appelant. Fragile — si un second processus correspondant apparaît entre les vérifications, seul le premier PID est tué.

Points clés à retenir

  • Toujours préférer ce script à kill -9 : L'arrêt progressif préserve l'intégrité de la base de données et évite les fuites de connexions.
  • Caché dans uploads/ : Se trouve dans site/uploads/ — les pièces jointes du site Jekyll — un emplacement inhabituel pour des outils opérationnels.
  • Pas de fichier PID : Identifie le processus par motif de ligne de commande, pas par fichier PID. Plus robuste lors des redémarrages mais échoue si deux instances de ProjectForge correspondent.
  • pgrep requis : Fait partie du paquet procps-ng — non disponible sur les images Docker minimales.
