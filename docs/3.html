File #3: buildSrc/settings.gradle.kts

Path: ./buildSrc/settings.gradle.kts

Type: Gradle settings script (Kotlin DSL)

Lines: 7

Purpose: Shares the version catalog with buildSrc/ — so convention plugins can reference the same dependency versions as the main build

Source: GitHub

What it does

This 7-line file solves a specific problem: buildSrc/ is a separate Gradle project from the main build. By default, it does NOT have access to the version catalog defined in gradle/libs.versions.toml.

This file re-shares the catalog — telling buildSrc/ to load version definitions from the same .toml file that the main build uses. Without it, convention plugins inside buildSrc/src/main/kotlin/ could not reference libs.versions.* or libs.plugins.*.

Line-by-line

1 dependencyResolutionManagement {
2     versionCatalogs {
3         create("libs") {
4             from(files("../gradle/libs.versions.toml"))
5         }
6     }
7 }

Line 3: create("libs") — creates a version catalog named libs. This is the same name used in the main build's settings.gradle.kts. The name must match for cross-project consistency.

Line 4: from(files("../gradle/libs.versions.toml")) — loads the catalog from one level up (../). The buildSrc/ directory is inside the project root, so ../gradle/ points to the main gradle/ directory. This is the same file used by the main build.

Lines 1–2: dependencyResolutionManagement { versionCatalogs { } } — the standard Gradle DSL for defining version catalogs in settings scripts.

Why a separate settings file for buildSrc/?

Gradle treats buildSrc/ as an included build — a separate Gradle project that is automatically compiled and made available to the main build. As a separate project, it has:

  • Its own build.gradle.kts — dependencies and plugins for the buildSrc project itself
  • Its own settings.gradle.kts — this file — namespace and version catalog configuration
  • Its own source code in src/main/kotlin/

Without this settings file, any reference to libs.versions.kotlin or libs.plugins.spring-boot inside buildSrc/src/main/kotlin/ would fail with "unresolved reference: libs".

Data flow: how version numbers travel

gradle/libs.versions.toml ← single source of truth │ ├──→ root settings.gradle.kts ← main build loads it │ dependencyResolutionManagement { │ versionCatalogs { create("libs") { from(...) } } │ } │ └──→ buildSrc/settings.gradle.kts ← THIS FILE — buildSrc loads it dependencyResolutionManagement { versionCatalogs { create("libs") { from("../gradle/...") } } } Both the main build AND buildSrc can now write: libs.versions.kotlin ← compiler version libs.plugins.spring-boot ← plugin version libs.dependencies.react ← dependency version

Result: changing a version in libs.versions.toml updates both the main build and buildSrc convention plugins. No duplication.

Key takeaways

  • 7 lines, one job: Give buildSrc access to the version catalog.
  • Same file, two consumers: Both the root settings.gradle.kts and this file load from the identical libs.versions.toml.
  • One level up: The ../ on line 4 is because buildSrc is a subdirectory — it reaches up to the project root's gradle/ folder.
  • Change rate: This file never changes — it was written once when the version catalog was introduced and remains stable.
