Zweck: DIE globale Fehlerseite – fängt JEDE unbehandelte Ausnahme in der Wicket-Webapp ab. Klassifiziert Ausnahmen in 6 Kategorien, protokolliert mit eindeutigen Nachrichtennummern (System.currentTimeMillis()), zeigt benutzerfreundliche übersetzte Meldungen, rendert optional ein Feedback-Formular für Benutzer zur Übermittlung von Fehlerberichten und sendet proaktiv E-Mails an das Support-Team bei kritischen Fehlern. Der 6-Wege-Ausnahmenklassifizierer – Zeilen 88-116

public static String getExceptionMessage(AbstractSecuredBasePage securedPage,
                                         ProjectForgeException exception, boolean doLog) {
  if (exception instanceof UserException) {           // Kategorie 1: Benutzerfehler
    return securedPage.translateParams(ex.getI18nKey(), ex.getMsgParams(), ex.getParams());
  } else if (exception instanceof InternalErrorException) { // Kategorie 2: interne Fehler
    return securedPage.translateParams(ex.getI18nKey(), ex.getMsgParams(), ex.getParams());
  } else if (exception instanceof AccessException) {  // Kategorie 3: Zugriff verweigert
    return securedPage.translateParams(ex.getI18nKey(), ex.getMessageArgs(), ex.getParams());
  }
  throw new UnsupportedOperationException("...füge hier unbekannte ProjectForgeException hinzu!", exception);
}

Drei ProjectForge-spezifische Ausnahmetypen, jeder mit i18n-Übersetzung behandelt. Der Hauptunterschied zwischen ihnen:

AusnahmeBenutzer siehtProtokollstufeParameter
UserExceptionÜbersetzte Nachricht von i18n-Schlüssel + NachrichtenparameterINFO (wenn doLog)getMsgParams() – benutzerseitige Parameter
InternalErrorExceptionGleich wie UserException – übersetzte NachrichtINFO (wenn doLog)getMsgParams() – interne Parameter
AccessExceptionLokalisierte "Zugriff verweigert"-Meldung mit ParameternINFO (wenn doLog)getParams() / getMessageArgs() – Zugriffsparameter

Die UnsupportedOperationException in Zeile 115 ist ein bewusster Absturz: Wenn eine unbekannte ProjectForgeException-Unterklasse diesen Punkt erreicht, hat der Entwickler vergessen, einen Handler hinzuzufügen. Der Kommentar "Für Entwickler: Bitte füge hier unbekannte ProjectForgeException hinzu!" ist ein selbstdokumentierendes Design – der Absturz zwingt den Entwickler, neue Ausnahmetypen explizit zu behandeln, anstatt stillschweigend mit einer generischen Fehlermeldung durchzufallen.

StackTrace-Filterung: ONLY4NAMESPACE = "org.projectforge" (Zeile 65) begrenzt Stacktraces auf ProjectForge-Pakete. Dies hält die Protokolle sauber – keine Dutzende von Spring/Hibernate/Tomcat-Frames, die Fehlerberichte überladen. ExceptionHelper.getFilteredStackTrace(ex, ONLY4NAMESPACE) entfernt alles außerhalb von org.projectforge.

Der Konstruktor – 4 Ausnahmepfade, 81 Zeilen Fehlerweiterleitung (Zeilen 118-199)

public ErrorPage(final Throwable throwable) {
  // Standard: generischen Fehler mit Feedback-Formular anzeigen
  errorMessage = getString("errorpage.unknownError");
  showFeedback = true;
  
  if (throwable != null) {
    rootCause = ExceptionHelper.getRootCause(throwable);
    
    // PFAD A: ProjectForgeException – übersetzte Nachricht
    if (rootCause instanceof ProjectForgeException) {
      errorMessage = getExceptionMessage(this, (ProjectForgeException) rootCause, true);
    
    // PFAD B: ServletException – protokollieren + "Kontaktieren Sie das Entwicklerteam"-Nachricht
    } else if (throwable instanceof ServletException) {
      messageNumber = String.valueOf(System.currentTimeMillis());
      log.error("Nachricht #" + messageNumber + ": " + throwable.getMessage(), throwable);
      errorMessage = getLocalizedMessage(UserException.I18N_KEY_PLEASE_CONTACT_DEVELOPER_TEAM, messageNumber);
    
    // PFAD C: PageExpiredException – Sitzung abgelaufen (kein Feedback-Formular)
    } else if (throwable instanceof PageExpiredException) {
      showFeedback = false;  // Benutzer bei Zeitüberschreitung nicht um Feedback bitten
      errorMessage = getString("message.wicket.pageExpired");
    
    // PFAD D: Alles andere – generische "Kontaktieren Sie das Entwicklerteam"-Meldung
    } else {
      messageNumber = String.valueOf(System.currentTimeMillis());
      log.error("Nachricht #" + messageNumber + ": " + throwable.getMessage(), throwable);
      errorMessage = getLocalizedMessage(UserException.I18N_KEY_PLEASE_CONTACT_DEVELOPER_TEAM, messageNumber);
    }
  }
}

PFAD A – ProjectForge-Ausnahmen (Zeilen 130-131): Der glückliche Pfad für bekannte Fehler. Die Ursache wird über ExceptionHelper.getRootCause() entpackt (entfernt ServletException/Spring-Wrapper), und die Nachricht wird über i18n übersetzt. Der Benutzer sieht eine hilfreiche Nachricht in seiner Sprache.

PFAD B – ServletException (Zeilen 132-138): Container-Level-Fehler (Tomcat-Filterkettenfehler, Anfrage-Parsing-Fehler). Erhält eine messageNumber – System.currentTimeMillis() als Zeichenkette. Dies ist die eindeutige Fehler-ID, die dem Benutzer als "Bitte kontaktieren Sie das Entwicklerteam mit Nachricht #1712345678901" angezeigt wird. Die Nummer ist ein Zeitstempel, sodass der Support sie mit Serverprotokollen korrelieren kann.

PFAD C – PageExpiredException (Zeilen 139-143): Die Wicket-Sitzung des Benutzers ist abgelaufen. showFeedback = false – kein Feedback-Formular, da der Benutzer keinen Fehler gefunden hat, sondern nur zu lange gewartet hat. Der Titel wird auf "Nachricht" (Zeile 143) anstelle des Standardtitels "Fehler" gesetzt.

PFAD D – Alles andere (Zeilen 144-148): Unbekannte Ausnahmen (NullPointerException, Hibernate-Ausnahmen usw.). Gleiche Behandlung wie ServletException – Nachrichtennummer + "Kontaktieren Sie das Entwicklerteam".

Proaktive Fehlerberichterstattung – E-Mail an das Support-Team (Zeilen 201-223)

private void sendProactiveMessageToSupportTeam() {
  if (configService.getPfSupportMailAddress() != null && configService.isSendMailConfigured()) {
    SendFeedbackData errorData = new SendFeedbackData();
    errorData.setSender(sendMail.getMailFromStandardEmailSender());
    errorData.setReceiver(configService.getPfSupportMailAddress());
    errorData.setSubject("Fehler aufgetreten: #" + messageNumber + " auf " + domainService.getDomain());
    errorData.setDescription(
      "Fehler aufgetreten um: " + dateString + "(" + timeZone + ")" +
      " mit Nummer: #" + messageNumber +
      " von Benutzer: " + sender +
      " Ausnahme-Stapelverfolgung: \n" + rootCauseStackTrace);
    sendFeedback.send(errorData);
  }
}

Dies ist das proaktive Überwachungssystem. Wenn ein kritischer Fehler auftritt UND die Support-E-Mail konfiguriert ist, sendet das System automatisch eine E-Mail mit:

  • Der eindeutigen Nachrichtennummer (Zeitstempel)
  • Der Domain, auf der der Fehler aufgetreten ist
  • Dem Datum/der Uhrzeit mit Zeitzone
  • Dem Benutzer, der den Fehler gefunden hat
  • Der vollständigen Stapelverfolgung der Ursache

Dies ist im Wesentlichen ein integriertes Fehlerüberwachungssystem ohne Sentry, Datadog oder ELK. Für selbst gehostete Bereitstellungen ist dies die primäre Methode, mit der Administratoren von Produktionsfehlern erfahren. Die E-Mail geht an configService.getPfSupportMailAddress() – konfiguriert in projectforge.properties.

Benutzer-Feedback-Formular – Crowd-sourced Fehlerberichte (Zeilen 150-178)

Wenn showFeedback = true UND eine Nachrichtennummer generiert wurde UND eine Empfänger-E-Mail konfiguriert ist, rendert die Seite ein ErrorForm (Wicket-Formularkomponente), mit dem Benutzer Fehlerberichte einreichen können. Vorausgefüllte Daten:

FeldWert

Die Methode sendFeedback() (Zeilen 229-246) behandelt das Absenden: ruft SendFeedback.send() auf, leitet zu MessagePage mit Erfolgs-/Fehlermeldung weiter. Bei Fehler wird "mail.error.exception" mit setWarning(true) angezeigt.

Ausnahmenunterdrückung – wann Stille bewahrt werden soll (Zeilen 180-198)

if (throwable == null ||
    throwable instanceof ComponentNotFoundException ||
    throwable instanceof ConnectException) {
  // STILL – dies sind keine Fehler, sondern erwartete Lebenszyklusereignisse
} else if (rootCause instanceof UserException) {
  // STILL – bereits dem Benutzer präsentiert
} else if (GlobalExceptionRegistry.sendMailToDevelopers(throwable)) {
  sendProactiveMessageToSupportTeam();  // Nur E-Mail für echte Fehler senden
}

Drei Kategorien von Ausnahmen werden bewusst unterdrückt – es wird keine E-Mail gesendet, keine proaktive Benachrichtigung:

AusnahmeWarum unterdrückt
null throwableErrorPage ohne Ausnahme aufgerufen – von CallAllPagesTest (Kommentar Zeile 188-189). Die Testsuite navigiert direkt zur ErrorPage, um zu überprüfen, ob sie gerendert wird.
ComponentNotFoundExceptionNormaler Wicket-Lebenszyklus. Wenn ein Benutzer durch die AddressListPage navigiert, werden Bildkomponenten vom Framework entfernt – Wicket wirft dies, wenn versucht wird, eine Komponente zu finden, die bereits bereinigt wurde. Kein Fehler.
ConnectExceptionDer Browser des Benutzers hat die Verbindung getrennt. Tritt auf, wenn der Benutzer während einer langlaufenden Anfrage wegklickt – bis die Antwort bereit ist, ist der Browser weg. Kein Fehler.

GlobalExceptionRegistry statischer Block (Zeilen 67-70): Vorregistriert StalePageException und ComponentNotFoundException mit menschenlesbaren Beschreibungen ("Wicket-Seite nicht mehr verfügbar"). Die Prüfung sendMailToDevelopers() in Zeile 196 konsultiert diese Registrierung – nur Ausnahmen, die NICHT als "bekannt/erwartet" registriert sind, lösen proaktive E-Mails aus.

Wicket-Überschreibungen – Seitenidentität

@Override public boolean isVersioned() { return false; }    // Niemals Seitenversionen speichern
@Override public boolean isErrorPage() { return true; }     // Wicket mitteilen, dass DIES eine Fehlerseite ist

isVersioned() = false (Zeile 257): Wicket versioniert normalerweise Seiten – speichert alte Kopien, damit die Zurück-Schaltfläche des Browsers funktioniert. Für Fehlerseiten ist die Versionierung deaktiviert, weil: (1) Fehlerseiten sind flüchtig – man sollte nicht zu einem Fehler zurücknavigieren, (2) die Versionierung speichert das Ausnahmeobjekt in der Sitzung, was Speicher verlieren oder sensible Daten enthalten könnte, (3) Fehlerseiten sollten bei erneutem Besuch immer frische Inhalte anzeigen.

isErrorPage() = true (Zeile 265): Teilt der Wicket-Ausnahmebehandlungskette mit, dass DIESE Seite die Fehlerseite ist – verhindert Endlosschleifen, wenn die Fehlerseite selbst eine Ausnahme auslöst (Wicket würde dann seine eigene Fallback-Fehlerseite anzeigen).

Wo Pac-Man hineinpasst

Der Pac-Man-Easter-Egg (#3780) wird VON dieser Fehlerseite verlinkt. Die HTML-Vorlage (ErrorPage.html, 24 Zeilen) zeigt die Struktur: ein alert-danger-Div für die Fehlermeldung, ein FeedbackPanel für Benutzerberichte und ein Formular mit Aktionsschaltflächen. Die Schaltfläche "Pac-Man spielen" würde als eine der Aktionsschaltflächen des Formulars gerendert – aus einem 500er-Fehler eine Spieleinladung machen. Dies ist der Moment, in dem Frustration zu Spaß wird.
