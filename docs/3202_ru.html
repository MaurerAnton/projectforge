Классификатор исключений из 6 категорий — строки 88-116

public static String getExceptionMessage(AbstractSecuredBasePage securedPage,
                                         ProjectForgeException exception, boolean doLog) {
  if (exception instanceof UserException) {           // Категория 1: ошибки для пользователя
    return securedPage.translateParams(ex.getI18nKey(), ex.getMsgParams(), ex.getParams());
  } else if (exception instanceof InternalErrorException) { // Категория 2: внутренние ошибки
    return securedPage.translateParams(ex.getI18nKey(), ex.getMsgParams(), ex.getParams());
  } else if (exception instanceof AccessException) {  // Категория 3: доступ запрещён
    return securedPage.translateParams(ex.getI18nKey(), ex.getMessageArgs(), ex.getParams());
  }
  throw new UnsupportedOperationException("...добавьте неизвестный ProjectForgeException сюда!", exception);
}

Три специфичных для ProjectForge типа исключений, каждый обрабатывается с i18n-переводом. Ключевые различия между ними:

ИсключениеПользователь видитУровень логированияПараметры
UserExceptionПереведённое сообщение из i18n ключа + параметры сообщенияINFO (если doLog)getMsgParams() — параметры для пользователя
InternalErrorExceptionТо же, что и UserException — переведённое сообщениеINFO (если doLog)getMsgParams() — внутренние параметры
AccessExceptionЛокализованное "доступ запрещён" с параметрамиINFO (если doLog)getParams() / getMessageArgs() — параметры доступа

UnsupportedOperationException в строке 115 — это намеренный сбой: Если неизвестный подкласс ProjectForgeException достигает этой точки, разработчик забыл добавить обработчик. Комментарий "Для разработчика: Пожалуйста, добавьте неизвестный ProjectForgeException сюда!" — это самодокументируемый дизайн: сбой заставляет разработчика явно обрабатывать новые типы исключений, а не молча проваливаться с общим сообщением об ошибке.

Фильтрация стека вызовов: ONLY4NAMESPACE = "org.projectforge" (строка 65) ограничивает стек вызовов только пакетами ProjectForge. Это сохраняет чистоту логов — никаких десятков фреймов Spring/Hibernate/Tomcat, загромождающих отчёты об ошибках. ExceptionHelper.getFilteredStackTrace(ex, ONLY4NAMESPACE) удаляет всё за пределами org.projectforge.

Конструктор — 4 пути исключений, 81 строка маршрутизации ошибок (строки 118-199)

public ErrorPage(final Throwable throwable) {
  // По умолчанию: показать общую ошибку с формой обратной связи
  errorMessage = getString("errorpage.unknownError");
  showFeedback = true;
  
  if (throwable != null) {
    rootCause = ExceptionHelper.getRootCause(throwable);
    
    // ПУТЬ A: ProjectForgeException — переведённое сообщение
    if (rootCause instanceof ProjectForgeException) {
      errorMessage = getExceptionMessage(this, (ProjectForgeException) rootCause, true);
    
    // ПУТЬ B: ServletException — логирование + сообщение "свяжитесь с командой разработчиков"
    } else if (throwable instanceof ServletException) {
      messageNumber = String.valueOf(System.currentTimeMillis());
      log.error("Сообщение #" + messageNumber + ": " + throwable.getMessage(), throwable);
      errorMessage = getLocalizedMessage(UserException.I18N_KEY_PLEASE_CONTACT_DEVELOPER_TEAM, messageNumber);
    
    // ПУТЬ C: PageExpiredException — тайм-аут сессии (без формы обратной связи)
    } else if (throwable instanceof PageExpiredException) {
      showFeedback = false;  // Не спрашивать пользователя об обратной связи при тайм-ауте
      errorMessage = getString("message.wicket.pageExpired");
    
    // ПУТЬ D: Всё остальное — общее сообщение "свяжитесь с командой разработчиков"
    } else {
      messageNumber = String.valueOf(System.currentTimeMillis());
      log.error("Сообщение #" + messageNumber + ": " + throwable.getMessage(), throwable);
      errorMessage = getLocalizedMessage(UserException.I18N_KEY_PLEASE_CONTACT_DEVELOPER_TEAM, messageNumber);
    }
  }
}

ПУТЬ A — Исключения ProjectForge (строки 130-131): Оптимальный путь для известных ошибок. Корневая причина извлекается через ExceptionHelper.getRootCause() (удаляет обёртки ServletException/Spring), и сообщение переводится через i18n. Пользователь видит полезное сообщение на своём языке.

ПУТЬ B — ServletException (строки 132-138): Ошибки уровня контейнера (сбои цепочки фильтров Tomcat, ошибки парсинга запросов). Получает messageNumber — System.currentTimeMillis() в виде строки. Это уникальный ID ошибки, показываемый пользователю как "Пожалуйста, свяжитесь с командой разработчиков с сообщением #1712345678901". Номер является временной меткой, поэтому поддержка может сопоставить его с серверными логами.

ПУТЬ C — PageExpiredException (строки 139-143): Сессия Wicket пользователя истекла. showFeedback = false — нет формы обратной связи, потому что пользователь не столкнулся с ошибкой, а просто ждал слишком долго. Заголовок устанавливается как "Сообщение" (строка 143) вместо стандартного "Ошибка".

ПУТЬ D — Всё остальное (строки 144-148): Неизвестные исключения (NullPointerException, исключения Hibernate и т.д.). Такая же обработка, как и для ServletException — номер сообщения + "свяжитесь с командой разработчиков".

Активное сообщение об ошибках — отправка электронного письма команде поддержки (строки 201-223)

private void sendProactiveMessageToSupportTeam() {
  if (configService.getPfSupportMailAddress() != null && configService.isSendMailConfigured()) {
    SendFeedbackData errorData = new SendFeedbackData();
    errorData.setSender(sendMail.getMailFromStandardEmailSender());
    errorData.setReceiver(configService.getPfSupportMailAddress());
    errorData.setSubject("Произошла ошибка: #" + messageNumber + " на " + domainService.getDomain());
    errorData.setDescription(
      "Ошибка произошла в: " + dateString + "(" + timeZone + ")" +
      " с номером: #" + messageNumber +
      " от пользователя: " + sender +
      " Стек вызовов исключения: \n" + rootCauseStackTrace);
    sendFeedback.send(errorData);
  }
}

Это система активного мониторинга. Когда происходит критическая ошибка И настроен адрес электронной почты поддержки, система автоматически отправляет электронное письмо, содержащее:

  • Уникальный номер сообщения (временная метка)
  • Домен, на котором произошла ошибка
  • Дата/время с часовым поясом
  • Пользователь, столкнувшийся с ошибкой
  • Полный стек вызовов корневой причины

По сути, это встроенная система мониторинга ошибок без необходимости в Sentry, Datadog или ELK. Для самостоятельных развёртываний это основной способ, с помощью которого администраторы узнают о производственных ошибках. Письмо отправляется на configService.getPfSupportMailAddress() — настраивается в projectforge.properties.

Три категории исключений намеренно подавляются — электронное письмо не отправляется, активное уведомление не производится:

ИсключениеПочему подавляется
null throwableErrorPage вызвана без исключения — из CallAllPagesTest (комментарий к строке 188-189). Тестовый набор переходит непосредственно на ErrorPage, чтобы проверить, что она отображается.
ComponentNotFoundExceptionНормальный жизненный цикл Wicket. Когда пользователь перемещается по AddressListPage, компоненты изображений удаляются фреймворком — Wicket выбрасывает это при попытке найти компонент, который уже был очищен. Не ошибка.
ConnectExceptionБраузер пользователя отключился. Происходит, когда пользователь уходит во время длительного запроса — к моменту готовности ответа браузер уже ушёл. Не ошибка.

Статический блок GlobalExceptionRegistry (строки 67-70): Предварительно регистрирует StalePageException и ComponentNotFoundException с понятными человеку описаниями ("Страница Wicket больше не доступна"). Проверка sendMailToDevelopers() в строке 196 обращается к этому реестру — только исключения, НЕ зарегистрированные как "известные/ожидаемые", вызывают активные электронные письма.

Переопределения Wicket — идентификация страницы

@Override public boolean isVersioned() { return false; }    // Никогда не сохранять версии страниц
@Override public boolean isErrorPage() { return true; }     // Сообщить Wicket, что ЭТО страница ошибки

isVersioned() = false (строка 257): Wicket обычно версионирует страницы — сохраняет старые копии, чтобы кнопка "назад" в браузере работала. Для страниц ошибок версионирование отключено, потому что: (1) страницы ошибок временны — не следует возвращаться к ошибке, (2) версионирование сохраняет объект исключения в сессии, что может привести к утечке памяти или содержать конфиденциальные данные, (3) страницы ошибок всегда должны показывать свежий контент при повторном посещении.

isErrorPage() = true (строка 265): Сообщает цепочке обработки исключений Wicket, что ЭТА страница является страницей ошибки — предотвращает бесконечную рекурсию, если сама страница ошибки вызовет исключение (в этом случае Wicket покажет свою собственную резервную страницу ошибки).

Где находится Pac-Man

Пасхальное яйцо Pac-Man (#3780) СВЯЗАНО с этой страницей ошибки. HTML-шаблон (ErrorPage.html, 24 строки) показывает структуру: div alert-danger для сообщения об ошибке, FeedbackPanel для отчётов пользователей и форму с кнопками действий. Кнопка "Играть в Pac-Man" отображалась бы как одна из кнопок действий формы — превращая ошибку 500 в приглашение к игре. Это момент, когда разочарование превращается в веселье.
