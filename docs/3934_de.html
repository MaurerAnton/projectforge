Die JPA→HTML-Brücke – warum dieser Test wichtig ist

PropertyModel<String> model = new PropertyModel<>(new PFUserDO(), "username");
assertInteger(255, MaxLengthTextField.getMaxLength(model));      // Von @Column(length=255)
assertInteger(255, MaxLengthTextField.getMaxLength(model, 300)); // Überschreibung ignoriert (DB gewinnt)
assertInteger(100, MaxLengthTextField.getMaxLength(model, 100)); // Manuelle Überschreibung gewinnt (100 < 255)

model = new PropertyModel<>(new BaseSearchFilter(), "searchString");
assertNull(MaxLengthTextField.getMaxLength(model));              // Kein @Column = keine maxlength
assertInteger(100, MaxLengthTextField.getMaxLength(model, 100)); // Manuelle Überschreibung

assertNull(MaxLengthTextField.getMaxLength(Model.of("test")));   // Einfaches Modell = keine maxlength

Der getestete Algorithmus: getMaxLength(propertyModel, manualMaxLength) folgt dieser Logik:

  1. Extrahiert den Eigenschaftsnamen aus dem Wicket PropertyModel (z. B. "username")
  2. Findet die entsprechende JPA-Entitätsklasse und das Feld
  3. Liest die @Column(length = N)-Annotation aus
  4. Wenn eine manuelle maxLength angegeben wurde UND diese kleiner als die DB-Spaltenlänge ist, wird der manuelle Wert verwendet (HTML-Validierung sollte strenger sein als die DB)
  5. Wenn keine @Column-Annotation existiert, wird null zurückgegeben (kein maxlength-Attribut im HTML-Input)

Dies verhindert einen häufigen Fehler: Benutzer geben 300 Zeichen in ein Formularfeld ein, senden ab, und die Datenbank kürzt auf 255. Mit HTML maxlength, das aus der JPA-Annotation gesetzt wird, verhindert der Browser überlange Eingaben vor dem Absenden.

assertInteger-Helfer: Benutzerdefinierte Assertion, die sowohl auf nicht-null als auch auf Gleichheit prüft. Vermeidet die häufige Falle, dass assertEquals(255, value) bestanden wird, wenn value null ist (Autounboxing würde NPE werfen).
