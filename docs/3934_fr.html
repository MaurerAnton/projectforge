Le pont JPA→HTML — pourquoi ce test est important

PropertyModel<String> model = new PropertyModel<>(new PFUserDO(), "username");
assertInteger(255, MaxLengthTextField.getMaxLength(model));      // Depuis @Column(length=255)
assertInteger(255, MaxLengthTextField.getMaxLength(model, 300)); // Surcharge ignorée (BDD gagne)
assertInteger(100, MaxLengthTextField.getMaxLength(model, 100)); // Surcharge manuelle gagne (100 < 255)

model = new PropertyModel<>(new BaseSearchFilter(), "searchString");
assertNull(MaxLengthTextField.getMaxLength(model));              // Pas de @Column = pas de maxlength
assertInteger(100, MaxLengthTextField.getMaxLength(model, 100)); // Surcharge manuelle

assertNull(MaxLengthTextField.getMaxLength(Model.of("test")));   // Modèle simple = pas de maxlength

L'algorithme testé : getMaxLength(propertyModel, manualMaxLength) suit cette logique :

  1. Extraire le nom de la propriété du PropertyModel Wicket (ex. "username")
  2. Trouver la classe d'entité JPA correspondante et le champ
  3. Lire l'annotation @Column(length = N)
  4. Si une maxLength manuelle est fournie ET qu'elle est inférieure à la longueur de la colonne BDD, utiliser la valeur manuelle (la validation HTML doit être plus stricte que la BDD)
  5. Si aucune annotation @Column n'existe, retourner null (pas d'attribut maxlength sur l'input HTML)

Cela évite un bug courant : les utilisateurs tapent 300 caractères dans un champ de formulaire, soumettent, et la base de données tronque à 255. Avec maxlength HTML défini depuis l'annotation JPA, le navigateur empêche la saisie trop longue avant la soumission.
