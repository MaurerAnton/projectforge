Мост JPA→HTML — почему этот тест важен

PropertyModel<String> model = new PropertyModel<>(new PFUserDO(), "username");
assertInteger(255, MaxLengthTextField.getMaxLength(model));      // Из @Column(length=255)
assertInteger(255, MaxLengthTextField.getMaxLength(model, 300)); // Переопределение игнорируется (БД побеждает)
assertInteger(100, MaxLengthTextField.getMaxLength(model, 100)); // Ручное переопределение побеждает (100 < 255)

model = new PropertyModel<>(new BaseSearchFilter(), "searchString");
assertNull(MaxLengthTextField.getMaxLength(model));              // Нет @Column = нет maxlength
assertInteger(100, MaxLengthTextField.getMaxLength(model, 100)); // Ручное переопределение

assertNull(MaxLengthTextField.getMaxLength(Model.of("test")));   // Обычная модель = нет maxlength

Тестируемый алгоритм: getMaxLength(propertyModel, manualMaxLength) следует следующей логике:

  1. Извлечь имя свойства из Wicket PropertyModel (например, "username")
  2. Найти соответствующий класс сущности JPA и поле
  3. Прочитать аннотацию @Column(length = N)
  4. Если указано ручное maxLength И оно меньше длины столбца БД, использовать ручное значение (HTML-валидация должна быть строже, чем БД)
  5. Если аннотация @Column отсутствует, вернуть null (без атрибута maxlength на HTML-поле ввода)

Это предотвращает распространённую ошибку: пользователи вводят 300 символов в поле формы, отправляют, и база данных обрезает до 255. С HTML maxlength, установленным из аннотации JPA, браузер предотвращает ввод слишком длинных данных до отправки.
