Raíz del árbol de herencia de layouts. Todos los demás layouts (page.html, doc.html, post.html, changelog.html) declaran layout: default en su front matter, lo que significa que su salida se inyecta en {{ content }} en la línea 14 de este archivo. Esta es la base de la cadena de herencia — genera el documento HTML real.

El ciclo de vida completo de la página — 12 includes en orden

1. {% include head.html %}               // <meta>, <title>, CSS, JS (en <head>)
2. {% include hero.html %} O navbar       // Condicional: sección hero o navbar simple
3. {{ content }}                          // Contenido específico de la página (del layout hijo)
4. {% include offcanvas-docs.html %}      // Panel de menú de documentación móvil
5. {% include offcanvas.html %}           // Panel de menú del sitio móvil
6. {% include footer.html %}              // Condicional: solo si NO es layout doc
7. {% include hook-pre-closing-body-doc.html %}  // Condicional: solo para layout doc
8. {% include hook-pre-closing-body.html %}      // Siempre: scripts globales antes de </body>

El orden importa — los paneles offcanvas deben ir después del contenido (son superposiciones position:fixed), el pie de página se suprime condicionalmente para páginas doc, y los includes hook se inyectan justo antes de </body> por rendimiento (scripts al final del body).

El sistema de hooks — extensibilidad sin editar layouts

Los tres includes hook-*.html son la versión de Jekyll de los hooks de WordPress — puntos de inyección donde los plugins o tipos de página pueden añadir scripts/estilos sin modificar la plantilla del layout:

HookPunto de inyecciónUsado por
hook-head.htmlDentro de <head> (a través de head.html)CSS específico de página, meta tags
hook-post-content-doc.htmlDespués del contenido, solo páginas docScripts post-contenido específicos de doc
hook-pre-closing-body.htmlAntes de </body>, siempreJS global: analíticas, inicio de búsqueda, inicio de UIkit
hook-pre-closing-body-doc.htmlAntes de </body>, solo páginas docJS específico de doc: scroll spy de TOC, navegación por teclado anterior/siguiente

Este es el mismo patrón arquitectónico que el sistema de hook/mixin de UIkit en SCSS (#4061) — puntos de extensión vacíos que los layouts hijos pueden implementar sin modificar el padre.
