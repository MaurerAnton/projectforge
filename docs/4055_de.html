Was hier ist, das UIkit nicht bietet

Im Gegensatz zu den 63 UIkit-Theme-Dateien (die meist Variablen definieren und Hooks auskommentiert lassen), enthält diese Datei tatsächliche CSS-Regeln — 110 Zeilen explizite Überschreibungen, geordnet nach visuellen Bereichen:

1. Marken-Linkfarbe — die einflussreichste Regel

p a, li a, table td a {
  color: #BF4040;    // ProjectForge-Rot — NICHT UIkits Standard-Blau
}

Jeder Link in Absätzen, Listenelementen und Tabellenzellen erhält #BF4040 — ein gedämpftes Rot. Dies ist DIE Markenfarbe von ProjectForge für Links. UIkits Standard-Linkfarbe ist sein primäres Blau ($global-primary-background ≈ #1e87f0). Diese einzelne Regel macht die ProjectForge-Site visuell von jeder anderen UIkit-Site unterscheidbar. Die Spezifität über Element+Kontext-Selektoren (p a, nicht nur a) stellt sicher, dass sie nur Inhaltslinks betrifft, nicht Navigations- oder Button-Links.

2. Fette Navigationsleiste + Dropdown-Positionierung

.uk-navbar-nav > li > a {
  font-weight: 700;            // Fette Nav-Elemente — stärker als UIkit-Standard
}
.uk-navbar-dropdown {
  padding: 10px 20px;          // Überschreibt das 25px-Padding des Themes
  top: 60px !important;        // ERZWUNGENE Position — überschreibt JS-berechnete Position
}

font-weight: 700 — macht Nav-Elemente fetter als UIkits normale Stärke. Kombiniert mit der GROSSSCHREIBUNG des Themes entsteht ein sehr selbstbewusster Navigationsstil.

top: 60px !important — das !important ist bemerkenswert. UIkits Drop-Komponente berechnet die Dropdown-Position über JavaScript und setzt sie inline. Das !important überschreibt den Inline-Stil, um einen konsistenten Abstand von 60px zu erzwingen. Ohne dies könnten Dropdowns je nach Viewport zu nah oder zu weit von der Nav entfernt erscheinen. Dies ist ein Muster "JavaScript mit CSS bekämpfen".

3. Tabellen-Styling — Lesbarkeit der Dokumentation

table {
  width: auto;                // Tabellen dehnen sich nicht über die volle Breite
  th { background: #f2f2f2; } // Hellgrauer Kopf — klarer als das gedämpfte Theme
  th:first-child, td:first-child { padding-left: 10px; }
}

width: auto — verhindert, dass Tabellen sich auf 100% ihres Containers ausdehnen. Auf Dokumentationsseiten mit schmalen Inhalten (Vergleichstabellen, Parameterlisten) verschwenden vollbreite Tabellen Platz. Auto-Breite lässt Tabellen nur so breit sein wie ihr Inhalt.

4. Code-Blöcke — AsciiDoc-Rendering-Korrekturen

pre {
  color: #b90505;              // Dunkelroter Code-Text
  font-size: .775rem;          // Kleiner als Fließtext
  &.highlight {
    padding: 15px; background: #f4f4f4;  // Hervorgehobener Code-Hintergrund
  }
}
.listingblock {
  pre code table { margin: 0; }          // AsciiDoc-Code-Listing — Ränder entfernen
  table.linenotable td { margin: 0; padding: 0; }  // Zeilennummern-Tabelle — kompakt
}

#b90505 Code-Farbe — dunkelrot für Code-Text. Eine ungewöhnliche Wahl (die meisten Seiten verwenden dunkelgrau/schwarz). Dies bindet Code visuell an die rote Farbpalette der Marke.

.listingblock Regeln — diese beheben AsciiDocs gerenderte Code-Blöcke. AsciiDoc generiert verschachtelte table > pre > code-Strukturen mit Standard-Rändern, die übermäßigen Leerraum erzeugen. Diese Regeln reduzieren diese Ränder. Der table.linenotable-Selektor zielt speziell auf AsciiDocs zeilennummerierte Code-Blöcke ab.

5. FAQ-Akkordeon — benutzerdefiniertes interaktives Styling

#pf-faq .uk-section {
  padding-top: 0; padding-bottom: 20px;
  .uk-accordion li a.uk-accordion-title {
    border-bottom: 1px solid #ebecee !important;  // Dezente Trennlinie zwischen FAQ-Elementen
    font-weight: 600; padding: 10px; font-size: 16px;  // Größerer klickbarer Bereich
  }
  > :nth-child(n+2) { margin-top: 10px; }  // Abstand zwischen Elementen
}

FAQ-spezifisches Styling, begrenzt auf #pf-faq. Jeder Akkordeon-Titel erhält einen hellen Rand-Trenner, fette Schrift und großzügiges Padding für Touch-Freundlichkeit. Das !important beim Rand überschreibt UIkits Akkordeon-Standard.
