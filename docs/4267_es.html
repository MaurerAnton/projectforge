Protocolo de apagado en dos fases

El script identifica el proceso Java de ProjectForge mediante pgrep -f "java.*projectforge-application" (coincidencia de patrón en la línea de comandos de la JVM), luego ejecuta:

  1. Fase 1 — Gradual (60 segundos): kill $pid envía SIGTERM (señal 15). La JVM lo captura y activa las devoluciones de llamada del ciclo de vida @PreDestroy de Spring — Hibernate vacía cachés, los pools de conexiones se cierran, los trabajos de Quartz se detienen, Tomcat se apaga. El script itera 20 veces × 3 segundos, verificando si el proceso ha desaparecido.
  2. Fase 2 — Forzoso: Si sigue vivo después de 60s, kill -9 $pid envía SIGKILL (señal 9) — no capturable, terminación inmediata. Sin limpieza: conexiones de base de datos huérfanas, índices de Lucene potencialmente corruptos, búferes de registro perdidos. El script espera 2 segundos y vuelve a comprobar.

Este enfoque de dos fases previene el problema de producción más común: fugas de conexión de base de datos por procesos Java eliminados. La ventana de 60 segundos es generosa — la mayoría de las aplicaciones Spring Boot se apagan en 5-15 segundos.

Análisis del script — líneas clave

checkStopped() {
  pid=$(pgrep -f $PROCESS_IDENTIFIER)      # Re-verificar si el proceso existe
  if [[ -z $pid ]]; then                     # Si no se encuentra PID
    echo "${APP_NAME} $1"                    # Mostrar mensaje de éxito
    exit 0                                   # Salir inmediatamente
  fi
  if [[ -n $2 ]]; then                       # Si se da segundo argumento (modo advertencia)
    echo "${APP_NAME} $2"                    # Mostrar advertencia pero continuar
  fi
}

Función de modo dual: checkStopped sirve para dos propósitos según el número de argumentos — con 1 argumento es una "verificación de éxito" (sale si está detenido), con 2 argumentos es un "informe de estado" (muestra y continúa).

Error de ámbito de variable: $pid se establece dentro de la función (línea 7) pero se usa fuera en la línea 20 — esto funciona porque pid no está declarado como local, por lo que se filtra al ámbito del llamante. Frágil — si aparece un segundo proceso coincidente entre verificaciones, solo se elimina el primer PID.

Conclusiones clave

  • Prefiera siempre este script sobre kill -9: El apagado gradual preserva la integridad de la base de datos y previene fugas de conexión.
  • Oculto en uploads/: Vive en site/uploads/ — los archivos adjuntos del sitio Jekyll — una ubicación inusual para herramientas operativas.
  • Sin archivo PID: Identifica el proceso por patrón de línea de comandos, no por un archivo PID. Más robusto entre reinicios pero falla si dos instancias de ProjectForge coinciden.
  • pgrep requerido: Parte del paquete procps-ng — no disponible en imágenes Docker mínimas.
