Différence avec l'application principale

Contrairement à l'application principale ProjectForge qui utilise Spring Boot (SpringApplication.run(ProjectForgeApplication.class, args)), cet outil démarre manuellement un contexte Spring simple :

ApplicationContext context = new AnnotationConfigApplicationContext(SchemaExpContext.class);
TenantRegistryMap.getInstance().setApplicationContext(context);
DatabaseSupport.setInstance(new DatabaseSupport(HibernateUtils.getDialect()));

Trois étapes de démarrage manuel remplacent ce que Spring Boot fait automatiquement : création du contexte, enregistrement du registre des locataires et configuration du dialecte Hibernate. Cela donne à l'outil une empreinte minimale — pas de Tomcat embarqué, pas de Spring Security, pas de planificateur Quartz.

Analyse des arguments CLI

L'outil accepte des options suivies d'un seul argument fichier. Indicateurs pris en charge :

IndicateurEffet
-expOpération d'export → SchemaExpService.doExport()
-impOpération d'import → SchemaExpService.doImport()
-cleardbSupprimer toutes les tables avant l'import (ou effacement autonome)
-insertnewRestoreMode.InsertNew — ignorer les enregistrements existants
-overwriteRestoreMode.OverWrite — mettre à jour les enregistrements existants
-insertallRestoreMode.InsertAll — tout insérer (par défaut)

L'analyseur d'options (parseOption(), lignes 40-65) utilise StringUtils.equalsIgnoreCase() pour une correspondance insensible à la casse. Options positionnelles — les indicateurs doivent précéder l'argument fichier. La boucle while (parseOption(args, pos++)) (ligne 78) itère jusqu'à rencontrer une non-option, puis --pos recule pour pointer vers le premier argument non-option (le nom du fichier).

Problèmes connus

  • Faute de frappe : initApplicatinContext (ligne 122) — il manque un 'o' dans "Application". La faute existe à la fois dans le nom de la méthode et dans son appel (ligne 73).
  • Code mort : Le bloc catch (IllegalArgumentException) à la ligne 82 ne s'exécute jamais — parseOption() ne lève jamais cette exception.
  • Vérification morte : Les lignes 95-98 vérifient restoreMode == null mais restoreMode est initialisé à RestoreMode.InsertAll (ligne 36) et jamais défini à null. Cette vérification ne peut jamais se déclencher.
  • Pas de codes de sortie : Le programme se termine toujours avec le code 0, même en cas d'exception. Les scripts dans l'IC nécessitent une analyse de stdout/stderr.
  • Analyse large de composants : @ComponentScan({"org.projectforge", ...}) (dans SchemaExpContext) importe des milliers de beans — bien plus que nécessaire. Le démarrage du contexte peut être lent.
