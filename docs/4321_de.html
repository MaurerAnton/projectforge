Was es tut

Dieser Test validiert ein kritisches Serialisierungsproblem für das SchemaExp-Tool: Kann XStream Java-Objekte, die zyklische Referenzen enthalten, korrekt serialisieren und deserialisieren? Das ProjectForge-Domänenmodell ist voll von bidirektionalen Beziehungen: UserDO ↔ GroupDO, TaskDO ↔ TaskDO (Eltern/Kind), RechnungDO ↔ RechnungsPositionDO (Rechnung ↔ Positionen). Ohne ordnungsgemäße Zyklenbehandlung würde die standardmäßige TreeMarshallingStrategy von XStream bei diesen Objekten in eine Endlosrekursion geraten und einen StackOverflowError auslösen.

Der Test konstruiert einen minimalen Eltern-Kind-Zyklus (Eltern haben Map<String, Kind>, jedes Kind hat eine Rückreferenz zum Elternteil), konfiguriert XStream mit ReferenceByIdMarshallingStrategy und überprüft, ob das Marshalling → Unmarshalling fehlerfrei abgeschlossen wird. Die Strategie ersetzt wiederholte Objektreferenzen durch interne IDs in der XML-Ausgabe und rekonstruiert den vollständigen Objektgraphen während der Deserialisierung.

Zeilen 1–5: Standardimporte. Serializable wird benötigt, da einige XStream-Serialisierungsmodi dies erfordern. HashMap speichert die Eltern→Kind-Zuordnung.

Zeile 7: org.junit.jupiter.api.Test – bestätigt, dass es sich um JUnit 5 (Jupiter) handelt, nicht um JUnit 4. Der Migrations-Commit (f46333761) erwähnt diese Änderung explizit.

Zeilen 9–10: Die beiden XStream-Importe:

  • XStream – die XML-Serialisierungsbibliothek von ThoughtWorks, die von ProjectForge für XML-Datenbank-Dumps verwendet wird
  • ReferenceByIdMarshallingStrategy – die Strategie, die die Verarbeitung zyklischer Referenzen ermöglicht, indem sie Objekten interne IDs zuweist und darauf verweist, anstatt sie inline zu verschachteln. Dies ist die mit Abstand wichtigste Zeile im Test.

Zeilen 14–22: Innere Klassen – das zyklische Graphenmodell

  public static class Parent implements Serializable {
    Map<String, Child> childres = new HashMap<>();
  }

  public static class Child implements Serializable {
    Parent parentRef;
  }

Parent (Zeile 14): Enthält eine Map<String, Child> – ein Elternteil kann mehrere Kinder referenzieren. Der Feldname childres enthält einen Tippfehler (fehlendes 'n' von "children") – ein bekanntes kleines Code-Problem, das die Funktionalität nicht beeinträchtigt.

Child (Zeile 19): Enthält eine einzelne Parent parentRef – die Rückreferenz, die den Zyklus erzeugt. Ohne dieses Feld gäbe es keinen zu testenden Zyklus.

static-Modifikator: Beide Klassen sind static innere Klassen – sie erfassen keine Referenz auf die äußere XStreamTest-Instanz. Dies verhindert, dass die Testklasse selbst serialisiert wird.

Zeilen 24–39: Die Testmethode – Marshal → Unmarshal Round-Trip

  @Test
  public void testXStream() {
    Parent parent = new Parent();
    Child child = new Child();
    child.parentRef = parent;              // Kind → Elternteil (Rückreferenz)
    parent.childres.put("asdf", child);    // Elternteil → Kind (Vorwärtsreferenz)
    // Jetzt existieren beide Richtungen – ein echter Zyklus
    
    XStream xstream = new XStream();
    xstream.setMarshallingStrategy(new ReferenceByIdMarshallingStrategy());
    String res = xstream.toXML(parent);    // Nach XML marshallen
    System.out.println("marshalled: " + res);
    
    xstream = new XStream();               // Neue Instanz (kein alter Zustand)
    xstream.setMarshallingStrategy(new ReferenceByIdMarshallingStrategy());
    Object object = xstream.fromXML(res);  // Aus XML unmarshallen
    Parent rparent = (Parent) object;      // Cast erfolgreich = Test bestanden
  }
}

Zeilen 27–30: Aufbau des Zyklus. Ein Parent und ein Child werden erstellt. Zeile 29 setzt child.parentRef = parent (Kind → Elternteil). Zeile 30 fügt das Kind mit dem Schlüssel "asdf" in die Map des Elternteils ein (Elternteil → Kind). Beide Richtungen existieren nun.

Zeilen 32–34: Marshalling. Eine neue XStream-Instanz wird mit ReferenceByIdMarshallingStrategy konfiguriert. Ohne Zeile 32 würde XStream die TreeMarshallingStrategy verwenden, die den gesamten Graphen rekursiv serialisiert – trifft auf den Zyklus und löst einen StackOverflowError aus. Die XML-Ausgabe wird <parentRef reference="1"/> enthalten, anstatt das Parent-Objekt erneut inline zu verschachteln.

Zeilen 36–38: Unmarshalling. Eine neue XStream-Instanz wird erstellt (Zeile 36), um sicherzustellen, dass kein Zustand vom Marshalling-Schritt überläuft. Dieselbe Strategie wird angewendet, dann wird der XML-String deserialisiert. Der Cast (Parent) object in Zeile 38 ist die implizite Behauptung – wenn die Deserialisierung fehlschlägt oder die Typen nicht übereinstimmen, wird eine ClassCastException ausgelöst und der Test schlägt fehl.

Keine expliziten Behauptungen: Der Test enthält keine assert*-Aufrufe. Er verlässt sich auf ausnahmebasiertes Fehlschlagen: Jeder StackOverflowError, jede ClassCastException oder jeder XStream-Parsing-Fehler führt zum Fehlschlagen des Tests. Dies ist ein "Smoke-Test"-Muster – überprüfen, ob die Operation nicht abstürzt.

Wie diese Datei mit dem Projekt verbunden ist

Dieser Test ist die grundlegende Validierung für die gesamte SchemaExp-Toolkette. Er beweist, dass XStream den Entity-Graphen von ProjectForge sicher verarbeiten kann, bevor Produktionsdaten berührt werden. Der Testablauf:

In der Produktion: Die Funktion "XML-Backup/Wiederherstellung" in der Admin-Oberfläche und die Initialisierung "Testsystem" im Setup-Assistenten hängen beide von der korrekten Funktion dieser Serialisierung ab. Ein Fehler hier bedeutet keine XML-Backups, keinen Testdatenimport und keine Datenbankmigration zwischen Anbietern (HSQLDB → PostgreSQL).

Wichtige Erkenntnisse

  • ReferenceById ist zwingend erforderlich: Verwenden Sie XStream niemals ohne diese Strategie, wenn Sie mit ProjectForge-Entitäten arbeiten. Das Domänenmodell ist von Natur aus zyklisch.
  • JUnit 5-Migration: Das @Test aus org.junit.jupiter.api bestätigt JUnit 5. Alle neuen Tests sollten diesem Muster folgen.
  • Keine Behauptungen = Designentscheidung: Ausnahmebasiertes Testen ist für Smoke-Tests gültig, aber für Regressionen fragil. Eine zukünftige Verbesserung würde explizite Behauptungen hinzufügen (z. B. überprüfen, ob rparent.childres.get("asdf").parentRef == rparent).
  • Muster der neuen Instanz: Zeile 36 erstellt ein neues XStream für das Unmarshalling – verhindert Zustandslecks zwischen Marshal- und Unmarshal-Operationen. Gute Praxis für Serialisierungstests.
  • Tippfehler im Feldnamen: childres in Zeile 16 sollte children heißen. Harmlos, aber zur Lesbarkeit korrigierbar.
