Qué hace

Esta prueba valida un aspecto crítico de serialización para la herramienta SchemaExp: ¿puede XStream serializar y deserializar correctamente objetos Java que contienen referencias circulares? El modelo de dominio de ProjectForge está lleno de relaciones bidireccionales: UserDO ↔ GroupDO, TaskDO ↔ TaskDO (padre/hijo), RechnungDO ↔ RechnungsPositionDO (factura ↔ líneas de detalle). Sin un manejo adecuado de ciclos, la estrategia predeterminada TreeMarshallingStrategy de XStream entraría en recursión infinita en estos objetos y lanzaría un StackOverflowError.

La prueba construye un ciclo mínimo padre-hijo (Parent tiene Map<String, Child>, cada Child tiene una referencia inversa a Parent), configura XStream con ReferenceByIdMarshallingStrategy, y verifica que el marshalling → unmarshalling se complete sin errores. La estrategia reemplaza las referencias repetidas a objetos con IDs internos en la salida XML y reconstruye el grafo de objetos completo durante la deserialización.

Líneas 1–5: Importaciones estándar. Serializable es necesario porque algunos modos de serialización de XStream lo exigen. HashMap almacena el mapeo padre→hijo.

Línea 7: org.junit.jupiter.api.Test — confirma que esto es JUnit 5 (Jupiter), no JUnit 4. El commit de migración (f46333761) menciona explícitamente este cambio.

Líneas 9–10: Las dos importaciones de XStream:

  • XStream — la biblioteca de serialización XML de ThoughtWorks, utilizada por ProjectForge para volcados XML de base de datos
  • ReferenceByIdMarshallingStrategy — la estrategia que permite el manejo de referencias cíclicas asignando IDs internos a los objetos y referenciándolos en lugar de anidarlos en línea. Esta es la línea más importante de toda la prueba.

Líneas 14–22: Clases internas — el modelo de grafo cíclico

  public static class Parent implements Serializable {
    Map<String, Child> childres = new HashMap<>();
  }

  public static class Child implements Serializable {
    Parent parentRef;
  }

Parent (línea 14): Contiene un Map<String, Child> — un padre puede referenciar múltiples hijos. El nombre del campo childres tiene un error tipográfico (falta la 'n' de "children") — un problema menor conocido de código que no afecta la funcionalidad.

Child (línea 19): Contiene un único Parent parentRef — la referencia inversa que crea el ciclo. Sin este campo, no habría ciclo que probar.

Modificador static: Ambas clases son clases internas static — no capturan una referencia a la instancia externa de XStreamTest. Esto evita que la propia clase de prueba sea serializada.

Líneas 24–39: El método de prueba — ida y vuelta marshal → unmarshal

  @Test
  public void testXStream() {
    Parent parent = new Parent();
    Child child = new Child();
    child.parentRef = parent;              // hijo → padre (referencia inversa)
    parent.childres.put("asdf", child);    // padre → hijo (referencia directa)
    // Ahora ambas direcciones existen — un ciclo verdadero
    
    XStream xstream = new XStream();
    xstream.setMarshallingStrategy(new ReferenceByIdMarshallingStrategy());
    String res = xstream.toXML(parent);    // Marshal a XML
    System.out.println("marshal realizado: " + res);
    
    xstream = new XStream();               // Instancia nueva (sin estado obsoleto)
    xstream.setMarshallingStrategy(new ReferenceByIdMarshallingStrategy());
    Object object = xstream.fromXML(res);  // Unmarshal desde XML
    Parent rparent = (Parent) object;      // Cast exitoso = prueba pasa
  }
}

Líneas 27–30: Construcción del ciclo. Se crean un Parent y un Child. La línea 29 establece child.parentRef = parent (hijo → padre). La línea 30 coloca al hijo en el mapa del padre con la clave "asdf" (padre → hijo). Ahora existen ambas direcciones.

Líneas 32–34: Marshalling. Se configura una instancia nueva de XStream con ReferenceByIdMarshallingStrategy. Sin la línea 32, XStream usaría TreeMarshallingStrategy que serializa recursivamente todo el grafo — encontrando el ciclo y lanzando StackOverflowError. La salida XML contendrá <parentRef reference="1"/> en lugar de anidar en línea el objeto Parent nuevamente.

Líneas 36–38: Unmarshalling. Se crea una instancia nueva de XStream (línea 36) para asegurar que no haya fuga de estado del paso de marshalling. Se aplica la misma estrategia, luego se deserializa la cadena XML. El cast (Parent) object de la línea 38 es la aserción implícita — si la deserialización falla o los tipos no coinciden, se lanza una ClassCastException y la prueba falla.

Sin aserciones explícitas: La prueba no tiene llamadas assert*. Se basa en fallos basados en excepciones: cualquier StackOverflowError, ClassCastException o error de análisis de XStream hará que la prueba falle. Este es un patrón de "prueba de humo" — verificar que la operación no se bloquee.

Cómo se conecta este archivo con el proyecto

Esta prueba es la validación fundamental para toda la cadena de herramientas SchemaExp. Demuestra que XStream puede manejar de forma segura el grafo de entidades de ProjectForge antes de tocar cualquier dato de producción. El flujo del conjunto de pruebas:

Un fallo aquí significa: sin copias de seguridad XML, sin importación de datos de prueba y sin migración de base de datos entre proveedores (HSQLDB → PostgreSQL).

Conclusiones clave

  • ReferenceById es obligatorio: Nunca uses XStream sin esta estrategia cuando trabajes con entidades de ProjectForge. El modelo de dominio es inherentemente cíclico.
  • Migración a JUnit 5: El @Test de org.junit.jupiter.api confirma JUnit 5. Todas las pruebas nuevas deben seguir este patrón.
  • Sin aserciones = elección de diseño: Las pruebas basadas en excepciones son válidas para pruebas de humo, pero frágiles para regresión. Una mejora futura añadiría aserciones explícitas (por ejemplo, verificar rparent.childres.get("asdf").parentRef == rparent).
  • Patrón de instancia nueva: La línea 36 crea un nuevo XStream para unmarshalling — evita la fuga de estado entre operaciones de marshal y unmarshal. Buena práctica para pruebas de serialización.
  • Error tipográfico en nombre de campo: childres en la línea 16 debería ser children. Inofensivo pero vale la pena corregirlo para mejorar la legibilidad.
