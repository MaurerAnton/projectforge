Créé à l'origine en 2016 dans le cadre de l'outil SchemaExp. Migré de JUnit4 vers JUnit5 en avril 2019. La logique de test principale est restée inchangée depuis 10 ans.

Ce qu'il fait

Ce test valide une préoccupation critique de sérialisation pour l'outil SchemaExp : XStream peut-il correctement sérialiser et désérialiser des objets Java contenant des références circulaires ? Le modèle de domaine de ProjectForge est rempli de relations bidirectionnelles : UserDO ↔ GroupDO, TaskDO ↔ TaskDO (parent/enfant), RechnungDO ↔ RechnungsPositionDO (facture ↔ lignes d'écriture). Sans une gestion appropriée des cycles, la TreeMarshallingStrategy par défaut de XStream entrerait dans une récursion infinie sur ces objets et lèverait une StackOverflowError.

Le test construit un cycle parent-enfant minimal (Parent a Map<String, Child>, chaque Child a une référence arrière vers Parent), configure XStream avec ReferenceByIdMarshallingStrategy, et vérifie que le marshalling → unmarshalling se termine sans erreur. La stratégie remplace les références d'objets répétées par des identifiants internes dans la sortie XML et reconstruit le graphe d'objets complet lors de la désérialisation.

Lignes 1–5 : Imports standards. Serializable est requis car certains modes de sérialisation XStream l'exigent. HashMap stocke le mappage parent→enfant.

Ligne 7 : org.junit.jupiter.api.Test — confirme qu'il s'agit de JUnit 5 (Jupiter), pas de JUnit 4. Le commit de migration (f46333761) mentionne explicitement ce changement.

Lignes 9–10 : Les deux imports XStream :

  • XStream — la bibliothèque de sérialisation XML de ThoughtWorks, utilisée par ProjectForge pour les vidages XML de base de données
  • ReferenceByIdMarshallingStrategy — la stratégie qui permet la gestion des références cycliques en attribuant des identifiants internes aux objets et en les référençant au lieu de les imbriquer en ligne. C'est la ligne la plus importante du test.

Lignes 14–22 : Classes internes — le modèle de graphe cyclique

  public static class Parent implements Serializable {
    Map<String, Child> childres = new HashMap<>();
  }

  public static class Child implements Serializable {
    Parent parentRef;
  }

Parent (ligne 14) : Contient une Map<String, Child> — un parent peut référencer plusieurs enfants. Le nom du champ childres a une faute de frappe (il manque le 'n' à "children") — un problème mineur de code connu qui n'affecte pas la fonctionnalité.

Child (ligne 19) : Contient une seule Parent parentRef — la référence arrière qui crée le cycle. Sans ce champ, il n'y aurait pas de cycle à tester.

Modificateur static : Les deux classes sont des classes internes static — elles ne capturent pas de référence à l'instance externe de XStreamTest. Cela empêche la classe de test elle-même d'être sérialisée.

Lignes 24–39 : La méthode de test — aller-retour marshal → unmarshal

  @Test
  public void testXStream() {
    Parent parent = new Parent();
    Child child = new Child();
    child.parentRef = parent;              // enfant → parent (référence arrière)
    parent.childres.put("asdf", child);    // parent → enfant (référence avant)
    // Maintenant les deux directions existent — un vrai cycle
    
    XStream xstream = new XStream();
    xstream.setMarshallingStrategy(new ReferenceByIdMarshallingStrategy());
    String res = xstream.toXML(parent);    // Marshal vers XML
    System.out.println("marshalisé : " + res);
    
    xstream = new XStream();               // Nouvelle instance (pas d'état obsolète)
    xstream.setMarshallingStrategy(new ReferenceByIdMarshallingStrategy());
    Object object = xstream.fromXML(res);  // Unmarshal depuis XML
    Parent rparent = (Parent) object;      // Le cast réussit = le test passe
  }
}

Lignes 27–30 : Construction du cycle. Un Parent et un Child sont créés. La ligne 29 définit child.parentRef = parent (enfant → parent). La ligne 30 place l'enfant dans la map du parent avec la clé "asdf" (parent → enfant). Les deux directions existent maintenant.

Lignes 32–34 : Marshalling. Une nouvelle instance XStream est configurée avec ReferenceByIdMarshallingStrategy. Sans la ligne 32, XStream utiliserait TreeMarshallingStrategy qui sérialise récursivement le graphe entier — rencontrant le cycle et levant une StackOverflowError. La sortie XML contiendra <parentRef reference="1"/> au lieu d'imbriquer à nouveau l'objet Parent en ligne.

Lignes 36–38 : Unmarshalling. Une nouvelle instance XStream est créée (ligne 36) pour garantir qu'aucun état ne fuit de l'étape de marshalling. La même stratégie est appliquée, puis la chaîne XML est désérialisée. Le cast (Parent) object de la ligne 38 est l'assertion implicite — si la désérialisation échoue ou si les types ne correspondent pas, une ClassCastException est levée et le test échoue.

Aucune assertion explicite : Le test n'a pas d'appels assert*. Il repose sur l'échec basé sur les exceptions : toute StackOverflowError, ClassCastException ou erreur d'analyse XStream fera échouer le test. C'est un modèle de "test de fumée" — vérifier que l'opération ne plante pas.

Comment ce fichier se connecte au projet

Ce test est la validation fondamentale pour toute la chaîne d'outils SchemaExp. Il prouve que XStream peut gérer en toute sécurité le graphe d'entités de ProjectForge avant que des données de production ne soient touchées. Le flux de la suite de tests :

FichierRôle
#4108 XStreamTestValide la gestion des cycles au niveau de la bibliothèque de sérialisation
#4107 ToXmlTestExport de bout en bout de la base de données réelle vers XML
#4106 FromXmlTestImport de bout en bout du XML dans une base de données propre

En production : La fonctionnalité "Sauvegarde/Restauration XML" de l'interface d'administration et l'initialisation "Système de test" de l'assistant d'installation dépendent toutes deux du bon fonctionnement de cette sérialisation. Un échec ici signifie pas de sauvegardes XML, pas d'import de données de test et pas de migration de base de données entre fournisseurs (HSQLDB → PostgreSQL).

Points clés à retenir

  • ReferenceById est obligatoire : N'utilisez jamais XStream sans cette stratégie lorsque vous travaillez avec des entités ProjectForge. Le modèle de domaine est intrinsèquement cyclique.
  • Migration JUnit 5 : Le @Test de org.junit.jupiter.api confirme JUnit 5. Tous les nouveaux tests doivent suivre ce modèle.
  • Aucune assertion = choix de conception : Les tests basés sur les exceptions sont valables pour les tests de fumée mais fragiles pour la régression. Une amélioration future ajouterait des assertions explicites (par exemple, vérifier rparent.childres.get("asdf").parentRef == rparent).
  • Modèle de nouvelle instance : La ligne 36 crée un nouveau XStream pour l'unmarshalling — empêche les fuites d'état entre les opérations de marshal et d'unmarshal. Bonne pratique pour les tests de sérialisation.
  • Faute de frappe dans le nom du champ : childres à la ligne 16 devrait être children. Inoffensif mais mérite d'être corrigé pour la lisibilité.
