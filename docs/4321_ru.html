Изначально создан в 2016 году как часть инструмента SchemaExp. Мигрирован с JUnit4 на JUnit5 в апреле 2019. Основная логика теста остаётся неизменной уже 10 лет.

Что он делает

Этот тест проверяет критический аспект сериализации для инструмента SchemaExp: может ли XStream корректно сериализовать и десериализовать Java-объекты, содержащие циклические ссылки? Доменная модель ProjectForge полна двунаправленных связей: UserDO ↔ GroupDO, TaskDO ↔ TaskDO (родитель/потомок), RechnungDO ↔ RechnungsPositionDO (счёт ↔ позиции счёта). Без правильной обработки циклов стандартная TreeMarshallingStrategy XStream войдёт в бесконечную рекурсию на этих объектах и вызовет StackOverflowError.

Тест создаёт минимальный цикл родитель-потомок (у Parent есть Map<String, Child>, каждый Child содержит обратную ссылку на Parent), настраивает XStream с ReferenceByIdMarshallingStrategy и проверяет, что маршаллинг → демаршаллинг завершается без ошибок. Эта стратегия заменяет повторяющиеся ссылки на объекты внутренними ID в XML-выводе и восстанавливает полный граф объектов при десериализации.

Строки 1–5: Стандартные импорты. Serializable требуется, так как некоторые режимы сериализации XStream требуют его. HashMap хранит отображение родитель→потомок.

Строка 7: org.junit.jupiter.api.Test — подтверждает, что это JUnit 5 (Jupiter), а не JUnit 4. Коммит миграции (f46333761) явно упоминает это изменение.

Строки 9–10: Два импорта XStream:

  • XStream — библиотека XML-сериализации ThoughtWorks, используемая ProjectForge для XML-дампов базы данных
  • ReferenceByIdMarshallingStrategy — стратегия, обеспечивающая обработку циклических ссылок путём присвоения внутренних ID объектам и ссылок на них вместо вложенного включения. Это самая важная строка в тесте.

Строки 14–22: Внутренние классы — модель циклического графа

  public static class Parent implements Serializable {
    Map<String, Child> childres = new HashMap<>();
  }

  public static class Child implements Serializable {
    Parent parentRef;
  }

Parent (строка 14): Содержит Map<String, Child> — один родитель может ссылаться на несколько потомков. В имени поля childres есть опечатка (пропущена 'n' в "children") — известная незначительная проблема кода, не влияющая на функциональность.

Child (строка 19): Содержит единственное поле Parent parentRef — обратную ссылку, создающую цикл. Без этого поля цикла для тестирования не было бы.

Модификатор static: Оба класса являются static внутренними классами — они не захватывают ссылку на внешний экземпляр XStreamTest. Это предотвращает сериализацию самого тестового класса.

Строки 24–39: Тестовый метод — маршаллинг → демаршаллинг (полный цикл)

  @Test
  public void testXStream() {
    Parent parent = new Parent();
    Child child = new Child();
    child.parentRef = parent;              // потомок → родитель (обратная ссылка)
    parent.childres.put("asdf", child);    // родитель → потомок (прямая ссылка)
    // Теперь существуют оба направления — настоящий цикл
    
    XStream xstream = new XStream();
    xstream.setMarshallingStrategy(new ReferenceByIdMarshallingStrategy());
    String res = xstream.toXML(parent);    // Маршаллинг в XML
    System.out.println("marshaled: " + res);
    
    xstream = new XStream();               // Новый экземпляр (без устаревшего состояния)
    xstream.setMarshallingStrategy(new ReferenceByIdMarshallingStrategy());
    Object object = xstream.fromXML(res);  // Демаршаллинг из XML
    Parent rparent = (Parent) object;      // Приведение успешно = тест пройден
  }
}

Строки 27–30: Построение цикла. Создаются Parent и Child. Строка 29 устанавливает child.parentRef = parent (потомок → родитель). Строка 30 помещает потомка в карту родителя с ключом "asdf" (родитель → потомок). Теперь существуют оба направления.

Строки 32–34: Маршаллинг. Новый экземпляр XStream настраивается с ReferenceByIdMarshallingStrategy. Без строки 32 XStream использовал бы TreeMarshallingStrategy, которая рекурсивно сериализует весь граф — попадая в цикл и вызывая StackOverflowError. XML-вывод будет содержать <parentRef reference="1"/> вместо повторного вложенного включения объекта Parent.

Строки 36–38: Демаршаллинг. Создаётся новый экземпляр XStream (строка 36), чтобы гарантировать отсутствие утечки состояния из этапа маршаллинга. Применяется та же стратегия, затем XML-строка десериализуется. Приведение (Parent) object в строке 38 является неявным утверждением — если десериализация не удалась или типы не совпадают, выбрасывается ClassCastException, и тест падает.

Нет явных утверждений: В тесте нет вызовов assert*. Он полагается на сбой на основе исключений: любой StackOverflowError, ClassCastException или ошибка парсинга XStream приведут к падению теста. Это паттерн "дымового теста" — проверка, что операция не вызывает сбоя.

Как этот файл связан с проектом

Этот тест является фундаментальной проверкой для всей цепочки инструментов SchemaExp. Он доказывает, что XStream может безопасно обрабатывать граф сущностей ProjectForge до того, как будут затронуты какие-либо производственные данные. Поток тестового набора:

Сбой здесь означает отсутствие XML-резервных копий, невозможность импорта тестовых данных и миграции базы данных между поставщиками (HSQLDB → PostgreSQL).

Ключевые выводы

  • ReferenceById обязателен: Никогда не используйте XStream без этой стратегии при работе с сущностями ProjectForge. Доменная модель по своей природе циклична.
  • Миграция на JUnit 5: @Test из org.junit.jupiter.api подтверждает JUnit 5. Все новые тесты должны следовать этому шаблону.
  • Отсутствие утверждений = осознанный выбор: Тестирование на основе исключений допустимо для дымовых тестов, но хрупко для регрессионного тестирования. Будущее улучшение могло бы добавить явные утверждения (например, проверить rparent.childres.get("asdf").parentRef == rparent).
  • Паттерн нового экземпляра: Строка 36 создаёт новый XStream для демаршаллинга — предотвращает утечку состояния между операциями маршаллинга и демаршаллинга. Хорошая практика для тестов сериализации.
  • Опечатка в имени поля: childres в строке 16 должно быть children. Безвредно, но стоит исправить для читаемости.
