projectforge-business/src/main/java/org/projectforge/database/jdbc/DatabaseExecutorImpl.java Zeilen: 161 · Autor: Kai Reinhard · Typ: Java — implementiert DatabaseExecutor · Paket: org.projectforge.database.jdbc 161 Zeilen · 120 Code · 29 Kommentare · 12 Leerzeilen

Einfache JDBC-Implementierung des DatabaseExecutor-Interfaces. 161 Zeilen. Wichtiger Javadoc-Hinweis: "DIESE KLASSE NICHT FÜR PRODUKTION VERWENDEN! Dies dient nur Demonstrationszwecken, da es kein Connection-Pooling gibt und Verbindungen verloren gehen können!!!!!" — diese Klasse ist für Flyway-Migrationen (die ausgeführt werden, bevor Hibernate initialisiert ist), Daten-Patching-Skripte und Entwicklung/Tests. Der Produktionscode verwendet eine JdbcTemplate-basierte Implementierung mit HikariCP-Connection-Pooling.

Architektur: Jede Methode erzeugt eine anonyme JdbcExecutor-Unterklasse (#638), die die Vorlagenmethode execute(PreparedStatement) überschreibt. Dies ist das Schablonenmethode-Muster — JdbcExecutor kümmert sich um den Verbindungslebenszyklus (öffnen, Parameter setzen, schließen), während jede anonyme Unterklasse die spezifische JDBC-Operation bereitstellt.

Methodendetails:

  • execute(sql, ignoreErrors) — führt DDL/DML über stmt.execute() aus. Gibt nichts zurück. Wenn ignoreErrors=true, fängt JdbcExecutor SQLException ab und protokolliert sie auf WARN-Ebene, anstatt sie erneut zu werfen. Wird für idempotente Operationen wie DROP TABLE IF EXISTS verwendet.
  • query(sql, args...) — die Hauptabfragemethode. Erstellt einen JdbcExecutor, dessen execute()-Überschreibung:
    1. stmt.executeQuery() aufruft, um ResultSet zu erhalten
    2. while(rs.next()) durchläuft und pro Zeile ein DatabaseResultRowImpl erstellt
    3. Für jede Zeile die ResultSetMetaData-Spalten durchläuft (1-basierte → 0-basierte Indexkonvertierung)
    4. Für jede Spalte ein DatabaseResultRowEntryImpl(type, name, value) erstellt
    5. List<DatabaseResultRow> zurückgibt — ordnungsgemäß mit Spaltenmetadaten befüllt
    Ressourcensicherheit: ResultSet wird in einem finally-Block geschlossen — entscheidend, da dies Hibernates Ressourcenverwaltung umgeht.
  • queryForInt(sql, args...) — gibt eine einzelne Ganzzahl zurück. Wirft RuntimeException, wenn das Ergebnisset leer ist (kein rs.next()). Wird für SELECT COUNT(*) und ähnliche Aggregatabfragen verwendet. Schließt ResultSet im finally-Block.
  • update(sql, args...) — führt stmt.executeUpdate() aus, gibt die Anzahl der betroffenen Zeilen als Integer zurück. Umwandlung von Object — die generische JdbcExecutor-Vorlage gibt Object zurück, um verschiedene Rückgabetypen zu ermöglichen.

Zwei Konstruktoren: DatabaseExecutorImpl() (parameterlos — DataSource muss später über setDataSource() gesetzt werden) und DatabaseExecutorImpl(DataSource) (einsatzbereit). Der parameterlose Konstruktor existiert für Spring-XML-Konfigurationsszenarien, in denen DataSource über einen Property-Setter injiziert wird.

DataSource-Ablauf: Die DataSource stammt von Springs @Bean DataSource (konfiguriert in Anwendungseigenschaften: spring.datasource.url, spring.datasource.username, spring.datasource.password). In der Produktion ist dies eine HikariCP-gepoolte DataSource — aber diese Klasse nutzt keine Pooling-Funktionen. Die Warnung "kein Connection-Pooling" bezieht sich auf ihre eigene Verbindungsverwaltung: Jeder Aufruf von JdbcExecutor öffnet eine neue rohe JDBC-Verbindung über DataSource.getConnection(), anstatt aus dem Pool zu leihen, was eigentlich mit HikariCP funktionieren sollte, aber nicht die beabsichtigte Nutzung ist.

Abhängigkeiten: JdbcExecutor (#638), DatabaseResultRowImpl (#637), DatabaseResultRowEntryImpl (#636). Alle im selben jdbc-Unterpaket.
