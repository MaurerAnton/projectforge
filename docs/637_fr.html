projectforge-business/src/main/java/org/projectforge/database/jdbc/DatabaseExecutorImpl.java Lignes : 161 · Auteur : Kai Reinhard · Type : Java — implémente DatabaseExecutor · Paquetage : org.projectforge.database.jdbc 161 lignes · 120 code · 29 commentaires · 12 vides

Implémentation JDBC simple de l'interface DatabaseExecutor. 161 lignes. Avertissement Javadoc important : "N'UTILISEZ PAS CETTE CLASSE EN PRODUCTION ! Ceci est uniquement à des fins de démonstration, car il n'y a pas de pooling de connexions et les connexions peuvent être perdues !!!!!" — cette classe est destinée aux migrations Flyway (qui s'exécutent avant l'initialisation d'Hibernate), aux scripts de correction de données et au développement/test. Le code de production utilise une implémentation basée sur JdbcTemplate avec le pooling de connexions HikariCP.

Architecture : Chaque méthode crée une sous-classe anonyme de JdbcExecutor (#638) qui redéfinit la méthode modèle execute(PreparedStatement). Il s'agit du patron Template Method — JdbcExecutor gère le cycle de vie de la connexion (ouverture, définition des paramètres, fermeture), tandis que chaque sous-classe anonyme fournit l'opération JDBC spécifique.

Détails des méthodes :

  • execute(sql, ignoreErrors) — exécute du DDL/DML via stmt.execute(). Ne retourne rien. Quand ignoreErrors=true, JdbcExecutor attrape SQLException et la journalise au niveau WARN sans la relancer. Utilisé pour les opérations idempotentes comme DROP TABLE IF EXISTS.
  • query(sql, args...) — la méthode de requête principale. Crée un JdbcExecutor dont la redéfinition de execute() :
    1. Appelle stmt.executeQuery() pour obtenir un ResultSet
    2. Itère while(rs.next()), créant un DatabaseResultRowImpl par ligne
    3. Pour chaque ligne, itère sur les colonnes de ResultSetMetaData (conversion d'index base 1 → base 0)
    4. Crée DatabaseResultRowEntryImpl(type, name, value) pour chaque colonne
    5. Retourne List<DatabaseResultRow> — correctement remplie avec les métadonnées des colonnes
    Sécurité des ressources : ResultSet est fermé dans un bloc finally — critique car cela contourne la gestion des ressources d'Hibernate.
  • queryForInt(sql, args...) — retourne un entier unique. Lève une RuntimeException si le jeu de résultats est vide (pas de rs.next()). Utilisé pour SELECT COUNT(*) et les requêtes agrégées similaires. Ferme ResultSet dans finally.
  • update(sql, args...) — exécute stmt.executeUpdate(), retourne le nombre de lignes affectées sous forme d'Integer. Conversion depuis Object — le modèle générique JdbcExecutor retourne Object pour s'adapter à différents types de retour.

Deux constructeurs : DatabaseExecutorImpl() (sans argument — la DataSource doit être définie ultérieurement via setDataSource()) et DatabaseExecutorImpl(DataSource) (prêt à l'emploi). Le constructeur sans argument existe pour les scénarios de configuration Spring XML où la DataSource est injectée via un setter de propriété.

Flux DataSource : La DataSource provient du @Bean DataSource de Spring (configuré dans les propriétés de l'application : spring.datasource.url, spring.datasource.username, spring.datasource.password). En production, il s'agit d'une DataSource poolée HikariCP — mais cette classe n'utilise pas les fonctionnalités de pooling. Son avertissement concernant "l'absence de pooling de connexions" fait référence à sa propre gestion des connexions : chaque appel à JdbcExecutor ouvre une nouvelle connexion JDBC brute via DataSource.getConnection() plutôt que d'emprunter au pool, ce qui devrait fonctionner avec HikariCP mais n'est pas l'utilisation prévue.

Dépendances : JdbcExecutor (#638), DatabaseResultRowImpl (#637), DatabaseResultRowEntryImpl (#636). Tous dans le même sous-paquetage jdbc.
