#640: DOGetterListExcelExporter.java

Lines: 55 · Author: blumenstein (2016) · Type: Java — extends DOListExcelExporter

Excel exporter with getter-based fallback for field value resolution. 55 lines. Extends DOListExcelExporter and overrides the single method addMapping(). This is a prime example of the Reflection + JavaBean convention pattern in ProjectForge exports.

The problem it solves: Standard DOListExcelExporter reads field values using Field.get(entry) — direct field access via reflection. This works for fields that are directly set on the object. However, some DO classes have computed properties that aren't stored as fields — they use getter methods with custom logic (e.g. getDisplayName() concatenating firstName + lastName, or getTotal() summing child values). Direct field reflection would return null for these, producing empty Excel cells.

The solution — addMapping() override:

  1. First tries BeanHelper.getFieldValue(entry, field) — direct field access. If the field has a non-null value, uses it normally
  2. Fallback: if the field value is null, uses BeanHelper.determineGetter(entry.getClass(), field.getName()) to find the getter method (standard JavaBean convention: get{FieldName}()), then calls BeanHelper.invoke(entry, getter). If the result is non-null, adds result.toString() to the mapping

This allows fields like orderString (computed via @Transient getOrderString()) to appear in Excel exports even though they have no backing field value.

Constructor: Takes filenameIdentifier — used as the base for the exported filename (e.g. "employeeBilling" → "employeeBilling_202501.xlsx"). Passes it to the superclass constructor.

Usage context: Used by the employee billing export (EmployeeBillingExcelExporter) and potentially any export where the DO has @Transient computed properties that need to appear in the spreadsheet. The getter-based fallback is a pragmatic alternative to requiring all exportable properties to be actual database fields.
