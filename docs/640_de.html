projectforge-business/src/main/java/org/projectforge/database/jdbc/JdbcExecutor.java Zeilen: 95 · Autor: Kai Reinhard · Typ: Java abstrakte Klasse — Template-Method-Pattern 95 Zeilen · 61 Code · 26 Kommentare · 8 leer

Abstrakter JDBC-Operationsausführer unter Verwendung des Template-Method-Patterns. 95 Zeilen. Dies ist die Grundlage für alle rohen JDBC-Operationen in ProjectForge — DatabaseExecutorImpl erstellt anonyme Unterklassen für jeden SQL-Aufruf. Diese Klasse besitzt den Verbindungslebenszyklus, während Unterklassen definieren, was mit dem Statement passiert.

Template-Methode — execute(String sql, boolean ignoreErrors, Object... args):

  1. Verbindungsaufnahme: dataSource.getConnection() — holt eine rohe JDBC-Verbindung aus dem Pool (oder direkt im Testmodus)
  2. Statement-Vorbereitung: con.prepareStatement(sql) — erstellt ein PreparedStatement
  3. Parameterbindung: iteriert über args[] und ruft stmt.setObject(i+1, args[i]) auf — beachten Sie die i+1-Konvertierung: JDBC-Parameter sind 1-basiert (JDBC-Spezifikation), während Java-Arrays 0-basiert sind. Dies ist eine häufige Fehlerquelle, wenn man es vergisst
  4. Delegation: ruft execute(stmt) auf — die abstrakte Methode, die von Unterklassen überschrieben wird. Der Rückgabewert ist als Object typisiert, da Unterklassen verschiedene Typen zurückgeben: null für DDL, List<DatabaseResultRow> für Abfragen, Integer für Updates/Zählungen
  5. Fehlerbehandlung: Wenn SQLException abgefangen wird und ignoreErrors=true ist, wird der Fehler auf ERROR-Ebene protokolliert und null zurückgegeben. Wenn ignoreErrors=false ist, wird die Exception in RuntimeException verpackt und erneut geworfen — dies ist eine Entwurfsentscheidung für ungeprüfte Ausnahmen; Aufrufer benötigen kein try-catch für SQL-Fehler

Ressourcenbereinigung (finally-Block): Schließt zuerst PreparedStatement, dann Connection. Jedes Schließen erfolgt in einem eigenen try-catch — falls das Schließen des Statements eine Exception wirft, wird die Verbindung dennoch geschlossen. Kritische Nuance: Wenn eines der Schließen eine Exception wirft, wird ein static boolean hasErrors-Flag gesetzt. Nach beiden Schließvorgängen wird, falls Fehler aufgetreten sind, eine RuntimeException geworfen. Dadurch wird sichergestellt, dass Ressourcenleck-Fehler nicht stillschweigend geschluckt werden — der Aufrufer erfährt, dass die Ressourcenbereinigung fehlgeschlagen ist.

Abstrakte Methode — execute(PreparedStatement stmt): Wird von anonymen Unterklassen in DatabaseExecutorImpl für 4 verschiedene Operationen implementiert: DDL-Ausführung (stmt.execute()), Abfrage (stmt.executeQuery() + ResultSet-Mapping), Skalarabfrage (rs.getInt(1)) und Update (stmt.executeUpdate()).

Fehlendes Connection-Pooling: Der Javadoc warnt: „Verbindungen können verloren gehen“ — diese Klasse holt eine Connection über DataSource.getConnection() und schließt sie im finally-Block. Dies ist korrekt für gepoolte DataSources (das Schließen gibt die Verbindung an den Pool zurück), aber die Sorge des Autors galt direkten DriverManager-Verbindungen im Testmodus, bei denen jeder Aufruf eine neue TCP-Verbindung öffnet. In der Produktion mit HikariCP funktioniert das Pooling einwandfrei — die Warnung ist übervorsichtig.
