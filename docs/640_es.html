#640: JdbcExecutor.java

projectforge-business/src/main/java/org/projectforge/database/jdbc/JdbcExecutor.java Líneas: 95 · Autor: Kai Reinhard · Tipo: Clase abstracta Java — Patrón Template Method 95 líneas · 61 código · 26 comentarios · 8 en blanco

Ejecutor abstracto de operaciones JDBC que utiliza el patrón Template Method. 95 líneas. Esta es la base para todas las operaciones JDBC sin procesar en ProjectForge — DatabaseExecutorImpl crea subclases anónimas para cada llamada SQL. Esta clase gestiona el ciclo de vida de la conexión mientras permite que las subclases definan qué sucede con la sentencia.

Template Method — execute(String sql, boolean ignoreErrors, Object... args):

  1. Adquisición de conexión: dataSource.getConnection() — obtiene una conexión JDBC sin procesar del pool (o directamente en modo de prueba)
  2. Preparación de la sentencia: con.prepareStatement(sql) — crea un PreparedStatement
  3. Vinculación de parámetros: itera sobre args[] y llama a stmt.setObject(i+1, args[i]) — observe la conversión i+1: los parámetros JDBC tienen base 1 (especificación JDBC), mientras que los arrays de Java tienen base 0. Esta es una fuente común de errores si se olvida
  4. Delegación: llama a execute(stmt) — el método abstracto sobrescrito por las subclases. El valor de retorno está tipado como Object porque las subclases devuelven diferentes tipos: null para DDL, List<DatabaseResultRow> para consultas, Integer para actualizaciones/contadores
  5. Manejo de errores: si se captura SQLException y ignoreErrors=true, registra el error a nivel ERROR y devuelve null. Si ignoreErrors=false, lo envuelve en RuntimeException y lo relanza — esta es una decisión de diseño de excepción no verificada; los llamadores no necesitan try-catch para errores SQL

Limpieza de recursos (bloque finally): Cierra primero PreparedStatement, luego Connection. Cada cierre está en su propio try-catch — si cerrar la sentencia lanza una excepción, la conexión aún se cierra. Matiz crítico: si alguno de los cierres lanza una excepción, se establece una bandera static boolean hasErrors. Después de ambos cierres, si ocurrió algún error, se lanza una RuntimeException. Esto asegura que los errores de fuga de recursos no se traguen silenciosamente — el llamador sabe que la limpieza de recursos falló.

Método abstracto — execute(PreparedStatement stmt): Implementado por subclases anónimas en DatabaseExecutorImpl para 4 operaciones diferentes: ejecución DDL (stmt.execute()), consulta (stmt.executeQuery() + mapeo de ResultSet), consulta escalar (rs.getInt(1)), y actualización (stmt.executeUpdate()).

Pool de conexiones faltante: El Javadoc advierte "las conexiones pueden perderse" — esta clase obtiene una Connection mediante DataSource.getConnection() y la cierra en finally. Esto es correcto para DataSources agrupados (el cierre devuelve la conexión al pool), pero la preocupación del autor era sobre conexiones directas de DriverManager en modo de prueba donde cada llamada abre una nueva conexión TCP. En producción con HikariCP, el agrupamiento funciona bien — la advertencia es demasiado cautelosa.
