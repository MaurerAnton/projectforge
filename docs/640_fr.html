projectforge-business/src/main/java/org/projectforge/database/jdbc/JdbcExecutor.java Lignes : 95 · Auteur : Kai Reinhard · Type : Classe abstraite Java — Patron Template Method 95 lignes · 61 code · 26 commentaires · 8 vides

Exécuteur d'opérations JDBC abstrait utilisant le patron Template Method. 95 lignes. C'est le fondement de toutes les opérations JDBC brutes dans ProjectForge — DatabaseExecutorImpl crée des sous-classes anonymes pour chaque appel SQL. Cette classe gère le cycle de vie de la connexion tout en laissant les sous-classes définir ce qui se passe avec l'instruction.

Template Method — execute(String sql, boolean ignoreErrors, Object... args) :

  1. Acquisition de la connexion : dataSource.getConnection() — obtient une connexion JDBC brute depuis le pool (ou directement en mode test)
  2. Préparation de l'instruction : con.prepareStatement(sql) — crée un PreparedStatement
  3. Liaison des paramètres : itère sur args[] et appelle stmt.setObject(i+1, args[i]) — notez la conversion i+1 : les paramètres JDBC sont indexés à partir de 1 (spécification JDBC), tandis que les tableaux Java sont indexés à partir de 0. C'est une source fréquente de bugs si oublié
  4. Délégation : appelle execute(stmt) — la méthode abstraite redéfinie par les sous-classes. La valeur de retour est typée comme Object car les sous-classes retournent différents types : null pour le DDL, List<DatabaseResultRow> pour les requêtes, Integer pour les mises à jour/comptages
  5. Gestion des erreurs : si une SQLException est attrapée et que ignoreErrors=true, enregistre l'erreur au niveau ERROR et retourne null. Si ignoreErrors=false, l'encapsule dans une RuntimeException et la relance — c'est un choix de conception d'exception non vérifiée ; les appelants n'ont pas besoin de try-catch pour les erreurs SQL

Nettoyage des ressources (bloc finally) : Ferme d'abord le PreparedStatement, puis la Connection. Chaque fermeture est dans son propre try-catch — si la fermeture de l'instruction échoue, la connexion est quand même fermée. Nuance critique : si l'une ou l'autre fermeture lève une exception, un indicateur static boolean hasErrors est positionné. Après les deux fermetures, si des erreurs sont survenues, une RuntimeException est levée. Cela garantit que les erreurs de fuite de ressources ne sont pas silencieusement ignorées — l'appelant sait que le nettoyage des ressources a échoué.

Méthode abstraite — execute(PreparedStatement stmt) : Implémentée par des sous-classes anonymes dans DatabaseExecutorImpl pour 4 opérations différentes : exécution DDL (stmt.execute()), requête (stmt.executeQuery() + mapping ResultSet), requête scalaire (rs.getInt(1)), et mise à jour (stmt.executeUpdate()).

Absence de pooling de connexion : La Javadoc avertit que « les connexions peuvent se perdre » — cette classe obtient une Connection via DataSource.getConnection() et la ferme dans le bloc finally. C'est correct pour les DataSources poolées (la fermeture retourne la connexion au pool), mais la préoccupation de l'auteur concernait les connexions directes DriverManager en mode test où chaque appel ouvre une nouvelle connexion TCP. En production avec HikariCP, le pooling fonctionne correctement — l'avertissement est excessivement prudent.
