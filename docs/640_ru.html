Абстрактный исполнитель операций JDBC, использующий шаблонный метод. 95 строк. Это основа для всех низкоуровневых операций JDBC в ProjectForge — DatabaseExecutorImpl создаёт анонимные подклассы для каждого SQL-вызова. Этот класс управляет жизненным циклом соединения, позволяя подклассам определять что происходит с выражением.

Шаблонный метод — execute(String sql, boolean ignoreErrors, Object... args):

  1. Получение соединения: dataSource.getConnection() — получает сырое JDBC-соединение из пула (или напрямую в тестовом режиме)
  2. Подготовка выражения: con.prepareStatement(sql) — создаёт PreparedStatement
  3. Привязка параметров: перебирает args[] и вызывает stmt.setObject(i+1, args[i]) — обратите внимание на преобразование i+1: параметры JDBC имеют нумерацию с 1 (спецификация JDBC), в то время как массивы Java — с 0. Это частая причина ошибок, если забыть
  4. Делегирование: вызывает execute(stmt) — абстрактный метод, переопределяемый подклассами. Возвращаемое значение типизировано как Object, поскольку подклассы возвращают разные типы: null для DDL, List<DatabaseResultRow> для запросов, Integer для обновлений/количеств
  5. Обработка ошибок: если перехвачено SQLException и ignoreErrors=true, записывает ошибку на уровне ERROR и возвращает null. Если ignoreErrors=false, оборачивает в RuntimeException и пробрасывает — это непроверяемое исключение по дизайну; вызывающим не нужен try-catch для SQL-ошибок

Очистка ресурсов (блок finally): Сначала закрывает PreparedStatement, затем Connection. Каждое закрытие в собственном try-catch — если закрытие выражения выбрасывает исключение, соединение всё равно закрывается. Критический нюанс: если любое из закрытий выбрасывает исключение, устанавливается флаг static boolean hasErrors. После обоих закрытий, если произошли ошибки, выбрасывается RuntimeException. Это гарантирует, что ошибки утечки ресурсов не будут молча проглочены — вызывающий узнает, что очистка ресурсов не удалась.

Абстрактный метод — execute(PreparedStatement stmt): Реализуется анонимными подклассами в DatabaseExecutorImpl для 4 различных операций: выполнение DDL (stmt.execute()), запрос (stmt.executeQuery() + маппинг ResultSet), скалярный запрос (rs.getInt(1)) и обновление (stmt.executeUpdate()).

Отсутствие пула соединений: В Javadoc предупреждается «соединения могут теряться» — этот класс получает Connection через DataSource.getConnection() и закрывает его в finally. Это корректно для пулированных DataSource (закрытие возвращает соединение в пул), но автор беспокоился о прямых соединениях DriverManager в тестовом режиме, где каждый вызов открывает новое TCP-соединение. В продакшене с HikariCP пулинг работает отлично — предупреждение излишне осторожно.
