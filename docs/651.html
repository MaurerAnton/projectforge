#651: V7_0_0_6__MigrateEmployeeAndCarryVacationDays.java

Lines: 157 · Type: Java Flyway migration — extends BaseJavaMigration

Second Java-based Flyway migration — migrates employee vacation carry-over data and fixes employee timestamp timezone issues. 157 lines. This is a complex data migration (not schema migration) that runs during the v7.0.0 upgrade. Uses Spring's JdbcTemplate and SimpleJdbcInsert (obtained from a SingleConnectionDataSource that wraps Flyway's connection) — this is the only migration that uses Spring JDBC, because it needs row-level data transformation that would be painfully verbose in raw SQL.

Part 1 — migrateEmployeesCarryVacationDays(DataSource): In pre-v7, remaining vacation days were stored as a previousyearleave attribute on the employee entity with no year tracking. In v7, they're in a separate t_employee_vacation_remaining table with a year column. This migration: (1) Looks up when v7.0.0 was installed from t_flyway_schema_version.installed_on to determine the migration year. (2) Queries t_fibu_employee_attr joined to t_fibu_employee to find all previousyearleave attributes. (3) For each entry, determines the year from the attribute's modifiedat timestamp (adjusted to UTC). (4) Bug fix logic: if the determined year is later than the v7 install year, caps it to the install year — handles a known bug where the cron job for updating vacation days failed due to a Kotlin NPE in EmployeeAttrDO.parent after v7 upgrade. (5) Inserts into t_employee_vacation_remaining using SimpleJdbcInsert with auto-generated pk values.

Part 2 — migrateEmployeeTable(DataSource): Fixes employee date fields (eintritt = start date, austritt = end date, birthday) that were stored as TIMESTAMP but should be DATE (date-only). The time component was set inconsistently depending on timezone. The migration: (1) Reads the configured timezone from t_configuration. (2) For each employee, converts the timestamp to a LocalDate using ensureMidnight() — if the time is after noon (hour > 12), adjusts to midnight of the next day; if between midnight and noon, adjusts to midnight of the same day. Birthdays are always treated as UTC (stored at midnight UTC). (3) Updates the employee row with the corrected DATE-only values.

Robustness: All database operations are wrapped in try-catch — if t_configuration doesn't exist (fresh install), falls back to system default timezone. If t_flyway_schema_version has no v7.0.0 entry (fresh database), uses current year. If any query returns no results, logs "No entries found (OK, if feature wasn't used.)" — the migration is designed to succeed on any database state.
