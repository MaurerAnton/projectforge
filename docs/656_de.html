Interface für die Zugriffskontrolle pro DO im „restricted“-Anwendungsmodus. 87 Zeilen. Das Javadoc besagt: „Alle Methoden dieses Interfaces sollten von jeder DOAccessControl-Klasse implementiert werden, die von jeder DO-Klasse im access-type='restricted'-Anwendungsmodus (Produktivmodus) benötigt wird.“ – dies gilt für Produktionsumgebungen, in denen die Zugriffskontrolle auf DO-Ebene durchgesetzt werden muss.

Fünf CRUD-Prüfmethoden:

  • checkFind(List list, PFUserDO user) — Post-Query-Filterung. Die Liste wurde bereits aus der Datenbank geladen. Die Implementierung kann Einträge entfernen, die der Benutzer nicht sehen soll (gibt gefilterte Liste zurück). Dies ist die einzige Methode, die die Liste verändert – alle anderen werfen bei Verweigerung Ausnahmen
  • checkLoad(Object obj, PFUserDO user) — wird beim Laden eines einzelnen Objekts anhand der ID aufgerufen. Wenn der Benutzer es nicht sehen soll, wird eine AccessException geworfen
  • checkSave(Object obj, PFUserDO user) — wird vor INSERT aufgerufen. Kann Objekteigenschaften ändern (z. B. owner auf aktuellen Benutzer setzen), um Zugriffsregeln zu erfüllen
  • checkUpdate(Object obj, PFUserDO user) — wird vor UPDATE aufgerufen. Gleiche Änderungsfähigkeit wie save
  • checkDestroy(Object obj, PFUserDO user) — wird vor DELETE aufgerufen. Keine Änderung – nur erlauben oder verweigern

Entwurfsphilosophie: CheckSave/CheckUpdate können das Objekt verändern, um Zugriffsregeln durchzusetzen (z. B. das Objekt dem aktuellen Benutzer erzwingend zuordnen), während CheckLoad/CheckDestroy dies nicht können – sie erlauben oder werfen eine Ausnahme. Dies ist der Ansatz der Vor-AOP-Ära zur Zugriffskontrolle, bevor @PreAuthorize-Annotationen und die Methodensicherheit von Spring Security zum Standard wurden. Das Interface verwendet rohe Object-Typen – keine Generics – da es auf Framework-Ebene arbeitet, wo DO-Typen zur Kompilierzeit nicht bekannt sind.
