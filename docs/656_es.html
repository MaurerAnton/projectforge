#656: AccessControlInterface.java

projectforge-business/src/main/java/org/projectforge/framework/access/AccessControlInterface.java Líneas: 87 · Autor: Kai Reinhard · Tipo: Interfaz Java — contrato de control de acceso a nivel DO 87 líneas · 12 código · 65 comentarios · 10 en blanco

Interfaz para control de acceso por DO en modo de aplicación "restringido". 87 líneas. El Javadoc indica: "Todos los métodos de esta interfaz deben ser implementados por cada clase DOAccessControl necesaria para cada clase DO en modo de aplicación access-type='restricted' (modo productivo)". — esto es para despliegues en producción donde el control de acceso debe aplicarse a nivel de DO.

Cinco métodos de verificación CRUD:

  • checkFind(List list, PFUserDO user) — filtrado posterior a la consulta. La lista ya está cargada desde la base de datos. La implementación puede eliminar entradas que el usuario no debería ver (devuelve la lista filtrada). Este es el único método que modifica la lista — todos los demás lanzan excepciones ante una denegación
  • checkLoad(Object obj, PFUserDO user) — se llama al cargar un objeto individual por ID. Si el usuario no debería verlo, lanza AccessException
  • checkSave(Object obj, PFUserDO user) — se llama antes de INSERT. Puede modificar propiedades del objeto (ej. establecer owner al usuario actual) para cumplir con las reglas de acceso
  • checkUpdate(Object obj, PFUserDO user) — se llama antes de UPDATE. Misma capacidad de modificación que save
  • checkDestroy(Object obj, PFUserDO user) — se llama antes de DELETE. Sin modificación — solo permitir o denegar

Filosofía de diseño: CheckSave/CheckUpdate pueden modificar el objeto para aplicar reglas de acceso (ej. forzar la propiedad del objeto al usuario actual), mientras que CheckLoad/CheckDestroy no pueden — o permiten o lanzan una excepción. Este es el enfoque de control de acceso de la era pre-AOP, antes de que las anotaciones @PreAuthorize y la seguridad de métodos de Spring Security se convirtieran en estándar. La interfaz utiliza tipos Object sin procesar — sin genéricos — porque opera a nivel de framework donde los tipos DO no se conocen en tiempo de compilación.
