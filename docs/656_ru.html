#656: AccessControlInterface.java

projectforge-business/src/main/java/org/projectforge/framework/access/AccessControlInterface.java Строк: 87 · Автор: Kai Reinhard · Тип: Java-интерфейс — контракт контроля доступа на уровне DO 87 строк · 12 кода · 65 комментариев · 10 пустых

Интерфейс для контроля доступа к каждому DO в «ограниченном» режиме приложения. 87 строк. В Javadoc сказано: «Все методы этого интерфейса должны быть реализованы каждым классом DOAccessControl, необходимым для каждого класса DO в режиме приложения с типом доступа 'restricted' (продуктивный режим)». — это для продуктивных развёртываний, где контроль доступа должен применяться на уровне DO.

Пять методов проверки CRUD:

  • checkFind(List list, PFUserDO user) — пост-запросная фильтрация. Список уже загружен из базы данных. Реализация может удалять записи, которые пользователь не должен видеть (возвращает отфильтрованный список). Это единственный метод, который изменяет список — все остальные выбрасывают исключения при отказе
  • checkLoad(Object obj, PFUserDO user) — вызывается при загрузке одного объекта по ID. Если пользователь не должен его видеть, выбрасывает AccessException
  • checkSave(Object obj, PFUserDO user) — вызывается перед INSERT. Может изменять свойства объекта (например, устанавливать owner на текущего пользователя) для соблюдения правил доступа
  • checkUpdate(Object obj, PFUserDO user) — вызывается перед UPDATE. Такая же возможность модификации, как и у save
  • checkDestroy(Object obj, PFUserDO user) — вызывается перед DELETE. Без модификации — только разрешить или запретить

Философия дизайна: CheckSave/CheckUpdate могут изменять объект для применения правил доступа (например, принудительно назначать владельца объекта текущему пользователю), тогда как CheckLoad/CheckDestroy не могут — они либо разрешают, либо выбрасывают исключение. Это подход к контролю доступа из эпохи до AOP, до того как аннотации @PreAuthorize и метод-секьюрити Spring Security стали стандартом. Интерфейс использует сырые типы Object — без дженериков — потому что он работает на уровне фреймворка, где типы DO неизвестны на этапе компиляции.
