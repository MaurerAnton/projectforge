What it does

This is the release manager's cookbook — a 13-step checklist for publishing a new ProjectForge version. It covers the entire pipeline from version bump to SourceForge upload. Every step is a manual action (not automated in CI), meaning a human release manager executes this sequentially.

The document is written in AsciiDoc (.adoc) — a lightweight markup language similar to Markdown but more powerful for technical documentation (tables of contents, cross-references, conditional output).

Step-by-step breakdown

1Update changelogsEdit site/_changelogs with new release notes. This is the user-facing documentation of what changed.
2Sort i18n + fix headersRun DevelopmentMainForRelease.kt — a one-shot Kotlin script that alphabetically sorts I18nResources*.properties files and adds/repairs GPLv3 license headers. Prevents merge conflicts from unsorted keys.
3Set release versionEdit build.gradle.kts line 9: version = "8.0". This is the single source of truth for the version string — see documentation for file #1.
4Build./gradlew clean build — compiles, tests, packages. The clean ensures no stale artifacts from previous builds.
5TestManual verification: check that all tests pass AND the application starts with both new and existing databases. This catches schema migration bugs that unit tests might miss.
6Upload JAR to SourceForgeCopy projectforge-application-*.jar to SourceForge — the primary distribution channel. Tag as default for all platforms.
7aDocker: read docsRefer to /docker/README.adoc for Docker-specific instructions.
7b–eDocker: build and pushdocker buildx build --platform linux/arm64,linux/amd64 — multi-architecture Docker image (ARM64 for Apple Silicon/Mac, AMD64 for x86 servers). Uses buildx for cross-platform builds.
7fDocker: verifyCheck Docker Hub — both arm64 and amd64 images should be available.
8Git Flow: finish releaseMerge the release branch into master AND develop. Follows Git Flow conventions.
9TagTag master with the version number (e.g. v8.0). This creates a permanent reference for reproducing builds.
10–11Bump to next SNAPSHOTSwitch to develop, increment version to 8.0.1-SNAPSHOT. This ensures new development doesn't conflict with the released version.
12–13Push + upload artifactsCommit everything, push to GitHub, upload JARs to GitHub Releases and SourceForge.

Technical details

Why multi-arch Docker?

Step 7e builds for both linux/arm64 and linux/amd64. Without this, Mac users (Apple Silicon) would get emulated x86 performance instead of native ARM speed. The buildx tool creates a multi-platform manifest — Docker Hub serves the correct architecture automatically.

Why SourceForge + Docker Hub + GitHub?

Three distribution channels for different audiences:

ChannelAudienceFormat
SourceForgeTraditional download usersJAR file
Docker HubContainer usersDocker image
GitHub ReleasesDevelopers, CI/CDJAR + source

Optional buildx setup (lines 42–46)

The docker buildx builder only needs to be created once. The commands at the bottom are run once per machine — they set up a buildx instance named mybuilder that can produce multi-architecture images.

Key takeaways

  • 47 lines, one purpose: Release checklist — no automation, human-executed.
  • Single source of truth (step 3): build.gradle.kts line 9 is the only place to change the version.
  • Step 5 is critical: Testing with both new AND existing databases catches schema migration bugs.
  • Multi-arch Docker (step 7e): ARM64 + AMD64 — covers both Mac and Intel servers.
  • SNAPSHOT bump (step 11): Essential for Git Flow — prevents version conflicts between release and development.
