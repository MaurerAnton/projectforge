#706 : HibernateMapper.java

Étend le MapperWrapper de XStream (patron Décorateur) pour servir de mappeur central pour toute sérialisation XStream compatible Hibernate. Il remplit deux fonctions critiques : (1) substituer les classes d'implémentation de collection internes d'Hibernate par leurs équivalents JDK standard lors de la détermination des implémentations par défaut pendant le marshalling/unmarshalling, et (2) détecter les instances HibernateProxy en vérifiant les interfaces implémentées et en résolvant leurs vrais noms de superclasse pour le nommage des éléments XML. C'est le plus complet des composants XStream pour Hibernate — il gère PersistentBag (que l'ancien HibernateCollectionsMapper omet) et détecte également les wrappers HibernateProxy ignorés par HibernateCollectionsMapper.

Architecture

Hiérarchie des classes

HibernateMapper étend com.thoughtworks.xstream.mapper.MapperWrapper, la classe de base pour les décorateurs de mappeur XStream. Deux constructeurs acceptent soit un délégué MapperWrapper soit un Mapper simple et appellent init() pour remplir la carte de substitution des collections.

Table de mappage des collections

La méthode init() remplit une Map<Class<?>, Class<?>> avec six correspondances Hibernate→JDK :

Collection persistante HibernateRemplacement JDK
PersistentBagArrayList
PersistentListArrayList
PersistentMapHashMap
PersistentSetHashSet
PersistentSortedMapTreeMap
PersistentSortedSetTreeSet
Contrairement à HibernateCollectionsMapper, ce mappeur inclut PersistentBag — la collection Hibernate par défaut pour les champs List non indexés déclarés sans @OrderColumn. C'est le type de collection le plus courant dans les entités ProjectForge et son absence dans l'ancien mappeur constitue une lacune notable.

Méthodes redéfinies

defaultImplementationOf(Class clazz)

Appelée par XStream lorsqu'il doit instancier une classe concrète pour une interface ou un type abstrait (par exemple, lors de la désérialisation d'un champ List, XStream demande quelle implémentation créer). Si la classe demandée se trouve dans la collectionMap, le remplacement JDK est renvoyé. Cela garantit que le XML désérialisé produit des objets ArrayList/HashSet simples plutôt que des implémentations spécifiques à Hibernate qui seraient inutilisables sans session Hibernate.

serializedClass(Class clazz)

Appelée par XStream pour déterminer le nom de classe à écrire dans le XML. Cette méthode effectue une vérification en deux étapes :

  1. Détection HibernateProxy : Parcourt clazz.getInterfaces() à la recherche de HibernateProxy.class. Si trouvé, renvoie clazz.getSuperclass().getName() — le vrai nom de la classe d'entité. Cela garantit que <org.projectforge.business.user.UserDO> apparaît dans le XML plutôt que <org.projectforge.business.user.UserDO_$$_jvstXXX> (le nom de proxy généré par Javassist).
  2. Substitution de collection : Si la classe se trouve dans la collectionMap, renvoie le nom complet du remplacement JDK.
  3. Repli : Délègue au mappeur encapsulé via super.serializedClass(clazz).

Points d'intégration

  • Encapsule le mappeur XStream de base lors de la construction des instances XStream pour l'export XML. Appliqué une fois lors de l'initialisation de XStream.
  • Fonctionne avec HibernateProxyConverter pour la gestion des proxies : le mappeur corrige le nom de classe écrit dans le XML, tandis que le convertisseur corrige les données d'instance marshallées.
  • Complète HibernateCollectionConverter : le mappeur gère la résolution de type, le convertisseur gère le marshalling des valeurs.
  • HibernateMapper et HibernateCollectionsMapper (#703) ne doivent pas être actifs simultanément — ils effectueraient une double substitution et causeraient des problèmes. HibernateMapper est l'implémentation préférée, plus complète.
  • Utilisé par l'infrastructure d'import/export XML incluant XStreamMarshallingStrategy.

Décisions de conception & pièges

  • Détection de proxy via vérification d'interface : Parcourir getInterfaces() pour trouver HibernateProxy est quelque peu fragile — cela suppose que le proxy Javassist/CGLIB implémente HibernateProxy comme l'une de ses interfaces. Dans Hibernate 5.x moderne, c'est fiable, mais d'autres frameworks de proxy (comme les proxies @Transactional de Spring) peuvent ne pas implémenter cette interface. Le code contient des lignes de débogage System.err.println commentées suggérant un débogage itératif.
  • Nom de superclasse pour les proxies : Appeler clazz.getSuperclass().getName() fonctionne car les proxies Hibernate sont générés comme sous-classes de la classe d'entité (ex. UserDO_$$_jvstXXX extends UserDO). C'est correct pour le nom de la classe mais ne gère pas le cas où la chaîne de proxy est plus profonde (proxies CGLIB imbriqués).
  • Substitution basée sur une carte : Utiliser une HashMap pour collectionMap est plus propre et plus maintenable que les tableaux parallèles dans HibernateCollectionsMapper. Ajouter de nouvelles correspondances est une modification d'une ligne dans init().
  • Surcharges de constructeurs : Deux constructeurs acceptant à la fois MapperWrapper et Mapper simple suggèrent que cette classe a évolué au fil du temps et doit s'intégrer à différents points de la chaîne de décorateurs de mappeurs.
