projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/HibernateProxyXPathMarshaller.java Marshaller XStream — marshaller de référence basé sur XPath qui dépaquette les proxies Hibernate lors du parcours du graphe d’entités, projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/HibernateProxyXPathMarshaller.java 56 lignes · 25 code · 25 commentaires · 6 vides
Étend le ReferenceByXPathMarshaller de XStream pour intercepter la méthode convertAnother() — le point de répartition central où XStream passe d’un objet à un autre lors de la sérialisation XML d’un graphe d’entités. Avant de déléguer à la classe parente pour le suivi des références basé sur XPath, il dépaquette tout HibernateProxy vers son implémentation réelle d’entité. Cela garantit que le suivi des références de XStream opère sur l’identité réelle de l’entité plutôt que sur l’identité du proxy, évitant ainsi la sérialisation en double de la même entité apparaissant à la fois par des références directes et par proxy. C’est un composant essentiel pour sérialiser les graphes d’entités JPA contenant des associations bidirectionnelles avec chargement paresseux.

Architecture

Hiérarchie des classes

HibernateProxyXPathMarshaller étend com.thoughtworks.xstream.core.ReferenceByXPathMarshaller, qui étend lui-même AbstractReferenceMarshaller (qui étend TreeMarshaller). La hiérarchie de marshalling XStream est :

TreeMarshaller
  └── AbstractReferenceMarshaller       (ajoute le suivi des références d’objets)
       ├── ReferenceByXPathMarshaller   (utilise des expressions XPath pour les références)
       │    └── HibernateProxyXPathMarshaller  (cette classe — ajoute le dépaquetage des proxies)
       └── ReferenceByIdMarshaller      (utilise les attributs ID/IDREF pour les références)
            └── ProxyIdRefMarshaller    (#708 — stratégie alternative basée sur l’ID)
Les deux classes HibernateProxyXPathMarshaller et ProxyIdRefMarshaller résolvent le même problème (marshalling compatible proxy) mais utilisent des modes de référence XStream différents : XPath vs. ID/IDREF. Le choix entre elles est effectué par XStreamMarshallingStrategy (utilise XPath) et la ProxyIdRefMarshallingStrategy (utilise ID/IDREF).

convertAnother(Object item, Converter converter)

C’est la seule méthode redéfinie — le point unique où le dépaquetage du proxy est injecté dans le flux de marshalling XPath :

  1. Détection du proxy : Vérifie HibernateProxy.class.isAssignableFrom(item.getClass()). Utilise isAssignableFrom plutôt que instanceof car item peut être passé dans un contexte non nul où le type statique est plus large.
  2. Dépaquetage : Appelle ((HibernateProxy) item).getHibernateLazyInitializer().getImplementation() pour obtenir l’entité réelle. Cela déclenche le chargement paresseux si le proxy n’a pas été initialisé.
  3. Délégation : Passe l’objet dépaqueté toConvert à super.convertAnother(toConvert, converter), qui gère le suivi des références XPath et l’écriture XML.

Mode de référence XPath

Le ReferenceByXPathMarshaller de XStream gère les références circulaires en écrivant des expressions XPath (par exemple, <task reference="../../../task">) au lieu de sérialiser deux fois le même objet. Le paramètre mode contrôle si ces expressions XPath sont relatives ou absolues. Les chemins relatifs rendent le XML plus résistant aux changements structurels et sont généralement préférés pour le XML orienté document.

Points d’intégration

  • Créé par : XStreamMarshallingStrategy, qui passe le mode RELATIVE. C’est le seul endroit où HibernateProxyXPathMarshaller est instancié — la stratégie agit comme une fabrique.
  • Opère dans : Le pipeline de marshalling arborescent de XStream. Lorsque XStream parcourt un graphe d’objets, il appelle convertAnother() pour chaque référence d’objet qu’il rencontre.
  • Référence JIRA XSTR-226 : Le commentaire source // http://jira.codehaus.org/browse/XSTR-226 renvoie au problème JIRA Codehaus original qui a motivé cette classe — une limitation connue dans XStream où les proxies Hibernate cassaient le mécanisme de suivi des références. Cette classe est le correctif pour ce problème.

Décisions de conception & pièges

  • Dépaquetage du proxy vs. suivi des références compatible proxy : Une conception alternative consisterait à modifier le suivi des références lui-même pour qu’il soit compatible proxy (mapper l’identité du proxy à l’identité réelle de l’objet). Cette classe adopte l’approche plus simple : dépaqueter avant d’entrer dans le tracker de références. La conséquence est que getImplementation() force l’initialisation — un accès à la base de données pour les proxies paresseux.
  • Mode XPath codé en dur au niveau de la stratégie : Le mode n’est pas configurable par appel — il est fixé au moment de la construction par la stratégie. XStreamMarshallingStrategy passe toujours RELATIVE. Si des XPaths absolus étaient nécessaires, une nouvelle classe de stratégie serait requise.
  • Potentiel d’initialisation en double : Si à la fois HibernateProxyConverter et ce marshaller sont actifs dans le même pipeline XStream, un proxy pourrait être dépaqueté deux fois. Cependant, le second dépaquetage sur un proxy déjà initialisé est une opération sans coût (Hibernate retourne la même instance d’implémentation).
  • Classe au niveau du package : Comme la plupart des classes de ce package, HibernateProxyXPathMarshaller a une visibilité de package (public class mais le package est interne). Elle est exposée publiquement uniquement pour permettre à la classe de stratégie de la construire.
