#710: ProxyIdRefMarshaller.java

projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/ProxyIdRefMarshaller.java XStream-Marshaller — ID-basierter Referenz-Marshaller mit CGLIB-Proxy-Entfernung, Hibernate-Proxy-Entpackung und Vermeidung zirkulärer Referenzen, projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/ProxyIdRefMarshaller.java 91 Zeilen · 54 Code · 24 Kommentare · 13 leer
Erweitert XStreams ReferenceByIdMarshaller, um eine robuste Serialisierung von Entitätsgraphen mit drei Ebenen der Proxy-Behandlung zu ermöglichen: (1) Entfernt Spring CGLIB Enhancer-Proxies durch Durchlaufen der Superklassenkette, (2) entpackt Hibernate-Proxies via HibernateProxyHelper.get() und (3) weist jedem veränderbaren Objekt inkrementelle numerische IDs zu und schreibt ID/IDREF-Referenzen, wenn dasselbe Objekt erneut angetroffen wird. Dies verhindert Endlosschleifen durch bidirektionale JPA-Assoziationen und stellt sicher, dass die Entitätsidentität (Datenbank-ID) im serialisierten XML erhalten bleibt – dieselbe Entität, die in mehreren Assoziationspfaden erscheint, wird nur einmal serialisiert, mit nachfolgenden Erscheinungen als <entity reference="3"/>. Dies ist der ausgefeilteste Proxy-bewusste Marshaller in der ProjectForge XStream-Brückenschicht.

Konstruktoren

Zwei Konstruktor-Überladungen:

  1. Vollständiger Konstruktor: Akzeptiert HierarchicalStreamWriter, ConverterLookup, Mapper und IDGenerator. Ermöglicht benutzerdefinierte ID-Generierungsstrategien.
  2. Bequemlichkeitskonstruktor: Lässt den IDGenerator-Parameter weg und verwendet standardmäßig SequenceGenerator(1) — erzeugt sequenzielle numerische IDs beginnend bei 1.

convertAnother(Object item) — Kernalgorithmus

Dies ist die überschriebene Methode, in der die gesamte Proxy-Behandlung und Referenzverfolgung stattfindet. Sie ersetzt XStreams standardmäßiges convertAnother() durch Proxy-bewusste Logik:

  1. CGLIB Enhancer-Entfernung (Zeilen ~56-59): 
    Class<?> targetClass = item.getClass();
while (Enhancer.isEnhanced(targetClass)) {
    targetClass = targetClass.getSuperclass();
}
    Durchläuft die Superklassenkette und entfernt Spring CGLIB-Proxies (erstellt durch @Transactional, @Cacheable, usw.). Enhancer.isEnhanced() gibt true für CGLIB-generierte Unterklassen zurück. Dies geschieht vor der Converter-Suche, damit der korrekte Entitäts-Converter ausgewählt wird.
  2. Converter-Suche (Zeile ~61): 
    Converter converter = converterLookup.lookupConverterForType(targetClass);
    Findet den passenden XStream-Converter für die echte (nicht-proxierte) Entitätsklasse.
  3. Hibernate-Proxy-Entpackung (Zeile ~62): 
    Object realItem = HibernateProxyHelper.get(item);
    Verwendet HibernateProxyHelper, um Hibernate-Lazy-Loading-Proxies zu entpacken. Nach diesem Schritt ist realItem die tatsächliche Entitätsinstanz ohne Proxy-Wrapper.
  4. Schnellpfad für unveränderliche Werttypen (Zeilen ~64-66): 
    if (classMapper.isImmutableValueType(realItem.getClass())) {
    converter.marshal(item, writer, this);
}
    Zeichenketten, Ganzzahlen, Datumsangaben, Aufzählungen und andere unveränderliche Typen werden direkt ohne ID-Verfolgung marshalliert. Dies vermeidet, dass das Referenzwörterbuch mit Werten überfrachtet wird, die niemals zirkuläre Referenzen bilden können.
  5. Erkennung doppelter Referenzen (Zeilen ~67-70): 
    Object idOfExistingReference = references.lookupId(realItem);
if (idOfExistingReference != null) {
    writer.addAttribute("reference", idOfExistingReference.toString());
    return;
}
    Überprüft das ObjectIdDictionary, ob realItem bereits serialisiert wurde. Wenn ja, wird ein reference-Attribut geschrieben (z.B. reference="3"), das auf die frühere Serialisierung durch ihre generierte ID verweist. Dies ist der Mechanismus, der Endlosschleifen in bidirektionalen Assoziationen verhindert – wenn XStream von einem Kind zurück zu einem Elternteil navigiert, findet es das Elternteil bereits im Wörterbuch und gibt eine Referenz aus, anstatt es erneut zu serialisieren.
  6. Erstmalige Serialisierung (Zeilen ~71-81): 
    String newId = idGenerator.next(realItem);
writer.addAttribute("id", newId);
references.associateId(realItem, newId);
converter.marshal(realItem, writer, this);
    Generiert eine neue eindeutige ID, speichert sie im Referenzwörterbuch, schreibt sie als id-Attribut auf das XML-Element und delegiert dann an den Converter für die vollständige Serialisierung. Das Element ist nun registriert, sodass zukünftige Begegnungen Schritt 5 auslösen.

ObjectIdDictionary

XStreams ObjectIdDictionary ist eine identitätsbasierte Map (verwendet System.identityHashCode() und ==-Vergleich, nicht .equals()). Dies ist entscheidend, da JPA-Entitäten equals() oft basierend auf der Datenbank-ID implementieren, die bei transienten Entitäten null sein kann. Die identitätsbasierte Verfolgung stellt sicher, dass jede Objektinstanz unabhängig von ihrer equals()-Implementierung eindeutig verfolgt wird.

Hinweis zur Hibernate-Proxy-Identität: Wenn zwei verschiedene Hibernate-Proxy-Instanzen dieselbe zugrunde liegende Entität umschließen (möglich, wenn die Entität über verschiedene Sitzungen oder Assoziationen geladen wird), würde das ObjectIdDictionary sie als unterschiedliche Objekte betrachten (unterschiedliche Identitäts-Hashes), selbst nach HibernateProxyHelper.get(). Dies kann dazu führen, dass dieselbe Datenbankzeile zweimal mit unterschiedlichen generierten IDs serialisiert wird. Dies ist eine bekannte Einschränkung der identitätsbasierten Verfolgung – die Alternative (wertbasierte Verfolgung unter Verwendung von Datenbank-IDs) würde eine spezielle Behandlung für transiente Entitäten erfordern.

Integrationspunkte

  • Erstellt von: Der ProxyIdRefMarshallingStrategy, der createMarshallingContext() überschreibt, um diesen Marshaller anstelle des standardmäßigen ReferenceByIdMarshaller zu instanziieren.
  • Alternative zu: HibernateProxyXPathMarshaller — dieser verwendet ID/IDREF-Attribute, während der andere XPath-Ausdrücke verwendet. Beide Ansätze sind gültig; die Wahl hängt davon ab, welche MarshallingStrategy konfiguriert ist.
  • Abhängigkeiten: HibernateProxyHelper zum Entpacken von Hibernate-Proxies. Verwendet das Spring Framework Enhancer zur CGLIB-Proxy-Erkennung (Kompilierabhängigkeit von spring-core).

Designentscheidungen & Fallstricke

  • Spring CGLIB-Abhängigkeit: Der Import von org.springframework.cglib.proxy.Enhancer erzeugt eine harte Abhängigkeit vom Spring Framework, was akzeptabel ist, da ProjectForge eine Spring-Anwendung ist. Diese Klasse würde jedoch außerhalb eines Spring-Kontexts ohne Änderungen nicht funktionieren.
  • Schnellpfad für unveränderliche Typen: Die Prüfung classMapper.isImmutableValueType() ist eine wichtige Optimierung. Ohne sie würde jedem Zeichenkettenliteral, jeder Ganzzahl und jedem Datum im Entitätsgraphen eine ID zugewiesen und zum Referenzwörterbuch hinzugefügt, was die Speichernutzung und XML-Ausgabe massiv aufbläht.
  • Debug-Logging: Die SLF4J-Debug-Anweisung protokolliert jede marshallierte Objektklasse. In der Produktion sollte dies auf TRACE-Ebene erfolgen, um Log-Spam bei großen Entitätsgraphen-Exporten zu vermeiden.
  • ID-Kollisionspotenzial: SequenceGenerator(1) erzeugt IDs innerhalb eines einzelnen Marshalling-Kontexts. Wenn zwei separate ProxyIdRefMarshaller-Instanzen unterschiedliche Objektgraphen innerhalb desselben XML-Dokuments serialisieren (unwahrscheinlich, aber theoretisch möglich mit XStreams MarshallingContext-Verschachtelung), könnten IDs kollidieren. Dies ist kein praktisches Problem, da jeder Marshalling-Kontext seine eigene Marshaller-Instanz verwendet.
  • Überschattung von classMapper: Sowohl diese Klasse als auch die Superklasse haben ein mapper-Feld. Der Zwei-Argumente-Konstruktor setzt this.classMapper, aber der Drei-Argumente-Konstruktor setzt beide. Der Code verwendet durchgängig this.classMapper für die lokal gespeicherte Referenz, um Verwechslungen mit dem geerbten Feld zu vermeiden.
