#710: ProxyIdRefMarshaller.java

projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/ProxyIdRefMarshaller.java Marshaller XStream — marshaller de referencias basado en ID con eliminación de proxies CGLIB, desenrollado de proxies Hibernate y prevención de referencias circulares, projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/ProxyIdRefMarshaller.java 91 líneas · 54 código · 24 comentarios · 13 en blanco
Extiende ReferenceByIdMarshaller de XStream para proporcionar una serialización robusta del grafo de entidades con tres capas de manejo de proxies: (1) elimina los proxies Spring CGLIB Enhancer recorriendo la cadena de superclases, (2) desenrolla los proxies Hibernate mediante HibernateProxyHelper.get(), y (3) asigna IDs numéricos incrementales a cada objeto mutable y escribe referencias ID/IDREF cuando el mismo objeto se encuentra nuevamente. Esto evita la recursión infinita de asociaciones JPA bidireccionales y garantiza que la identidad de la entidad (ID de base de datos) se conserve en el XML serializado — la misma entidad que aparece en múltiples rutas de asociación se serializa solo una vez, con apariciones posteriores representadas como <entity reference="3"/>. Este es el marshaller más sofisticado con conocimiento de proxies en la capa puente XStream de ProjectForge.

Constructores

Dos sobrecargas de constructores:

  1. Constructor completo: Acepta HierarchicalStreamWriter, ConverterLookup, Mapper y IDGenerator. Permite estrategias personalizadas de generación de IDs.
  2. Constructor de conveniencia: Omite el parámetro IDGenerator y usa por defecto SequenceGenerator(1) — produce IDs numéricos secuenciales comenzando en 1.

convertAnother(Object item) — Algoritmo principal

Este es el método sobrescrito donde ocurre todo el manejo de proxies y seguimiento de referencias. Reemplaza el convertAnother() predeterminado de XStream con lógica consciente de proxies:

  1. Eliminación de Enhancer CGLIB (líneas ~56-59): 
    Class<?> targetClass = item.getClass();
while (Enhancer.isEnhanced(targetClass)) {
    targetClass = targetClass.getSuperclass();
}
    Recorre la cadena de superclases eliminando los proxies Spring CGLIB (creados por @Transactional, @Cacheable, etc.). Enhancer.isEnhanced() devuelve true para subclases generadas por CGLIB. Esto se hace antes de la búsqueda del converter para que se seleccione el converter de entidad correcto.
  2. Búsqueda de converter (línea ~61): 
    Converter converter = converterLookup.lookupConverterForType(targetClass);
    Encuentra el converter XStream apropiado para la clase de entidad real (sin proxy).
  3. Desenrollado de proxy Hibernate (línea ~62): 
    Object realItem = HibernateProxyHelper.get(item);
    Utiliza HibernateProxyHelper para desenrollar los proxies de carga perezosa de Hibernate. Después de este paso, realItem es la instancia de entidad real sin envoltorios de proxy.
  4. Ruta rápida para tipos de valor inmutables (líneas ~64-66): 
    if (classMapper.isImmutableValueType(realItem.getClass())) {
    converter.marshal(item, writer, this);
}
    Strings, enteros, fechas, enums y otros tipos inmutables se marshallan directamente sin seguimiento de ID. Esto evita contaminar el diccionario de referencias con valores que nunca pueden formar referencias circulares.
  5. Detección de referencias duplicadas (líneas ~67-70): 
    Object idOfExistingReference = references.lookupId(realItem);
if (idOfExistingReference != null) {
    writer.addAttribute("reference", idOfExistingReference.toString());
    return;
}
    Verifica el ObjectIdDictionary para ver si realItem ya ha sido serializado. Si es así, escribe un atributo reference (ej., reference="3") apuntando a la serialización anterior mediante su ID generado. Este es el mecanismo que evita la recursión infinita en asociaciones bidireccionales — cuando XStream vuelve a un padre desde un hijo, encuentra el padre ya en el diccionario y emite una referencia en lugar de re-serializar.
  6. Serialización por primera vez (líneas ~71-81): 
    String newId = idGenerator.next(realItem);
writer.addAttribute("id", newId);
references.associateId(realItem, newId);
converter.marshal(realItem, writer, this);
    Genera un nuevo ID único, lo almacena en el diccionario de referencias, lo escribe como atributo id en el elemento XML, luego delega al converter para la serialización completa. El elemento ahora está registrado para que futuros encuentros ejecuten el paso 5.

ObjectIdDictionary

El ObjectIdDictionary de XStream es un mapa basado en identidad (usa System.identityHashCode() y comparación ==, no .equals()). Esto es crítico porque las entidades JPA a menudo implementan equals() basado en el ID de base de datos, que puede ser null para entidades transitorias. El seguimiento basado en identidad garantiza que cada instancia de objeto se rastree de manera única independientemente de su implementación de equals().

Advertencia sobre identidad de proxy Hibernate: Si dos instancias diferentes de proxy Hibernate envuelven la misma entidad subyacente (posible cuando la entidad se carga a través de diferentes sesiones o asociaciones), el ObjectIdDictionary las vería como objetos diferentes (diferentes hashes de identidad) incluso después de HibernateProxyHelper.get(). Esto puede causar que la misma fila de base de datos se serialice dos veces con diferentes IDs generados. Esta es una limitación conocida del seguimiento basado en identidad — la alternativa (seguimiento basado en valor usando IDs de base de datos) requeriría manejo especial para entidades transitorias.

Puntos de integración

  • Creado por: La ProxyIdRefMarshallingStrategy, que sobrescribe createMarshallingContext() para instanciar este marshaller en lugar del ReferenceByIdMarshaller predeterminado.
  • Alternativa a: HibernateProxyXPathMarshaller — este usa atributos ID/IDREF mientras que el otro usa expresiones XPath. Ambos son enfoques válidos; la elección depende de qué MarshallingStrategy esté configurada.
  • Depende de: HibernateProxyHelper para el desenrollado de proxies Hibernate. Utiliza el Enhancer de Spring Framework para la detección de proxies CGLIB (dependencia de compilación en spring-core).

Decisiones de diseño y trampas

  • Dependencia de Spring CGLIB: La importación de org.springframework.cglib.proxy.Enhancer crea una dependencia fuerte de Spring Framework, lo cual es aceptable ya que ProjectForge es una aplicación Spring. Sin embargo, esta clase no funcionaría fuera de un contexto Spring sin modificación.
  • Ruta rápida para inmutables: La verificación classMapper.isImmutableValueType() es una optimización importante. Sin ella, cada literal de cadena, entero y fecha en el grafo de entidades recibiría un ID y se agregaría al diccionario de referencias, inflando masivamente el uso de memoria y la salida XML.
  • Registro de depuración: La declaración de depuración SLF4J registra cada clase de objeto marshalled. En producción, esto debería estar a nivel TRACE para evitar spam de registros durante exportaciones grandes de grafos de entidades.
  • Potencial de colisión de IDs: SequenceGenerator(1) produce IDs dentro de un único contexto de marshalling. Si dos instancias separadas de ProxyIdRefMarshaller serializan diferentes grafos de objetos dentro del mismo documento XML (poco probable pero teóricamente posible con el anidamiento de MarshallingContext de XStream), los IDs podrían colisionar. Esto no es una preocupación práctica porque cada contexto de marshalling usa su propia instancia de marshaller.
  • Sombreado de classMapper: Tanto esta clase como la superclase tienen un campo mapper. El constructor de dos argumentos establece this.classMapper pero el constructor de tres argumentos establece ambos. El código usa consistentemente this.classMapper para la referencia almacenada localmente, evitando confusión con el campo heredado.
