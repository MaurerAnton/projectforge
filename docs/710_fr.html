#710 : ProxyIdRefMarshaller.java

projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/ProxyIdRefMarshaller.java Marshaller XStream — marshaller de références basé sur l'ID avec suppression des proxies CGLIB, déballage des proxies Hibernate et prévention des références circulaires, projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/ProxyIdRefMarshaller.java 91 lignes · 54 lignes de code · 24 commentaires · 13 lignes vides
Étend ReferenceByIdMarshaller de XStream pour fournir une sérialisation robuste du graphe d'entités avec trois couches de gestion des proxies : (1) supprime les proxies Spring CGLIB Enhancer en remontant la chaîne des superclasses, (2) déballage des proxies Hibernate via HibernateProxyHelper.get(), et (3) attribue des identifiants numériques incrémentaux à chaque objet mutable et écrit des références ID/IDREF lorsque le même objet est rencontré à nouveau. Cela empêche la récursion infinie due aux associations JPA bidirectionnelles et garantit que l'identité de l'entité (ID de base de données) est préservée dans le XML sérialisé — la même entité apparaissant dans plusieurs chemins d'association est sérialisée une seule fois, les apparitions suivantes étant rendues sous la forme <entity reference="3"/>. C'est le marshaller le plus sophistiqué avec gestion des proxies dans la couche de pont XStream de ProjectForge.

Constructeurs

Deux surcharges de constructeurs :

  1. Constructeur complet : Accepte HierarchicalStreamWriter, ConverterLookup, Mapper et IDGenerator. Permet des stratégies de génération d'ID personnalisées.
  2. Constructeur de commodité : Omet le paramètre IDGenerator et utilise par défaut SequenceGenerator(1) — produit des ID numériques séquentiels commençant à 1.

convertAnother(Object item) — Algorithme principal

C'est la méthode surchargée où toute la gestion des proxies et le suivi des références ont lieu. Elle remplace le convertAnother() par défaut de XStream par une logique consciente des proxies :

  1. Suppression de l'Enhancer CGLIB (lignes ~56-59) : 
    Class<?> targetClass = item.getClass();
while (Enhancer.isEnhanced(targetClass)) {
    targetClass = targetClass.getSuperclass();
}
    Remonte la chaîne des superclasses en supprimant les proxies Spring CGLIB (créés par @Transactional, @Cacheable, etc.). Enhancer.isEnhanced() retourne vrai pour les sous-classes générées par CGLIB. Ceci est fait avant la recherche du convertisseur afin que le convertisseur d'entité correct soit sélectionné.
  2. Recherche du convertisseur (ligne ~61) : 
    Converter converter = converterLookup.lookupConverterForType(targetClass);
    Trouve le convertisseur XStream approprié pour la classe d'entité réelle (non proxyfiée).
  3. Déballage du proxy Hibernate (ligne ~62) : 
    Object realItem = HibernateProxyHelper.get(item);
    Utilise HibernateProxyHelper pour déballer les proxies de chargement différé Hibernate. Après cette étape, realItem est l'instance d'entité réelle sans aucun wrapper de proxy.
  4. Chemin rapide pour les types de valeur immuables (lignes ~64-66) : 
    if (classMapper.isImmutableValueType(realItem.getClass())) {
    converter.marshal(item, writer, this);
}
    Les chaînes, entiers, dates, énumérations et autres types immuables sont marshallés directement sans suivi d'ID. Cela évite de polluer le dictionnaire de références avec des valeurs qui ne peuvent jamais former de références circulaires.
  5. Détection des références dupliquées (lignes ~67-70) : 
    Object idOfExistingReference = references.lookupId(realItem);
if (idOfExistingReference != null) {
    writer.addAttribute("reference", idOfExistingReference.toString());
    return;
}
    Vérifie le ObjectIdDictionary pour voir si realItem a déjà été sérialisé. Si c'est le cas, écrit un attribut reference (par exemple, reference="3") pointant vers la sérialisation précédente par son ID généré. C'est le mécanisme qui empêche la récursion infinie dans les associations bidirectionnelles — lorsque XStream revient à un parent depuis un enfant, il trouve le parent déjà dans le dictionnaire et émet une référence au lieu de re-sérialiser.
  6. Première sérialisation (lignes ~71-81) : 
    String newId = idGenerator.next(realItem);
writer.addAttribute("id", newId);
references.associateId(realItem, newId);
converter.marshal(realItem, writer, this);
    Génère un nouvel ID unique, le stocke dans le dictionnaire de références, l'écrit comme attribut id sur l'élément XML, puis délègue au convertisseur pour la sérialisation complète. L'élément est maintenant enregistré, donc les rencontres futures passeront par l'étape 5.

ObjectIdDictionary

Le ObjectIdDictionary de XStream est une carte basée sur l'identité (utilise System.identityHashCode() et la comparaison ==, pas .equals()). C'est crucial car les entités JPA implémentent souvent equals() basé sur l'ID de base de données, qui peut être nul pour les entités transientes. Le suivi basé sur l'identité garantit que chaque instance d'objet est suivie de manière unique indépendamment de son implémentation de equals().

Mise en garde sur l'identité des proxies Hibernate : Si deux instances de proxy Hibernate différentes encapsulent la même entité sous-jacente (possible lorsque l'entité est chargée via différentes sessions ou associations), le ObjectIdDictionary les verrait comme des objets différents (différents hashcodes d'identité) même après HibernateProxyHelper.get(). Cela peut entraîner la sérialisation deux fois de la même ligne de base de données avec des ID générés différents. C'est une limitation connue du suivi basé sur l'identité — l'alternative (suivi basé sur la valeur utilisant les ID de base de données) nécessiterait un traitement spécial pour les entités transientes.

Points d'intégration

  • Créé par : La ProxyIdRefMarshallingStrategy, qui surcharge createMarshallingContext() pour instancier ce marshaller au lieu du ReferenceByIdMarshaller par défaut.
  • Alternative à : HibernateProxyXPathMarshaller — celui-ci utilise des attributs ID/IDREF tandis que l'autre utilise des expressions XPath. Les deux approches sont valides ; le choix dépend de la MarshallingStrategy configurée.
  • Dépend de : HibernateProxyHelper pour le déballage des proxies Hibernate. Utilise l'Enhancer du framework Spring pour la détection des proxies CGLIB (dépendance de compilation sur spring-core).

Décisions de conception & Pièges

  • Dépendance Spring CGLIB : L'import de org.springframework.cglib.proxy.Enhancer crée une dépendance forte envers le framework Spring, ce qui est acceptable puisque ProjectForge est une application Spring. Cependant, cette classe ne fonctionnerait pas en dehors d'un contexte Spring sans modification.
  • Chemin rapide pour les immuables : La vérification classMapper.isImmutableValueType() est une optimisation importante. Sans elle, chaque littéral de chaîne, entier et date dans le graphe d'entités se verrait attribuer un ID et serait ajouté au dictionnaire de références, gonflant massivement l'utilisation mémoire et la sortie XML.
  • Journalisation de débogage : L'instruction de débogage SLF4J enregistre chaque classe d'objet marshallé. En production, cela devrait être au niveau TRACE pour éviter le spam de journal lors des exportations de grands graphes d'entités.
  • Potentiel de collision d'ID : SequenceGenerator(1) produit des ID dans un seul contexte de marshalling. Si deux instances distinctes de ProxyIdRefMarshaller sérialisent différents graphes d'objets dans le même document XML (peu probable mais théoriquement possible avec l'imbrication du MarshallingContext de XStream), les ID pourraient entrer en collision. Ce n'est pas une préoccupation pratique car chaque contexte de marshalling utilise sa propre instance de marshaller.
  • Masquage de classMapper : Cette classe et la superclasse ont toutes deux un champ mapper. Le constructeur à deux arguments définit this.classMapper mais le constructeur à trois arguments définit les deux. Le code utilise systématiquement this.classMapper pour la référence stockée localement, évitant ainsi toute confusion avec le champ hérité.
