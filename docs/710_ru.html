#710: ProxyIdRefMarshaller.java

projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/ProxyIdRefMarshaller.java Маршаллер XStream — маршаллер ссылок на основе ID с удалением CGLIB-прокси, разворачиванием Hibernate-прокси и предотвращением циклических ссылок, projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/ProxyIdRefMarshaller.java 91 строка · 54 кода · 24 комментария · 13 пустых
Расширяет ReferenceByIdMarshaller от XStream для обеспечения надежной сериализации графа сущностей с тремя уровнями обработки прокси: (1) удаляет Spring CGLIB-прокси Enhancer путем обхода цепочки суперклассов, (2) разворачивает Hibernate-прокси через HibernateProxyHelper.get() и (3) присваивает инкрементальные числовые ID каждому изменяемому объекту и записывает ссылки ID/IDREF при повторной встрече того же объекта. Это предотвращает бесконечную рекурсию из-за двунаправленных JPA-связей и гарантирует, что идентичность сущности (ID в БД) сохраняется в сериализованном XML — одна и та же сущность, появляющаяся в нескольких путях ассоциаций, сериализуется только один раз, а последующие появления отображаются как <entity reference="3"/>. Это самый сложный прокси-ориентированный маршаллер в слое моста XStream ProjectForge.

Конструкторы

Две перегрузки конструктора:

  1. Полный конструктор: Принимает HierarchicalStreamWriter, ConverterLookup, Mapper и IDGenerator. Позволяет использовать пользовательские стратегии генерации ID.
  2. Упрощенный конструктор: Опускает параметр IDGenerator и по умолчанию использует SequenceGenerator(1) — создает последовательные числовые ID, начиная с 1.

convertAnother(Object item) — Основной алгоритм

Это переопределенный метод, в котором происходит вся обработка прокси и отслеживание ссылок. Он заменяет стандартный convertAnother() XStream на логику с поддержкой прокси:

  1. Удаление CGLIB Enhancer (строки ~56-59): 
    Class<?> targetClass = item.getClass();
while (Enhancer.isEnhanced(targetClass)) {
    targetClass = targetClass.getSuperclass();
}
    Поднимается по цепочке суперклассов, удаляя Spring CGLIB-прокси (созданные @Transactional, @Cacheable и т.д.). Enhancer.isEnhanced() возвращает true для CGLIB-сгенерированных подклассов. Это делается до поиска конвертера, чтобы был выбран правильный конвертер сущностей.
  2. Поиск конвертера (строка ~61): 
    Converter converter = converterLookup.lookupConverterForType(targetClass);
    Находит подходящий конвертер XStream для реального (без прокси) класса сущности.
  3. Разворачивание Hibernate-прокси (строка ~62): 
    Object realItem = HibernateProxyHelper.get(item);
    Использует HibernateProxyHelper для разворачивания Hibernate-прокси ленивой загрузки. После этого шага realItem — это реальный экземпляр сущности без прокси-оберток.
  4. Быстрый путь для неизменяемых типов (строки ~64-66): 
    if (classMapper.isImmutableValueType(realItem.getClass())) {
    converter.marshal(item, writer, this);
}
    Строки, целые числа, даты, перечисления и другие неизменяемые типы маршаллируются напрямую без отслеживания ID. Это предотвращает загрязнение словаря ссылок значениями, которые никогда не могут образовывать циклические ссылки.
  5. Обнаружение дублирующихся ссылок (строки ~67-70): 
    Object idOfExistingReference = references.lookupId(realItem);
if (idOfExistingReference != null) {
    writer.addAttribute("reference", idOfExistingReference.toString());
    return;
}
    Проверяет ObjectIdDictionary на наличие realItem в уже сериализованных. Если найден, записывает атрибут reference (например, reference="3"), указывающий на предыдущую сериализацию по сгенерированному ID. Это механизм, предотвращающий бесконечную рекурсию в двунаправленных ассоциациях — когда XStream возвращается к родителю от дочернего элемента, он находит родителя уже в словаре и выдает ссылку вместо повторной сериализации.
  6. Первичная сериализация (строки ~71-81): 
    String newId = idGenerator.next(realItem);
writer.addAttribute("id", newId);
references.associateId(realItem, newId);
converter.marshal(realItem, writer, this);
    Генерирует новый уникальный ID, сохраняет его в словаре ссылок, записывает как атрибут id в XML-элементе, затем делегирует конвертеру полную сериализацию. Теперь элемент зарегистрирован, так что будущие встречи приведут к шагу 5.

ObjectIdDictionary

ObjectIdDictionary от XStream — это карта на основе идентичности (использует System.identityHashCode() и сравнение ==, а не .equals()). Это критически важно, поскольку JPA-сущности часто реализуют equals() на основе ID в БД, который может быть null для транзиентных сущностей. Отслеживание на основе идентичности гарантирует уникальное отслеживание каждого экземпляра объекта независимо от реализации equals().

Особенность идентичности Hibernate-прокси: Если два разных экземпляра Hibernate-прокси оборачивают одну и ту же базовую сущность (возможно, когда сущность загружается через разные сессии или ассоциации), ObjectIdDictionary увидит их как разные объекты (разные хеши идентичности) даже после HibernateProxyHelper.get(). Это может привести к тому, что одна и та же строка БД будет сериализована дважды с разными сгенерированными ID. Это известное ограничение отслеживания на основе идентичности — альтернатива (отслеживание на основе значений с использованием ID БД) потребовала бы специальной обработки для транзиентных сущностей.

Точки интеграции

  • Создается: Стратегией ProxyIdRefMarshallingStrategy, которая переопределяет createMarshallingContext() для создания этого маршаллера вместо стандартного ReferenceByIdMarshaller.
  • Альтернатива: HibernateProxyXPathMarshaller — этот использует атрибуты ID/IDREF, тогда как другой использует XPath-выражения. Оба подхода валидны; выбор зависит от того, какая MarshallingStrategy сконфигурирована.
  • Зависит от: HibernateProxyHelper для разворачивания Hibernate-прокси. Использует Enhancer от Spring Framework для обнаружения CGLIB-прокси (зависимость компиляции от spring-core).

Проектные решения и подводные камни

  • Зависимость от Spring CGLIB: Импорт org.springframework.cglib.proxy.Enhancer создает жесткую зависимость от Spring Framework, что приемлемо, поскольку ProjectForge — Spring-приложение. Однако этот класс не будет работать вне Spring-контекста без модификации.
  • Быстрый путь для неизменяемых: Проверка classMapper.isImmutableValueType() — важная оптимизация. Без нее каждой строке, целому числу и дате в графе сущностей присваивался бы ID и добавлялся в словарь ссылок, что сильно увеличило бы использование памяти и объем XML.
  • Отладочное логирование: SLF4J-отладка логирует каждый класс маршаллированного объекта. В продакшене это должно быть на уровне TRACE, чтобы избежать спама в логах при экспорте больших графов сущностей.
  • Потенциальная коллизия ID: SequenceGenerator(1) создает ID в рамках одного контекста маршаллинга. Если два отдельных экземпляра ProxyIdRefMarshaller сериализуют разные графы объектов в одном XML-документе (маловероятно, но теоретически возможно при вложенности MarshallingContext от XStream), ID могут конфликтовать. Это не является практической проблемой, поскольку каждый контекст маршаллинга использует свой собственный экземпляр маршаллера.
  • Затенение classMapper: И этот класс, и суперкласс имеют поле mapper. Двухаргументный конструктор устанавливает this.classMapper, но трехаргументный устанавливает оба. Код последовательно использует this.classMapper для локально хранимой ссылки, избегая путаницы с унаследованным полем.
