Propósito: Al serializar entidades JPA a XML (para almacenamiento de historial en base de datos, copia de seguridad/restauración XML e intercambio de datos entre plugins), Hibernate crea objetos proxy (subclases mejoradas con cglib) para asociaciones cargadas de forma perezosa. El marshalling estándar de XStream serializaría estos proxies con sus nombres de clase wrapper cglib y campos internos, produciendo XML ilegible y no deserializable. Esta estrategia intercepta el proceso de marshalling para desempaquetar proxies y serializar solo datos de entidad reales con seguimiento de referencias (deduplicación basada en ID).

Arquitectura

Patrón Estrategia — Delegación Compuesta

La clase extiende ReferenceByIdMarshallingStrategy (de XStream) y sobrescribe solo dos métodos:

marshal() → Crea un nuevo ProxyIdRefMarshaller (NO el estándar ReferenceByIdMarshaller). El ProxyIdRefMarshaller desempaqueta proxies de Hibernate mediante HibernateProxyHelper.get(), elimina las mejoras cglib con Enhancer.isEnhanced() y maneja el seguimiento de referencias usando un ObjectIdDictionary interno.

unmarshal() → Utiliza el estándar ReferenceByIdUnmarshaller de XStream. La deserialización ya recibe XML limpio (los proxies se eliminaron durante el marshal), por lo que no se necesita un manejo especial en el lado de lectura.

Este diseño asimétrico refleja la realidad de que los problemas de proxy existen solo en el momento de la serialización — la salida XML siempre es «limpia».

Jerarquía de Herencia

El Problema del Proxy de Hibernate

Qué sucede sin esta estrategia:

1. La entidad JPA AddressDO tiene un @ManyToOne(fetch = LAZY) hacia AddressbookDO
2. Hibernate crea un proxy cglib: AddressbookDO$$EnhancerByCGLIB$$a1b2c3d4@123
3. XStream estándar serializa esto como: <addressbook class="AddressbookDO$$EnhancerByCGLIB$$a1b2c3d4">...internos de hibernate...</addressbook>
4. Resultado: XML ilegible, rompe la deserialización, filtra internos de Hibernate

Con ProxyIdRefMarshallingStrategy:

1. Enhancer.isEnhanced(targetClass) → detecta proxy cglib, asciende a la superclase
2. HibernateProxyHelper.get(item) → extrae la entidad real detrás del proxy
3. references.lookupId(realItem) → si ya se vio, emite el atributo reference="ID" (sin duplicación de datos)
4. De lo contrario, emite id="ID" y serializa los datos de la entidad real

Resultado: XML limpio con nombres de clase reales, sin internos de Hibernate y con deduplicación basada en referencias.

Seguimiento de Referencias — Evitando Referencias Circulares

El ProxyIdRefMarshaller mantiene un ObjectIdDictionary (mapa hash de identidad). Para cada objeto no inmutable que encuentra:

• Primer encuentro: Asigna un ID mediante SequenceGenerator, lo almacena en el diccionario, serializa el objeto completo
• Encuentros posteriores: Emite solo el atributo reference="ID", omitiendo el cuerpo del objeto

Esto es crítico porque los grafos de entidades JPA a menudo contienen ciclos: AddressDO → AddressbookDO → owner → addresses → AddressDO. Sin seguimiento de referencias, XStream entraría en recursión infinita. Con él, las referencias cíclicas se convierten en etiquetas compactas <addressbook reference="42"/>.

Los objetos inmutables se excluyen del seguimiento de referencias (classMapper.isImmutableValueType()): Strings, Integers, Dates, etc. siempre se serializan en línea. Esto evita contaminar la tabla de referencias con miles de entradas de tipo valor.

Commits Clave

9ebb88522 (commit inicial): ProxyIdRefMarshallingStrategy se introdujo junto con toda la capa de persistencia XStream. En ese momento, ProjectForge usaba XStream para:
• Historial de Base de Datos: Serializar instantáneas de entidades antes/después de modificaciones en una columna de tabla de historial
• Importación/Exportación XML: Intercambio de datos entre plugins y scripts de migración
• Preferencias de Usuario: Serializar configuraciones de usuario como blobs XML

La estrategia era un prerrequisito para estas funcionalidades — sin un marshalling seguro para proxies, las instantáneas de historial de entidades con relaciones perezosas se corromperían.

Sin cambios de lógica desde el commit inicial: El archivo solo ha recibido actualizaciones de año de copyright. El algoritmo (detección cglib → desempaquetado de proxy → seguimiento de referencias) ha demostrado ser estable a lo largo de más de 5 años de actualizaciones de versiones de Hibernate y XStream.

Decisiones de Diseño

DecisiónPor quéCompensación
Extender ReferenceByIdMarshallingStrategy en lugar de implementar desde cero Reutiliza el formato de cable de referencia por ID de XStream (atributos id/reference) que está bien documentado y es comprendido Acoplamiento fuerte a la jerarquía interna de clases de XStream — podría romperse en actualizaciones mayores de XStream
Marshal/unmarshal asimétrico (personalizado solo en escritura) Los problemas de proxy solo existen en tiempo de serialización; los objetos deserializados nunca son proxies Si la deserialización comienza a recibir XML con proxies (ej. de fuentes externas), surgirían problemas
Usar Enhancer.isEnhanced() (cglib) directamente XStream 1.4.x no tenía detección integrada de proxies de Hibernate; esta era la única forma fiable Dependencia directa de cglib — necesitaría actualización si Hibernate 6+ cambia de cglib a proxies ByteBuddy
Clase ProxyIdRefMarshaller separada (no en línea) Marshaller es la clase «pesada» con ~70 líneas de lógica de proxy; Strategy es una clase delgada de delegación de 25 líneas Añade un archivo extra al espacio de nombres, pero sigue el Principio de Responsabilidad Única
Advertencia — Proxies ByteBuddy de Hibernate 6+: ProjectForge 8.x usa Hibernate 5.x con cglib. Si se actualiza a Hibernate 6.x, Enhancer.isEnhanced() no detectará proxies ByteBuddy (Hibernate 6 reemplazó cglib con ByteBuddy). La lógica de detección de proxies necesitaría actualizarse para soportar ambos: Enhancer.isEnhanced() de cglib y la detección de proxies de ByteBuddy (Hibernate.isInitialized() + Hibernate.unproxy()). Este es un riesgo de migración conocido para futuras actualizaciones de Hibernate.
Dónde se usa: Registrada como la estrategia de marshalling predeterminada de XStream en XmlRegistry. Cada operación XStream en ProjectForge — instantáneas de historial, copia de seguridad/restauración XML, serialización de preferencias de usuario — pasa por esta estrategia. Los componentes XmlObjectWriter y XmlObjectReader (el framework xmlstream) usan XStream internamente, por lo que esta estrategia es efectivamente la «puerta de enlace» para toda la E/S XML en la aplicación.
