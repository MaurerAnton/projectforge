Objectif : Lors de la sérialisation d'entités JPA en XML (pour le stockage d'historique en base de données, la sauvegarde/restauration XML et l'échange de données entre plugins), Hibernate crée des objets proxy (sous-classes enrichies par cglib) pour les associations chargées paresseusement. Le marshalling XStream standard sérialiserait ces proxies avec leurs noms de classe wrapper cglib et leurs champs internes, produisant un XML illisible et non désérialisable. Cette stratégie intercepte le processus de marshalling pour déballer les proxies et sérialiser uniquement les données réelles de l'entité avec un suivi des références (déduplication basée sur l'ID).

Architecture

Patron Stratégie — Délégation Composite

La classe étend ReferenceByIdMarshallingStrategy (de XStream) et ne surcharge que deux méthodes :

marshal() → Crée un nouveau ProxyIdRefMarshaller (PAS le ReferenceByIdMarshaller standard). Le ProxyIdRefMarshaller déballage les proxies Hibernate via HibernateProxyHelper.get(), supprime les enrichissements cglib via Enhancer.isEnhanced(), et gère le suivi des références à l'aide d'un ObjectIdDictionary interne.

unmarshal() → Utilise le standard ReferenceByIdUnmarshaller de XStream. La désérialisation reçoit déjà un XML propre (les proxies ont été supprimés lors du marshal), donc aucun traitement spécial n'est nécessaire côté lecture.

Cette conception asymétrique reflète la réalité selon laquelle les problèmes de proxy n'existent qu'au moment de la sérialisation — la sortie XML est toujours « propre ».

Hiérarchie d'Héritage

ReferenceByIdMarshallingStrategy          (base XStream)
  └── ProxyIdRefMarshallingStrategy       (#709 — ce fichier)
        ├── marshal()  → ProxyIdRefMarshaller  (#708)
        └── unmarshal() → ReferenceByIdUnmarshaller  (standard XStream)

Le Problème des Proxies Hibernate

Ce qui se passe sans cette stratégie :

1. L'entité JPA AddressDO a un @ManyToOne(fetch = LAZY) vers AddressbookDO
2. Hibernate crée un proxy cglib : AddressbookDO$$EnhancerByCGLIB$$a1b2c3d4@123
3. XStream standard sérialise cela comme : <addressbook class="AddressbookDO$$EnhancerByCGLIB$$a1b2c3d4">...internes Hibernate...</addressbook>
4. Résultat : XML illisible, casse la désérialisation, fuit les internes d'Hibernate

Avec ProxyIdRefMarshallingStrategy :

1. Enhancer.isEnhanced(targetClass) → détecte le proxy cglib, remonte à la superclasse
2. HibernateProxyHelper.get(item) → extrait l'entité réelle derrière le proxy
3. references.lookupId(realItem) → si déjà vu, émet l'attribut reference="ID" (pas de duplication de données)
4. Sinon, émet id="ID" et sérialise les données réelles de l'entité

Résultat : XML propre avec de vrais noms de classe, pas d'internes Hibernate, et déduplication basée sur les références.

Suivi des Références — Éviter les Références Circulaires

Le ProxyIdRefMarshaller maintient un ObjectIdDictionary (table de hachage d'identité). Pour chaque objet non immuable rencontré :

• Première rencontre : Assigne un ID via SequenceGenerator, stocke dans le dictionnaire, sérialise l'objet complet
• Rencontres suivantes : Émet uniquement l'attribut reference="ID", en ignorant le corps de l'objet

Ceci est critique car les graphes d'entités JPA contiennent souvent des cycles : AddressDO → AddressbookDO → owner → addresses → AddressDO. Sans suivi des références, XStream entrerait dans une récursion infinie. Avec celui-ci, les références cycliques deviennent des balises <addressbook reference="42"/> compactes.

Les immuables sont exclus du suivi des références (classMapper.isImmutableValueType()) : chaînes, entiers, dates, etc. toujours sérialisés en ligne. Cela évite de polluer la table de référence avec des milliers d'entrées de type valeur.

Commits Clés

9ebb88522 (commit initial) : La ProxyIdRefMarshallingStrategy a été introduite avec l'ensemble de la couche de persistance XStream. À l'époque, ProjectForge utilisait XStream pour :
• Historique base de données : Sérialisation d'instantanés d'entités avant/après modifications dans une colonne de table d'historique
• Import/Export XML : Échange de données entre plugins et scripts de migration
• Préférences utilisateur : Sérialisation des paramètres utilisateur sous forme de blobs XML

La stratégie était un prérequis pour ces fonctionnalités — sans marshalling sûr pour les proxies, les instantanés d'historique d'entités avec relations chargées paresseusement seraient corrompus.

Aucun changement de logique depuis le commit initial : Le fichier n'a reçu que des mises à jour d'année de copyright. L'algorithme (détection cglib → déballage proxy → suivi des références) s'est avéré stable sur plus de 5 ans de mises à jour de versions Hibernate et XStream.

Décisions de Conception

DécisionPourquoiCompromis
Étendre ReferenceByIdMarshallingStrategy plutôt que d'implémenter depuis zéro Réutilise le format filaire référence-par-ID de XStream (attributs id/reference) qui est bien documenté et compris Couplage fort à la hiérarchie de classes interne de XStream — pourrait casser lors de mises à jour majeures de XStream
Marshal/unmarshal asymétrique (personnalisé uniquement en écriture) Les problèmes de proxy n'existent qu'au moment de la sérialisation ; les objets désérialisés ne sont jamais des proxies Si la désérialisation commence à recevoir du XML contenant des proxies (par exemple, de sources externes), des problèmes surviendraient
Utiliser Enhancer.isEnhanced() (cglib) directement XStream 1.4.x n'avait pas de détection de proxy Hibernate intégrée ; c'était le seul moyen fiable Dépendance directe à cglib — nécessiterait une mise à jour si Hibernate 6+ passe de cglib aux proxies ByteBuddy
Classe ProxyIdRefMarshaller séparée (pas en ligne) Le Marshaller est la classe « lourde » avec ~70 lignes de logique proxy ; la Stratégie est une fine classe de délégation de 25 lignes Ajoute un fichier supplémentaire à l'espace de noms, mais suit le Principe de Responsabilité Unique
Piège — Proxies ByteBuddy Hibernate 6+ : ProjectForge 8.x utilise Hibernate 5.x avec cglib. Si vous mettez à niveau vers Hibernate 6.x, Enhancer.isEnhanced() ne détectera pas les proxies ByteBuddy (Hibernate 6 a remplacé cglib par ByteBuddy). La logique de détection des proxies devrait être mise à jour pour prendre en charge les deux : Enhancer.isEnhanced() de cglib et la détection de proxy ByteBuddy (Hibernate.isInitialized() + Hibernate.unproxy()). C'est un risque de migration connu pour les futures mises à niveau Hibernate.
Où c'est utilisé : Enregistré comme stratégie de marshalling XStream par défaut dans XmlRegistry. Chaque opération XStream dans ProjectForge — instantanés d'historique, sauvegarde/restauration XML, sérialisation des préférences utilisateur — passe par cette stratégie. Les composants XmlObjectWriter et XmlObjectReader (le framework xmlstream) utilisent XStream sous le capot, donc cette stratégie est effectivement la « passerelle » pour toutes les entrées/sorties XML de l'application.
