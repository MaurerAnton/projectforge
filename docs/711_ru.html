#711: ProxyIdRefMarshallingStrategy.java

Источник: projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/ProxyIdRefMarshallingStrategy.java 54 строки · 26 кода · 22 комментария · 6 пустых
Назначение: При сериализации JPA-сущностей в XML (для хранения истории базы данных, резервного копирования/восстановления XML и обмена данными плагинов) Hibernate создаёт прокси-объекты (подклассы, расширенные cglib) для лениво загружаемых ассоциаций. Стандартный маршалинг XStream сериализовал бы эти прокси с их именами классов-обёрток cglib и внутренними полями, создавая нечитаемый, не поддающийся десериализации XML. Эта стратегия перехватывает процесс маршалинга, чтобы развернуть прокси и сериализовать только реальные данные сущности с отслеживанием ссылок (дедупликация на основе ID).

Архитектура

Паттерн «Стратегия» — составное делегирование

Класс расширяет ReferenceByIdMarshallingStrategy (из XStream) и переопределяет только два метода:

marshal() → Создаёт новый ProxyIdRefMarshaller (НЕ стандартный ReferenceByIdMarshaller). ProxyIdRefMarshaller разворачивает прокси Hibernate через HibernateProxyHelper.get(), удаляет cglib-улучшения через Enhancer.isEnhanced() и обрабатывает отслеживание ссылок с помощью внутреннего ObjectIdDictionary.

unmarshal() → Использует стандартный ReferenceByIdUnmarshaller из XStream. Десериализация уже получает чистый XML (прокси были удалены во время маршалинга), поэтому на стороне чтения не требуется специальной обработки.

Эта асимметричная конструкция отражает реальность: проблемы с прокси существуют только во время сериализации — XML-вывод всегда «чист».

Проблема прокси Hibernate

Что происходит без этой стратегии:

1. JPA-сущность AddressDO имеет @ManyToOne(fetch = LAZY) к AddressbookDO
2. Hibernate создаёт cglib-прокси: AddressbookDO$$EnhancerByCGLIB$$a1b2c3d4@123
3. Стандартный XStream сериализует это как: <addressbook class="AddressbookDO$$EnhancerByCGLIB$$a1b2c3d4">...внутренности hibernate...</addressbook>
4. Результат: нечитаемый XML, нарушение десериализации, утечка внутренностей Hibernate

С ProxyIdRefMarshallingStrategy:

1. Enhancer.isEnhanced(targetClass) → обнаруживает cglib-прокси, поднимается до суперкласса
2. HibernateProxyHelper.get(item) → извлекает реальную сущность за прокси
3. references.lookupId(realItem) → если уже встречалось, выводит атрибут reference="ID" (без дублирования данных)
4. В противном случае выводит id="ID" и сериализует данные реальной сущности

Результат: чистый XML с реальными именами классов, без внутренностей Hibernate и с дедупликацией на основе ссылок.

Отслеживание ссылок — предотвращение циклических ссылок

ProxyIdRefMarshaller поддерживает ObjectIdDictionary (хеш-карта идентичности). Для каждого неиммутабельного объекта, который он встречает:

• Первое появление: Назначает ID через SequenceGenerator, сохраняет в словаре, сериализует полный объект
• Последующие появления: Выводит только атрибут reference="ID", пропуская тело объекта

Это критически важно, потому что графы JPA-сущностей часто содержат циклы: AddressDO → AddressbookDO → owner → addresses → AddressDO. Без отслеживания ссылок XStream вошёл бы в бесконечную рекурсию. С ним циклические ссылки становятся компактными тегами <addressbook reference="42"/>.

Иммутабельные объекты исключены из отслеживания ссылок (classMapper.isImmutableValueType()): строки, целые числа, даты и т.д. всегда сериализуются встроенно. Это предотвращает загрязнение таблицы ссылок тысячами записей значений.

Файл существует с самого первого коммита проекта. Он является частью фундаментальной интеграции XStream — одного из самых ранних архитектурных решений в ProjectForge.

Ключевые коммиты

9ebb88522 (первоначальный коммит): ProxyIdRefMarshallingStrategy была представлена вместе со всем уровнем персистентности XStream. В то время ProjectForge использовал XStream для:
• Истории базы данных: Сериализация снимков сущностей до/после изменений в столбец таблицы истории
• Импорта/Экспорта XML: Обмен данными плагинов и скрипты миграции
• Пользовательских настроек: Сериализация пользовательских настроек в виде XML-блобов

Стратегия была предварительным условием для этих функций — без безопасного маршалинга прокси снимки истории сущностей с лениво загружаемыми связями были бы повреждены.

Никаких изменений логики с момента первоначального коммита: Файл получал только обновления года авторских прав. Алгоритм (обнаружение cglib → разворачивание прокси → отслеживание ссылок) доказал свою стабильность на протяжении более 5 лет обновлений версий Hibernate и XStream.

Проектные решения

РешениеПочемуКомпромисс
Расширение ReferenceByIdMarshallingStrategy, а не реализация с нуля Повторно использует формат проводов XStream «ссылка по ID» (атрибуты id/reference), который хорошо документирован и понятен Тесная связь с внутренней иерархией классов XStream — может сломаться при крупных обновлениях XStream
Асимметричный маршалинг/анмаршалинг (только на запись) Проблемы с прокси существуют только во время сериализации; десериализованные объекты никогда не являются прокси Если десериализация начнёт получать XML, содержащий прокси (например, из внешних источников), возникнут проблемы
Использование Enhancer.isEnhanced() (cglib) напрямую XStream 1.4.x не имел встроенного обнаружения прокси Hibernate; это был единственный надёжный способ Прямая зависимость от cglib — потребует обновления, если Hibernate 6+ перейдёт с cglib на прокси ByteBuddy
Отдельный класс ProxyIdRefMarshaller (не встроенный) Marshaller — «тяжёлый» класс с ~70 строками логики прокси; Strategy — тонкий класс делегирования на 25 строк Добавляет один дополнительный файл в пространство имён, но следует принципу единственной ответственности
Особенность — прокси ByteBuddy в Hibernate 6+: ProjectForge 8.x использует Hibernate 5.x с cglib. При обновлении до Hibernate 6.x Enhancer.isEnhanced() не обнаружит прокси ByteBuddy (Hibernate 6 заменил cglib на ByteBuddy). Логику обнаружения прокси потребуется обновить для поддержки обоих: cglib Enhancer.isEnhanced() и обнаружения прокси ByteBuddy (Hibernate.isInitialized() + Hibernate.unproxy()). Это известный риск миграции для будущих обновлений Hibernate.
Где используется: Зарегистрирована как стратегия маршалинга XStream по умолчанию в XmlRegistry. Каждая операция XStream в ProjectForge — снимки истории, резервное копирование/восстановление XML, сериализация пользовательских настроек — проходит через эту стратегию. Компоненты XmlObjectWriter и XmlObjectReader (фреймворк xmlstream) используют XStream под капотом, поэтому эта стратегия фактически является «шлюзом» для всего XML-ввода/вывода в приложении.
