#712: XStreamMarshallingStrategy.java

projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/XStreamMarshallingStrategy.java XStream-Marshalling-Strategie — Factory, die Hibernate-Proxy-bewusstes XPath-Marshalling in XStreams Baum-Serialisierungspipeline einbindet, projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/XStreamMarshallingStrategy.java 49 Zeilen · 18 Code · 25 Kommentare · 6 leer
Erweitert XStreams ReferenceByXPathMarshallingStrategy, um als übergeordnete Verbindungsebene zu dienen, die den Hibernate-Proxy-bewussten Marshaller mit XStreams Serialisierungs-Engine verbindet. Dies ist die Strategieklasse, die XStream verwenden soll – sie überschreibt die Factory-Methode createMarshallingContext(), um den standardmäßigen XPath-Marshaller durch HibernateProxyXPathMarshaller zu ersetzen und so Hibernate-Proxy-Bewusstsein in jeden XStream-Serialisierungsvorgang einzubringen. Dies ist der einzige Konfigurationspunkt, der die gesamte XStream+Hibernate-Brückenschicht funktionsfähig macht. Ohne diese Strategie würde keiner der Converter-, Mapper- oder Marshaller-Klassen in diesem Paket während der XStream-Serialisierung aktiviert werden.

Architektur

Klassenhierarchie

MarshallingStrategy (Schnittstelle)
  └── AbstractTreeMarshallingStrategy
       ├── ReferenceByXPathMarshallingStrategy  (XPath-basierte Behandlung zirkulärer Referenzen)
       │    └── XStreamMarshallingStrategy       (diese Klasse – tauscht HibernateProxyXPathMarshaller ein)
       └── ReferenceByIdMarshallingStrategy      (ID/IDREF-basierte Behandlung zirkulärer Referenzen)
            └── ProxyIdRefMarshallingStrategy     (#709 – tauscht ProxyIdRefMarshaller ein)

Konstruktor

public XStreamMarshallingStrategy(int mode) {
    super(mode);
}

Akzeptiert eine XPath-Referenzmodus-Konstante (RELATIVE, ABSOLUTE, SINGLE_NODE usw.) und übergibt sie an die Oberklasse. Der Modus steuert, wie XPath-Ausdrücke für Rückverweise in zirkulären Entitätsgraphen erzeugt werden.

createMarshallingContext() — Die Factory-Methode

@Override
protected TreeMarshaller createMarshallingContext(
    HierarchicalStreamWriter writer,
    ConverterLookup converterLookup,
    Mapper mapper)
{
    return new HibernateProxyXPathMarshaller(writer, converterLookup, mapper, RELATIVE);
}

Dies ist die einzige überschriebene Methode – ein Paradebeispiel für das Template-Methoden-Muster. Die Oberklasse ReferenceByXPathMarshallingStrategy ruft createMarshallingContext() immer dann auf, wenn sie einen TreeMarshaller benötigt, um einen Objektgraphen zu serialisieren. Anstatt den standardmäßigen ReferenceByXPathMarshaller zurückzugeben, gibt diese Überschreibung eine HibernateProxyXPathMarshaller-Instanz zurück.

Fest codierter RELATIVE-Modus: Obwohl der Konstruktor einen mode-Parameter akzeptiert, codiert die Überschreibung von createMarshallingContext() fest RELATIVE, anstatt den Modus der Instanz zu verwenden. Dies bedeutet, dass der Konstruktorparameter für die Marshaller-Erstellung faktisch ignoriert wird. Falls ein anderer XPath-Modus benötigt würde, müsste diese Klasse geändert oder eine Unterklasse mit einer anderen Überschreibung erstellt werden.

Integrationspunkte

  • XStream-Konfiguration: Wird auf einer XStream-Instanz gesetzt via xstream.setMarshallingStrategy(new XStreamMarshallingStrategy(ReferenceByXPathMarshallingStrategy.RELATIVE)). Dies geschieht typischerweise einmalig beim Anwendungsstart, wenn die XStream-Instanz für den XML-Export konfiguriert wird.
  • Erzeugt: HibernateProxyXPathMarshaller als Marshaller für alle Serialisierungsvorgänge.
  • Geschwisterstrategie: ProxyIdRefMarshallingStrategy – bietet dasselbe Proxy-bewusste Marshalling, jedoch unter Verwendung von ID/IDREF-Attributen anstelle von XPath-Referenzen. Beide Strategien dienen demselben Zweck, verwenden jedoch unterschiedliche XML-Referenzmechanismen. Die Anwendung kann basierend auf den XML-Formatpräferenzen zwischen ihnen wählen.
  • Verweist auf JIRA XSTR-226: Der Quellkommentar verlinkt auf das Codehaus-JIRA-Problem, das die ursprüngliche Inkompatibilität von XStream/Hibernate-Proxys dokumentierte.

Wie die gesamte Brückenschicht zusammenspielt

Wenn XStream einen JPA-Entitätsgraphen in ProjectForge serialisiert, wird die folgende Pipeline ausgeführt:

  1. XStreamMarshallingStrategy (diese Klasse) wird aufgerufen, um einen Marshalling-Kontext zu erstellen.
  2. Sie instanziiert HibernateProxyXPathMarshaller als Baum-Marshaller.
  3. Während der Marshaller den Objektgraphen durchläuft, ruft er convertAnother() auf, was HibernateProxy-Instanzen entpackt, bevor es an XStreams Referenzverfolgung delegiert.
  4. Wenn XStream eine bestimmte Klasse konvertieren muss, löst HibernateMapper den Klassennamen auf (ersetzt Proxy-Namen durch echte Entitätsnamen und Hibernate-Collection-Namen durch JDK-Collection-Namen).
  5. Wenn XStream auf eine PersistentCollection trifft, erzwingt HibernateCollectionConverter die Initialisierung und delegiert an den entsprechenden JDK-Collection-Converter.
  6. Wenn XStream auf einen HibernateProxy trifft, entpackt HibernateProxyConverter ihn vor der Serialisierung zur echten Entität.

Entwurfsentscheidungen & Fallstricke

  • Template-Methoden-Muster: Die Strategie verwendet das Template-Methoden-Muster – die Oberklasse definiert den Algorithmus (wie ein Objektgraph marshallt wird), und diese Unterklasse stellt die spezifische TreeMarshaller-Implementierung bereit. Dies ist der kanonische XStream-Erweiterungspunkt für benutzerdefiniertes Marshalling-Verhalten.
  • Fest codierter RELATIVE-Modus: Die feste Codierung von RELATIVE in createMarshallingContext() bedeutet, dass der mode-Parameter des Konstruktors rudimentär ist. Dies ist wahrscheinlich ein Versehen oder eine bewusste Entscheidung, um sicherzustellen, dass Proxy-bewusstes Marshalling unabhängig von den übergebenen Werten immer relative XPaths verwendet. In der Praxis ist RELATIVE der robusteste Modus für Entitätsgraphen, da Entitätshierarchien während der Refaktorisierung verschoben werden können.
  • Minimale Implementierung: Diese Klasse umfasst nur etwa 20 Zeilen – die eigentliche Arbeit wird an HibernateProxyXPathMarshaller delegiert. Dies ist ein gutes Beispiel für das Single-Responsibility-Prinzip: Die Aufgabe der Strategie ist es, Komponenten zu verbinden, nicht die Marshalling-Logik zu implementieren.
  • Keine Converter oder Mapper hier registriert: Diese Strategie befasst sich nur mit dem Marshaller. Converter (HibernateCollectionConverter, HibernateProxyConverter) und Mapper (HibernateCollectionsMapper, HibernateMapper) werden separat auf der XStream-Instanz registriert. Die Strategie weiß nichts von ihnen – sie arbeiten unabhängig auf ihren jeweiligen Ebenen.
