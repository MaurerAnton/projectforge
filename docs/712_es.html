#712: XStreamMarshallingStrategy.java

projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/XStreamMarshallingStrategy.java Estrategia de marshalling de XStream — fábrica que integra el marshalling XPath consciente de proxies de Hibernate en el pipeline de serialización de árbol de XStream, projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/XStreamMarshallingStrategy.java 49 líneas · 18 código · 25 comentarios · 6 en blanco
Extiende ReferenceByXPathMarshallingStrategy de XStream para servir como la plomería de alto nivel que conecta el marshaller consciente de proxies de Hibernate con el motor de serialización de XStream. Esta es la clase de estrategia que XStream está configurado para usar — sobrescribe el método de fábrica createMarshallingContext() para reemplazar el marshaller XPath predeterminado con HibernateProxyXPathMarshaller, inyectando conciencia de proxies de Hibernate en cada operación de serialización de XStream. Este es el punto de configuración único que hace que toda la capa de puente XStream+Hibernate esté operativa. Sin esta estrategia, ninguna de las clases de convertidor, mapeador o marshaller en este paquete se activaría durante la serialización de XStream.

Arquitectura

Constructor

public XStreamMarshallingStrategy(int mode) {
    super(mode);
}

Acepta una constante de modo de referencia XPath (RELATIVE, ABSOLUTE, SINGLE_NODE, etc.) y la pasa a la superclase. El modo controla cómo se generan las expresiones XPath para las referencias inversas en grafos de entidades circulares.

createMarshallingContext() — El método de fábrica

@Override
protected TreeMarshaller createMarshallingContext(
    HierarchicalStreamWriter writer,
    ConverterLookup converterLookup,
    Mapper mapper)
{
    return new HibernateProxyXPathMarshaller(writer, converterLookup, mapper, RELATIVE);
}

Este es el único método sobrescrito — un ejemplo clásico del patrón Template Method. La superclase ReferenceByXPathMarshallingStrategy llama a createMarshallingContext() cada vez que necesita un TreeMarshaller para serializar un grafo de objetos. En lugar de devolver el ReferenceByXPathMarshaller predeterminado, esta sobrescritura devuelve una instancia de HibernateProxyXPathMarshaller.

Modo RELATIVE hardcodeado: A pesar de que el constructor acepta un parámetro mode, la sobrescritura de createMarshallingContext() hardcodea RELATIVE en lugar de usar el modo de la instancia. Esto significa que el parámetro del constructor es efectivamente ignorado para la creación del marshaller. Si se necesitara un modo XPath diferente, esta clase requeriría modificación o una subclase con una sobrescritura diferente.

Puntos de integración

  • Configuración de XStream: Se establece en una instancia de XStream mediante xstream.setMarshallingStrategy(new XStreamMarshallingStrategy(ReferenceByXPathMarshallingStrategy.RELATIVE)). Esto se hace típicamente una vez durante el inicio de la aplicación al configurar la instancia de XStream para la exportación XML.
  • Crea: HibernateProxyXPathMarshaller como el marshaller para todas las operaciones de serialización.
  • Estrategia hermana: ProxyIdRefMarshallingStrategy — proporciona el mismo marshalling consciente de proxies pero utilizando atributos ID/IDREF en lugar de referencias XPath. Ambas estrategias sirven al mismo propósito pero utilizan diferentes mecanismos de referencia XML. La aplicación puede elegir entre ellas según las preferencias de formato XML.
  • Referencia a JIRA XSTR-226: El comentario de la fuente enlaza al issue de Codehaus JIRA que documentó la incompatibilidad original entre XStream y los proxies de Hibernate.

Cómo encaja toda la capa de puente

Cuando XStream serializa un grafo de entidades JPA en ProjectForge, se ejecuta el siguiente pipeline:

  1. XStreamMarshallingStrategy (esta clase) es invocada para crear un contexto de marshalling.
  2. Instancia HibernateProxyXPathMarshaller como el marshaller de árbol.
  3. A medida que el marshaller recorre el grafo de objetos, llama a convertAnother(), que desenvuelve instancias de HibernateProxy antes de delegar en el seguimiento de referencias de XStream.
  4. Cuando XStream necesita convertir una clase específica, HibernateMapper resuelve el nombre de la clase (sustituyendo nombres de proxy con nombres de entidad reales, y nombres de colecciones de Hibernate con nombres de colecciones de JDK).
  5. Cuando XStream encuentra una PersistentCollection, HibernateCollectionConverter fuerza la inicialización y delega en el convertidor de colecciones JDK apropiado.
  6. Cuando XStream encuentra un HibernateProxy, HibernateProxyConverter lo desenvuelve a la entidad real antes de la serialización.

Decisiones de diseño y aspectos a tener en cuenta

  • Patrón Template Method: La estrategia utiliza el patrón Template Method — la superclase define el algoritmo (cómo serializar un grafo de objetos), y esta subclase proporciona la implementación específica de TreeMarshaller. Este es el punto de extensión canónico de XStream para comportamiento de marshalling personalizado.
  • Hardcode del modo RELATIVE: El RELATIVE hardcodeado en createMarshallingContext() significa que el parámetro mode del constructor es vestigial. Esto es probablemente un descuido o una decisión deliberada para asegurar que el marshalling consciente de proxies siempre use XPaths relativos independientemente de lo que pasen los llamadores. En la práctica, RELATIVE es el modo más robusto para grafos de entidades porque las jerarquías de entidades pueden cambiar durante la refactorización.
  • Implementación mínima: Esta clase tiene solo ~20 líneas — el trabajo real se delega a HibernateProxyXPathMarshaller. Este es un buen ejemplo del Principio de Responsabilidad Única: el trabajo de la estrategia es conectar componentes, no implementar lógica de marshalling.
  • No se registran convertidores ni mapeadores aquí: Esta estrategia solo se ocupa del marshaller. Los convertidores (HibernateCollectionConverter, HibernateProxyConverter) y los mapeadores (HibernateCollectionsMapper, HibernateMapper) se registran por separado en la instancia de XStream. La estrategia no sabe nada de ellos — operan de forma independiente en sus respectivas capas.
