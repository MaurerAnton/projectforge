#712 : XStreamMarshallingStrategy.java

projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/XStreamMarshallingStrategy.java Stratégie de marshalling XStream — fabrique qui intègre le marshalling XPath compatible avec les proxies Hibernate dans le pipeline de sérialisation arborescente de XStream, projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/XStreamMarshallingStrategy.java 49 lignes · 18 code · 25 commentaires · 6 vides
Étend la ReferenceByXPathMarshallingStrategy de XStream pour servir de câblage de haut niveau qui connecte le marshaller compatible avec les proxies Hibernate au moteur de sérialisation de XStream. C'est la classe de stratégie que XStream est configuré pour utiliser — elle remplace la méthode d'usine createMarshallingContext() pour substituer le marshaller XPath par défaut par HibernateProxyXPathMarshaller, injectant ainsi la gestion des proxies Hibernate dans chaque opération de sérialisation XStream. C'est le point de configuration unique qui rend opérationnelle l'ensemble de la couche de pont XStream+Hibernate. Sans cette stratégie, aucune des classes de convertisseur, mapper ou marshaller de ce paquetage ne serait activée lors de la sérialisation XStream.

Architecture

Hiérarchie des classes

MarshallingStrategy (interface)
  └── AbstractTreeMarshallingStrategy
       ├── ReferenceByXPathMarshallingStrategy  (gestion des références circulaires basée sur XPath)
       │    └── XStreamMarshallingStrategy       (cette classe — remplace par HibernateProxyXPathMarshaller)
       └── ReferenceByIdMarshallingStrategy      (gestion des références circulaires basée sur ID/IDREF)
            └── ProxyIdRefMarshallingStrategy     (#709 — remplace par ProxyIdRefMarshaller)

Constructeur

public XStreamMarshallingStrategy(int mode) {
    super(mode);
}

Accepte une constante de mode de référence XPath (RELATIVE, ABSOLUTE, SINGLE_NODE, etc.) et la transmet à la superclasse. Le mode contrôle la façon dont les expressions XPath sont générées pour les rétro-références dans les graphes d'entités circulaires.

createMarshallingContext() — La méthode d'usine

@Override
protected TreeMarshaller createMarshallingContext(
    HierarchicalStreamWriter writer,
    ConverterLookup converterLookup,
    Mapper mapper)
{
    return new HibernateProxyXPathMarshaller(writer, converterLookup, mapper, RELATIVE);
}

C'est la seule méthode redéfinie — un exemple classique du patron Template Method. La superclasse ReferenceByXPathMarshallingStrategy appelle createMarshallingContext() chaque fois qu'elle a besoin d'un TreeMarshaller pour sérialiser un graphe d'objets. Au lieu de retourner le ReferenceByXPathMarshaller par défaut, cette redéfinition retourne une instance de HibernateProxyXPathMarshaller.

Mode RELATIVE codé en dur : Bien que le constructeur accepte un paramètre mode, la redéfinition de createMarshallingContext() code en dur RELATIVE au lieu d'utiliser le mode de l'instance. Cela signifie que le paramètre du constructeur est effectivement ignoré pour la création du marshaller. Si un mode XPath différent était nécessaire, cette classe devrait être modifiée ou une sous-classe avec une redéfinition différente serait nécessaire.

Points d'intégration

  • Configuration XStream : Défini sur une instance XStream via xstream.setMarshallingStrategy(new XStreamMarshallingStrategy(ReferenceByXPathMarshallingStrategy.RELATIVE)). Cela est généralement fait une fois au démarrage de l'application lors de la configuration de l'instance XStream pour l'export XML.
  • Crée : HibernateProxyXPathMarshaller comme marshaller pour toutes les opérations de sérialisation.
  • Stratégie sœur : ProxyIdRefMarshallingStrategy — fournit le même marshalling compatible avec les proxies mais en utilisant des attributs ID/IDREF au lieu de références XPath. Les deux stratégies servent le même objectif mais utilisent des mécanismes de référence XML différents. L'application peut choisir entre elles en fonction des préférences de format XML.
  • Référence JIRA XSTR-226 : Le commentaire source renvoie au problème JIRA Codehaus qui documentait l'incompatibilité originale entre XStream et les proxies Hibernate.

Comment l'ensemble de la couche de pont s'assemble

Lorsque XStream sérialise un graphe d'entités JPA dans ProjectForge, le pipeline suivant s'exécute :

  1. XStreamMarshallingStrategy (cette classe) est invoquée pour créer un contexte de marshalling.
  2. Elle instancie HibernateProxyXPathMarshaller comme marshaller arborescent.
  3. Lorsque le marshaller parcourt le graphe d'objets, il appelle convertAnother(), qui déballe les instances HibernateProxy avant de déléguer au suivi des références de XStream.
  4. Lorsque XStream doit convertir une classe spécifique, HibernateMapper résout le nom de la classe (en substituant les noms de proxies par les noms d'entités réels, et les noms de collections Hibernate par les noms de collections JDK).
  5. Lorsque XStream rencontre une PersistentCollection, HibernateCollectionConverter force l'initialisation et délègue au convertisseur de collection JDK approprié.
  6. Lorsque XStream rencontre un HibernateProxy, HibernateProxyConverter le déballe vers l'entité réelle avant la sérialisation.

Décisions de conception et pièges

  • Patron Template Method : La stratégie utilise le patron Template Method — la superclasse définit l'algorithme (comment marshaler un graphe d'objets), et cette sous-classe fournit l'implémentation spécifique du TreeMarshaller. C'est le point d'extension canonique de XStream pour un comportement de marshalling personnalisé.
  • Mode RELATIVE codé en dur : Le RELATIVE codé en dur dans createMarshallingContext() signifie que le paramètre mode du constructeur est vestigial. C'est probablement un oubli ou une décision délibérée pour garantir que le marshalling compatible avec les proxies utilise toujours des XPaths relatifs, indépendamment de ce que les appelants passent. En pratique, RELATIVE est le mode le plus robuste pour les graphes d'entités car les hiérarchies d'entités peuvent changer lors du refactoring.
  • Implémentation minimale : Cette classe ne fait qu'environ 20 lignes — le vrai travail est délégué à HibernateProxyXPathMarshaller. C'est un bon exemple du principe de responsabilité unique : le travail de la stratégie est de câbler les composants ensemble, pas d'implémenter la logique de marshalling.
  • Aucun convertisseur ou mapper enregistré ici : Cette stratégie ne traite que du marshaller. Les convertisseurs (HibernateCollectionConverter, HibernateProxyConverter) et les mappers (HibernateCollectionsMapper, HibernateMapper) sont enregistrés séparément sur l'instance XStream. La stratégie ne les connaît pas — ils opèrent indépendamment à leurs couches respectives.
