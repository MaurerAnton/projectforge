#712: XStreamMarshallingStrategy.java

projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/XStreamMarshallingStrategy.java Стратегия маршалинга XStream — фабрика, которая подключает Hibernate-прокси-совместимый XPath-маршалинг в конвейер древовидной сериализации XStream, projectforge-business/src/main/java/org/projectforge/framework/persistence/xstream/XStreamMarshallingStrategy.java 49 строк · 18 кода · 25 комментариев · 6 пустых
Расширяет ReferenceByXPathMarshallingStrategy от XStream, чтобы служить верхнеуровневым связующим звеном, которое соединяет Hibernate-прокси-совместимый маршаллер с движком сериализации XStream. Это класс стратегии, который XStream настроен использовать — он переопределяет фабричный метод createMarshallingContext(), чтобы заменить стандартный XPath-маршаллер на HibernateProxyXPathMarshaller, внедряя осведомлённость о Hibernate-прокси в каждую операцию сериализации XStream. Это единственная точка конфигурации, которая делает весь связующий слой XStream+Hibernate работоспособным. Без этой стратегии ни один из классов конвертера, маппера или маршаллера в этом пакете не был бы активирован во время сериализации XStream.

Архитектура

Иерархия классов

MarshallingStrategy (интерфейс)
  └── AbstractTreeMarshallingStrategy
       ├── ReferenceByXPathMarshallingStrategy  (XPath-обработка циклических ссылок)
       │    └── XStreamMarshallingStrategy       (этот класс — подставляет HibernateProxyXPathMarshaller)
       └── ReferenceByIdMarshallingStrategy      (ID/IDREF-обработка циклических ссылок)
            └── ProxyIdRefMarshallingStrategy     (#709 — подставляет ProxyIdRefMarshaller)

Конструктор

public XStreamMarshallingStrategy(int mode) {
    super(mode);
}

Принимает константу режима XPath-ссылок (RELATIVE, ABSOLUTE, SINGLE_NODE и т.д.) и передаёт её в суперкласс. Режим управляет тем, как генерируются XPath-выражения для обратных ссылок в циклических графах сущностей.

createMarshallingContext() — Фабричный метод

@Override
protected TreeMarshaller createMarshallingContext(
    HierarchicalStreamWriter writer,
    ConverterLookup converterLookup,
    Mapper mapper)
{
    return new HibernateProxyXPathMarshaller(writer, converterLookup, mapper, RELATIVE);
}

Это единственный переопределённый метод — классический шаблон «Template Method». Суперкласс ReferenceByXPathMarshallingStrategy вызывает createMarshallingContext() всякий раз, когда ему требуется TreeMarshaller для сериализации графа объектов. Вместо возврата стандартного ReferenceByXPathMarshaller эта переопределённая версия возвращает экземпляр HibernateProxyXPathMarshaller.

Жёстко заданный режим RELATIVE: Несмотря на то, что конструктор принимает параметр mode, переопределённый createMarshallingContext() жёстко задаёт RELATIVE вместо использования режима экземпляра. Это означает, что параметр конструктора фактически игнорируется при создании маршаллера. Если бы потребовался другой режим XPath, этот класс нужно было бы модифицировать или создать подкласс с другим переопределением.

Точки интеграции

  • Конфигурация XStream: Устанавливается на экземпляр XStream через xstream.setMarshallingStrategy(new XStreamMarshallingStrategy(ReferenceByXPathMarshallingStrategy.RELATIVE)). Обычно это делается один раз во время запуска приложения при настройке экземпляра XStream для экспорта XML.
  • Создаёт: HibernateProxyXPathMarshaller в качестве маршаллера для всех операций сериализации.
  • Родственная стратегия: ProxyIdRefMarshallingStrategy — обеспечивает тот же прокси-совместимый маршалинг, но с использованием атрибутов ID/IDREF вместо XPath-ссылок. Обе стратегии служат одной цели, но используют разные механизмы XML-ссылок. Приложение может выбирать между ними в зависимости от предпочтений формата XML.
  • Ссылка на JIRA XSTR-226: Комментарий в исходнике ссылается на issue Codehaus JIRA, в котором документирована исходная несовместимость XStream/Hibernate прокси.

Как работает весь связующий слой

Когда XStream сериализует граф JPA-сущностей в ProjectForge, выполняется следующий конвейер:

  1. XStreamMarshallingStrategy (этот класс) вызывается для создания контекста маршалинга.
  2. Он создаёт экземпляр HibernateProxyXPathMarshaller в качестве древовидного маршаллера.
  3. По мере того как маршаллер обходит граф объектов, он вызывает convertAnother(), который распаковывает экземпляры HibernateProxy перед делегированием отслеживанию ссылок XStream.
  4. Когда XStream требуется преобразовать конкретный класс, HibernateMapper разрешает имя класса (заменяя имена прокси на реальные имена сущностей, а имена Hibernate-коллекций — на имена JDK-коллекций).
  5. Когда XStream встречает PersistentCollection, HibernateCollectionConverter принудительно инициализирует её и делегирует соответствующему конвертеру JDK-коллекций.
  6. Когда XStream встречает HibernateProxy, HibernateProxyConverter распаковывает его до реальной сущности перед сериализацией.

Проектные решения и «подводные камни»

  • Шаблон «Template Method»: Стратегия использует шаблон «Template Method» — суперкласс определяет алгоритм (как маршалировать граф объектов), а этот подкласс предоставляет конкретную реализацию TreeMarshaller. Это каноническая точка расширения XStream для настройки поведения маршалинга.
  • Жёстко заданный режим RELATIVE: Жёстко заданный RELATIVE в createMarshallingContext() означает, что параметр mode конструктора является рудиментарным. Вероятно, это оплошность или осознанное решение, гарантирующее, что прокси-совместимый маршалинг всегда использует относительные XPath, независимо от того, что передают вызывающие стороны. На практике RELATIVE является наиболее надёжным режимом для графов сущностей, поскольку иерархии сущностей могут меняться при рефакторинге.
  • Минимальная реализация: Этот класс состоит всего из ~20 строк — реальная работа делегируется HibernateProxyXPathMarshaller. Это хороший пример принципа единственной ответственности: задача стратегии — связывать компоненты вместе, а не реализовывать логику маршалинга.
  • Конвертеры и мапперы здесь не регистрируются: Эта стратегия работает только с маршаллером. Конвертеры (HibernateCollectionConverter, HibernateProxyConverter) и мапперы (HibernateCollectionsMapper, HibernateMapper) регистрируются отдельно на экземпляре XStream. Стратегия ничего о них не знает — они работают независимо на своих уровнях.
