Zentraler PDF-Rendering-Dienst. Akzeptiert ein XSL-FO-Stylesheet, ein Groovy/XML-Template und eine Daten-Map und erzeugt ein PDF-Byte-Array unter Verwendung von Apache FOP mit XSLT-Transformation und Groovy-Vorverarbeitung.

Architektur & Verarbeitungspipeline

PdfRenderer ist ein Spring @Service mit einer einzigen öffentlichen Methode render(String stylesheet, String groovyXml, Map<String, Object> data). Die Rendering-Pipeline durchläuft vier Stufen:

1. Datenanreicherung

Vor jeder Transformation wird die Daten-Map mit Standard-Template-Variablen angereichert:

  • createdLabel — lokalisierter "erstellt"-String
  • loggedInUser — der aktuelle PFUserDO
  • baseDir — Ressourcenverzeichnispfad vom ConfigurationService
  • logoFile — vollständiger Pfad zur konfigurierten Logo-Datei
  • appId / appVersion — aus ProjectForgeVersion-Konstanten
  • organization — aus der Konfiguration (Fallback auf appId)

2. FOP-Konfiguration

Apache FOP wird konfiguriert mit:

  • Einer FopFactory, instanziiert mit der URI des Schriftarten-Ressourcenverzeichnisses
  • Einem FOUserAgent für Einstellungen auf Benutzeragenten-Ebene
  • Einem Fop-Objekt, das auf MIME_PDF-Ausgabe in einen ByteArrayOutputStream abzielt
  • Hinweis: Auskommentierter Code zeigt einen früheren Versuch mit setFontBaseURL(), der entfernt wurde

3. Groovy-Template-Vorverarbeitung

Das XML-Template (groovyXml) durchläuft zwei Durchläufe der Groovy-Engine:

  1. preprocessGroovyXml() — bereitet das Template vor
  2. executeTemplate() — führt das Groovy-Template mit der Daten-Map aus, um das endgültige XML zu erzeugen

4. XSLT-Transformation + FOP-Rendering

  • Das XSLT-Stylesheet wird über ConfigurationService.getResourceAsInputStream() aus den Ressourcen geladen
  • Ein Transformer wird mit Parametern aus der Daten-Map erstellt
  • Das von Groovy erzeugte XML wird als StreamSource-Eingabe zugeführt
  • Das Ergebnis wird als SAXResult über den Standard-Handler von FOP weitergeleitet, wodurch PDF-Bytes erzeugt werden

Fehlerbehandlung

Ausnahmen werden abgefangen und verpackt:

AusnahmeBehandlung
FOPExceptionProtokolliert und in RuntimeException verpackt
TransformerExceptionProtokolliert und in RuntimeException verpackt
IOException (beim Schließen von BAOS)Protokolliert und in RuntimeException verpackt

Der finally-Block schließt den ByteArrayOutputStream und verwendet IOUtils.closeQuietly() für den XSLT-Eingabestrom. Nach dem Schließen wird baos.toByteArray() aufgerufen – beachten Sie, dass dies funktioniert, da ByteArrayOutputStream.close() ein No-Op ist.

Spring-Integration

  • @Service — automatisch erkannter Spring-Bean
  • @Autowired — ConfigurationService injiziert
  • @Value("${projectforge.export.logoFile}") — Logo-Dateiname aus den Anwendungseigenschaften
  • Faule Initialisierung von fontResourcePath über getFontResourcePath()

Abhängigkeiten

  • Apache FOP: FopFactory, Fop, FOUserAgent, FOPException
  • JAXP XSLT: TransformerFactory, Transformer, StreamSource, SAXResult
  • Intern: ConfigurationService, GroovyEngine, Configuration, ProjectForgeVersion, ThreadLocalUserContext
  • Commons IO: IOUtils.closeQuietly()
  • Commons Lang3: StringUtils.defaultString()
