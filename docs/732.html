#732: FileHelper.java

Lines: 69 · Author: Kai Reinhard · Type: Java utility class — @Deprecated · org.projectforge.framework.utils

Purpose

A thin, now-deprecated wrapper around two newer utility classes (org.projectforge.common.FileUtils and org.projectforge.common.FilenameUtils). All methods simply delegate to the newer implementations — no logic of its own. The Javadoc explicitly says: "Deprecated: Use org.projectforge.common.FileUtils and org.projectforge.common.FilenameUtils instead."

Why does this file still exist? It's a compatibility shim. When ProjectForge migrated utility code from the framework.utils package to the common package (to be shared across modules without depending on the full framework), old code that still imported FileHelper continued working. The @Deprecated annotation is a signal to developers to update their imports — but the shim remains to avoid breaking plugins and legacy Wicket code that still reference it.

Architecture: the refactoring story

Originally, FileHelper contained the actual file utility logic. At some point, that logic was extracted into org.projectforge.common.FileUtils and org.projectforge.common.FilenameUtils — two classes with clearer names and the ability to be used by the commons module (which framework.utils depends on — the reverse dependency can't exist). This is the standard "extract to interface/shared module" refactoring, with the old class left as a delegating shim for backward compatibility. The @Deprecated annotation was added but the class was never deleted — typical of large projects where removing deprecated code risks breaking obscure references.

Methods (all static)

getAbsolutePath(String parent, String path)

If path is already absolute (starts with / on Unix or C:\ on Windows), returns it unchanged. Otherwise, resolves it relative to parent. Delegates to FileUtils.getAbsolutePath(). Used by the setup wizard (Lanterna + Swing) when the user browses directories — ensures relative path entries are resolved against the correct parent.

createSafeFilename(String str, int maxlength)

Creates a filesystem-safe filename from arbitrary user input. Converts: German umlauts → ASCII equivalents (ä→ae, ö→oe, ü→ue, ß→ss), non-ASCII characters → underscores, spaces → underscores, multiple consecutive special chars → single underscore. Truncates to maxlength characters. Example: "Schrödinger's Report 2025" → "Schroedingers_Report_202" (if maxlength=25). Delegates to FilenameUtils.createSafeFilename().

createSafeFilename(String str, String suffix, int maxlength, boolean appendTimestamp)

Full version with file extension and optional timestamp. Adds the suffix (e.g. ".pdf") after truncation. If appendTimestamp=true, inserts the current date before the suffix: "basename_2010-08-12.pdf" (note: uses yyyy-MM-dd format, not yyyyMMdd — unlike the export filename generator in DOListExcelExporter). The timestamp format is fixed — not configurable. Delegates to FilenameUtils.createSafeFilename().

Key design details

  • Timestamp format inconsistency: The createSafeFilename timestamp uses yyyy-MM-dd with hyphens, while DOListExcelExporter uses yyyyMMdd without separators. This means exported Excel files have a different date format in their filenames than files created through this utility. This is a known inconsistency — the two were written at different times by different developers
  • No instance: All methods are static. The class has no constructor defined (uses the implicit default constructor) — but since all methods are static and the class is @Deprecated, no one should be instantiating it
  • No logging: Unlike most ProjectForge utility classes, this has no Logger — because it's a pure delegation layer. Errors in the underlying methods are handled by FileUtils/FilenameUtils

Migration guide

If you encounter FileHelper in code you're maintaining:

  • FileHelper.getAbsolutePath(a, b) → FileUtils.getAbsolutePath(a, b) (same signature)
  • FileHelper.createSafeFilename(str, maxlength) → FilenameUtils.createSafeFilename(str, maxlength)
  • FileHelper.createSafeFilename(str, suffix, max, timestamp) → FilenameUtils.createSafeFilename(str, suffix, max, timestamp)

The signatures are identical — the refactoring was a pure cut-and-paste from this class to the common package.
