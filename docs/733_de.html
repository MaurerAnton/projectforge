Zweck

Komprimiert und dekomprimiert Zeichenketten mittels GZIP + Base64-Kodierung. Löst zwei Probleme: (1) Manche Datenbankfelder haben eine begrenzte Zeichenlänge (z. B. VARCHAR(4000)), und (2) das Speichern großer JSON-Blobs in Datenbankspalten verschwendet Platz. Dieses Dienstprogramm komprimiert die Zeichenkette mit GZIP und kodiert das binäre Ergebnis dann Base64, sodass es als einfache Zeichenkette in einer Datenbank-VARCHAR- oder TEXT-Spalte gespeichert werden kann. Die Dekomprimierung kehrt den Prozess um: Base64-Dekodierung → GZIP-Dekomprimierung → ursprüngliche Zeichenkette.

Warum Base64 nach GZIP? GZIP erzeugt Binärbytes – diese sind für die Speicherung in textbasierten Datenbankspalten (die Zeichenkodierungen wie UTF-8 verwenden, die bestimmte Bytewerte als Steuerzeichen interpretieren können) nicht sicher. Base64 wandelt Binärdaten in eine reine ASCII-Zeichenkette um (unter Verwendung von 64 sicheren Zeichen: A-Z, a-z, 0-9, +, /) – garantiert sicher für jede Textspeicherung.

API — zwei Methoden

compress(String str) → String

Nimmt eine beliebige Zeichenkette entgegen (null-sicher – gibt null für null/leere Eingabe zurück). Kapselt Benutzervorgaben-XML, JSON-Konfigurations-Blobs und große Textfelder für die Datenbankspeicherung. Algorithmus:

  1. str.getBytes() – konvertiert in Bytes der plattformstandardmäßigen Zeichenkodierung. Warnung: Verwendet die Standard-Zeichenkodierung der JVM (typischerweise UTF-8 auf modernen Systemen, könnte aber auf älteren Systemen abweichen). Enthält die ursprüngliche Zeichenkette Nicht-ASCII-Zeichen, könnten verschiedene JVMs unterschiedliche komprimierte Ergebnisse liefern.
  2. Einbettung in GZIPOutputStream – die Java-Standardbibliotheksimplementierung von GZIP (RFC 1952).
  3. Schließt den GZIP-Stream – dies spült die komprimierten Daten in den zugrunde liegenden ByteArrayOutputStream.
  4. Kodiert die komprimierten Bytes mittels Base64Helper.encodeObject() in eine Base64-Zeichenkette – gibt die Base64-Zeichenkette zurück.

Fehlerbehandlung: Bei einer IOException wird der Fehler auf ERROR-Ebene protokolliert und null zurückgegeben. Der Aufrufer muss null behandeln – die meisten Aufrufer behandeln null wie eine leere Zeichenkette.

uncompress(String base64ByteArray) → String

Kehrt compress() um. Nimmt eine Base64-kodierte komprimierte Zeichenkette entgegen und gibt die ursprüngliche zurück. Algorithmus:

  1. Base64Helper.decodeObject(base64ByteArray) – dekodiert Base64 in rohe Bytes (Cast von Object zu byte[] – beachten Sie den ungeprüften Cast. Die Methode decodeObject gibt aus historischen XStream-Kompatibilitätsgründen Object zurück).
  2. Einbettung in GZIPInputStream – dekomprimiert die GZIP-Daten.
  3. Verwendet IOUtils.copy(gzip, out) (Apache Commons IO), um die dekomprimierten Daten in einen ByteArrayOutputStream zu streamen.
  4. out.toString() – wandelt Bytes mit der plattformstandardmäßigen Zeichenkodierung zurück in eine Zeichenkette (gleiche Zeichenkodierungsannahme wie bei compress).

Fehlerbehandlung: Fängt sowohl IOException als auch ClassNotFoundException ab (letztere von Base64Helper.decodeObject(), das intern Java-Objekt-Deserialisierung verwendet – ein potenzielles Sicherheitsproblem, wenn bösartige Base64-Daten übergeben werden). Gibt bei jedem Fehler null zurück.

Verwendung in ProjectForge

Wird von zwei Schlüsselkomponenten verwendet:

  • Benutzervorgaben (UserXmlPreferencesService): Benutzervorgaben-XML kann recht umfangreich werden (insbesondere Kalenderansichtskonfigurationen mit mehreren Kalendern, benutzerdefinierten Farben und gespeicherten Filtern). Vor dem Speichern in der Datenbank wird das XML mittels GZIPHelper.compress() komprimiert und als Base64-Zeichenkette in der Entität UserPrefDO gespeichert. Beim Laden stellt uncompress() das ursprüngliche XML wieder her.
  • Prüfpfad / Ereignisprotokoll: Die Spalte external_access_logs in t_plugin_datatransfer_area (siehe #105) speichert eine JSON-serialisierte Liste von Zugriffsereignissen. Bei häufigem externem Zugriff könnte diese Zeichenkette das VARCHAR(10000)-Limit überschreiten – GZIP-Komprimierung reduziert ihre Größe erheblich.

Bemerkenswerterweise wird dies nicht für die Lizenzschlüssel-BLOB-Speicherung (LicenseDO) verwendet – Binärdateien verwenden direkte JDBC-BLOB-Spalten, keine Textkomprimierung.

Wichtige Designentscheidungen und Fallstricke

  • Plattformstandard-Zeichenkodierung: Beide Methoden verwenden str.getBytes() und out.toString() ohne Angabe einer Zeichenkodierung. Dies bedeutet, dass der Komprimierungsdurchlauf nur garantiert ist, wenn Komprimierung und Dekomprimierung auf der gleichen JVM ausgeführt werden. Wenn komprimierte Daten auf einen anderen Server mit einer anderen Standard-Zeichenkodierung verschoben werden, könnte die dekomprimierte Zeichenkette beschädigt werden. In der Praxis verwenden alle modernen JVMs standardmäßig UTF-8 (seit Java 18), daher ist dies in der Produktion selten ein Problem.
  • Base64-Overhead: GZIP komprimiert Text typischerweise auf 20-30 % der Originalgröße, aber die Base64-Kodierung fügt etwa 33 % Overhead hinzu (3 Binärbytes → 4 Base64-Zeichen). Nettoergebnis: Komprimiert+Base64 ist typischerweise 25-40 % der Originalgröße. Dies bedeutet, dass es für Zeichenketten über ~2 KB nützlich ist, wo die Komprimierung den Base64-Overhead dominiert.
  • Null-Behandlung: Beide Methoden geben null für null-Eingabe zurück – Aufrufer müssen nicht vorab prüfen. Aber Aufrufer müssen null-Rückgaben behandeln (wenn Komprimierung/Dekomprimierung fehlschlägt) – die Behandlung von null als leere Zeichenkette ist üblich.
  • Keine Thread-Sicherheitsbedenken: Die gesamte E/A erfolgt über lokale ByteArrayInputStream/OutputStream-Objekte – kein gemeinsamer Zustand, vollständig threadsicher.
  • ClassNotFoundException in uncompress: Dies ist ein Code-Geruch – Base64Helper.decodeObject() verwendet Java's ObjectInputStream, das beliebige Java-Objekte deserialisieren kann (eine bekannte Sicherheitslücke). Wenn ein Angreifer Base64-Daten einschleusen kann, die an uncompress() übergeben werden, könnte er möglicherweise beliebigen Code ausführen. In der Praxis stammen die Daten nur aus der Datenbank und werden von compress() erzeugt, sodass die Angriffsfläche auf Datenbank-Kompromittierungsszenarien beschränkt ist.
