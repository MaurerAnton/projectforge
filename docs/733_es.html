#733: GZIPHelper.java

projectforge-business/src/main/java/org/projectforge/framework/utils/GZIPHelper.java Líneas: 81 · Tipo: Utilidad Java — org.projectforge.framework.utils 81 líneas · 45 código · 30 comentarios · 6 en blanco

Propósito

Comprime y descomprime cadenas usando codificación GZIP + Base64. Resuelve dos problemas: (1) algunos campos de base de datos tienen longitud de caracteres limitada (ej. VARCHAR(4000)), y (2) almacenar grandes blobs JSON en columnas de base de datos desperdicia espacio. Esta utilidad comprime la cadena con GZIP, luego codifica en Base64 el resultado binario para que pueda almacenarse como una cadena simple en una columna VARCHAR o TEXT de la base de datos. La descompresión invierte el proceso: decodificar Base64 → descomprimir GZIP → cadena original.

¿Por qué Base64 después de GZIP? GZIP produce bytes binarios — no son seguros para almacenar en columnas de base de datos basadas en texto (que usan codificaciones de caracteres como UTF-8 que pueden interpretar ciertos valores de bytes como caracteres de control). Base64 convierte datos binarios en una cadena ASCII pura (usando 64 caracteres seguros: A-Z, a-z, 0-9, +, /) — garantizada segura para cualquier almacenamiento de texto.

API — dos métodos

compress(String str) → String

Toma cualquier cadena (segura para nulos — devuelve nulo para entrada nula/vacía). Envuelve XML de preferencias de usuario, blobs de configuración JSON y campos de texto grandes para almacenamiento en base de datos. Algoritmo:

  1. str.getBytes() — convierte a bytes del juego de caracteres predeterminado de la plataforma. Advertencia: usa el juego de caracteres predeterminado de la JVM (típicamente UTF-8 en sistemas modernos pero podría ser diferente en configuraciones heredadas). Si la cadena original contiene caracteres no ASCII, diferentes JVM podrían producir resultados comprimidos diferentes
  2. Envuelve en GZIPOutputStream — la implementación GZIP estándar de Java (RFC 1952)
  3. Cierra el flujo GZIP — esto vacia los datos comprimidos al ByteArrayOutputStream subyacente
  4. Codifica los bytes comprimidos a cadena Base64 mediante Base64Helper.encodeObject() — devuelve la cadena Base64
Manejo de errores: En caso de IOException, registra el error a nivel ERROR y devuelve null. Quien llama debe manejar el nulo — la mayoría de los llamantes tratan el nulo igual que una cadena vacía.

uncompress(String base64ByteArray) → String

Invierte compress(). Toma una cadena comprimida codificada en Base64, devuelve la original. Algoritmo:

  1. Base64Helper.decodeObject(base64ByteArray) — decodifica Base64 a bytes sin procesar (conversión de Object a byte[] — note la conversión no verificada. El método decodeObject devuelve Object por compatibilidad histórica con XStream)
  2. Envuelve en GZIPInputStream — descomprime los datos GZIP
  3. Usa IOUtils.copy(gzip, out) (Apache Commons IO) para transmitir los datos descomprimidos a un ByteArrayOutputStream
  4. out.toString() — convierte los bytes de vuelta a cadena usando el juego de caracteres predeterminado de la plataforma (la misma suposición de juego de caracteres que compress)
Manejo de errores: Captura tanto IOException como ClassNotFoundException (este último de Base64Helper.decodeObject() que usa deserialización de objetos Java internamente — un posible problema de seguridad si se pasan datos Base64 maliciosos). Devuelve null en cualquier error.

Uso en ProjectForge

Usado por dos componentes clave:

  • Preferencias de usuario (UserXmlPreferencesService): El XML de preferencias de usuario puede volverse bastante grande (especialmente configuraciones de vista de calendario con múltiples calendarios, colores personalizados y filtros guardados). Antes de almacenar en la base de datos, el XML se comprime mediante GZIPHelper.compress() y se almacena como una cadena Base64 en la entidad UserPrefDO. Al cargar, uncompress() restaura el XML original
  • Registro de auditoría / registro de eventos: La columna external_access_logs en t_plugin_datatransfer_area (ver #105) almacena una lista serializada en JSON de eventos de acceso. Con acceso externo frecuente, esta cadena podría exceder el límite de VARCHAR(10000) — la compresión GZIP reduce su tamaño significativamente

Notablemente, esto no se usa para el almacenamiento BLOB de clave de licencia (LicenseDO) — los archivos binarios usan columnas BLOB directas de JDBC, no compresión de texto.

Decisiones de diseño clave y problemas

  • Juego de caracteres predeterminado de la plataforma: Ambos métodos usan str.getBytes() y out.toString() sin especificar un juego de caracteres. Esto significa que el ciclo de compresión solo está garantizado si compress y uncompress se ejecutan en la misma JVM. Si los datos comprimidos se mueven a un servidor diferente con un juego de caracteres predeterminado diferente, la cadena descomprimida podría corromperse. En la práctica, todas las JVM modernas usan UTF-8 por defecto (desde Java 18), por lo que esto rara vez es un problema en producción
  • Sobrecarga de Base64: GZIP típicamente comprime texto al 20-30% del tamaño original, pero la codificación Base64 agrega ~33% de sobrecarga (3 bytes binarios → 4 caracteres Base64). Resultado neto: comprimido+Base64 es típicamente 25-40% del tamaño original. Esto significa que es útil para cadenas de más de ~2KB donde la compresión domina la sobrecarga de Base64
  • Manejo de nulos: Ambos métodos devuelven null para entrada nula — los llamantes no necesitan verificar previamente. Pero los llamantes sí necesitan manejar devoluciones nulas (cuando la compresión/descompresión falla) — tratar el nulo como cadena vacía es típico
  • Sin problemas de seguridad de hilos: Toda la E/S es a través de objetos locales ByteArrayInputStream/OutputStream — sin estado compartido, completamente seguro para hilos
  • ClassNotFoundException en uncompress: Esto es un olor a código — Base64Helper.decodeObject() usa ObjectInputStream de Java, que puede deserializar objetos Java arbitrarios (una vulnerabilidad de seguridad conocida). Si un atacante puede inyectar datos Base64 que se pasen a uncompress(), potencialmente podría ejecutar código arbitrario. En la práctica, los datos solo provienen de la base de datos y son generados por compress(), por lo que la superficie de ataque se limita a escenarios de compromiso de la base de datos
