Objectif

Compresse et décompresse des chaînes de caractères en utilisant GZIP + encodage Base64. Résout deux problèmes : (1) certains champs de base de données ont une longueur de caractères limitée (par exemple VARCHAR(4000)), et (2) stocker de gros blobs JSON dans des colonnes de base de données gaspille de l'espace. Cet utilitaire compresse la chaîne avec GZIP, puis encode en Base64 le résultat binaire afin qu'il puisse être stocké comme une chaîne simple dans une colonne VARCHAR ou TEXT de la base de données. La décompression inverse le processus : décodage Base64 → décompression GZIP → chaîne d'origine.

Pourquoi Base64 après GZIP ? GZIP produit des octets binaires — non sûrs pour le stockage dans des colonnes de base de données textuelles (qui utilisent des encodages de caractères comme UTF-8 pouvant interpréter certaines valeurs d'octets comme des caractères de contrôle). Base64 convertit les données binaires en une chaîne ASCII pure (utilisant 64 caractères sûrs : A-Z, a-z, 0-9, +, /) — garantie sûre pour tout stockage textuel.

API — deux méthodes

compress(String str) → String

Prend n'importe quelle chaîne (sûre pour null — retourne null pour une entrée nulle/vide). Enveloppe le XML de préférences utilisateur, les blobs de configuration JSON et les grands champs de texte pour le stockage en base de données. Algorithme :

  1. str.getBytes() — convertit en octets du jeu de caractères par défaut de la plateforme. Attention : utilise le jeu de caractères par défaut de la JVM (généralement UTF-8 sur les systèmes modernes mais peut être différent sur des configurations héritées). Si la chaîne d'origine contient des caractères non ASCII, différentes JVM pourraient produire des résultats compressés différents
  2. Enveloppe dans GZIPOutputStream — l'implémentation GZIP de la bibliothèque standard Java (RFC 1952)
  3. Ferme le flux GZIP — cela vide les données compressées dans le ByteArrayOutputStream sous-jacent
  4. Encode les octets compressés en chaîne Base64 via Base64Helper.encodeObject() — retourne la chaîne Base64
Gestion des erreurs : En cas d'IOException, enregistre l'erreur au niveau ERROR et retourne null. L'appelant doit gérer null — la plupart des appelants traitent null comme une chaîne vide.

uncompress(String base64ByteArray) → String

Inverse compress(). Prend une chaîne compressée encodée en Base64, retourne l'originale. Algorithme :

  1. Base64Helper.decodeObject(base64ByteArray) — décode le Base64 en octets bruts (cast de Object vers byte[] — notez le cast non vérifié. La méthode decodeObject retourne Object pour la compatibilité historique avec XStream)
  2. Enveloppe dans GZIPInputStream — décompresse les données GZIP
  3. Utilise IOUtils.copy(gzip, out) (Apache Commons IO) pour transférer les données décompressées dans un ByteArrayOutputStream
  4. out.toString() — convertit les octets en chaîne en utilisant le jeu de caractères par défaut de la plateforme (même hypothèse de jeu de caractères que compress)
Gestion des erreurs : Capture à la fois IOException et ClassNotFoundException (ce dernier provenant de Base64Helper.decodeObject() qui utilise la désérialisation d'objets Java en interne — un problème de sécurité potentiel si des données Base64 malveillantes sont transmises). Retourne null en cas d'erreur.

Utilisation dans ProjectForge

Utilisé par deux composants clés :

  • Préférences utilisateur (UserXmlPreferencesService) : Le XML des préférences utilisateur peut devenir assez volumineux (en particulier les configurations de vue calendrier avec plusieurs calendriers, couleurs personnalisées et filtres sauvegardés). Avant le stockage en base de données, le XML est compressé via GZIPHelper.compress() et stocké comme une chaîne Base64 dans l'entité UserPrefDO. Au chargement, uncompress() restaure le XML d'origine
  • Journal d'audit / journal d'événements : La colonne external_access_logs sur t_plugin_datatransfer_area (voir #105) stocke une liste sérialisée en JSON des événements d'accès. Avec un accès externe fréquent, cette chaîne pourrait dépasser la limite VARCHAR(10000) — la compression GZIP réduit considérablement sa taille

Notablement, ceci n'est pas utilisé pour le stockage BLOB de clé de licence (LicenseDO) — les fichiers binaires utilisent des colonnes BLOB JDBC directes, pas de compression textuelle.

Décisions de conception clés et pièges

  • Jeu de caractères par défaut de la plateforme : Les deux méthodes utilisent str.getBytes() et out.toString() sans spécifier de jeu de caractères. Cela signifie que l'aller-retour de compression n'est garanti que si la compression et la décompression s'exécutent sur la même JVM. Si les données compressées sont déplacées vers un serveur différent avec un jeu de caractères par défaut différent, la chaîne décompressée pourrait être corrompue. En pratique, toutes les JVM modernes utilisent UTF-8 par défaut (depuis Java 18), donc c'est rarement un problème en production
  • Surcharge Base64 : GZIP compresse généralement le texte à 20-30 % de sa taille d'origine, mais l'encodage Base64 ajoute environ 33 % de surcharge (3 octets binaires → 4 caractères Base64). Résultat net : compressé+Base64 représente généralement 25-40 % de la taille d'origine. Cela signifie que c'est utile pour les chaînes de plus de ~2 Ko où la compression domine la surcharge Base64
  • Gestion de null : Les deux méthodes retournent null pour une entrée nulle — les appelants n'ont pas besoin de pré-vérifier. Mais les appelants doivent gérer les retours null (lorsque la compression/décompression échoue) — traiter null comme une chaîne vide est typique
  • Pas de problèmes de sécurité des threads : Toutes les E/S passent par des objets locaux ByteArrayInputStream/OutputStream — aucun état partagé, entièrement thread-safe
  • ClassNotFoundException dans uncompress : C'est un code smell — Base64Helper.decodeObject() utilise ObjectInputStream de Java, qui peut désérialiser des objets Java arbitraires (une vulnérabilité de sécurité connue). Si un attaquant peut injecter des données Base64 qui sont transmises à uncompress(), il pourrait potentiellement exécuter du code arbitraire. En pratique, les données proviennent uniquement de la base de données et sont générées par compress(), donc la surface d'attaque est limitée aux scénarios de compromission de la base de données
