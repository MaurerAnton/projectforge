Назначение

Сжимает и распаковывает строки с использованием GZIP + кодировки Base64. Решает две проблемы: (1) некоторые поля базы данных имеют ограниченную длину символов (например, VARCHAR(4000)), и (2) хранение больших JSON-блобов в столбцах базы данных расходует место. Эта утилита сжимает строку с помощью GZIP, затем кодирует в Base64 двоичный результат, чтобы его можно было хранить как обычную строку в столбце базы данных VARCHAR или TEXT. Распаковка выполняет обратный процесс: декодирование Base64 → распаковка GZIP → исходная строка.

Зачем Base64 после GZIP? GZIP создает двоичные байты — они небезопасны для хранения в текстовых столбцах базы данных (которые используют кодировки символов, такие как UTF-8, которые могут интерпретировать некоторые значения байтов как управляющие символы). Base64 преобразует двоичные данные в чистую ASCII-строку (используя 64 безопасных символа: A-Z, a-z, 0-9, +, /) — гарантированно безопасно для любого текстового хранения.

API — два метода

compress(String str) → String

Принимает любую строку (безопасен для null — возвращает null для пустого ввода/null). Оборачивает XML пользовательских настроек, JSON-конфигурации и большие текстовые поля для хранения в базе данных. Алгоритм:

  1. str.getBytes() — преобразует в байты кодировки платформы по умолчанию. Предупреждение: использует кодировку JVM по умолчанию (обычно UTF-8 в современных системах, но может отличаться в устаревших). Если исходная строка содержит не-ASCII символы, разные JVM могут дать разные сжатые результаты
  2. Оборачивает в GZIPOutputStream — реализация GZIP стандартной библиотеки Java (RFC 1952)
  3. Закрывает поток GZIP — это сбрасывает сжатые данные в нижележащий ByteArrayOutputStream
  4. Кодирует сжатые байты в строку Base64 через Base64Helper.encodeObject() — возвращает строку Base64
Обработка ошибок: При IOException логирует ошибку на уровне ERROR и возвращает null. Вызывающий код должен обрабатывать null — большинство вызывающих кодов обрабатывают null так же, как пустую строку.

uncompress(String base64ByteArray) → String

Обратная операция для compress(). Принимает сжатую строку в кодировке Base64, возвращает исходную. Алгоритм:

  1. Base64Helper.decodeObject(base64ByteArray) — декодирует Base64 в сырые байты (приведение от Object к byte[] — обратите внимание на непроверяемое приведение. Метод decodeObject возвращает Object для обратной совместимости с XStream)
  2. Оборачивает в GZIPInputStream — распаковывает данные GZIP
  3. Использует IOUtils.copy(gzip, out) (Apache Commons IO) для потокового копирования распакованных данных в ByteArrayOutputStream
  4. out.toString() — преобразует байты обратно в строку, используя кодировку платформы по умолчанию (та же кодировка, что и в compress)
Обработка ошибок: Перехватывает как IOException, так и ClassNotFoundException (последнее из Base64Helper.decodeObject(), который под капотом использует десериализацию объектов Java — потенциальная проблема безопасности, если переданы вредоносные данные Base64). Возвращает null при любой ошибке.

Использование в ProjectForge

Используется двумя ключевыми компонентами:

  • Пользовательские настройки (UserXmlPreferencesService): XML пользовательских настроек может быть довольно большим (особенно конфигурации календаря с несколькими календарями, пользовательскими цветами и сохраненными фильтрами). Перед сохранением в базе данных XML сжимается через GZIPHelper.compress() и сохраняется как строка Base64 в сущности UserPrefDO. При загрузке uncompress() восстанавливает исходный XML
  • Журнал аудита / событий: Столбец external_access_logs в t_plugin_datatransfer_area (см. #105) хранит JSON-сериализованный список событий доступа. При частом внешнем доступе эта строка может превысить лимит VARCHAR(10000) — сжатие GZIP значительно уменьшает ее размер

Примечательно, что это не используется для хранения BLOB лицензионных ключей (LicenseDO) — двоичные файлы используют прямые столбцы JDBC BLOB, а не сжатие текста.

Ключевые проектные решения и подводные камни

  • Кодировка платформы по умолчанию: Оба метода используют str.getBytes() и out.toString() без указания кодировки. Это означает, что цикл сжатия гарантирован только если compress и uncompress выполняются на одной и той же JVM. Если сжатые данные переносятся на другой сервер с другой кодировкой по умолчанию, распакованная строка может быть повреждена. На практике все современные JVM по умолчанию используют UTF-8 (начиная с Java 18), поэтому в продакшене это редко является проблемой
  • Накладные расходы Base64: GZIP обычно сжимает текст до 20-30% от исходного размера, но кодирование Base64 добавляет ~33% накладных расходов (3 двоичных байта → 4 символа Base64). Чистый результат: сжатый+Base64 обычно составляет 25-40% от исходного размера. Это означает, что утилита полезна для строк размером более ~2 КБ, где сжатие преобладает над накладными расходами Base64
  • Обработка null: Оба метода возвращают null для null-ввода — вызывающему коду не нужно предварительно проверять. Но вызывающий код должен обрабатывать возврат null (когда сжатие/распаковка не удается) — обычно null обрабатывается как пустая строка
  • Отсутствие проблем с потокобезопасностью: Весь ввод/вывод осуществляется через локальные объекты ByteArrayInputStream/OutputStream — нет общего состояния, полностью потокобезопасно
  • ClassNotFoundException в uncompress: Это признак проблемного кода — Base64Helper.decodeObject() использует Java ObjectInputStream, который может десериализовать произвольные объекты Java (известная уязвимость безопасности). Если злоумышленник может внедрить данные Base64, которые передаются в uncompress(), он потенциально может выполнить произвольный код. На практике данные поступают только из базы данных и генерируются compress(), поэтому поверхность атаки ограничена сценариями компрометации базы данных
