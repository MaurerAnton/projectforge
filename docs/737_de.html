Zweck

Ein handgeschriebener Stream-Parser, der Schlüssel=Wert-Paare aus einem java.io.Reader liest, Zeichen für Zeichen. Kein Regex, keine Drittanbieter-Parser-Bibliothek — reines zustandsbasiertes Parsen Zeichen für Zeichen mit einem 5-Elemente-Pushback-Puffer. Diese Art von Code existierte, bevor Bibliotheken wie Apache Commons CSV zum Standard wurden — oder wurde geschrieben, weil der Autor ohne Abhängigkeits-Overhead die genaue Kontrolle über Fehlermeldungen und Randfälle haben wollte.

Der Parser unterstützt: in Anführungszeichen gesetzte Werte (mit "), escapte Anführungszeichen innerhalb von Zeichenketten in Anführungszeichen ("" → ein literales "), konfigurierbares Trennzeichen (Standard aus KeyValuePairWriter.DEFAULT_SEPARATOR_CHAR), Zeilen-/Spaltenverfolgung für Fehlermeldungen und Überspringen von Leerzeichen. Eingabeformat: schlüssel1=wert1,schlüssel2="zitierter Wert, mit Komma",schlüssel3=123.

Architektur: ein Miniatur-Lexer

301 Zeilen. Der Parser ist als klassischer Zweiphasen-Lexer strukturiert:

  1. Zeichenleser (read() / nextToken() / unread()): liest ein Zeichen aus dem Reader, verfolgt Zeilen-/Spaltennummern, behandelt \r\n (Windows) und \n (Unix) Zeilenumbrüche und klassifiziert das Token als EOF, EOL oder CHAR. Die Methode nextToken() ist der Tokenizer
  2. Parser (parseKey() / parseValue()): verbraucht Tokens, um Schlüssel- und Wert-Zeichenketten zu erstellen. parse() ist der Einstiegspunkt, der in einer Schleife parseKey+parseValue aufruft, bis EOF/EOL erreicht ist

Dies ist dieselbe Architektur wie ein Compiler-Frontend — Tokenizer + Parser — nur für Schlüssel=Wert-Daten anstelle von Programmiersprachen.

Pushback-Puffer

Ein 5-Elemente int[] pushbackBuffer mit Index pushbackIndex. Wenn der Parser ein Zeichen zu weit liest (z.B. in skipWhitespaces()), schiebt er das Zeichen zurück über unread(int b). Der Puffer aktualisiert die Zeilen-/Spaltenzähler beim Zurückschieben von Zeilenumbrüchen — entscheidend für genaue Fehlermeldungen. 5 Elemente reichen für jedes Lookahead aus, das dieser Parser benötigt (maximales Lookahead beträgt 1-2 Zeichen). Dies ist die Standardimplementierung von 1-Zeichen-Lookahead — die einfachste Form des Backtrackings.

Behandlung von Werten in Anführungszeichen — die komplexeste Logik

parseValue() (Zeilen 141-189) implementiert einen vollständigen CSV-ähnlichen Parser für Felder in Anführungszeichen:

  1. Überspringt Leerzeichen, liest das erste Zeichen
  2. Wenn das erste Zeichen " ist, wechselt in den Modus für Anführungszeichen (quoted=true)
  3. Im Modus für Anführungszeichen:
    • "" → escaptes Anführungszeichen (fügt ein " zum Wert hinzu)
    • " gefolgt von Trennzeichen oder Leerzeichen+Trennzeichen → Ende des Werts
    • " gefolgt von etwas anderem → Fehler (UNEXPECTED_CHARACTER_AFTER_QUOTATION_MARK)
    • Jedes andere Zeichen → an den Wert-Puffer angehängt
  4. Im Modus ohne Anführungszeichen:
    • Trennzeichen → Ende des Werts
    • " → Fehler (UNEXPECTED_QUOTATIONMARK — Anführungszeichen sind nur im Modus mit Anführungszeichen erlaubt)
    • Jedes andere Zeichen → angehängt
  5. Wenn EOF/EOL erreicht wird, während Anführungszeichen aktiv sind → Fehler (QUOTATIONMARK_MISSED_AT_END_OF_CELL)

Dies folgt der RFC 4180 CSV-Spezifikation für Felder in Anführungszeichen, jedoch vereinfacht — keine mehrzeiligen Felder in Anführungszeichen, keine Header-Erkennung, keine Typinferenz.

Fehlerbehandlung — präzise Positionsinformationen

Jede Fehlermeldung enthält Zeilen- und Spaltennummer — z.B. "Unerwartetes Anführungszeichen... Fehler in Zeile: 3 (14)". Dies ist entscheidend für das Debuggen von Konfigurationsdateien. Die statische Methode createMessage() formatiert Fehler mit dem Muster: msg + " Fehler in Zeile: " + line + " (" + col + ")" + (s != null ? ": " + s : ""). Die Zähler lineno und colno werden von read() (erhöht die Zeile bei \n) und nextToken() (erhöht die Spalte bei jedem Zeichen) verwaltet.

Verwendungskontext

Dieser Parser wird verwendet, um Konfigurationsdateien und Skript-Parametereingaben zu lesen — Orte, an denen Benutzer oder Administratoren Schlüssel=Wert-Daten in einfachen Textdateien schreiben. Beispiel für eine Datei, die von diesem Parser verarbeitet wird:

name=ProjectForge
version="8.0.0"
description="ERP-System mit Zeiterfassung, Kalender und Fibu"
maxUsers=100

Der Parser liest Zeile für Zeile (EOL stoppt jeden parse()-Aufruf) und erzeugt eine Map<String, String>. Die Begleitklasse KeyValuePairWriter macht das Gegenteil — schreibt Maps in das Schlüssel=Wert-Textformat.
