Objectif

Un analyseur de flux écrit à la main qui lit les paires clé=valeur à partir d’un java.io.Reader, un caractère à la fois. Pas d’expression régulière, pas de bibliothèque d’analyse tierce — juste une analyse étatique pure, caractère par caractère, avec un tampon de réinjection de 5 éléments. C’est le genre de code qui existait avant que des bibliothèques comme Apache Commons CSV ne deviennent standard — ou écrit parce que l’auteur voulait un contrôle précis sur les messages d’erreur et les cas limites sans surcharge de dépendances.

L’analyseur prend en charge : les valeurs entre guillemets (avec "), les guillemets échappés dans les chaînes entre guillemets ("" → un " littéral), un caractère séparateur configurable (par défaut depuis KeyValuePairWriter.DEFAULT_SEPARATOR_CHAR), le suivi ligne/colonne pour les messages d’erreur, et le saut des espaces. Format d’entrée : clé1=valeur1,clé2="valeur entre guillemets, avec virgule",clé3=123.

Architecture : un mini analyseur lexical

301 lignes. L’analyseur est structuré comme un analyseur lexical classique en deux phases :

  1. Lecteur de caractères (read() / nextToken() / unread()) : lit un caractère depuis le Reader, suit les numéros de ligne/colonne, gère les sauts de ligne \r\n (Windows) et \n (Unix), et classe le jeton comme EOF, EOL ou CHAR. La méthode nextToken() est le tokeniseur
  2. Analyseur syntaxique (parseKey() / parseValue()) : consomme les jetons pour construire les chaînes clé et valeur. parse() est le point d’entrée qui appelle parseKey+parseValue en boucle jusqu’à EOF/EOL

C’est la même architecture qu’un front-end de compilateur — tokeniseur + analyseur syntaxique — juste pour des données clé=valeur au lieu de langages de programmation.

Tampon de réinjection

Un int[] pushbackBuffer de 5 éléments avec un index pushbackIndex. Lorsque l’analyseur lit un caractère trop loin (par exemple dans skipWhitespaces()), il réinjecte le caractère via unread(int b). Le tampon met à jour les compteurs de ligne/colonne lors de la réinjection de sauts de ligne — essentiel pour des messages d’erreur précis. 5 éléments suffisent pour toute anticipation nécessaire à cet analyseur (l’anticipation maximale est de 1 à 2 caractères). C’est l’implémentation standard de l’anticipation à 1 caractère — la forme la plus simple de retour arrière.

Gestion des valeurs entre guillemets — la logique la plus complexe

parseValue() (lignes 141-189) implémente un analyseur de champ entre guillemets complet de type CSV :

  1. Ignore les espaces, lit le premier caractère
  2. Si le premier caractère est ", entre en mode guillemets (quoted=true)
  3. En mode guillemets :
    • "" → guillemet échappé (ajoute un " à la valeur)
    • " suivi d’un séparateur ou d’un espace+séparateur → fin de la valeur
    • " suivi de tout autre chose → erreur (UNEXPECTED_CHARACTER_AFTER_QUOTATION_MARK)
    • Tout autre caractère → ajouté au tampon de valeur
  4. En mode sans guillemets :
    • Caractère séparateur → fin de la valeur
    • " → erreur (UNEXPECTED_QUOTATIONMARK — les guillemets ne sont autorisés qu’en mode guillemets)
    • Tout autre caractère → ajouté
  5. Si EOF/EOL est atteint alors qu’on est en mode guillemets → erreur (QUOTATIONMARK_MISSED_AT_END_OF_CELL)

Cela suit la spécification CSV RFC 4180 pour les champs entre guillemets, mais simplifié — pas de champs entre guillemets multilignes, pas de détection d’en-tête, pas d’inférence de type.

Gestion des erreurs — informations de localisation précises

Chaque message d’erreur inclut le numéro de ligne et le numéro de colonne — par exemple "Guillemet inattendu... Erreur à la ligne : 3 (14)". C’est essentiel pour déboguer les fichiers de configuration. La méthode statique createMessage() formate les erreurs avec le motif : msg + " Erreur à la ligne : " + line + " (" + col + ")" + (s != null ? " : " + s : ""). Les compteurs lineno et colno sont maintenus par read() (incrémente la ligne sur \n) et nextToken() (incrémente la colonne à chaque caractère).

Contexte d’utilisation

Cet analyseur est utilisé pour lire les fichiers de configuration et les entrées de paramètres de script — des endroits où les utilisateurs ou administrateurs écrivent des données clé=valeur dans des fichiers texte simples. Exemple de fichier analysé par celui-ci :

nom=ProjectForge
version="8.0.0"
description="Système ERP avec feuille de temps, calendrier et comptabilité"
maxUtilisateurs=100

L’analyseur lit ligne par ligne (EOL arrête chaque appel à parse()), produisant une Map<String, String>. La classe compagnon KeyValuePairWriter fait l’inverse — écrit des cartes au format texte clé=valeur.
