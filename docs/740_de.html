#740: ListHelper.java

projectforge-business/src/main/java/org/projectforge/framework/utils/ListHelper.java Zeilen: 39 · Autor: Kai Reinhard · Typ: Java-Dienstprogramm — 1 Methode 39 Zeilen · 10 Code · 26 Kommentare · 3 leer

Zweck

Eine Dienstprogrammklasse mit einer Methode — buchstäblich 39 Zeilen (davon 17 für den GPLv3-Lizenzheader). Stellt addAll(List<T> list, T... elements) bereit — eine Varargs-Konvention zum Hinzufügen mehrerer Elemente zu einer Liste in einem einzigen Aufruf. Ohne diese: list.addAll(Arrays.asList(a, b, c)). Mit dieser: ListHelper.addAll(list, a, b, c).

Warum existiert das? Javas List.addAll() erwartet eine Collection, keine Varargs. Um einzelne Elemente hinzuzufügen, müssen diese zuerst in Arrays.asList() verpackt werden — was bei 3-4 Inline-Elementen umständlich ist. Diese Methode ist reine syntaktische Zucker — sie macht genau dasselbe wie list.addAll(Arrays.asList(elements)) ohne zusätzliche Logik.

In Java 9+ fügte die Standardbibliothek List.of(a, b, c) hinzu (das eine unveränderliche Liste zurückgibt), aber da ProjectForge auf Java 17 abzielt und dieser Code aus der Java-8-Ära stammt, war das Varargs-Muster eine gängige benutzerdefinierte Ergänzung. Moderner Code würde stattdessen die Stream-API oder List.copyOf() verwenden.

Designkritik

Eine Klasse mit einer einzigen einzeiligen Methode ist im Allgemeinen ein Code-Geruch — sie sollte entweder entfernt werden (Aufrufer können direkt Arrays.asList verwenden) oder um weitere Listen-Dienstprogramme erweitert werden. Dieses Muster (einzelne Methoden-Helferklassen) ist jedoch im älteren Code von ProjectForge üblich und spiegelt eine Entwicklungskultur wider, in der das Erstellen einer neuen Dienstprogrammklasse gegenüber Inline-Boilerplate bevorzugt wurde. Im modernen ProjectForge-Kotlin-Code wäre dies eine einfache Erweiterungsfunktion: fun <T> MutableList<T>.addAll(vararg elements: T) — aber die Java-API unterstützt keine Erweiterungsfunktionen, daher bleibt die Klasse bestehen.
