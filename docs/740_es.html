#740: ListHelper.java

projectforge-business/src/main/java/org/projectforge/framework/utils/ListHelper.java Líneas: 39 · Autor: Kai Reinhard · Tipo: Utilidad Java — 1 método 39 líneas · 10 código · 26 comentarios · 3 en blanco

Propósito

Una clase de utilidad de 1 método — literalmente 39 líneas (17 de las cuales son el encabezado de licencia GPLv3). Proporciona addAll(List<T> list, T... elements) — una conveniencia de argumentos variables para agregar múltiples elementos a una lista en una sola llamada. Sin esto: list.addAll(Arrays.asList(a, b, c)). Con esto: ListHelper.addAll(list, a, b, c).

¿Por qué existe esto? El método List.addAll() de Java toma una Collection, no argumentos variables. Para agregar elementos individuales, primero debes envolverlos en Arrays.asList() — lo cual es verboso cuando tienes 3-4 elementos en línea. Este método es puro azúcar sintáctico — hace exactamente lo mismo que list.addAll(Arrays.asList(elements)) sin lógica adicional.

En Java 9+, la biblioteca estándar agregó List.of(a, b, c) (que devuelve una lista inmutable), pero dado que ProjectForge apunta a Java 17 y este código data de la era de Java 8, el patrón de argumentos variables era una adición personalizada común. El código moderno usaría la API Stream o List.copyOf() en su lugar.

Crítica de diseño

Una clase con un único método de 1 línea es generalmente un mal olor en el código — debería eliminarse (los llamadores pueden usar Arrays.asList directamente) o expandirse con más utilidades de lista. Sin embargo, este patrón (clases auxiliares de un solo método) es común en el código antiguo de ProjectForge, reflejando una cultura de desarrollo donde se prefería crear una nueva clase de utilidad en lugar de código repetitivo en línea. En el código Kotlin moderno de ProjectForge, esto sería una simple función de extensión: fun <T> MutableList<T>.addAll(vararg elements: T) — pero la API de Java no soporta funciones de extensión, por lo que la clase permanece.
