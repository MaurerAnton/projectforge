#827: AddressTextParser.kt

Kotlin object (singleton) — free-text address extractor. Parses unstructured text blocks (email signatures, clipboard pastes) into structured ParsedAddressData. Location: projectforge-business/src/main/kotlin/org/projectforge/business/address/AddressTextParser.kt
Purpose: Users frequently paste email signatures or clipboard text into the address form. This parser auto-populates fields by recognizing names, titles, phone numbers, emails, websites, street addresses, ZIP+city combinations, company names, and countries from raw text — reducing manual data entry. It powers both the web UI address import dialog and the AddressTextImportService batch importer.

Architecture

Two-Pass Parsing Strategy

The parser uses a two-pass approach:

Pass 1 (line-by-line scanning): Extract easily-recognizable patterns — email, website, phone numbers (labeled and bare), ZIP+city, and country — using dedicated regex patterns. Lines that contain extracted data are marked as "processed" and removed from further consideration.

Pass 2 (contextual interpretation): Remaining unprocessed lines are interpreted based on position and content heuristics. The first line is assumed to be a name (unless it looks like a street address or company). Subsequent lines are classified as position/title, organization, or street address based on pattern matching and order.

This two-pass design mirrors how human readers scan contact information: first spot the obvious structured elements (email format, phone format), then make sense of the remaining prose.

Class Structure

AddressTextParser is a Kotlin object (singleton) — it has no mutable state and all methods are pure functions of the input text. This makes it inherently thread-safe and testable. It delegates name parsing to PersonNameParser and phone normalization to PhoneNumberUtils.normalizePhoneNumber().

Edge Cases Handled

  • Website vs. title ambiguity: Dipl.Phys would match a naive website regex due to the .Phys dot. The parser checks if 2+ words follow the match — if so, it assumes a title rather than a website.
  • TLD ordering: The website regex lists longer TLDs (solutions, company) before shorter ones (com, co) to prevent false partial matches.
  • Bare phone threshold: Requires ≥8 digits to avoid misclassifying short numbers (house numbers, years, etc.) as phone numbers.
  • Phone type disambiguation: Labels like Mobil, Mobile route to mobilePhone field; Fax to fax; others to businessPhone.
  • "i. A." prefix: German convention "im Auftrag" (on behalf of) is stripped from the beginning of name lines before name parsing.
  • Comma-separated name/position: Lines like Dr. Max Mustermann, Geschäftsführer are split at the comma — the first part parsed as name, the second as position.
  • Multi-country notation: Schweiz/Switzerland extracts only the first country name before the slash.
  • Company suffix detection: Recognizes GmbH, AG, e.V., KG, OHG, UG, SE, Ltd., Inc., Corp., LLC, PLC as organization indicators.

Data Flow

Input: raw text string
  ↓
parseAddressText(text)
  ├── Normalize: split into lines, trim, filter blanks
  ├── Pass 1: per-line pattern matching
  │     ├── EMAIL_REGEX.find()       → result.email
  │     ├── WEBSITE_REGEX.find()     → result.website  (with title disambiguation)
  │     ├── PHONE_REGEX.find()       → result.businessPhone/mobilePhone/fax  (by label)
  │     ├── BARE_PHONE_REGEX.matches() → businessPhone/mobilePhone/fax  (by priority)
  │     ├── ZIP_CITY_REGEX.find()    → result.zipCode, result.city  (+ inline street)
  │     └── COUNTRY_REGEX.find()     → result.country
  └── Pass 2: remaining lines (contextual)
        ├── Line 0 → parseName() via PersonNameParser → title, form, firstName, name
        │     └── (skip if line looks like street address or company)
        ├── containsCompanySuffix()? → result.organization
        ├── STREET_REGEX.find()?     → result.addressText
        └── fallback heuristics      → positionText, organization, addressText
  ↓
Output: ParsedAddressData

Design Decisions

Why a Kotlin object rather than a Spring bean? The parser has no dependencies on Spring services or configuration. It's a pure function operating on string input. Making it a singleton object avoids DI overhead, simplifies testing, and allows use from non-Spring contexts (like batch/cli tools).

Why two passes instead of one? A single-pass parser would need to maintain complex state about what's been found so far and make premature classification decisions. Two passes let the first pass purely extract facts (email, phone, etc.) without worrying about semantics, and the second pass interpret only the remaining unclassified text with full context of what was already found.

Why regex-based rather than ML/NLP? Contact information follows highly structured patterns (email RFC format, phone number conventions, postal code + city name adjacency). Regex is both more efficient and more predictable than ML for this specific domain. The localized patterns (German street names, "GmbH", "i. A.") reflect that ProjectForge primarily serves DACH-region companies.

Why separate PersonNameParser? Name parsing was originally inline but grew complex as support for titles (Prof. Dr. med., Dipl.-Ing.), international forms of address (Herr/Frau/Mr/Mrs/Sr/Sra/Señor/etc.), and academic suffixes accumulated. Extracting it into a dedicated parser follows the Single Responsibility Principle and enables independent testing and reuse.

Testing

Tested by AddressTextParserTest.kt (#1673) which covers:
• Basic name extraction (with/without titles)
• Phone number formats: Tel: +49 89 123456, Mobil: 0171/1234567, Fax: 089-12345
• Bare phone numbers (without label prefix)
• ZIP+city extraction with optional D- prefix
• Street address with house numbers and ranges
• Company name detection via GmbH/AG suffixes
• Multi-line email signatures
• "i. A." prefix stripping
• Comma-separated name + position
Gotcha — Website false positives: Email signatures often contain titles like Dipl.-Phys. or Dipl.-Ing. after the name. The dot notation matches naive URL regex. The parser's heuristic (checking for 2+ words after the match) prevents this but may accidentally reject legitimate short-form URLs like example.com followed by a single word. Test edge cases carefully.
Integration point: Used by AddressTextImportService for batch CSV/Excel address import and by the Wicket web form's paste-to-import feature. The output ParsedAddressData feeds directly into AddressDO field setters.
