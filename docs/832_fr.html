Résumé : AddressbookDO représente une collection nommée d'adresses — un carnet d'adresses appartenant à un utilisateur ou à un groupe. Il étend BaseUserGroupRightsDO pour hériter d'un modèle de propriété et de permissions de groupe, implémente DisplayNameCapable pour des étiquettes d'interface utilisateur cohérentes, et porte des annotations Hibernate Search (@Indexed, @FullTextField) afin que les carnets d'adresses puissent être localisés via le moteur de recherche en texte intégral de l'application. Les champs sont annotés avec @PropertyInfo pour piloter la génération automatique de formulaires d'interface utilisateur.

Cette conception de classe parente signifie que chaque carnet d'adresses participe automatiquement au modèle de visibilité multi-locataire de ProjectForge.

Intégration Hibernate Search

Le marqueur @Indexed, combiné avec @FullTextField sur title et description, rend cette entité découvrable via Hibernate Search. Le HibernateSearchUsersGroupsTypeBinder (référencé dans la source mais non montré dans le contenu abrégé) fait le pont entre les droits utilisateur/groupe et l'index Lucene afin que les résultats de recherche respectent les mêmes contraintes de visibilité que les requêtes de base de données — un utilisateur recherchant des carnets d'adresses ne verra que les résultats pour lesquels il a la permission d'accéder.

DisplayNameCapable & Intégration UI

La propriété displayName retourne "$title", fournissant une étiquette cohérente pour les listes déroulantes, le fil d'Ariane et les entrées d'historique. Les annotations @PropertyInfo alimentent le système de rendu automatique de formulaires de ProjectForge, qui génère des champs de saisie, des messages de validation (par exemple "Le titre est requis") et des en-têtes de colonnes à partir des recherches i18nKey.

Justification de la Conception

Pourquoi étendre BaseUserGroupRightsDO ?

Les carnets d'adresses sont des ressources partagées — un utilisateur en crée un et peut accorder un accès en lecture ou écriture à d'autres utilisateurs ou groupes. La superclasse BaseUserGroupRightsDO fournit un modèle de droits uniforme (propriétaire + autorisations par utilisateur + autorisations par groupe) qui est réutilisé dans de nombreux types d'entités ProjectForge (carnets d'adresses, calendriers, listes de tâches, etc.). Cela évite de dupliquer le même schéma de contrôle d'accès dans chaque entité et garantit un comportement cohérent dans les couches DAO et UI.

Pourquoi charger owner avec empressement ?

Les carnets d'adresses sont presque toujours affichés avec le nom de leur propriétaire. Si owner était chargé paresseusement, chaque page de liste déclencherait N+1 requêtes supplémentaires. Le chargement eager est un compromis de performance délibéré : il ajoute une JOIN à chaque requête de carnet d'adresses mais élimine le problème N+1 dans le cas courant. L'annotation @JsonSerialize(using = IdOnlySerializer::class) garantit que lorsque l'entité est sérialisée en JSON (par exemple pour les API REST), seul l'ID numérique du propriétaire est émis, empêchant la sérialisation profonde du graphe d'objets et les références circulaires.

Pourquoi l'indexation Hibernate Search ?

ProjectForge fournit une fonction de recherche globale qui couvre plusieurs types d'entités. En annotant AddressbookDO avec @Indexed et @FullTextField, l'index Lucene est maintenu synchronisé avec la base de données via l'indexation automatique de Hibernate Search lors de la sauvegarde/mise à jour/suppression. Le HibernateSearchUsersGroupsTypeBinder garantit en outre que les métadonnées de contrôle d'accès sont intégrées dans l'index de recherche, de sorte que le même utilisateur qui ne peut pas voir un carnet d'adresses dans une vue liste ne peut pas non plus le trouver via la recherche en texte intégral — une propriété de sécurité critique.

Pourquoi implémenter DisplayNameCapable ?

Cette interface (fournissant displayName: String) est une convention ProjectForge utilisée par la journalisation d'historique/d'audit, le fil d'Ariane de l'interface utilisateur et les listes déroulantes de sélection. En l'implémentant, AddressbookDO s'intègre à ces sous-systèmes sans que chaque consommateur ait besoin de savoir que le nom d'affichage est simplement le champ title.

Pourquoi Constants.LENGTH_TITLE au lieu de longueurs codées en dur ?

ProjectForge utilise une classe Constants partagée pour définir des longueurs de colonnes standard. Cela garantit que toutes les entités utilisant les champs "title" ou "description" ont des tailles de colonnes de base de données cohérentes, simplifiant la gestion du schéma et évitant des bogues subtils où le titre d'une entité fait 255 caractères mais celui d'une autre fait 1000.
