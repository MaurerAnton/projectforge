Zusammenfassung: AddressbookDao ist das primäre Datenzugriffsobjekt für AddressbookDO-Entitäten. Es erweitert BaseDao, um standardmäßige CRUD-Operationen (speichern, aktualisieren, löschen, finden, Liste abrufen, als gelöscht markieren, wiederherstellen) zu erben und überschreibt select(), um eine benutzerspezifische Zugriffskontrollfilterung über AddressbookRight zu erzwingen. Es ist als Spring @Service-Singleton annotiert und gehört zu den ältesten Dateien im Codebestand, die seit dem ersten Commit vorhanden ist.

Architektur & Position im System

Klassenhierarchie

AddressbookDao erweitert BaseDao<AddressbookDO>, welches selbst ein generisches Hibernate-DAO ist und Folgendes bereitstellt:

  • save(obj) / update(obj) — eine Entität persistieren oder zusammenführen
  • delete(obj) / markAsDeleted(obj) — hartes oder weiches Löschen
  • select(filter) — gefilterte Listenabfragen (hier überschrieben)
  • find(id) / getList(filter) — Einzelabruf und paginierte Listen
  • undelete(obj) — eine weich gelöschte Entität wiederherstellen

Zugriffskontrollintegration

Das DAO ist auf zwei Arten in das Rechteverwaltungssystem von ProjectForge eingebunden:

MechanismusBeschreibung
UserRightId.MISC_ADDRESSBOOK Wird im init-Block gesetzt. Dieses Recht wird von BaseDao vor jeder ändernden Operation (speichern, aktualisieren, löschen usw.) überprüft, um sicherzustellen, dass der Aufrufer die Berechtigung MISC_ADDRESSBOOK besitzt.
AddressbookRight Wird innerhalb der überschriebenen select()-Methode verwendet. Erstellt eine HQL-Abfrage, die eine Verknüpfung mit den Benutzer-/Gruppenrechtetabellen herstellt und die Ergebnisse auf Adressbücher beschränkt, die der aktuelle Benutzer lesen kann, basierend auf den von BaseUserGroupRightsDO geerbten Besitz- und Gruppenregeln.

Wichtige Methoden

setOwner(ab: AddressbookDO, userId: Long)

Löst ein PFUserDO über UserDao auf und weist es dem owner-Feld des Adressbuchs zu. Dies ist eine praktische Methode, die das von UI-Controllern verwendete Muster der Besitzersuche zentralisiert.

override fun select(filter: BaseSearchFilter): List<AddressbookDO>

Überschreibt die Basisimplementierung, um den generischen Filter in einen AddressbookFilter umzuwandeln und die Filterung basierend auf AddressbookRight zu integrieren. Das generierte HQL fügt JOIN-Klauseln zu den Rechttabellen hinzu, sodass nur Adressbücher zurückgegeben werden, die für den aktuellen Benutzer sichtbar sind (durch Besitz, Gruppenmitgliedschaft oder explizite Zugriffsgewährung). Benutzer ohne MISC_ADDRESSBOOK sehen möglicherweise eine leere Liste.

override val additionalSearchFields: Array<String>

Design-Grundlagen

Warum eine separate DAO-Klasse?

ProjectForge folgt dem Standardmuster "DAO pro Entität". Jede Geschäftsentität erhält ihr eigenes DAO, damit querschnittliche Belange (Zugriffskontrolle, Auditierung, Volltextindizierung) pro Entität angepasst werden können. Das generische BaseDao behandelt die Standard-CRUD-Operationen, und die untergeordnete Klasse pro Entität fügt entitätsspezifische Regeln ein – hier die Logik für den Adressbuchzugriff.

Warum select() überschreiben anstatt Spring Security-Annotationen zu verwenden?

ProjectForge existiert bereits vor der weit verbreiteten Einführung von Spring Security und verwendet eine eigene, auf HQL-JOINs basierende Rechteverwaltungsschicht. Das Überschreiben von select() ermöglicht es, die Zugriffsprüfungen direkt in die Datenbankabfrage zu integrieren, wodurch das N+1-Problem vermieden wird, das beim Laden aller Zeilen und anschließenden Filtern im Anwendungscode auftreten würde. Dieser Ansatz ermöglicht es dem Filter auch, Zugriffskontrollprädikate mit benutzerdefinierten Suchkriterien in einer einzigen HQL-Anweisung zu kombinieren.

Warum wird eine AddressbookRight-Klasse anstelle von inline-HQL verwendet?

Die Klasse AddressbookRight kapselt das von BaseUserGroupRightsDO definierte Benutzer-/Gruppenberechtigungsmodell. Durch die Delegierung an eine separate Klasse kann dieselbe Zugriffslogik in Berichten, Exporten und REST-Endpunkten wiederverwendet werden, ohne das Multi-JOIN-Muster zu duplizieren. Außerdem wird das Zugriffsmodell so leichter isoliert testbar.

Warum @Service anstelle von @Repository?

Obwohl das Spring-@Repository-Stereotyp für DAOs typisch ist, verwendet ProjectForge durchgängig @Service in seiner DAO-Schicht. Dies spiegelt wahrscheinlich eine Konvention wider, die vor der breiten Einführung der Ausnahmeübersetzungsfunktion von @Repository etabliert wurde, oder eine bewusste Entscheidung, DAOs als transaktionale Dienstkomponenten zu behandeln. Der funktionale Unterschied ist vernachlässigbar, da beide Spring-verwaltete Singletons sind.
