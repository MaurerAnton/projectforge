#833: AddressbookDao.kt

projectforge-business/src/main/kotlin/org/projectforge/business/address/AddressbookDao.kt Tipo: Objeto de Acceso a Datos (DAO) — Servicio gestionado por Spring
Propósito: Capa de persistencia y control de acceso para entidades de libretas de direcciones
Ubicación: projectforge-business/src/main/kotlin/org/projectforge/business/address/AddressbookDao.kt 174 líneas · 120 código · 38 comentarios · 16 en blanco
Resumen: AddressbookDao es el objeto de acceso a datos principal para las entidades AddressbookDO. Extiende BaseDao para heredar operaciones CRUD estándar (guardar, actualizar, eliminar, buscar, obtenerLista, marcarComoEliminado, recuperar) y sobrescribe select() para imponer el filtrado de control de acceso por usuario mediante AddressbookRight. Está anotado como un singleton @Service de Spring y es uno de los archivos más antiguos del código base, presente desde la confirmación inicial.

Arquitectura y Posición en el Sistema

Jerarquía de Clases

AddressbookDao extiende BaseDao<AddressbookDO>, que a su vez es un DAO genérico de Hibernate que proporciona:

  • guardar(obj) / actualizar(obj) — persistir o fusionar una entidad
  • eliminar(obj) / marcarComoEliminado(obj) — eliminación física o lógica
  • select(filtro) — consultas de listas filtradas (sobrescrito aquí)
  • buscar(id) / obtenerLista(filtro) — recuperación individual y listas paginadas
  • recuperar(obj) — restaurar una entidad eliminada lógicamente

Integración de Control de Acceso

El DAO participa en el sistema de gestión de derechos de ProjectForge de dos maneras:

MecanismoDescripción
UserRightId.MISC_ADDRESSBOOK Establecido en el bloque init. Este derecho es verificado por BaseDao antes de cualquier operación de modificación (guardar, actualizar, eliminar, etc.) para asegurar que quien llama posee el permiso MISC_ADDRESSBOOK.
AddressbookRight Utilizado dentro del método select() sobrescrito. Construye una consulta HQL que se une a las tablas de derechos de usuario/grupo y restringe los resultados a las libretas de direcciones que el usuario actual puede leer, basándose en las reglas de propiedad y acceso grupal heredadas de BaseUserGroupRightsDO.

override fun select(filter: BaseSearchFilter): List<AddressbookDO>

Sobrescribe la implementación base para convertir el filtro genérico en un AddressbookFilter e incorporar el filtrado basado en AddressbookRight. El HQL generado añade cláusulas JOIN en las tablas de derechos para que solo se devuelvan las libretas de direcciones visibles para el usuario actual (por propiedad, membresía de grupo o concesiones de acceso explícitas). Los usuarios sin MISC_ADDRESSBOOK pueden ver una lista vacía.

Justificación del Diseño

¿Por qué una clase DAO separada?

ProjectForge sigue el patrón estándar de DAO por entidad. Cada entidad de negocio tiene su propio DAO para que las preocupaciones transversales (control de acceso, auditoría, indexación de texto completo) puedan personalizarse por entidad. El BaseDao genérico maneja el CRUD estándar y la subclase por entidad inyecta reglas específicas de la entidad — aquí la lógica de acceso a la libreta de direcciones.

¿Por qué sobrescribir select() en lugar de usar anotaciones de Spring Security?

ProjectForge es anterior a la adopción generalizada de Spring Security y utiliza su propia capa de gestión de derechos construida sobre JOINs de HQL. Sobrescribir select() permite que las comprobaciones de acceso se compilen directamente en la consulta de la base de datos, evitando el problema N+1 que surgiría al cargar todas las filas y luego filtrar en el código de la aplicación. Este enfoque también permite que el filtro combine predicados de control de acceso con criterios de búsqueda proporcionados por el usuario en una sola sentencia HQL.

¿Por qué se usa una clase AddressbookRight en lugar de HQL en línea?

La clase AddressbookRight encapsula el modelo de permisos de usuario/grupo definido por BaseUserGroupRightsDO. Al delegar en una clase separada, la misma lógica de acceso puede reutilizarse en informes, exportaciones y endpoints REST sin duplicar el patrón de múltiples JOINs. También facilita probar el modelo de acceso de forma aislada.

¿Por qué @Service en lugar de @Repository?

Aunque el estereotipo @Repository de Spring es típico para DAOs, ProjectForge utiliza @Service en toda su capa DAO. Esto probablemente refleja una convención establecida antes de que la característica de traducción de excepciones de @Repository se adoptara ampliamente, o una elección deliberada de tratar los DAOs como componentes de servicio transaccionales. La diferencia funcional es insignificante ya que ambos son singletons gestionados por Spring.
