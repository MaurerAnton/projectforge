Résumé : AddressbookDao est l'objet d'accès aux données principal pour les entités AddressbookDO. Il étend BaseDao pour hériter des opérations CRUD standard (sauvegarder, mettre à jour, supprimer, trouver, getList, markAsDeleted, undelete) et surcharge select() pour appliquer un filtrage de contrôle d'accès par utilisateur via AddressbookRight. Il est annoté comme un singleton Spring @Service et est l'un des fichiers les plus anciens de la base de code, présent depuis le commit initial.

Architecture & Position dans le système

Hiérarchie des classes

AddressbookDao étend BaseDao<AddressbookDO>, qui est lui-même un DAO Hibernate générique fournissant :

  • save(obj) / update(obj) — persister ou fusionner une entité
  • delete(obj) / markAsDeleted(obj) — suppression physique ou logique
  • select(filter) — requêtes de liste filtrées (surchargé ici)
  • find(id) / getList(filter) — récupération unique et listes paginées
  • undelete(obj) — restaurer une entité supprimée logiquement

Intégration du contrôle d'accès

Le DAO participe au système de gestion des droits de ProjectForge de deux manières :

MécanismeDescription
UserRightId.MISC_ADDRESSBOOK Défini dans le bloc init. Ce droit est vérifié par BaseDao avant toute opération de mutation (sauvegarde, mise à jour, suppression, etc.) pour s'assurer que l'appelant possède la permission MISC_ADDRESSBOOK.
AddressbookRight Utilisé dans la méthode select() surchargée. Construit une requête HQL qui effectue une jointure sur les tables de droits des utilisateurs/groupes et restreint les résultats aux carnets d'adresses que l'utilisateur actuel peut lire, en fonction des règles de propriété et d'accès de groupe héritées de BaseUserGroupRightsDO.

Méthodes clés

setOwner(ab: AddressbookDO, userId: Long)

Résout un PFUserDO via UserDao et l'assigne au champ owner du carnet d'adresses. Il s'agit d'une méthode de commodité qui centralise le modèle de recherche de propriétaire utilisé par les contrôleurs de l'interface utilisateur.

override fun select(filter: BaseSearchFilter): List<AddressbookDO>

Surcharge l'implémentation de base pour convertir le filtre générique en un AddressbookFilter et intégrer le filtrage basé sur AddressbookRight. Le HQL généré ajoute des clauses JOIN sur les tables de droits afin que seuls les carnets d'adresses visibles par l'utilisateur actuel (par propriété, appartenance à un groupe ou octroi d'accès explicite) soient retournés. Les utilisateurs sans MISC_ADDRESSBOOK peuvent voir une liste vide.

override fun newInstance(): AddressbookDO

Méthode d'usine requise par l'infrastructure DAO générique ; retourne un nouveau AddressbookDO() simple.

override val additionalSearchFields: Array<String>

Retourne ADDITIONAL_SEARCH_FIELDS, un tableau constant listant les propriétés de l'entité qui doivent être incluses dans les requêtes de texte intégral / Hibernate Search en plus des champs par défaut hérités de BaseDO.

Justification de la conception

Pourquoi une classe DAO séparée ?

ProjectForge suit le modèle standard DAO-par-entité. Chaque entité métier obtient son propre DAO afin que les préoccupations transversales (contrôle d'accès, audit, indexation plein texte) puissent être personnalisées par entité. Le BaseDao générique gère le CRUD standard et la sous-classe par entité injecte les règles spécifiques à l'entité — ici la logique d'accès au carnet d'adresses.

Pourquoi surcharger select() plutôt que d'utiliser les annotations Spring Security ?

ProjectForge est antérieur à l'adoption généralisée de Spring Security et utilise sa propre couche de gestion des droits construite sur des JOINs HQL. La surcharge de select() permet de compiler les vérifications d'accès directement dans la requête de base de données, évitant ainsi le problème N+1 qui surviendrait si l'on chargeait toutes les lignes pour les filtrer ensuite dans le code applicatif. Cette approche permet également au filtre de combiner les prédicats de contrôle d'accès avec les critères de recherche fournis par l'utilisateur dans une seule instruction HQL.

Pourquoi utiliser une classe AddressbookRight plutôt que du HQL en ligne ?

La classe AddressbookRight encapsule le modèle de permission utilisateur/groupe défini par BaseUserGroupRightsDO. En déléguant à une classe séparée, la même logique d'accès peut être réutilisée dans les rapports, l'exportation et les points de terminaison REST sans dupliquer le modèle à plusieurs JOINs. Cela rend également le modèle d'accès plus facile à tester de manière isolée.

Pourquoi @Service plutôt que @Repository ?

Bien que le stéréotype @Repository de Spring soit typique pour les DAO, ProjectForge utilise @Service dans toute sa couche DAO. Cela reflète probablement une convention établie avant que la fonctionnalité de traduction d'exceptions de @Repository ne soit largement adoptée, ou un choix délibéré de traiter les DAO comme des composants de service transactionnels. La différence fonctionnelle est négligeable puisque les deux sont des singletons gérés par Spring.
