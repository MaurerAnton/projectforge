Краткое описание: AddressbookDao — это основной объект доступа к данным для сущностей AddressbookDO. Он расширяет BaseDao, наследуя стандартные CRUD-операции (сохранение, обновление, удаление, поиск, getList, markAsDeleted, undelete), и переопределяет select() для обеспечения фильтрации контроля доступа для каждого пользователя через AddressbookRight. Он аннотирован как синглтон Spring @Service и является одним из старейших файлов в кодовой базе, присутствующим с самого первого коммита.

Архитектура и положение в системе

Иерархия классов

AddressbookDao расширяет BaseDao<AddressbookDO>, который сам является обобщённым Hibernate DAO, предоставляющим:

  • save(obj) / update(obj) — сохранение или слияние сущности
  • delete(obj) / markAsDeleted(obj) — жёсткое или мягкое удаление
  • select(filter) — запросы отфильтрованных списков (переопределён здесь)
  • find(id) / getList(filter) — одиночное получение и списки с пагинацией
  • undelete(obj) — восстановление мягко удалённой сущности

Интеграция контроля доступа

DAO участвует в системе управления правами ProjectForge двумя способами:

МеханизмОписание
UserRightId.MISC_ADDRESSBOOK Устанавливается в блоке init. Это право проверяется BaseDao перед любой изменяющей операцией (сохранение, обновление, удаление и т.д.), чтобы убедиться, что вызывающий обладает разрешением MISC_ADDRESSBOOK.
AddressbookRight Используется внутри переопределённого метода select(). Строит HQL-запрос, который присоединяет таблицы прав пользователей/групп и ограничивает результаты адресными книгами, которые текущий пользователь может читать, на основе правил владения и группового доступа, унаследованных от BaseUserGroupRightsDO.

Ключевые методы

setOwner(ab: AddressbookDO, userId: Long)

Разрешает PFUserDO через UserDao и назначает его полю owner адресной книги. Это удобный метод, который централизует шаблон поиска владельца, используемый контроллерами пользовательского интерфейса.

override fun select(filter: BaseSearchFilter): List<AddressbookDO>

Переопределяет базовую реализацию, чтобы привести обобщённый фильтр к AddressbookFilter и включить фильтрацию на основе AddressbookRight. Сгенерированный HQL добавляет предложения JOIN к таблицам прав, чтобы возвращались только адресные книги, видимые текущему пользователю (по владению, членству в группе или явным разрешениям доступа). Пользователи без MISC_ADDRESSBOOK могут увидеть пустой список.

override fun newInstance(): AddressbookDO

Фабричный метод, требуемый обобщённой инфраструктурой DAO; возвращает простой новый AddressbookDO().

override val additionalSearchFields: Array<String>

Возвращает ADDITIONAL_SEARCH_FIELDS, константный массив, перечисляющий свойства сущности, которые должны быть включены в полнотекстовые / Hibernate Search запросы помимо полей по умолчанию, унаследованных от BaseDO.

Обоснование дизайна

Почему отдельный класс DAO?

ProjectForge следует стандартному шаблону «один DAO на сущность». Каждая бизнес-сущность получает свой собственный DAO, чтобы сквозные аспекты (контроль доступа, аудит, полнотекстовое индексирование) могли быть настроены для каждой сущности. Обобщённый BaseDao обрабатывает шаблонный CRUD, а подкласс для конкретной сущности внедряет специфичные для сущности правила — здесь это логика доступа к адресной книге.

Почему переопределён select(), а не используются аннотации Spring Security?

ProjectForge предшествует широкому внедрению Spring Security и использует собственный уровень управления правами, построенный на HQL JOIN. Переопределение select() позволяет встраивать проверки доступа непосредственно в запрос к базе данных, избегая проблемы N+1, которая возникла бы при загрузке всех строк и последующей фильтрации в коде приложения. Этот подход также позволяет фильтру объединять предикаты контроля доступа с критериями поиска, предоставленными пользователем, в одном HQL-выражении.

Почему используется класс AddressbookRight вместо встроенного HQL?

Класс AddressbookRight инкапсулирует модель разрешений пользователей/групп, определённую BaseUserGroupRightsDO. Делегируя отдельному классу, ту же логику доступа можно повторно использовать в отчётах, экспорте и REST-конечных точках без дублирования шаблона с несколькими JOIN. Это также упрощает тестирование модели доступа изолированно.

Почему @Service вместо @Repository?

Хотя стереотип Spring @Repository типичен для DAO, ProjectForge использует @Service во всём своём DAO-слое. Вероятно, это отражает соглашение, установленное до того, как функция трансляции исключений @Repository была широко принята, или осознанный выбор рассматривать DAO как транзакционные сервисные компоненты. Функциональная разница незначительна, поскольку оба являются синглтонами, управляемыми Spring.
