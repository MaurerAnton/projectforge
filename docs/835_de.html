#835: BirthdayCache.kt

projectforge-business/src/main/kotlin/org/projectforge/business/address/BirthdayCache.kt Kotlin-Cache-Klasse — zwischengespeicherter Index aller Adressbuch-Geburtstage für schnelle Datumsbereichsabfragen. Erweitert AbstractCache für automatische TTL-basierte Aktualisierung. Standort: projectforge-business/src/main/kotlin/org/projectforge/business/address/BirthdayCache.kt 124 Zeilen · 81 Code · 33 Kommentare · 10 leer
Zweck: Das Kalender-Dashboard und das Geburtstagsbenachrichtigungssystem müssen effizient beantworten können: „Wer hat diese Woche/diesen Monat Geburtstag?“ Ohne Cache müsste jede Abfrage die gesamte Adresstabelle durchsuchen. BirthdayCache lädt alle nicht gelöschten Adressen mit einem Geburtsdatum einmal in den Speicher und führt eine datumsbasierte Filterung im Speicher durch, wodurch nach dem ersten Laden O(1)-Abfragekosten erreicht werden.

Architektur

Vererbungskette

BirthdayCache erweitert AbstractCache (aus org.projectforge.framework.cache), die Basisklasse von ProjectForge für TTL-basierte Caches. Dies bietet:
• checkRefresh() — ruft automatisch refresh() auf, wenn die TTL abgelaufen ist
• setExpireInMinutes() — konfigurierbare TTL
• Thread-sichere Registrierung in PfCaches (#820)
• Teilnahme an SystemService.refreshCaches() Massenaktualisierung

Singleton-Schutz

Der Cache verwendet ein Begleitobjekt mit einer lateinit var instance und einem instanceCounter-Schutz. Wenn Spring (oder Testcode) eine zweite Instanz erstellt, wird eine Warnung protokolliert. Dies verhindert, dass die Basisklasse AbstractCache den Cache doppelt in PfCaches registriert, was zu doppelten Aktualisierungsaufrufen führen würde.

Datenmodell

Der Cache speichert eine MutableList<BirthdayAddress>, wobei jedes BirthdayAddress ein AddressDO kapselt und Comparable implementiert. Der Vergleich sortiert zuerst nach Geburtstagsmonat/-tag, dann nach Name – dies ermöglicht dem TreeSet, das in getBirthdays() verwendet wird, eine natürlich sortierte Ausgabe ohne explizite Sortieraufrufe.

Abfragealgorithmus

getBirthdays(fromDate, toDate, all, favorites) filtert die zwischengespeicherte Liste mit vier Schutzbedingungen, die aus Effizienzgründen in dieser Prioritätsreihenfolge angewendet werden:

1. Zugriffskontrolle (addressDao.hasLoggedInUserSelectAccess): Überspringt Adressen, die der aktuelle Benutzer nicht sehen kann. Dies ist wichtig, da der Cache ALLE Adressen lädt (mit checkAccess = false in der DAO-Abfrage).
2. Favoritenfilter (!all && !favorites.contains(address.id)): Wenn nicht im „Alle“-Modus, werden nur Adressen in der Favoritenliste des Benutzers einbezogen.
3. Geburtstagsverfügbarkeit: Überspringt Adressen, bei denen PFDateTime.fromOrNull(address.birthday) null zurückgibt.
4. Datumsbereichsprüfung (DateHelper.dateOfYearBetween): Vergleicht Monat/Tag (ignoriert Jahr) mit dem Bereich. Dies behandelt jahresübergreifende Bereiche (z. B. 15. Dez. – 15. Jan.).

Die Ergebnisse werden in einem TreeSet<BirthdayAddress> für automatische Sortierung gesammelt.

Aktualisierungslogik

refresh() wird innerhalb von persistenceService.runIsolatedReadOnly { } ausgeführt – einem dedizierten Transaktionskontext, getrennt von jeder aktiven HTTP-Anfrage-Transaktion. Diese Isolierung verhindert:
• Konflikte mit anfragebezogenen Hibernate-Sitzungen
• Probleme mit verzögertem Laden (alle Daten werden eager geladen)
• Lese-Phänomene aus nicht festgeschriebenen Schreibvorgängen in der Anfrage-Transaktion

Die Abfrage verwendet QueryFilter.isNotNull("birthday"), um Adressen ohne Geburtsdatum auszuschließen (die Mehrheit). Der Filter deleted = false stellt sicher, dass soft-gelöschte Adressen ausgeschlossen werden.

Eine zusätzliche defensive Prüfung (if (it.deleted != true)) schützt vor Entitäten, bei denen der JPA-Filter möglicherweise nicht angewendet wurde (z. B. während einer Migration oder wenn die Filterkonfiguration geändert wird).

Die Ausführung von PersonalAddressDao.getList dauerte Sekunden, und die Anzeige von Geburtstagen in der Kalenderansicht verursachte spürbare Latenz. Der Cache eliminierte den pro Anfrage durchgeführten Scan der Adresstabelle.

4c04cfd65 — int→Long-Migration: Alle ID-Typen wurden von Integer auf Long geändert, was den Parameter favorites: List<Long> und die address.id-Vergleiche in der gesamten Filterlogik betrifft.

cf80afb28 — Mandantenentfernung: Die Multi-Mandanten-Funktion wurde entfernt, was den Cache vereinfacht (keine Mandantenisolierung erforderlich).

bfa336a64 — Fehlerbehebung für gelöschte Benutzer: Die explizite Prüfung auf Geburtstage gelöschter Benutzer wurde hinzugefügt, um sicherzustellen, dass diese nicht in Dashboard-Widgets erscheinen.

Der lineare Scan ist akzeptabel, da der Cache nur Adressen mit Geburtstagen enthält (nicht das gesamte Adressbuch) und die Zugriffs-/Favoritenfilterung teure DB-Lookups pro Eintrag vermeidet, indem vollständig im Speicher mit vorab geladenen Sicherheitsdaten gearbeitet wird.
Achtung — Zugriffskontrollumgehung bei der Aktualisierung: Die Aktualisierungsabfrage verwendet checkAccess = false, um ALLE Adressen zu laden. Die Zugriffskontrolle wird später in getBirthdays() pro Abfrage angewendet. Dies bedeutet, dass der Cache selbst Daten enthält, die der aktuelle Benutzer möglicherweise nicht sehen darf. Jeder getBirthdays()-Aufruf wertet den Zugriff basierend auf dem aktuellen angemeldeten Benutzer neu aus, wodurch der Cache zur Speicherzeit benutzerunabhängig, aber zur Abfragezeit benutzerbewusst ist. Wenn der Zugriff eines Benutzers entzogen wird, schließt die nächste Geburtstagsabfrage (nicht die nächste Cache-Aktualisierung) seine Einträge aus.
