Objectif : Le tableau de bord du calendrier et le système de notification d'anniversaire doivent répondre efficacement à la question « dont l'anniversaire est-ce cette semaine/ce mois ? ». Sans cache, chaque requête scannerait l'intégralité de la table des adresses. BirthdayCache charge en mémoire toutes les adresses non supprimées avec une date d'anniversaire une fois, et effectue un filtrage en mémoire par plage de dates, atteignant un coût de requête O(1) après le chargement initial.

Architecture

Chaîne d'héritage

BirthdayCache étend AbstractCache (de org.projectforge.framework.cache), la classe de base de ProjectForge pour les caches basés sur TTL. Cela lui donne :
• checkRefresh() — appelle automatiquement refresh() si le TTL a expiré
• setExpireInMinutes() — TTL configurable
• Enregistrement thread-safe dans PfCaches (#820)
• Participation au rafraîchissement groupé SystemService.refreshCaches()

Protection singleton

Le cache utilise un objet compagnon avec une lateinit var instance et un garde instanceCounter. Si Spring (ou le code de test) crée une seconde instance, un avertissement est journalisé. Cela empêche la classe de base AbstractCache de double-enregistrer le cache dans PfCaches, ce qui provoquerait des appels de rafraîchissement en double.

Modèle de données

Le cache stocke une MutableList<BirthdayAddress> où chaque BirthdayAddress encapsule un AddressDO et implémente Comparable. La comparaison trie d'abord par mois/jour d'anniversaire, puis par nom — permettant au TreeSet utilisé dans getBirthdays() de produire une sortie naturellement triée sans appels de tri explicites.

Algorithme de requête

getBirthdays(fromDate, toDate, all, favorites) filtre la liste mise en cache avec quatre conditions de garde appliquées dans cet ordre de priorité pour l'efficacité :

1. Contrôle d'accès (addressDao.hasLoggedInUserSelectAccess) : Ignore les adresses que l'utilisateur actuel ne peut pas voir. Ceci est essentiel car le cache charge TOUTES les adresses (en utilisant checkAccess = false dans la requête DAO).
2. Filtre des favoris (!all && !favorites.contains(address.id)) : Si pas en mode « tout », seules les adresses dans la liste des favoris de l'utilisateur sont incluses.
3. Disponibilité de l'anniversaire : Ignore les adresses où PFDateTime.fromOrNull(address.birthday) retourne null.
4. Vérification de la plage de dates (DateHelper.dateOfYearBetween) : Compare le mois/jour (en ignorant l'année) avec la plage. Cela gère les plages chevauchant les années (ex. 15 déc. — 15 janv.).

Les résultats sont collectés dans un TreeSet<BirthdayAddress> pour un tri automatique.

Logique de rafraîchissement

refresh() s'exécute dans persistenceService.runIsolatedReadOnly { } — un contexte de transaction dédié, séparé de toute transaction de requête HTTP active. Cet isolement empêche :
• La contention avec les sessions Hibernate liées à la requête
• Les problèmes de chargement paresseux (toutes les données sont chargées de manière eager)
• Les phénomènes de lecture provenant d'écritures non validées dans la transaction de la requête

La requête utilise QueryFilter.isNotNull("birthday") pour exclure les adresses sans date d'anniversaire (qui sont la majorité). Le filtre deleted = false garantit que les adresses supprimées logiquement sont exclues.

Une vérification défensive supplémentaire (if (it.deleted != true)) protège contre les entités où le filtre JPA pourrait ne pas avoir été appliqué (par exemple, lors d'une migration ou si la configuration du filtre change).

Principaux commits expliqués

615c248f4 (le plus ancien) — Correction de performance : Le cache a été créé pour résoudre un problème de performance critique. PersonalAddressDao.getList prenait des secondes à s'exécuter, et l'affichage des anniversaires dans la vue calendrier provoquait une latence notable. Le cache a éliminé le scan de la table des adresses à chaque requête.

0ceceb28f — Transactions isolées : Les opérations de rafraîchissement ont été déplacées de la transaction de requête vers runIsolatedReadOnly. Cela a corrigé une classe de bugs où un rafraîchissement de longue durée dans une transaction de requête pouvait provoquer des timeouts de session Hibernate ou des problèmes de visibilité de données obsolètes.

4c04cfd65 — Migration int→Long : Tous les types d'ID sont passés de Integer à Long, affectant le paramètre favorites: List<Long> et les comparaisons address.id dans toute la logique de filtrage.

cf80afb28 — Suppression de la location : La fonctionnalité multi-locataire a été supprimée, simplifiant le cache (plus d'isolation par locataire nécessaire).

bfa336a64 — Correction utilisateur supprimé : Ajout de la vérification explicite pour l'anniversaire des utilisateurs supprimés, garantissant qu'ils n'apparaissent pas dans les widgets du tableau de bord.

Le scan linéaire est acceptable car le cache ne contient que les adresses avec anniversaire (pas le carnet d'adresses complet), et le filtrage par accès/favoris évite les recherches coûteuses en base de données par entrée en travaillant entièrement en mémoire avec des données de sécurité préchargées.
Piège — Contournement du contrôle d'accès lors du rafraîchissement : La requête de rafraîchissement utilise checkAccess = false pour charger TOUTES les adresses. Le contrôle d'accès est appliqué plus tard dans getBirthdays() par requête. Cela signifie que le cache lui-même contient des données que l'utilisateur actuel pourrait ne pas être autorisé à voir. Chaque appel à getBirthdays() réévalue l'accès en fonction de l'utilisateur actuellement connecté, rendant le cache agnostique de l'utilisateur au moment du stockage, mais conscient de l'utilisateur au moment de la requête. Si l'accès d'un utilisateur est révoqué, la prochaine requête d'anniversaire (pas le prochain rafraîchissement du cache) exclura ses entrées.
