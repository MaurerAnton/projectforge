Расширяет AbstractCache для автоматического обновления на основе TTL. Расположение: projectforge-business/src/main/kotlin/org/projectforge/business/address/BirthdayCache.kt 124 строки · 81 код · 33 комментария · 10 пустых
Назначение: Панель управления календарем и система уведомлений о днях рождения должны эффективно отвечать на вопрос «чей день рождения на этой неделе / в этом месяце?». Без кэша каждый запрос сканировал бы всю таблицу адресов. BirthdayCache загружает все неудаленные адреса с датой рождения в память один раз и выполняет фильтрацию по диапазону дат в памяти, обеспечивая стоимость запроса O(1) после начальной загрузки.

Архитектура

Цепочка наследования

BirthdayCache расширяет AbstractCache (из org.projectforge.framework.cache), базовый класс ProjectForge для кэшей на основе TTL. Это дает ему:
• checkRefresh() — автоматически вызывает refresh(), если TTL истек
• setExpireInMinutes() — настраиваемый TTL
• Потокобезопасная регистрация в PfCaches (#820)
• Участие в массовом обновлении SystemService.refreshCaches()

Защита от множественных экземпляров (Singleton)

Кэш использует companion object с lateinit var instance и защитой instanceCounter. Если Spring (или тестовый код) создает второй экземпляр, записывается предупреждение. Это предотвращает двойную регистрацию кэша в PfCaches базовым классом AbstractCache, что могло бы вызвать дублирующие вызовы обновления.

Модель данных

Кэш хранит MutableList<BirthdayAddress>, где каждый BirthdayAddress оборачивает AddressDO и реализует Comparable. Сравнение упорядочивает сначала по месяцу/дню рождения, затем по имени — это позволяет TreeSet, используемому в getBirthdays(), выдавать естественно отсортированный результат без явных вызовов сортировки.

Алгоритм запроса

getBirthdays(fromDate, toDate, all, favorites) фильтрует кэшированный список с четырьмя условиями, применяемыми в следующем порядке приоритета для эффективности:

1. Контроль доступа (addressDao.hasLoggedInUserSelectAccess): Пропускает адреса, которые текущий пользователь не может видеть. Это необходимо, так как кэш загружает ВСЕ адреса (используя checkAccess = false в запросе DAO).
2. Фильтр избранного (!all && !favorites.contains(address.id)): Если не в режиме «все», включаются только адреса из списка избранного пользователя.
3. Наличие дня рождения: Пропускает адреса, где PFDateTime.fromOrNull(address.birthday) возвращает null.
4. Проверка диапазона дат (DateHelper.dateOfYearBetween): Сравнивает месяц/день (игнорируя год) с диапазоном. Обрабатывает диапазоны, переходящие через год (например, 15 дек — 15 янв).

Результаты собираются в TreeSet<BirthdayAddress> для автоматической сортировки.

Логика обновления

refresh() выполняется внутри persistenceService.runIsolatedReadOnly { } — выделенного контекста транзакции, отдельного от любого активного HTTP-запроса. Эта изоляция предотвращает:
• Конкуренцию с сессиями Hibernate в области запроса
• Проблемы с ленивой загрузкой (все данные загружаются жадно)
• Феномены чтения от незафиксированных записей в транзакции запроса

Запрос использует QueryFilter.isNotNull("birthday") для исключения адресов без даты рождения (которые составляют большинство). Фильтр deleted = false гарантирует исключение мягко удаленных адресов.

Дополнительная защитная проверка (if (it.deleted != true)) защищает от сущностей, к которым фильтр JPA мог не применяться (например, во время миграции или при изменении конфигурации фильтра).

Линейное сканирование приемлемо, потому что кэш содержит только адреса с днями рождения (не всю адресную книгу), а фильтрация доступа/избранного избегает дорогих обращений к БД для каждой записи, работая полностью в памяти с предварительно загруженными данными безопасности.
Ловушка — Обход контроля доступа при обновлении: Запрос обновления использует checkAccess = false для загрузки ВСЕХ адресов. Контроль доступа применяется позже в getBirthdays() для каждого запроса. Это означает, что кэш сам хранит данные, которые текущий пользователь может быть не вправе видеть. Каждый вызов getBirthdays() повторно оценивает доступ на основе текущего вошедшего в систему пользователя, делая кэш независимым от пользователя при хранении, но учитывающим пользователя при запросе. Если доступ пользователя отозван, следующий запрос дня рождения (а не следующее обновление кэша) исключит его записи.
