Implementiert CustomResultFilter<AddressDO>, um doppelte Adresseinträge (Dubletten) basierend auf einem normalisierten Vollnamen-Vergleich zu erkennen und zu extrahieren. Standort: projectforge-business/src/main/kotlin/org/projectforge/business/address/DoubletsResultFilter.kt 57 Zeilen · 30 Code · 23 Kommentare · 4 leer
Zweck: Wenn ein Adressbuch organisch wächst (Importe, manuelle Eingaben, Datenmigration), sammeln sich doppelte Kontakte an – oft mit geringfügigen Formatierungsunterschieden, aber identischen normalisierten Namen. Dieser Filter ermöglicht es der Adresslisten-Oberfläche, eine Ansicht „Nur Dubletten anzeigen“ bereitzustellen, damit Administratoren Duplikate finden und zusammenführen können.

Architektur

Implementiert CustomResultFilter<AddressDO> – ein ProjectForge-Framework-Interface für die Nachfilterung von Abfrageergebnissen. Im Gegensatz zur Filterung auf Datenbankebene (WHERE-Klauseln) arbeiten Ergebnisfilter im Arbeitsspeicher auf der vom DAO zurückgegebenen Ergebnismenge. Dies ist für die Deduplizierung notwendig, weil:

• Duplikate über verschiedene Datenbankzeilen mit unterschiedlichen IDs verteilt sein können
• Die Normalisierungslogik (getNormalizedFullname) Zeichenfolgenmanipulationen umfasst, die sich nicht einfach in SQL/HQL ausdrücken lassen
• Der Filter einen Zustand über mehrere Elemente hinweg aufbauen muss – die Methode match() wird für jedes Element der Reihe nach aufgerufen, verändert aber interne Mengen

Zustandsautomat

Der Filter arbeitet als Zwei-Mengen-, Zwei-Durchlauf-Zustandsautomat:

Durchlauf 1 (Ansammlung): Wenn jedes Adresselement an match() übergeben wird:
• Wenn der normalisierte Vollname bereits in fullnames vorhanden ist, handelt es sich um eine Dublette – wird zu doubletFullnames hinzugefügt
• Wenn nicht in fullnames vorhanden, handelt es sich um ein erstes Vorkommen – wird zu all und fullnames hinzugefügt

Durchlauf 2 (Leeren): Wenn eine Dublette erkannt wird, werden alle zuvor gesehenen Adressen, deren Namen mit einem Dublettennamen übereinstimmen, zur Ergebnisliste hinzugefügt. Die Menge addedDoublets verhindert, dass dieselbe Adresse zweimal hinzugefügt wird.

Datenstrukturentscheidungen

FeldTypZweck

Algorithmus-Ablauf

Für jede Adresse im Abfrageergebnis (sortiert nach Name):

1. Gelöschte Adressen überspringen → false zurückgeben
  
2. normalizedFullname = AddressDao.getNormalizedFullname(element) berechnen
   (Leerzeichen entfernen, Kleinschreibung, usw.)

3. Prüfen, ob fullnames.contains(normalizedFullname):
   
   NEIN (erstes Vorkommen):
     all.add(element)
     fullnames.add(normalizedFullname)
     return false  (noch nicht in die Ergebnisse aufnehmen)
   
   JA (Duplikat erkannt):
     doubletFullnames.add(normalizedFullname)
     
     // Leeren: Alle zuvor gesehenen Adressen mit diesem Namen hinzufügen
     for (adr in all):
       if (addedDoublets.contains(adr.id)) continue  // bereits hinzugefügt überspringen
       if (doubletFullnames.contains(getNormalizedFullname(adr))):
         list.add(adr)                                // in das Ergebnis einfügen
         addedDoublets.add(adr.id)                    // als eingefügt markieren
     
     // Das aktuelle Element (das Duplikat) wird ebenfalls zurückgegeben
     return true

Entwurfsbegründung

Warum ein Post-Filter anstelle eines Datenbank-GROUP-BY + HAVING? Ein SQL GROUP BY normalized_name HAVING COUNT(*) > 1 würde erfordern, dass die Normalisierungsfunktion in SQL ausdrückbar ist (möglich, aber fragil aufgrund von SQL-Dialektunterschieden) und würde nicht die genauen Entitätsobjekte liefern, die für den Zusammenführungsdialog der Benutzeroberfläche benötigt werden. Der Post-Filter-Ansatz hält die Normalisierungslogik in Java/Kotlin, wo sie typisiert, testbar und konsistent mit dem Rest der Anwendung ist.

Warum das rückwirkende Leerungsmuster? Die match()-Schnittstelle gibt pro Element true/false zurück (ein-/ausschließen aus den Ergebnissen). Elemente, die verarbeitet wurden, bevor eine Dublette erkannt wurde, waren bereits ausgeschlossen (gaben false zurück). Das rückwirkende Leeren fügt diese früheren Instanzen durch direkte Änderung der Ergebnisliste ein. Dies ist ein beabsichtigter Nebeneffekt – der Filter hat Schreibzugriff auf die Liste und nutzt ihn, um die Streaming-Natur der match()-API auszugleichen.
