Propósito: Cuando una libreta de direcciones crece orgánicamente (importaciones, entradas manuales, migración de datos), se acumulan contactos duplicados — a menudo con variaciones menores en el formato pero nombres normalizados idénticos. Este filtro permite que la interfaz de la lista de direcciones muestre una vista de "Mostrar solo dobletes", ayudando a los administradores a encontrar y fusionar duplicados.

Arquitectura

Implementa CustomResultFilter<AddressDO> — una interfaz del framework ProjectForge para el filtrado posterior a la consulta. A diferencia del filtrado del lado de la base de datos (cláusulas WHERE), los filtros de resultados se ejecutan en memoria sobre el conjunto de resultados devuelto por el DAO. Esto es necesario para la deduplicación porque:

• Los duplicados pueden abarcar diferentes filas de la base de datos con diferentes IDs
• La lógica de normalización (getNormalizedFullname) implica manipulación de cadenas que no se puede expresar fácilmente en SQL/HQL
• El filtro necesita acumular estado a través de múltiples elementos — el método match() se llama para cada elemento en orden, pero muta conjuntos internos

Máquina de estados

El filtro opera como una máquina de estados de dos conjuntos y dos pasos:

Paso 1 (acumulación): A medida que cada elemento de dirección se pasa a match():
• Si el nombre completo normalizado ya está en fullnames, es un doblete — se añade a doubletFullnames
• Si no está en fullnames, es una primera ocurrencia — se añade a all y fullnames

Paso 2 (vaciado): Cuando se detecta un doblete, todas las direcciones vistas previamente cuyos nombres coincidan con cualquier nombre de doblete se añaden a la lista de resultados. El conjunto addedDoublets evita añadir la misma dirección dos veces.

Elecciones de estructura de datos

CampoTipoPropósito
fullnamesMutableSet<String> (HashSet)Rastrea todos los nombres normalizados únicos vistos hasta ahora — búsqueda O(1)
doubletFullnamesMutableSet<String> (HashSet)Rastrea nombres confirmados con ≥2 ocurrencias — usado para vaciado retroactivo
allMutableList<AddressDO> (ArrayList)Lista ordenada de todas las direcciones procesadas — necesaria porque las entradas anteriores no se devolvieron como coincidencias
addedDoubletsMutableSet<Long?> (HashSet)Guardia de deduplicación — evita añadir el mismo ID de dirección dos veces al resultado

Recorrido del algoritmo

Para cada dirección en el resultado de la consulta (ordenado por nombre):

1. Omitir direcciones eliminadas → devolver falso
  
2. Calcular normalizedFullname = AddressDao.getNormalizedFullname(elemento)
   (eliminar espacios en blanco, minúsculas, etc.)

3. Verificar fullnames.contains(normalizedFullname):
   
   NO (primera ocurrencia):
     all.add(elemento)
     fullnames.add(normalizedFullname)
     return false  (no incluir aún en resultados)
   
   SÍ (duplicado detectado):
     doubletFullnames.add(normalizedFullname)
     
     // Vaciar: añadir todas las direcciones vistas previamente que compartan este nombre
     for (adr in all):
       if (addedDoublets.contains(adr.id)) continue  // saltar ya añadido
       if (doubletFullnames.contains(getNormalizedFullname(adr))):
         list.add(adr)                                // inyectar en resultado
         addedDoublets.add(adr.id)                    // marcar como inyectado
     
     // El elemento actual (el duplicado) también se devuelve
     return true

Justificación del diseño

¿Por qué un filtro posterior en lugar de un GROUP BY + HAVING en la base de datos? Un GROUP BY normalized_name HAVING COUNT(*) > 1 en SQL requeriría que la función de normalización se pudiera expresar en SQL (posible pero frágil con diferencias de dialectos SQL) y no proporcionaría los objetos de entidad exactos necesarios para el diálogo de fusión de la interfaz. El enfoque de filtro posterior mantiene la lógica de normalización en Java/Kotlin, donde está tipificada, es comprobable y consistente con el resto de la aplicación.

¿Por qué el patrón de vaciado retroactivo? La interfaz match() devuelve true/false por elemento (incluir/excluir de los resultados). Los elementos procesados antes de detectar un doblete ya estaban excluidos (devolvían false). El vaciado retroactivo inyecta esas instancias anteriores mutando directamente la lista de resultados. Esto es un efecto secundario intencional — el filtro tiene acceso de escritura a la lista y lo usa para compensar la naturaleza de flujo continuo de la API match().
