Objectif : Lorsqu'un carnet d'adresses se développe de manière organique (importations, saisies manuelles, migration de données), des contacts en double s'accumulent — souvent avec des variations mineures dans le formatage mais des noms normalisés identiques. Ce filtre permet à l'interface de la liste d'adresses d'afficher une vue « Afficher uniquement les doublets », aidant les administrateurs à trouver et fusionner les doublons.

Architecture

Implémente CustomResultFilter<AddressDO> — une interface du framework ProjectForge pour le filtrage des résultats après requête. Contrairement au filtrage côté base de données (clauses WHERE), les filtres de résultats s'exécutent en mémoire sur l'ensemble de résultats renvoyé par le DAO. Cela est nécessaire pour le dédoublonnage car :

• Les doublons peuvent s'étendre sur différentes lignes de base de données avec des ID différents
• La logique de normalisation (getNormalizedFullname) implique des manipulations de chaînes qui ne peuvent pas être exprimées facilement en SQL/HQL
• Le filtre doit accumuler un état sur plusieurs éléments — la méthode match() est appelée pour chaque élément dans l'ordre mais modifie des ensembles internes

Machine à états

Le filtre fonctionne comme une machine à états à deux ensembles et deux passes :

Passe 1 (accumulation) : Lorsque chaque élément d'adresse est passé à match() :
• Si le nom complet normalisé est déjà dans fullnames, c'est un doublet — ajouté à doubletFullnames
• S'il n'est pas dans fullnames, c'est une première occurrence — ajouté à all et fullnames

Passe 2 (vidage) : Lorsqu'un doublet est détecté, toutes les adresses déjà vues dont le nom correspond à un nom de doublet sont ajoutées à la liste de résultats. L'ensemble addedDoublets empêche d'ajouter deux fois la même adresse.

Choix des structures de données

ChampTypeObjectif
fullnamesMutableSet<String> (HashSet)Stocke tous les noms normalisés uniques vus jusqu'à présent — recherche en O(1)
doubletFullnamesMutableSet<String> (HashSet)Stocke les noms confirmés comme ayant ≥2 occurrences — utilisé pour le vidage rétroactif
allMutableList<AddressDO> (ArrayList)Liste ordonnée de toutes les adresses traitées — nécessaire car les entrées précédentes n'ont pas été renvoyées comme correspondances
addedDoubletsMutableSet<Long?> (HashSet)Garde de dédoublonnage — empêche d'ajouter deux fois le même ID d'adresse au résultat

Parcours de l'algorithme

Pour chaque adresse dans le résultat de la requête (trié par nom) :

1. Ignorer les adresses supprimées → retourner false
  
2. Calculer normalizedFullname = AddressDao.getNormalizedFullname(element)
   (supprimer les espaces, mettre en minuscules, etc.)

3. Vérifier fullnames.contains(normalizedFullname) :
   
   NON (première occurrence) :
     all.add(element)
     fullnames.add(normalizedFullname)
     return false  (ne pas inclure dans les résultats pour l'instant)
   
   OUI (doublet détecté) :
     doubletFullnames.add(normalizedFullname)
     
     // Vidage : ajouter toutes les adresses déjà vues partageant ce nom
     pour (adr dans all) :
       si (addedDoublets.contains(adr.id)) continuer  // ignorer déjà ajouté
       si (doubletFullnames.contains(getNormalizedFullname(adr))) :
         list.add(adr)                                // injecter dans le résultat
         addedDoublets.add(adr.id)                    // marquer comme injecté
     
     // L'élément courant (le doublon) est également renvoyé
     return true

Justification de la conception

Pourquoi un post-filtre plutôt qu'un GROUP BY + HAVING en base de données ? Un GROUP BY normalized_name HAVING COUNT(*) > 1 en SQL nécessiterait que la fonction de normalisation soit exprimable en SQL (possible mais fragile avec les différences de dialectes SQL) et ne fournirait pas les objets d'entité exacts nécessaires à la boîte de dialogue de fusion de l'interface utilisateur. L'approche par post-filtre maintient la logique de normalisation en Java/Kotlin où elle est typée, testable et cohérente avec le reste de l'application.

Pourquoi le modèle de vidage rétroactif ? L'interface match() renvoie true/false par élément (inclure/exclure des résultats). Les éléments traités avant la détection d'un doublet étaient déjà exclus (renvoyaient false). Le vidage rétroactif injecte ces instances antérieures en mutant directement la liste de résultats. C'est un effet secondaire intentionnel — le filtre a un accès en écriture à la liste et l'utilise pour compenser la nature séquentielle de l'API match().
