Zusammenfassung: CalendarEventColorScheme ist ein minimales Zwei-Werte-Enum, das steuert, wie Kalenderereignisse in der Kalender-Benutzeroberfläche eingefärbt werden. STANDARD rendert Ereignisse mit der ProjectForge-Standardpalette und -Deckkraft, während CLASSIC Deckkraft-Effekte für Benutzer entfernt, die einen höheren Kontrast benötigen – insbesondere für Menschen mit Sehbehinderungen oder bei der Verwendung von Projektoren in Besprechungsräumen.

Enum-Werte

Enum-KonstanteSchlüsseli18n-EigenschaftVerhalten
STANDARD standard calendar.settings.colors.scheme.standard Standard-Farbdarstellung mit Deckkraft-/Transparenzeffekten, wie vom Thema definiert.
CLASSIC classic calendar.settings.colors.scheme.classic Solide, vollständig deckende Farben ohne Transparenz – besser für Benutzer, die einen höheren Kontrast benötigen, oder für Anzeigegeräte mit geringer Qualität.

Architektur

Dieses Enum wird aus benutzerspezifischen Kalendereinstellungen referenziert (wahrscheinlich den PFUserDO-Einstellungen oder einer dedizierten Kalendereinstellungs-Entität). Der ausgewählte Wert wird als Zeichenkette ("standard" oder "classic") gespeichert und von der Frontend-Rendering-Schicht (Wicket-Komponenten oder JavaScript) verwendet, um die CSS-Klasse oder das Inline-Style zu bestimmen, die auf Kalenderereigniszellen angewendet werden. Die I18nEnum-Implementierung stellt lokalisierte Bezeichnungen für die Einstellungs-Benutzeroberfläche bereit, in der Benutzer ihr bevorzugtes Schema auswählen.

Da es nur zwei Werte hat, ist das Enum bewusst einfach gehalten. Eine Erweiterung um weitere Schemata (z. B. einen kontrastreichen Modus, eine farbenblindenfreundliche Palette) würde nur das Hinzufügen neuer Konstanten erfordern – das Muster unterstützt bereits eine Erweiterung.

Design-Entscheidungen

Warum nur zwei Werte?

Das CLASSIC-Schema wurde speziell hinzugefügt, um ein Barrierefreiheitsproblem zu adressieren – teilweise transparente Ereignisrechtecke können für Benutzer mit Sehschwäche oder auf Projektoren mit schlechtem Kontrast schwer zu unterscheiden sein. Anstatt eine vollständige Theme-Engine zu bauen, entschied sich das Team für einen einfachen binären Umschalter. Dies hält die Einstellungs-Benutzeroberfläche einfach und den Rendering-Code unkompliziert: eine einzelne bedingte Verzweigung im Frontend anstelle einer komplexen Farbzuordnungs-Pipeline.

Warum ein Enum anstelle eines booleschen Werts isHighContrast: Boolean?

Ein Enum ist zukunftssicher. Wenn zukünftige Anforderungen ein drittes Schema verlangen (z. B. eine Dunkelmodus-Palette oder einen deuteranopie-freundlichen Farbsatz), ist das Hinzufügen einer neuen Konstante eine nicht-brechende Änderung. Ein boolescher Wert würde später eine Migration zu einem Enum erfordern, die das Datenbankschema, die Einstellungs-Benutzeroberfläche und alle Verbraucher betrifft. Mit einem Enum zu beginnen – selbst einem mit zwei Werten – vermeidet diese zukünftigen Refactoring-Kosten ohne nennenswerten Mehraufwand.

Warum I18nEnum für eine so kleine Menge implementieren?

Konsistenz. Jede benutzersichtbare Aufzählung in ProjectForge implementiert I18nEnum, damit die Einstellungs-Benutzeroberfläche Dropdowns generisch rendern kann: Bei einer beliebigen I18nEnum-Unterklasse kann das Framework ihre Werte durchlaufen und lokalisierte Bezeichnungen nachschlagen. Diese Einheitlichkeit bedeutet, dass die Kalendereinstellungsseite keinen Sonderfall-Code benötigt, um den Farbschema-Auswähler zu behandeln – sie verwendet dieselbe Komponente wie jede andere Enum-gestützte Einstellung.
