Résumé : CalendarEventColorScheme est une énumération minimale à deux valeurs qui contrôle la façon dont les événements du calendrier sont colorés dans l'interface utilisateur du calendrier. STANDARD affiche les événements avec la palette et l'opacité par défaut de ProjectForge, tandis que CLASSIC supprime les effets d'opacité pour les utilisateurs qui ont besoin d'un contraste plus élevé — en particulier ceux ayant des déficiences visuelles ou lors de l'utilisation de projecteurs dans les salles de réunion.

Valeurs de l'énumération

Constante d'énumérationCléPropriété i18nComportement
STANDARD standard calendar.settings.colors.scheme.standard Rendu des couleurs par défaut avec effets d'opacité/transparence tels que définis par le thème.
CLASSIC classic calendar.settings.colors.scheme.classic Couleurs unies, entièrement opaques sans transparence — meilleur pour les utilisateurs ayant besoin d'un contraste plus élevé ou pour les dispositifs d'affichage de faible qualité.

Architecture

Cette énumération est référencée à partir des paramètres de calendrier spécifiques à l'utilisateur (probablement les préférences PFUserDO ou une entité dédiée de paramètres de calendrier). La valeur sélectionnée est persistée sous forme de chaîne ("standard" ou "classic") et utilisée par la couche de rendu front-end (composants Wicket ou JavaScript) pour déterminer la classe CSS ou le style en ligne appliqué aux cellules des événements du calendrier. L'implémentation de I18nEnum fournit des étiquettes localisées pour l'interface utilisateur des paramètres où les utilisateurs choisissent leur schéma préféré.

Parce qu'elle n'a que deux valeurs, l'énumération est intentionnellement simple. L'étendre avec plus de schémas (par exemple un mode à contraste élevé, une palette adaptée aux daltoniens) nécessiterait seulement d'ajouter de nouvelles constantes — le modèle prend déjà en charge l'expansion.

Justification de la conception

Pourquoi seulement deux valeurs ?

Le schéma CLASSIC a été ajouté spécifiquement pour répondre à un problème d'accessibilité — les rectangles d'événements partiellement transparents peuvent être difficiles à distinguer pour les utilisateurs malvoyants ou sur des projecteurs avec un faible contraste. Plutôt que de construire un moteur de thème complet, l'équipe a choisi un simple basculement binaire. Cela maintient l'interface utilisateur des paramètres simple et le code de rendu direct : une branche conditionnelle unique dans le front-end au lieu d'un pipeline complexe de mappage des couleurs.

Pourquoi une énumération plutôt qu'un booléen isHighContrast: Boolean ?

Une énumération est évolutive. Si de futures exigences nécessitent un troisième schéma (par exemple une palette en mode sombre, ou un jeu de couleurs adapté à la deutéranopie), l'ajout d'une nouvelle constante est un changement non cassant. Un booléen nécessiterait une migration vers une énumération plus tard, touchant le schéma de base de données, l'interface utilisateur des paramètres et tous les consommateurs. Commencer par une énumération — même à deux valeurs — évite ce futur coût de refactorisation sans surcharge significative.

Pourquoi implémenter I18nEnum pour un ensemble aussi petit ?

Cohérence. Chaque énumération visible par l'utilisateur dans ProjectForge implémente I18nEnum afin que l'interface utilisateur des paramètres puisse afficher les listes déroulantes de manière générique : étant donné n'importe quelle sous-classe de I18nEnum, le framework peut itérer ses valeurs et rechercher les étiquettes localisées. Cette uniformité signifie que la page des paramètres du calendrier n'a pas besoin de code spécial pour gérer le sélecteur de schéma de couleurs — elle utilise le même composant que tous les autres paramètres basés sur une énumération.
