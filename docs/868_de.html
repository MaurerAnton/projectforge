#868: ICalendarEvent.kt

projectforge-business/src/main/kotlin/org/projectforge/business/calendar/event/model/ICalendarEvent.kt Typ: Kotlin-Schnittstelle
Zweck: Gemeinsamer Vertrag für alle Kalenderereignis-Implementierungen über Kalendertypen hinweg
Quellpfad: projectforge-business/src/main/kotlin/org/projectforge/business/calendar/event/model/ICalendarEvent.kt 45 Zeilen · 11 Code · 25 Kommentare · 9 leer

ICalendarEvent definiert die minimale Menge an Eigenschaften, die jedes Kalenderereignis im ProjectForge-System bereitstellen muss. Diese Schnittstelle ermöglicht es, verschiedene Ereignistypen (Team-Kalenderereignisse, Zeiterfassungseinträge, Urlaubseinträge, Geburtstage) einheitlich durch Kalender-Rendering- und Filtercode zu behandeln. Ursprünglich handelte es sich um eine Java-Klasse (TeamEvent.java), die im Rahmen der Modernisierungsbemühungen in eine Kotlin-Schnittstelle umgewandelt wurde.

Schnittstelleneigenschaften

EigenschaftTypBeschreibung
uid String? Eindeutige Kennung für das Ereignis. Kann null sein, um Ereignistypen ohne native UIDs zu berücksichtigen.
subject String? Der Ereignistitel oder die Betreffzeile. Wird als primärer Text im Kalender angezeigt.
location String? Physischer oder virtueller Ort des Ereignisses. Kann null sein für Ereignisse ohne Ort.
allDay Boolean Gibt an, ob das Ereignis einen ganzen Tag (oder mehrere volle Tage) umfasst. Beeinflusst die Darstellung (keine Zeitschlitze).
startDate Date? Das Startdatum und die Startzeit des Ereignisses (legacy java.util.Date). Kann null sein, um Randfälle zu unterstützen.
endDate Date? Das Enddatum und die Endzeit des Ereignisses. Kann null sein – einige Implementierungen können die Dauer aus startDate ableiten.
note String? Optionale Beschreibung oder Notiztext. Wird in Tooltips und Detailansichten angezeigt.

Architektur

Diese Schnittstelle dient als gemeinsamer Nenner für Ereignisquellen:

  • Team-Kalenderereignisse implementieren die vollständige Schnittstelle mit persistierten Daten.
  • Zeiterfassungseinträge werden an diese Schnittstelle angepasst, sodass sie neben Kalenderereignissen erscheinen können.
  • Urlaubseinträge implementieren die Schnittstelle für die Überlagerungsanzeige von Urlaub.
  • Geburtstagsereignisse sind synthetische Ereignisse, die aus Benutzerprofildaten erstellt werden.

Indem das Kalender-Rendering und die Filterung gegen ICalendarEvent anstatt gegen eine konkrete Klasse codiert werden, erreicht das System Polymorphie über diese unterschiedlichen Ereignisquellen hinweg, ohne eine gemeinsame Basisklasse oder Datenbanktabelle zu benötigen.

Design-Entscheidungen

Die Umwandlung der ursprünglichen Java-Klasse TeamEvent in eine Kotlin-Schnittstelle (ICalendarEvent) war eine wichtige architektonische Verbesserung (Commit aab28d48a). Eine konkrete Klasse implizierte eine einzelne Implementierung mit gemeinsamem Zustand; eine Schnittstelle erlaubt es jedem Ereignistyp, seine Datenstruktur unabhängig zu verwalten und dennoch polymorph durch den Kalendercode behandelt zu werden. Der Typ java.util.Date (anstelle von java.time) bleibt bestehen, da viele Implementierungen JPA-Entitäten sind, die auf Date-Datenbankspalten basieren. Die umfangreiche Verwendung von nullable-Typen spiegelt die Realität unvollständiger Ereignisdaten wider (z. B. hat ein ganztägiges Ereignis möglicherweise keine sinnvolle Start-/Endzeit, ein Geburtstag hat keinen Ort).
