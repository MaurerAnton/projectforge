Propósito: Contrato común para todas las implementaciones de eventos de calendario en todos los tipos de calendario
Ruta de origen: projectforge-business/src/main/kotlin/org/projectforge/business/calendar/event/model/ICalendarEvent.kt 45 líneas · 11 código · 25 comentarios · 9 en blanco

ICalendarEvent define el conjunto mínimo de propiedades que cualquier evento de calendario en el sistema ProjectForge debe exponer. Esta interfaz permite que diferentes tipos de eventos (eventos de calendario de equipo, registros de horas, entradas de vacaciones, cumpleaños) sean manejados de manera uniforme por el código de renderizado y filtrado del calendario. Originalmente era una clase Java (TeamEvent.java) y se convirtió a una interfaz Kotlin durante el esfuerzo de modernización.

Propiedades de la interfaz

PropiedadTipoDescripción
uid String? Identificador único del evento. Puede ser anulable para adaptarse a tipos de eventos sin UID nativos.
subject String? El título o línea de asunto del evento. Se muestra como texto principal en el calendario.
location String? Ubicación física o virtual del evento. Anulable para eventos sin ubicación.
allDay Boolean Indica si el evento abarca un día completo (o varios días completos). Afecta la representación (sin franjas horarias).
startDate Date? La fecha y hora de inicio del evento (java.util.Date heredado). Anulable para soportar casos extremos.
endDate Date? La fecha y hora de finalización del evento. Anulable — algunas implementaciones pueden inferir la duración desde startDate.
note String? Descripción opcional o texto de nota. Se muestra en tooltips y vistas de detalle.

Arquitectura

Esta interfaz sirve como denominador común entre las fuentes de eventos:

  • Eventos de calendario de equipo implementan la interfaz completa con datos persistidos.
  • Registros de horas se adaptan a esta interfaz para que puedan aparecer junto a los eventos del calendario.
  • Entradas de vacaciones implementan la interfaz para la visualización superpuesta de vacaciones.
  • Eventos de cumpleaños son eventos sintéticos creados a partir de los datos del perfil de usuario.

Al programar el renderizado y filtrado del calendario contra ICalendarEvent en lugar de una clase concreta, el sistema logra polimorfismo entre estas diversas fuentes de eventos sin requerir una clase base común o una tabla de base de datos.

Justificación del diseño

Convertir la clase Java original TeamEvent a una interfaz Kotlin (ICalendarEvent) fue una mejora arquitectónica clave (commit aab28d48a). Una clase concreta implicaba una única implementación con estado compartido; una interfaz permite que cada tipo de evento posea su propia estructura de datos de forma independiente, mientras sigue siendo tratado polimórficamente por el código del calendario. El tipo java.util.Date (en lugar de java.time) persiste porque muchos implementadores son entidades JPA respaldadas por columnas de base de datos Date. El uso extensivo de tipos anulables refleja la realidad de los datos parciales del evento (por ejemplo, un evento de todo el día puede no tener una hora de inicio/fin significativa, un cumpleaños no tiene ubicación).
