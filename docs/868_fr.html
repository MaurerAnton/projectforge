ICalendarEvent définit l'ensemble minimal de propriétés que tout événement de calendrier dans le système ProjectForge doit exposer. Cette interface permet aux différents types d'événements (événements de calendrier d'équipe, saisies de temps, entrées de congés, anniversaires) d'être traités de manière uniforme par le code de rendu et de filtrage du calendrier. Elle était à l'origine une classe Java (TeamEvent.java) et a été convertie en interface Kotlin lors de l'effort de modernisation.

Propriétés de l'interface

PropriétéTypeDescription
uid String? Identifiant unique de l'événement. Peut être nullable pour prendre en charge les types d'événements sans UID natif.
subject String? Le titre ou l'objet de l'événement. Affiché comme texte principal dans le calendrier.
location String? Lieu physique ou virtuel de l'événement. Nullable pour les événements sans lieu.
allDay Boolean Indique si l'événement s'étend sur une journée entière (ou plusieurs jours complets). Affecte le rendu (pas de créneaux horaires).
startDate Date? La date et l'heure de début de l'événement (java.util.Date hérité). Nullable pour prendre en charge les cas particuliers.
endDate Date? La date et l'heure de fin de l'événement. Nullable — certaines implémentations peuvent déduire la durée à partir de startDate.
note String? Description facultative ou texte de note. Affiché dans les infobulles et les vues détaillées.

Architecture

Cette interface sert de dénominateur commun entre les sources d'événements :

  • Les événements du calendrier d'équipe implémentent l'interface complète avec des données persistées.
  • Les saisies de temps sont adaptées à cette interface afin de pouvoir apparaître aux côtés des événements du calendrier.
  • Les entrées de congés implémentent l'interface pour l'affichage de la superposition des congés.
  • Les événements d'anniversaire sont des événements synthétiques créés à partir des données du profil utilisateur.

En programmant le rendu et le filtrage du calendrier par rapport à ICalendarEvent plutôt qu'à une classe concrète, le système atteint un polymorphisme entre ces sources d'événements disparates sans nécessiter de classe de base commune ni de table de base de données.

Justification de la conception

La conversion de la classe Java d'origine TeamEvent en une interface Kotlin (ICalendarEvent) a été une amélioration architecturale clé (commit aab28d48a). Une classe concrète impliquait une implémentation unique avec un état partagé ; une interface permet à chaque type d'événement de posséder sa propre structure de données de manière indépendante tout en étant traité de manière polymorphe par le code du calendrier. Le type java.util.Date (plutôt que java.time) persiste car de nombreux implémenteurs sont des entités JPA adossées à des colonnes de base de données de type Date. L'utilisation intensive de types nullables reflète la réalité des données partielles d'événement (par exemple, un événement d'une journée entière peut ne pas avoir d'heure de début/fin significative, un anniversaire n'a pas de lieu).
