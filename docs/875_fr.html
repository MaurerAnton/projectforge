Un ValueBridge<String?, String> Hibernate Search qui transforme un champ de numéro de téléphone en une chaîne richement indexable en combinant la valeur originale, une forme normalisée (chiffres uniquement) et une extraction formatée. Permet aux recherches comme « +49 30 123456 », « 4930123456 » et « 030/123456 » de toutes correspondre au même enregistrement.

Signature du pont

class HibernateSearchPhoneNumberBridge : ValueBridge<String?, String>
  • Type d'entrée : String nullable (le numéro de téléphone brut depuis l'entité)
  • Type indexé : String (la chaîne composite stockée dans l'index de recherche)

toIndexedValue()

override fun toIndexedValue(number: String?, context: ValueBridgeToIndexedValueContext): String

Produit une chaîne composite séparée par des espaces contenant trois représentations :

  1. Numéro original : L'entrée brute (ex. "+49 30 123456-78")
  2. Numéro normalisé : Chiffres uniquement via StringHelper.removeNonDigits(number) (ex. "493012345678")
  3. Numéro formaté : Numéro de téléphone extrait via NumberHelper.extractPhonenumber(number)

Exemple de résultat : "+49 30 123456-78 493012345678 030/12345678"

L'analyseur par défaut de Hibernate Search tokenise sur les espaces blancs, rendant les trois formes indépendamment recherchables.

Une entrée nulle retourne une chaîne vide (""), pas null. Cela évite les NPE dans l'écrivain d'index de recherche.

Justification de la conception

Les numéros de téléphone sont notoirement difficiles à rechercher car les utilisateurs les saisissent dans divers formats : international (+49 30 123456), local (030/123456), compact (4930123456), ou avec ponctuation. En indexant plusieurs formes normalisées côte à côte dans un seul champ, tout format de recherche saisi par l'utilisateur peut correspondre.

L'approche onlyDigits traite le cas le plus général (tout format se réduit à la même séquence de chiffres), tandis que l'approche extractPhonenumber préserve les conventions de formatage local pour les scénarios de correspondance exacte.
