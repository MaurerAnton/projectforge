#875: HibernateSearchPhoneNumberBridge.kt

projectforge-business/src/main/kotlin/org/projectforge/business/common/HibernateSearchPhoneNumberBridge.kt Тип: Hibernate Search ValueBridge · Назначение: Полнотекстовый поиск по номеру телефона · Исходник: projectforge-business/src/main/kotlin/org/projectforge/business/common/HibernateSearchPhoneNumberBridge.kt 46 строк · 16 кода · 26 комментариев · 4 пустых
Мост Hibernate Search ValueBridge<String?, String>, который преобразует поле номера телефона в расширенную строку для поиска, объединяя исходное значение, нормализованную форму (только цифры) и форматированное извлечение. Позволяет таким запросам, как "+49 30 123456", "4930123456" и "030/123456", находить одну и ту же запись.

Сигнатура моста

class HibernateSearchPhoneNumberBridge : ValueBridge<String?, String>
  • Входной тип: nullable String (сырой номер телефона из сущности)
  • Индексируемый тип: String (составная строка, сохраняемая в поисковом индексе)

toIndexedValue()

override fun toIndexedValue(number: String?, context: ValueBridgeToIndexedValueContext): String

Создаёт составную строку, разделённую пробелами, содержащую три представления:

  1. Исходный номер: Сырой ввод (например, "+49 30 123456-78")
  2. Нормализованный номер: Только цифры через StringHelper.removeNonDigits(number) (например, "493012345678")
  3. Форматированный номер: Извлечённый номер телефона через NumberHelper.extractPhonenumber(number)

Пример результата: "+49 30 123456-78 493012345678 030/12345678"

Стандартный анализатор Hibernate Search разбивает по пробелам, делая все три формы независимо доступными для поиска.

При пустом вводе возвращается пустая строка (""), а не null. Это предотвращает NPE в писателе поискового индекса.

Обоснование дизайна

Номера телефонов notoriously сложны для поиска, поскольку пользователи вводят их в разных форматах: международном (+49 30 123456), локальном (030/123456), компактном (4930123456) или с пунктуацией. Индексируя несколько нормализованных форм рядом в одном поле, любой введённый пользователем формат поиска может совпасть.

Подход onlyDigits обрабатывает наиболее общий случай (любой формат сводится к одной и той же последовательности цифр), в то время как подход extractPhonenumber сохраняет локальные соглашения форматирования для сценариев точного совпадения.
