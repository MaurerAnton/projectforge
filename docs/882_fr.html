Objectif : Extrait les partenaires commerciaux (fournisseurs, clients) des tables financières de ProjectForge et les convertit en objets TradingPartner adaptés à l'import initial D-velop.

Agit comme la passerelle entre les données financières historiques de ProjectForge (factures entrantes, factures sortantes et données maîtres clients) et le modèle de partenaire commercial de D-velop. Il analyse 5 années de données de facturation, déduplique les entités entre comptes, gère le modèle de compte « divers », analyse les adresses de facturation en texte libre en champs structurés et classe les entités en FOURNISSEUR, CLIENT ou PARTENAIRE. Fournit également une fonctionnalité d'export Excel pour le rapprochement.

Phases d'extraction

Phase 1 : extractTradingVendors(invoices)

Traite les EingangsrechnungDO (factures entrantes/créanciers) :

  • Ignore les factures sans nom de kreditor ou sans affectation de konto
  • Comptes « divers » : Si la description du compte contient « divers », chaque nom de créancier unique reçoit un nouveau numéro de partenaire synthétique (depuis nextVal) car plusieurs créanciers partagent le même compte
  • Comptes normaux : Un partenaire par numéro de compte ; le champ importCode est défini sur le numéro de compte pour référence croisée lors des phases ultérieures
  • Tous les fournisseurs voient leur champ datevKonto défini sur le numéro de compte et les remarques sont préfixées par les informations du compte

Phase 2 : extractTradingCustomersInvoices(invoices, context)

Traite les RechnungDO (factures sortantes/clients) :

  • Si la facture a un kunde (client) lié, délègue à handleKunde()
  • Si pas de client mais un compte existe, tente de faire correspondre les fournisseurs existants (en les promouvant en PARTENAIRE) ou crée de nouvelles entrées client
  • Ignore les comptes « divers » (aucun partenaire commercial nécessaire)

Phase 3 : extractTradingCustomers(customers, context)

Traite les KundeDO (données maîtres clients) pour les clients non encore capturés via les factures. Appelle context.cleanUp() à la fin.

Logique centrale de déduplication : handleKunde()

La méthode la plus complexe de ce service. Pour chaque KundeDO :

  1. Vérifie si un client avec le même numéro existe déjà → ignore la création, remplit éventuellement datevKonto
  2. Vérifie si le compte correspond à un fournisseur existant → promeut le fournisseur en PARTENAIRE, réaffecte le numéro client comme numéro principal
  3. Sinon, crée un nouveau client ; les clients actifs sont ceux avec le statut ACQUISITION ou ACTIVE (ou null)

Analyse d'adresse : checkBillAddress()

Analyse les adresses de facturation en texte libre des chaînes customerAddress des factures en utilisant une heuristique ascendante :

  1. Divise l'adresse en lignes non vides
  2. Filtre les lignes de début correspondant à des mots de remplissage connus (« Herr », « Frau », « Firma », « An », « Portal », « Klinikdienst »)
  3. Dernière ligne : pays ou code postal+ville (tente extractZipCodeCity())
  4. Avant-dernière : ligne de rue
  5. Toutes les lignes restantes sont ajoutées en préfixe à billToAddressAdditional

extractZipCodeCity(line)

Utilise une expression régulière ^[0-9 ]{5,10} pour extraire un code postal allemand de 5 chiffres ou plus. Supprime les préfixes de pays « D- » et « D ». Retourne Pair<String, String> de (codePostal, ville) ou null si aucune correspondance.

Export Excel : extractTradingPartnersAsExcel()

Crée un classeur Excel à deux feuilles en utilisant ExcelWorkbook :

  • Feuille 1 : « D.velop TradingPartners » — la liste passée en paramètre
  • Feuille 2 : « ProjectForge TradingPartners » — liste fraîchement extraite de la base de données

Les colonnes incluent le numéro, datevKonto, importCode, type, société, nom court, remarques, actif et tous les champs d'adresse de facturation. Les valeurs d'énumération (contactType, type, active) sont résolues en leur représentation sous forme de chaîne value.
