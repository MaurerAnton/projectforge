#886: AbstractRechnungCache.kt

projectforge-business/src/main/kotlin/org/projectforge/business/fibu/AbstractRechnungCache.kt

Typ: Kotlin-abstrakte Klasse, die AbstractCache erweitert — Cache-Schicht für Rechnungsberechnungen

Zweck: Zwischenspeichert vorberechnete Rechnungssummen (RechnungInfo) und Positionsberechnungen (RechnungPosInfo), um redundante Neuberechnungen zu vermeiden. Unterstützt sowohl ausgehende Rechnungen (RechnungDO) als auch eingehende Rechnungen (EingangsrechnungDO) über seinen generischen Typparameter.

Quellpfad: projectforge-business/src/main/kotlin/org/projectforge/business/fibu/AbstractRechnungCache.kt

136 Zeilen · 79 Code · 44 Kommentare · 13 leer

Eine In-Memory-Performance-Cache-Schicht auf Basis des AbstractCache-Frameworks. Rechnungsberechnungen (Netto-/Bruttosummen, Umsatzsteueraufschlüsselung, Kostenverteilung) sind aufwändig, da sie das Durchlaufen des gesamten Positionsbaums mit Kostenzuordnungsabfragen erfordern. Dieser Cache speichert vorberechnete RechnungInfo- und RechnungPosInfo-Objekte, die nach Entitäts-ID indiziert sind, mit automatischer Aktualisierung über den CacheHelper-Scheduling-Mechanismus. Der Cache wurde von synchronized-Blöcken auf ConcurrentHashMap umgestellt, um einen Deadlock zu beseitigen.

Typparameter & Konstruktor

abstract class AbstractRechnungCache(

Interner Zustand

FeldTypBeschreibung

invoicePosInfoMapConcurrentHashMap<Long, RechnungPosInfo>Sekundärer Cache: Positions-ID → positionsbezogene Berechnungen

Beide Maps verwenden ConcurrentHashMap (keine synchronisierten Blöcke) — diese Änderung wurde im Commit 85d8930b3 vorgenommen, um einen Deadlock zu beheben, der auftrat, wenn Cache-Operationen unter Synchronisation miteinander interagierten.

Öffentliche API

update(invoice: AbstractRechnungDO)

Erzwingt die Neuberechnung einer einzelnen Rechnung und speichert das Ergebnis im Cache. Wird aufgerufen, wenn eine Rechnung geändert wird (eingefügt, aktualisiert oder gelöscht über die DAO-Schicht). Verwendet RechnungCalculator.calculate(invoice), um aktuelle Werte zu berechnen.

ensureRechnungInfo(rechnung: AbstractRechnungDO): RechnungInfo

Garantiert, dass eine RechnungInfo für die angegebene Rechnung existiert. Wenn bereits zwischengespeichert, wird die gecachte Version zurückgegeben (und setzt rechnung.info). Andernfalls wird sie über RechnungCalculator berechnet, im Cache gespeichert und zurückgegeben. Dies ist der bevorzugte Zugriff — er funktioniert auch, wenn der Positionsbaum noch nicht nachgeladen wurde.

getRechnungInfo(rechnungId: Long?): RechnungInfo?

Gibt zwischengespeicherte Rechnungsinformationen nach ID zurück (null-sicher für den ID-Parameter). Ruft checkRefresh() auf, das sicherstellt, dass der Cache nicht veraltet ist.

getRechnungInfo(rechnung: AbstractRechnungDO?): RechnungInfo?

Überladung, die die ID aus der Entität extrahiert. Null-sicher.

ensureRechnungPosInfo(pos: AbstractRechnungsPositionDO): RechnungPosInfo

Analog zu ensureRechnungInfo, aber für einzelne Positionen. Stellt sicher, dass die RechnungInfo der übergeordneten Rechnung zuerst existiert (wird als Kontext benötigt), und berechnet dann positionsspezifische Informationen über RechnungCalculator.calculate(posInfo, pos).

getRechnungPosInfo(rechnungPosId: Long?): RechnungPosInfo?

Gibt zwischengespeicherte Positionsinformationen nach ID zurück. Null-sicher.

Cache-Aktualisierung (override fun refresh())

Wird automatisch vom CacheHelper-Framework zeitgesteuert und während der checkRefresh()-Absicherung aufgerufen. Die Aktualisierungsstrategie verwendet Copy-and-Swap für die Thread-Sicherheit:

  1. Erstellt neue ConcurrentHashMap-Instanzen (nInvoiceInfoMap, nInvoicePosInfoMap)
  2. Lädt alle Rechnungsinformationen massenweise über rechnungJdbcService.selectRechnungInfos(entityClass) — dies verwendet JDBC direkt für die Leistung und umgeht Hibernate
  3. Befüllt beide Maps aus dem JDBC-Ergebnissatz
  4. Tauscht atomar die neuen Maps anstelle der alten aus

Dieser Ansatz bedeutet, dass der Cache nie länger als einen Aktualisierungszyklus veraltet ist und Lesevorgänge nie durch den Aktualisierungsvorgang blockiert werden.

Architekturanmerkungen

  • Konkrete Unterklassen: RechnungCache (für RechnungDO) und EingangsrechnungCache (für EingangsrechnungDO), die jeweils nur den entityClass-Parameter bereitstellen
  • Verwendet Kotlins kotlin.reflect.KClass anstelle von Javas Class für Typsicherheit
  • Das @Transient lateinit var info auf AbstractRechnungDO ist das Begleitfeld, das dieser Cache befüllt
  • Während der Aktualisierung werden Positionen ohne IDs als Fehler protokolliert — dies kann bei geklonten Rechnungen passieren, bei denen Positions-IDs noch nicht zugewiesen wurden
  • Das LogDuration-Dienstprogramm verfolgt die Aktualisierungsleistung in den Protokollen
