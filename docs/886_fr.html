Type : Classe abstraite Kotlin étendant AbstractCache — Couche de cache pour les calculs de factures

Objectif : Met en cache les totaux de factures pré-calculés (RechnungInfo) et les calculs de positions (RechnungPosInfo) afin d'éviter des recalculs redondants. Une couche de cache de performance en mémoire au-dessus du framework AbstractCache. Les calculs de factures (totaux nets/bruts, ventilation de la TVA, affectations des coûts) sont coûteux car ils nécessitent de parcourir l'ensemble de l'arborescence des positions avec des recherches d'affectation des coûts. Ce cache stocke des objets RechnungInfo et RechnungPosInfo pré-calculés, indexés par l'ID de l'entité, avec un rafraîchissement automatique via le mécanisme de planification CacheHelper. Le cache a été refactorisé, passant de blocs synchronized à ConcurrentHashMap pour éliminer un interblocage.

Paramètres de type et constructeur

abstract class AbstractRechnungCache(
    val entityClass: KClass<out AbstractRechnungDO>,
    protected val rechnungJdbcService: RechnungJdbcService,
) : AbstractCache()
ParamètreDescription
entityClassLa référence de classe Kotlin pour le type d'entité de facture (RechnungDO::class ou EingangsrechnungDO::class) — utilisée pour les requêtes JDBC et la journalisation
rechnungJdbcServiceService JDBC pour le chargement groupé efficace des informations de facture depuis la base de données (contourne Hibernate pour la performance)

État interne

ChampTypeDescription
invoiceInfoMapConcurrentHashMap<Long, RechnungInfo>Cache principal : ID de facture → calculs de facture agrégés
invoicePosInfoMapConcurrentHashMap<Long, RechnungPosInfo>Cache secondaire : ID de position → calculs au niveau de la position

Les deux maps utilisent ConcurrentHashMap (pas de blocs synchronisés) — ce changement a été effectué dans le commit 85d8930b3 pour corriger un interblocage qui se produisait lorsque les opérations du cache interagissaient entre elles sous synchronisation.

API publique

update(invoice: AbstractRechnungDO)

Force le recalcul d'une seule facture et stocke le résultat dans le cache. Appelé lorsqu'une facture est modifiée (insérée, mise à jour ou supprimée via la couche DAO). Utilise RechnungCalculator.calculate(invoice) pour calculer des valeurs à jour.

ensureRechnungInfo(rechnung: AbstractRechnungDO): RechnungInfo

Garantit qu'un RechnungInfo existe pour la facture donnée. Si déjà en cache, retourne la version en cache (et définit rechnung.info). Sinon, le calcule via RechnungCalculator, le stocke dans le cache et le retourne. C'est l'accesseur privilégié — il fonctionne même si l'arborescence des positions n'a pas encore été chargée paresseusement.

getRechnungInfo(rechnungId: Long?): RechnungInfo?

Retourne les informations de facture mises en cache par ID (sécurisé contre les valeurs nulles pour le paramètre ID). Appelle checkRefresh() qui garantit que le cache n'est pas obsolète.

getRechnungInfo(rechnung: AbstractRechnungDO?): RechnungInfo?

Surcharge qui extrait l'ID de l'entité. Sécurisé contre les valeurs nulles.

ensureRechnungPosInfo(pos: AbstractRechnungsPositionDO): RechnungPosInfo

Analogue à ensureRechnungInfo mais pour les positions individuelles. Garantit d'abord que le RechnungInfo de la facture parente existe (nécessaire comme contexte), puis calcule les informations spécifiques à la position via RechnungCalculator.calculate(posInfo, pos).

getRechnungPosInfo(rechnungPosId: Long?): RechnungPosInfo?

Retourne les informations de position mises en cache par ID. Sécurisé contre les valeurs nulles.

Rafraîchissement du cache (override fun refresh())

Appelé automatiquement par le framework CacheHelper sur une minuterie et pendant la garde checkRefresh(). La stratégie de rafraîchissement utilise la copie et l'échange pour la sécurité des threads :

  1. Crée de nouvelles instances de ConcurrentHashMap (nInvoiceInfoMap, nInvoicePosInfoMap)
  2. Charge en masse toutes les informations de facture via rechnungJdbcService.selectRechnungInfos(entityClass) — cela utilise JDBC directement pour la performance, contournant Hibernate
  3. Remplit les deux maps à partir du jeu de résultats JDBC
  4. Échange atomiquement les nouvelles maps à la place des anciennes

Cette approche signifie que le cache n'est jamais obsolète plus longtemps qu'un cycle de rafraîchissement, et les lectures ne bloquent jamais l'opération de rafraîchissement.

Notes d'architecture

  • Sous-classes concrètes : RechnungCache (pour RechnungDO) et EingangsrechnungCache (pour EingangsrechnungDO), chacune fournissant uniquement le paramètre entityClass
  • Utilise kotlin.reflect.KClass de Kotlin au lieu de Class de Java pour la sécurité des types
  • Le champ @Transient lateinit var info sur AbstractRechnungDO est le champ compagnon que ce cache remplit
  • Lors du rafraîchissement, les positions sans ID sont journalisées comme des erreurs — cela peut se produire avec des factures clonées dont les ID de position n'ont pas encore été attribués
  • L'utilitaire LogDuration suit les performances de rafraîchissement dans les journaux
