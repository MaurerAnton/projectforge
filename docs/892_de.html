Das primäre Datenzugriffsobjekt für AuftragDO (Aufträge/Angebote). Erweitert BaseDao<AuftragDO> und bietet umfassende CRUD-Operationen, erweiterte Filterung (nach Status, Positionstyp, Zahlungsart, Benutzerzuordnung, Projekt, Datumsbereichen), Validierung beim Einfügen/Ändern, E-Mail-Benachrichtigungen, Laden des Verlaufs und Integration mit dem AuftragsCache. Verantwortlich für die „zu fakturieren“-Logik und mehrstufige Filterung von Auftragspositionen.

Wichtige Operationen

Abfrage & Auswahl

select(filter, checkAccess) — Die Kernabfragemethode, überschrieben von BaseDao. Erstellt einen komplexen QueryFilter mit Unterstützung für:

  • Fakturiert-Filter: Bei ZU_FAKTURIEREN werden Aufträge/Positionen mit Status ABGESCHLOSSEN oder erreichten Zahlungsplänen über einen LEFT JOIN abgefragt
  • Benutzerfilter: Findet Aufträge, bei denen der Benutzer Kontaktperson, Projektleiter, Geschäftsführer oder Vertriebsleiter ist
  • Projektfilter: isIn auf Projektliste
  • Datumsfilter: between/ge/le auf erfassungsDatum (Erstellungsdatum)
  • Leistungszeitraum: Delegiert an AuftragAndRechnungDaoHelper
  • Positionstyp-Filter: filterPositionsArten mittels AuftragsPositionsArtFilter
  • Positionsstatus-Filter: filterPositionsStatus — findet Aufträge, bei denen mindestens eine nicht gelöschte Position den angegebenen Status hat
  • Zahlungsart-Filter: filterPositionsPaymentTypes mittels AuftragsPositionsPaymentTypeFilter
  • Ergebnisse sortiert nach nummer absteigend

Validierung: onInsertOrModify(obj, operationType)

Erzwingt Geschäftsregeln vor dem Persistieren:

  1. nummer darf nicht null sein
  2. status darf nicht null oder OPTIONAL sein
  3. Beim Einfügen: nummer muss die nächste fortlaufende Nummer sein (keine Lücken)
  4. Beim Aktualisieren: nummer darf nicht mit einem anderen vorhandenen Auftrag kollidieren
  5. Es muss mindestens eine Position vorhanden sein
  6. Nachgestellte leere Positionen (id=null, isEmpty=true) werden am Ende entfernt (die erste Position wird jedoch nie entfernt)
  7. Das Flag vollstaendigFakturiert jeder Position wird über checkVollstaendigFakturiert() geprüft
  8. Der UI-Status wird in XML serialisiert und in uiStatusAsXml gespeichert
  9. Nachgestellte leere Zahlungspläne werden entfernt
  10. validateDatesInPaymentScheduleWithinPeriodOfPerformanceOfPosition() — stellt sicher, dass alle Zahlungsplandaten innerhalb des Leistungszeitraums der Position liegen (plus 3 Monate Toleranz für das Enddatum)
  11. validateAmountsInPaymentScheduleNotGreaterThanNetSumOfPosition() — die Summe aller Zahlungsplanbeträge für eine Position darf die Nettosumme der Position nicht überschreiten

Nummernverwaltung

  • nextNumber — Gibt die nächste verfügbare Auftragsnummer zurück (höchste vorhandene + 1)
  • getNextNumber(auftrag) — Wenn der Auftrag bereits eine ID hat, wird seine ursprüngliche Nummer abgerufen, um sie zu erhalten; andernfalls wird die nächste fortlaufende Nummer zugewiesen
  • Die Startnummer ist definiert als START_NUMBER = 1

Benachrichtigung: sendNotificationIfRequired(auftrag, operationType, requestUrl)

Sendet eine HTML-E-Mail-Benachrichtigung an die Kontaktperson, wenn ein Auftrag erstellt/geändert/gelöscht wird. Verwendet die Groovy-Vorlage mail/orderChangeNotification.html. Enthält bis zu 10 aktuellste Verlaufseinträge. Gibt false zurück, wenn E-Mail nicht konfiguriert ist, keine Kontaktperson zugewiesen ist oder die Kontaktperson keinen SELECT-Zugriff hat.

Verlaufsintegration

  • addOwnHistoryEntries(obj, context) — Lädt und führt den Verlauf für alle Positionen (einschließlich gelöschter) und Zahlungspläne zusammen
  • getHistoryPropertyPrefix(context) — Gibt "pos#N" für Positionsverlaufseinträge und "payment#N" für Zahlungsplanverlaufseinträge zurück
  • additionalHistorySearchDOs — Enthält AuftragsPositionDO für die Volltext-Verlaufssuche

Suchmethoden

  • getAuftragsPosition(posString) — Analysiert das Format "###.##" (Auftragsnummer.Positionsnummer) und gibt die passende Position zurück
  • getAuftragsPosition(id) — Findet eine Position anhand ihrer Datenbank-ID
  • years — Gibt ein Array aller Jahre mit Auftragsaktivität zurück (min/max von angebotsDatum)
  • buildStatistik(list) — Aggregiert Statistiken für eine Liste von Aufträgen

Setter-Hilfsmethoden

Die Methoden setContactPerson(), setTask(), setKunde() und setProjekt() lösen verwandte Entitäten anhand der ID mittels findOrLoad auf und setzen sie auf den Auftrag oder die Position.

Zusätzliche Suchfelder

Das Array ADDITIONAL_SEARCH_FIELDS erweitert die Hibernate-Suche um Felder aus verwandten Entitäten zu indizieren:

contactPerson.username, contactPerson.firstname, contactPerson.lastname,
kunde.name, projekt.name, projekt.kunde.name,
positionen.position, positionen.art, positionen.status,
positionen.titel, positionen.bemerkung, positionen.nettoSumme
