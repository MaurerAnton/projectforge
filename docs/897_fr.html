Cache temporisé critique pour les performances qui précharge et maintient toutes les informations de commande (Auftrag) pour le carnet de commandes. Étend AbstractCache avec un cycle d'actualisation de 8 heures. Charge toutes les commandes non supprimées, leurs positions et les échéanciers de paiement dans des cartes en mémoire pour éviter des requêtes répétées à la base de données. Calcule les sommes facturées, le statut de facturation complète, les indicateurs « à facturer » et suit le nombre de commandes nécessitant une facturation. Écoute les modifications via les hooks BaseDOModifiedListener sur AuftragDO et RechnungDO pour invalider les données mises en cache. Gère une dépendance cyclique avec AuftragDao via un câblage post-construction.

Initialisation (@PostConstruct init())

Définit l'instance singleton, câble this dans auftragDao.auftragsCache et enregistre deux écouteurs de changement :

  • Écouteur de facture : Toute insertion/modification sur RechnungDO appelle setExpired() pour invalider l'ensemble du cache (car les factures affectent les sommes facturées des positions de commande)
  • Écouteur de commande : Toute insertion/modification sur AuftragDO appelle setExpired()

Invalidation du cache

  • setExpired() — Remplace AbstractCache.setExpired() pour également réinitialiser toBeInvoicedCounter à null, forçant un recalcul lors du prochain accès
  • setExpired(order) — Identique à ci-dessus (mettait auparavant à jour des entrées individuelles ; maintenant expire le cache complet)
  • Les deux implémentations d'écouteurs (auftragListener, rechnungListener) appellent setExpired() lors de tout changement

Logique d'actualisation (refresh())

Appelée lorsque la TTL du cache expire (toutes les 8 heures) ou lors d'une expiration manuelle :

  1. Enregistre le début de l'actualisation avec le minuteur LogDuration
  2. Charge toutes les positions de commande non supprimées via auftragsCacheService.selectNonDeletedAuftragsPositions(), regroupées par auftrag.id
  3. Charge toutes les commandes via auftragsCacheService.selectAuftragsList()
  4. Charge tous les échéanciers de paiement non supprimés via auftragsCacheService.selectNonDeletedPaymentSchedules(), regroupés par auftrag.id
  5. Initialise les objets OrderInfo pour chaque commande (en appelant updateFields(order) pour copier les données de base)
  6. Crée des objets OrderPositionInfo pour chaque position (nota : le constructeur utilise AuftragsRechnungCache, qui à son tour utilise AuftragsCache — la dépendance cyclique est résolue en exécutant les caches deux fois lors de l'initialisation)
  7. Assigne les positions et les échéanciers de paiement à chaque commande, en appelant order.info.calculateAll(order, positions, paymentSchedules)
  8. Remplace les cartes immuables de manière atomique
  9. Réinitialise toBeInvoicedCounter à null
  10. Enregistre l'heure de fin

Sécurité des threads

Les cartes (orderInfoMap, orderPositionMapByPosId) sont remplacées atomiquement par de nouvelles cartes immuables lors de l'actualisation. Le commentaire « No sync, immutable map » sur tous les accès en lecture indique un modèle d'instantané en lecture seule : à chaque appel checkRefresh(), le cache peut reconstruire une nouvelle carte et échanger la référence.

Notes de conception

  • Le paramètre checkRefresh sur getOrderInfo(order, checkRefresh) existe pour éviter les blocages lors de l'initialisation du cache — lorsque le cache est déjà en cours d'actualisation, les appels récursifs ignorent l'actualisation
  • La dépendance cyclique entre AuftragsCache, AuftragsRechnungCache et OrderPositionInfo est documentée dans le commit 51d352133 — résolue en exécutant les caches deux fois lors de l'initialisation
  • Le toBeInvoicedCounter utilise un modèle de calcul paresseux avec journalisation de débogage des numéros de commande comptés
  • Toutes les méthodes d'accès pratiques appellent checkRefresh() avant l'accès pour garantir des données fraîches
